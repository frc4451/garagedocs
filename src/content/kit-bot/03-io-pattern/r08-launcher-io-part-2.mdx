Part 1 gave the feeder and **launcher roller** separate outputs. This page uses “launcher roller” as the shorter name for the intake and launcher roller. Intake and eject run both motors immediately. Launch first spins up the launcher roller, then changes the feeder voltage.

## Step 1: Create the Subsystem

Create `src/main/java/frc/robot/subsystems/launcher/Launcher.java` with this complete file.

```java
package frc.robot.subsystems.launcher;

import edu.wpi.first.units.measure.AngularVelocity;
import edu.wpi.first.units.measure.Current;
import edu.wpi.first.units.measure.Voltage;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.SubsystemBase;

public class Launcher extends SubsystemBase {
    private final LauncherIO io;
    private final LauncherIO.LauncherInputs inputs =
        new LauncherIO.LauncherInputs();

    private Voltage targetFeederVoltage =
        LauncherConstants.IDLE_VOLTAGE;
    private Voltage targetIntakeLauncherVoltage =
        LauncherConstants.IDLE_VOLTAGE;

    public Launcher(LauncherIO io) {
        this.io = io;
    }

    @Override
    public void periodic() {
        io.setFeederVoltage(targetFeederVoltage);
        io.setIntakeLauncherVoltage(targetIntakeLauncherVoltage);
        io.updateInputs(inputs);
    }

    public void runAt(
            Voltage feederVoltage,
            Voltage intakeLauncherVoltage) {
        targetFeederVoltage = feederVoltage;
        targetIntakeLauncherVoltage = intakeLauncherVoltage;
    }

    public void stop() {
        runAt(
            LauncherConstants.IDLE_VOLTAGE,
            LauncherConstants.IDLE_VOLTAGE);
    }

    public Command intakeFuel() {
        return runAtVoltages(
            LauncherConstants.INTAKE_FEEDER_VOLTAGE,
            LauncherConstants.INTAKE_ROLLER_VOLTAGE);
    }

    public Command ejectFuel() {
        return runAtVoltages(
            LauncherConstants.EJECT_FEEDER_VOLTAGE,
            LauncherConstants.EJECT_ROLLER_VOLTAGE);
    }

    public Command launchFuel() {
        return launchAtVoltage(LauncherConstants.LAUNCH_ROLLER_VOLTAGE);
    }

    private Command runAtVoltages(
            Voltage feederVoltage,
            Voltage intakeLauncherVoltage) {
        return startEnd(
            () -> runAt(feederVoltage, intakeLauncherVoltage),
            this::stop);
    }

    private Command launchAtVoltage(Voltage intakeLauncherVoltage) {
        return run(() -> runAt(
                LauncherConstants.LAUNCH_SPINUP_FEEDER_VOLTAGE,
                intakeLauncherVoltage))
            .withTimeout(LauncherConstants.LAUNCH_SPINUP_SECONDS)
            .andThen(run(() -> runAt(
                LauncherConstants.LAUNCH_FEEDER_VOLTAGE,
                intakeLauncherVoltage)))
            .finallyDo(this::stop);
    }

    public AngularVelocity feederVelocity() {
        return inputs.feederVelocity;
    }

    public Current feederCurrent() {
        return inputs.feederCurrent;
    }

    public Voltage feederAppliedVoltage() {
        return inputs.feederAppliedVoltage;
    }

    public AngularVelocity launcherVelocity() {
        return inputs.intakeLauncherVelocity;
    }

    public Current launcherCurrent() {
        return inputs.intakeLauncherCurrent;
    }

    public Voltage launcherAppliedVoltage() {
        return inputs.intakeLauncherAppliedVoltage;
    }
}
```

The two target fields remain separate all the way to the IO layer. `periodic()` sends both commands every robot loop and then refreshes both sets of readings. Because the outputs are sent before the inputs refresh, each displayed reading describes the simulation after the request for that loop has been applied.

The launch command has two phases:

1. Spin the intake and launcher roller while applying only the feeder's small spin-up voltage.
2. Keep the roller running and apply the feeder's full launch voltage.

Releasing the button interrupts whichever phase is active. `finallyDo(this::stop)` then sets both targets to zero.

Build before editing `RobotContainer`. If the compiler points to `finallyDo`, confirm that the import is WPILib's `Command` and that both phases were created with this subsystem's `run(...)` method.

## Step 2: Construct the Simulated Launcher

Add this field inside `RobotContainer`, outside its methods. Import `frc.robot.subsystems.launcher.Launcher` and `frc.robot.subsystems.launcher.LauncherIOSim`:

```java
private final Launcher launcher = new Launcher(new LauncherIOSim());
```

## Step 3: Bind the Actions

Keep the drive default command inside `configureBindings()` and add these bindings below it. Remove any old heartbeat A-button binding so A has only one job:

```java
driver.rightBumper().whileTrue(launcher.launchFuel());
driver.leftBumper().whileTrue(launcher.intakeFuel());
driver.a().whileTrue(launcher.ejectFuel());
```

- Hold the **left bumper** to intake fuel.
- Hold the **right bumper** to launch fuel.
- Hold **A** to eject fuel back through the intake.

These commands belong to `Launcher` because it owns both motors. `RobotContainer` chooses buttons; it does not repeat feeder voltages, roller voltages, delays, or stop behavior.

## Step 4: Inspect Both Motors

Add a temporary X-button binding:

```java
driver.x().onTrue(
    Commands.runOnce(() -> System.out.printf(
        "feeder=%.1f RPM, launcher=%.1f RPM, "
            + "feederCurrent=%.2f A, launcherCurrent=%.2f A%n",
        launcher.feederVelocity().in(RPM),
        launcher.launcherVelocity().in(RPM),
        launcher.feederCurrent().in(Amps),
        launcher.launcherCurrent().in(Amps))));
```

Import `edu.wpi.first.wpilibj2.command.Commands` and statically import `RPM` and `Amps` from `edu.wpi.first.units.Units`. This print command does not require the launcher, so it can read values while a launcher command runs.

## Run the Simulation

1. Build and start simulation.
2. Put a controller or keyboard on Joystick 0.
3. Enable teleop.
4. Use the table below. For each row, hold the action control, press X at the listed time, then release the action control and press X again.

| Action control | When to press X | Expected simulation observation |
|---|---|---|
| Left bumper | While held | Both RPM readings move away from zero; their signs follow the Part 1 constants and simulation inputs |
| Right bumper | During the first second | Launcher RPM moves; feeder RPM reflects the small spin-up request |
| Right bumper | After one second | Feeder behavior changes when the full launch request begins |
| A | While held | Both readings move away from zero with the eject requests |
| Any action, then release | After release | Both requested voltages become zero and both RPM values move toward zero |

Simulation RPM signs report model direction. They do not prove a direction of fuel travel. Compare each observation with the voltage constants instead of assuming that intake, launch, and eject must all use matching signs.

## Inspect the Fuel Path After First Deploy

Do not run this hardware check during this lesson. Save it for a mentor-supervised session after [R12: First Deploy](/kit-bot/r12-first-deploy). Simulation shows motor readings, not fuel movement. When real fuel enters or exits in an unexpected direction, record a slow-motion side view. Follow one piece of fuel from first contact until it leaves the mechanism. Then check these items in order:

1. Compare the intake-guide orientations with the intake section of the official assembly guide on the [2026 KitBot hub](https://www.firstinspires.org/resources/library/frc/kitbot).
2. Confirm the intake and launcher roller turns in the intended direction.
3. Confirm the feeder carries fuel toward that roller during launch.
4. Look for the exact point where fuel stalls, slips, or changes direction.
5. Change one mechanical or software value, then record the same view again.
