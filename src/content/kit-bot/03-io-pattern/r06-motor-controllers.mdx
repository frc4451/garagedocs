### What a motor controller does

A motor on its own takes raw current and spins. A motor *controller* sits between the battery and the motor and decides how much energy reaches the motor each instant. Your robot code talks to the controller, not the motor directly.

Three jobs every controller does:

1. **Switch power on and off, fast.** Modern controllers do this tens of thousands of times a second (PWM at ~20 kHz). The duty cycle (what fraction of each cycle the motor is energized) is what determines speed.
2. **Limit current** to protect the motor. A stalled motor would otherwise pull dangerous current; the controller caps it.
3. **Report sensor readings**. Encoders (built into the NEO), bus voltage, applied voltage, output current.

You command the controller using a high-level API (set a voltage, set a percent). The controller translates that into the PWM duty cycle and reports back.

---

### SparkMax and NEO: the Kit Bot's pair

The Kit Bot uses **REV Robotics SparkMax** motor controllers paired with **NEO** brushless motors. SparkMax is the only motor controller this curriculum covers; if your team is using TalonFX (CTRE), the *shape* of everything below is the same: only the class names change.

A few specifics worth knowing:

- **Brushless.** The NEO is a brushless DC motor. Brushless motors need electronic commutation, which is why a SparkMax has to know what *kind* of motor it's driving: `MotorType.kBrushless`.
- **CAN bus.** SparkMax talks to the roboRIO over a CAN bus: a two-wire network shared by every motor controller on the robot. Each controller has a unique numeric **CAN ID** in the range 1–62. Two devices with the same CAN ID is a common, hard-to-debug failure.
- **Encoder built in.** The NEO has a Hall-effect rotor sensor. You get position (rotations) and velocity (RPM) for free, with no extra wiring.

### Voltage vs percent

You can command a SparkMax two ways:

| Method | Argument | What it means |
|---|---|---|
| `motor.set(percent)` | `-1.0` to `+1.0` | "Drive at this fraction of bus voltage." If the battery is at 12.4 V, `set(0.5)` produces 6.2 V at the motor. As the battery sags, output sags with it. |
| `motor.setVoltage(volts)` | typically `-12.0` to `+12.0` | "Drive at exactly this many volts." The controller compensates for bus voltage: `setVoltage(6.0)` produces 6.0 V whether the battery is at 12.6 V or 11.2 V. |

**Prefer `setVoltage` everywhere.** It's more predictable, and the math you'll do in sim is in volts, not percents. The only reason to use `set` is a habit from old code; in 2026 there's no reason to start there.

Both methods above take a plain `double`, that's REVLib's own API, and REVLib doesn't use WPILib's Units library. [R03](/kit-bot/r03-constants) introduced that library; R07 and R08 are where you'll see it wrap every voltage, RPM, and current that crosses the boundary between REVLib and your own subsystem code. This module describes REVLib as it actually is, `double` in, `double` out, so you recognize the raw shape underneath the typed wrapper.

### Smart current limiting

A stalled NEO will draw ~100 A briefly. That's fine for a moment but cooks the motor over seconds. The fix is one line of config:

```java
config.smartCurrentLimit(60);   // amps
```

`smartCurrentLimit` enables the SparkMax's internal current-limiting algorithm. The single-argument form used above applies that number as a flat cap at every RPM. REVLib also supports a two-tier form: a *stall* limit that applies at 0 RPM, and a separate, **lower** free-speed limit that the cap linearly ramps down to as RPM climbs. That direction makes sense physically: a spinning motor is already held in check by its own back-EMF, so it needs less help from the controller than a stalled one does. The flat, single-argument form is fine for the Kit Bot.

Practical numbers:

- **Drivetrain NEOs**: 60 A is the Kit Bot default. Higher means more power off the line but risks blown breakers and burned motors.
- **Launcher NEOs**: 40 A is the Kit Bot default. The launcher spins a much lighter load than the drivetrain, so it needs less current headroom.
- **NEO 550** (a smaller motor some teams use on intakes or other light mechanisms, not part of the stock Kit Bot): 30 to 40 A. The 550 is much smaller and heats faster.

The 120 A main breaker on the robot also caps total draw: if all four drive motors plus a launcher are at limit at the same time, you'll trip it. We won't worry about that yet; the Kit Bot's defaults are well within budget.

### Encoders and what they report

The NEO's built-in encoder gives you two values:

```java
double rotations = motor.getEncoder().getPosition();   // motor rotations since boot
double rpm       = motor.getEncoder().getVelocity();   // motor RPM (revolutions/minute)
```

Two things to remember:

1. **Position is in motor rotations**, not wheel rotations and not meters. You convert. (Coming up.)
2. **Position is relative**. It starts at 0 at boot. There's no absolute zero. If you need to track total distance, store the value periodically and don't reset.

You can reset with `motor.getEncoder().setPosition(0)`, usually called once in your subsystem constructor so position is zero-referenced at boot.

Both `getPosition()` and `getVelocity()` return bare `double`s, motor rotations and motor RPM respectively, with no unit information attached beyond the method name. R07 and R08 wrap these readings into typed `Distance`, `LinearVelocity`, and `AngularVelocity` measures the moment they cross into your IO implementation, so nothing above the IO layer has to remember "this one's RPM" by convention.

### Gear ratios and units

The motor turns fast; the wheel turns slow. The Kit Bot's drive gearbox has a ratio of about 10.71:1. The motor turns 10.71 times for every one wheel turn. Going from motor revolutions to wheel revolutions is one division:

```
wheelRotations = motorRotations / gearRatio
```

From wheel rotations to distance:

```
distanceMeters = wheelRotations × π × wheelDiameterMeters
```

For RPM the same idea, plus a unit conversion:

```
wheelMetersPerSecond = (motorRPM / gearRatio) × (π × wheelDiameter) / 60.0
```

These conversions live in the IO implementation (R08), not scattered across the codebase. The subsystem above the IO sees clean meters and meters-per-second.

### Follower mode

Every multi-motor mechanism on the Kit Bot (both drivetrain sides, and the launcher) wires its motors as a *leader* and a *follower*. The leader receives the speed/voltage command. The follower watches the leader over the CAN bus and mirrors its output automatically. Your code only commands the leaders.

The follower configuration is one line of config:

```java
SparkMaxConfig followerConfig = new SparkMaxConfig();
followerConfig.follow(leaderCanId);
follower.configure(followerConfig, ResetMode.kResetSafeParameters, PersistMode.kPersistParameters);
```

There's a second argument for "follow inverted", useful if a follower happens to be mounted backwards relative to its leader.

### The SparkMax setup shape

Modern REVLib (2025+) configures a SparkMax with a fluent `SparkMaxConfig` object, applied once. You don't reconfigure every tick; you configure once, then call `setVoltage` in your loop.

```java
import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;
import com.revrobotics.spark.SparkBase.ResetMode;
import com.revrobotics.spark.SparkBase.PersistMode;
import com.revrobotics.spark.config.SparkMaxConfig;
import com.revrobotics.spark.config.SparkBaseConfig.IdleMode;

SparkMax motor = new SparkMax(40, MotorType.kBrushless);   // CAN ID 40, NEO

SparkMaxConfig cfg = new SparkMaxConfig();
cfg.idleMode(IdleMode.kBrake)        // brake when not commanded; alternative: kCoast
   .inverted(false)
   .smartCurrentLimit(60);

motor.configure(cfg,
    ResetMode.kResetSafeParameters,  // reset to defaults first
    PersistMode.kPersistParameters); // save to flash so it survives a reboot
```

The four lines after the constructor are essentially the same on every motor in your robot. The differences are CAN ID, inversion, and current limit. The IO modules (R07, R08) build small helpers around this so you don't repeat the config boilerplate.

`IdleMode.kBrake` makes the motor resist movement when commanded to 0. `kCoast` lets it spin freely. Brake is right for a drivetrain you want to stop crisply; coast is right for a launcher you want to spin down gently.

### Why every motor goes through an IO interface

Every paragraph above is about *how a SparkMax works*. None of it is about *what your subsystem wants the motor to do*. Mixing them is how robot code becomes a knot: the drivetrain subsystem ends up importing REVLib types directly, the launcher imports them again, the unit conversions get scattered, and swapping for a sim requires editing every file.

The IO pattern from [A17](/assignments/a17-io-interface) is the cure. One small interface per mechanism. One implementation per environment (real, sim). Subsystems talk only to the interface.

The next two modules apply the pattern. R07 to the launcher (a leader/follower pair driving one output, conceptually simplest since there's only one voltage to command); R08 to the drivetrain (two leader/follower pairs, four motors total; more wiring but the same shape).
