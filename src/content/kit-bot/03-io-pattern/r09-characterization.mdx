`SHOOT_VOLTAGE` in R07 is a guess: one number that happened to spin the launcher up to something reasonable. R08's `arcadeDrive` has the same guess baked in, `(speed + rotation) * 12.0 * MAX_DRIVE_PERCENT`, full battery voltage, ignoring that the mechanism has friction to overcome before it moves at all and that its speed doesn't scale linearly with voltage once it's moving. Both work well enough to demo, which is why neither module stopped to fix it.

This module measures two real numbers, **kS** and **kV**, that describe how a spinning mechanism, flywheel or drivetrain, actually responds to voltage. Every competitive team runs a routine like this before trusting any velocity-based control (closed-loop driving, `SysId`-tuned autos, a shooter that hits a real RPM target). This is the manual, do-it-yourself version, the same kind of routine you'll find in a `Drive.java` characterization command on a real team's codebase, just built from parts you already have.

We build the routine once, in full, against the **launcher**: one motor, one velocity reading, no left/right to keep in sync. The exact reason R07 taught the launcher before R08 taught the drivetrain applies again here. Once the technique is solid, applying it to the **drivetrain** is a short list of differences, not a second module's worth of new ideas.

---

### The model

A DC motor mechanism's voltage-to-speed relationship is well approximated by:

```
voltage = kS · sign(velocity) + kV · velocity
```

- **kS** (volts): the voltage it takes to overcome static friction and just barely start moving. Below this, you command a voltage and nothing happens.
- **kV** (volts per unit of velocity): how much *more* voltage each additional unit of speed costs, once the mechanism is already moving.

A third term, **kA** (volts per unit of acceleration, how much extra voltage it takes to *accelerate*), exists in the full model. Measuring it needs a second kind of test (a step-voltage "dynamic" test, reading acceleration instead of steady-state velocity), and this curriculum doesn't cover it, the same scope line R07 drew around PID: kS and kV alone get you a meaningfully better feedforward than a bare guess, without a second test rig or a control-theory detour.

---

### The routine: a quasistatic ramp

The standard technique (this is what WPILib's own `SysId` tool automates, and what hand-rolled characterization commands do too) is a **quasistatic ramp**: apply voltage so slowly that acceleration stays near zero throughout. At every instant the mechanism is close enough to steady-state that `voltage ≈ kS·sign(v) + kV·v` holds, with the (ignored) kA·acceleration term staying small because acceleration itself stays small.

Concretely: start at 0 V, ramp up at a slow constant rate, and record `(voltage, velocity)` pairs the whole way. After the ramp, throw out the earliest samples, the ones from before the mechanism broke static friction and started moving, and fit a line through the rest.

---

### Collecting samples: why a `Queue`

The ramp command **produces** samples once per tick, live, while the mechanism is moving. The fit **consumes** all of them at once, after it has stopped. Those are two different points in time with two different jobs, exactly the shape a `Queue` is for: `offer` during the ramp, `poll` in order during the fit. [Queues](/java/java-ds-queues#using-one) covers this interface; `ArrayDeque` is the implementation.

### Characterizing the launcher

```java
package frc.robot.commands;

import edu.wpi.first.units.measure.AngularVelocity;
import edu.wpi.first.units.measure.Voltage;
import edu.wpi.first.wpilibj.Timer;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.Commands;
import frc.robot.subsystems.launcher.Launcher;

import java.util.ArrayDeque;
import java.util.Queue;

import static edu.wpi.first.units.Units.RPM;
import static edu.wpi.first.units.Units.Seconds;
import static edu.wpi.first.units.Units.Volts;

public final class LauncherCharacterization {

    private static final double RAMP_VOLTS_PER_SECOND = 0.25;
    private static final double MAX_VOLTS = 6.0;
    private static final double MIN_VELOCITY_RPM = 50.0;   // below this, static friction hasn't broken yet

    private record Sample(Voltage voltage, AngularVelocity velocity) {}

    public static Command run(Launcher launcher) {
        Queue<Sample> samples = new ArrayDeque<>();
        Timer timer = new Timer();

        Command ramp = Commands.run(() -> {
            Voltage voltage = Volts.of(RAMP_VOLTS_PER_SECOND * timer.get());
            launcher.runAt(voltage);
            samples.offer(new Sample(voltage, launcher.velocity()));
        }, launcher).withTimeout(Seconds.of(MAX_VOLTS / RAMP_VOLTS_PER_SECOND));

        return Commands.runOnce(() -> { samples.clear(); timer.restart(); })
            .andThen(ramp)
            .andThen(Commands.runOnce(launcher::stop, launcher))
            .andThen(Commands.runOnce(() -> fitAndReport(samples)));
    }

    private static void fitAndReport(Queue<Sample> samples) {
        int n = 0;
        double sumV = 0, sumU = 0, sumVV = 0, sumVU = 0;

        Sample sample;
        while ((sample = samples.poll()) != null) {
            double velocity = sample.velocity().in(RPM);
            if (velocity < MIN_VELOCITY_RPM) {
                continue;   // still overcoming static friction; would corrupt the fit
            }
            double voltage = sample.voltage().in(Volts);
            n++;
            sumV  += velocity;
            sumU  += voltage;
            sumVV += velocity * velocity;
            sumVU += velocity * voltage;
        }

        if (n < 2) {
            System.out.println("Not enough moving samples to fit a line. "
                + "Raise MAX_VOLTS, or check the launcher isn't jammed.");
            return;
        }

        double kV = (n * sumVU - sumV * sumU) / (n * sumVV - sumV * sumV);
        double kS = (sumU - kV * sumV) / n;

        System.out.printf("kS = %.4f volts%n", kS);
        System.out.printf("kV = %.6f volts per RPM%n", kV);
    }

    private LauncherCharacterization() {}
}
```

Walk through it in order:

1. **`samples.clear(); timer.restart();`** runs once, before the ramp starts. Wipe any samples left over from a previous run, zero the clock.
2. **The ramp** is `Commands.run` with a `withTimeout`: exactly the shape from R05 and R14. Each tick, the commanded voltage is `0.25 × secondsElapsed`, so it climbs from 0 V to `MAX_VOLTS` (6 V here) over 24 seconds, slow enough to stay quasistatic. Every tick, `launcher.runAt(voltage)` commands it and `samples.offer(...)` records what was commanded alongside what the launcher actually reported for velocity. Neither method is new: `runAt(Voltage)` and `velocity()` are exactly what R07 already built.
3. **After the timeout**, `launcher::stop` kills the motor, then `fitAndReport` runs the regression and prints the result.
4. **`fitAndReport` drains the queue with `poll()`** in FIFO order, oldest sample first, exactly the order they were recorded. Samples below `MIN_VELOCITY_RPM` are skipped: for the first fraction of a second, the launcher is commanded a nonzero voltage but genuinely isn't spinning yet (static friction), and including those points would pull the fit toward a wrong answer.
5. **The regression** is ordinary least-squares, fitting `voltage = kS + kV·velocity` to the (velocity, voltage) points. `kV` is the slope, `kS` the intercept. If you want to see why those particular sums produce a slope and an intercept, this is the same line-of-best-fit formula from any intro statistics course, nothing FRC-specific about the math itself.
6. **`kV` comes out in volts per RPM.** `SimpleMotorFeedforward` (used below) doesn't care which unit you characterize in, kS and kV just have to agree with whatever unit you pass to `calculate` later. The launcher's native reading is RPM, R07 never converts it to anything else, so RPM is what gets characterized.

### Try it: launcher

Add `LauncherCharacterization.java`. Bind it to a spare button for testing, for example:

```java
driver.back().onTrue(LauncherCharacterization.run(launcher));
```

Run the sim (`F5`), enable in teleop, press the bound button, and leave the launcher alone until it stops on its own (24 seconds at the defaults above). Watch the console. You should see something like:

```
kS = 0.2100 volts
kV = 0.002050 volts per RPM
```

The exact numbers depend on `LauncherConstants` and the sim's physics model; don't expect to match this example. Sanity-check instead: `kS` should be a small positive number (well under a volt), and `kS + kV × topSpeedRpm` should land somewhere near 12 V, since that's roughly what it takes to hold the launcher at its actual top speed.

If `kS` comes out negative or `kV` comes out negative, something fed the fit bad data, check that `MIN_VELOCITY_RPM` is actually filtering out the static region, and that the launcher was spinning freely during the test.

### What this bought the launcher

This is the piece R07 left open. Its shot-calibration table originally stored `distance -> target voltage`, measured by trial and error. With `kS`/`kV` in hand, [R07's `Launcher`](/kit-bot/r07-launcher-io) stores `distance -> target RPM` instead, a number that means the same thing regardless of battery state, and converts it to voltage with a [`SimpleMotorFeedforward`](https://github.wpilib.org/allwpilib/docs/release/java/edu/wpi/first/math/controller/SimpleMotorFeedforward.html) built from the constants this routine just printed:

```java
SimpleMotorFeedforward feedforward = new SimpleMotorFeedforward(kS, kV);
double volts = feedforward.calculate(targetRpm);
```

`SimpleMotorFeedforward` itself is untyped, plain `double` in the constructor and in `calculate`, the same "not every WPILib class has caught up to the Units library" story from R07 and R08. Go update `LauncherConstants.KS`/`KV` with your own measured values if you haven't already.

Pressing the bound button runs the launcher routine to completion on its own, and the console prints a small positive `kS` and a `kV` such that `kS + kV × topRPM` lands near 12 V. A negative constant usually means bad data went into the fit. Explain why before moving on.
