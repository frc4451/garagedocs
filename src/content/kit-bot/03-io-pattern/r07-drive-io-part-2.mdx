## Create the Subsystem

Create `src/main/java/frc/robot/subsystems/drive/Drive.java`. This is a **complete file**.

```java
package frc.robot.subsystems.drive;

import edu.wpi.first.units.measure.Distance;
import edu.wpi.first.units.measure.LinearVelocity;
import edu.wpi.first.units.measure.Voltage;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.SubsystemBase;
import static edu.wpi.first.units.Units.Volts;

public class Drive extends SubsystemBase {

    private final DriveIO io;
    private final DriveIO.DriveInputs inputs = new DriveIO.DriveInputs();

    private Voltage leftVoltage  = Volts.of(0);
    private Voltage rightVoltage = Volts.of(0);

    public Drive(DriveIO io) {
        this.io = io;
    }

    @Override
    public void periodic() {
        io.updateInputs(inputs);
        io.setVoltages(leftVoltage, rightVoltage);
    }

    /** Standard arcade-drive math: speed in [-1,1], rotation in [-1,1] (dimensionless, not units). */
    public void arcadeDrive(double speed, double rotation) {
        double left = speed + rotation;
        double right = speed - rotation;
        double scale = Math.max(1.0, Math.max(Math.abs(left), Math.abs(right)));
        double maxVolts = 12.0 * DriveConstants.MAX_DRIVE_PERCENT;

        leftVoltage = Volts.of(left / scale * maxVolts);
        rightVoltage = Volts.of(right / scale * maxVolts);
    }

    public void stop() {
        leftVoltage  = Volts.of(0);
        rightVoltage = Volts.of(0);
    }

    public Command driveAt(double speed, double rotation) {
        return runEnd(
            () -> arcadeDrive(speed, rotation),
            this::stop);
    }

    public Command stopCommand() {
        return runOnce(this::stop);
    }

    public Distance leftPosition() {
        return inputs.leftPosition;
    }

    public Distance rightPosition() {
        return inputs.rightPosition;
    }

    public LinearVelocity leftVelocity() {
        return inputs.leftVelocity;
    }

    public LinearVelocity rightVelocity() {
        return inputs.rightVelocity;
    }
}
```

`arcadeDrive(speed, rotation)` turns forward and turning requests into left and right voltages. `driveAt` wraps that action in a command for fixed-output moves, and `stopCommand` exposes a one-shot stop. These command factories belong in the subsystem because they operate only `Drive` and automatically require it. The IO receives voltage requests and does not read joysticks.

If driving and turning together would put either side above 1.0, `scale` reduces both sides by the same factor. This preserves their ratio and keeps each request within the voltage cap.

For `speed = 0.5` and `rotation = 0.0`, the unscaled left and right requests are both `0.5`. For `speed = 1.0` and `rotation = 0.5`, the raw requests are `1.5` and `0.5`; dividing both by `1.5` produces `1.0` and about `0.33`. The ratio remains 3:1 and neither side exceeds the cap.

`speed` and `rotation` remain `double` values because they are fractions of full input. They have no physical unit. [R03](/kit-bot/r03-constants) made the same distinction between `Distance` and `MAX_DRIVE_PERCENT`.

The teleop deadband and stick scaling are *not* here either. They belong to the command that reads the joystick (R10). The subsystem only does drive math, not driver-input math.

## Wire It in RobotContainer

This is a partial snippet. Add the `drive` field and replace the existing `configureBindings()` method. Keep the `driver` field, the constructor call to `configureBindings()`, and `getAutonomousCommand()`. Remove the heartbeat field and its bindings. If another binding already uses the same control, remove the duplicate before building.

Add imports for `frc.robot.subsystems.drive.Drive`, `frc.robot.subsystems.drive.DriveIOSim`, and `edu.wpi.first.wpilibj2.command.Commands`.

```java
private final Drive drive = new Drive(new DriveIOSim());

private final CommandXboxController driver =
    new CommandXboxController(OperatorConstants.DRIVER_CONTROLLER_PORT);

private void configureBindings() {
    drive.setDefaultCommand(
        Commands.runEnd(
            () -> drive.arcadeDrive(-driver.getLeftY(), driver.getRightX()),
            drive::stop,
            drive
        )
    );
}
```

Two new patterns:

- **Default command** on `drive`. While no other command requires `drive`, this one runs every tick, reading the sticks and calling `arcadeDrive`. `runEnd` also calls `drive.stop()` when the command ends, including when the robot disables or another command interrupts it. Negating left Y makes forward positive. Right X stays positive for a right turn because our `arcadeDrive` adds rotation to the left side and subtracts it from the right.
- **One simulated subsystem** is constructed at the top. R08 will add the launcher beside it, and R12 will select real or simulation IO for both mechanisms.

## Run the Simulation Check

1. Add `import static edu.wpi.first.units.Units.Meters;` to `Drive.java`.
2. Add this temporary partial snippet at the end of `Drive.periodic()`:

```java
System.out.printf("left=%.2f m, right=%.2f m%n",
    leftPosition().in(Meters), rightPosition().in(Meters));
```

3. In VS Code, open the Command Palette and run **WPILib: Build Robot Code**. Continue when the terminal ends with `BUILD SUCCESSFUL`; use the first compiler error and file name if it does not.
4. Run **WPILib: Simulate Robot Code**. Keep **Sim GUI** selected in the extension dialog and choose **OK**. In the Simulation GUI, drag the controller from **System Joysticks** to the first slot under **Joysticks**. If you do not have a controller, drag **Keyboard 0** instead and configure its axes from **DS > Keyboard 0 Settings**.
5. In the Simulation GUI's **Robot State** panel, select **Teleoperated** and then **Enabled**.
6. Push the left stick forward with the right stick centered. Both distance values should increase.
7. Push backward. Both values should decrease.
8. Center the left stick and push the right stick right. The left distance should increase and the right distance decrease.
9. Release the sticks and confirm both requested voltages return to zero. Select **Disabled** in **Robot State** and confirm `runEnd` calls `stop()`. Remove the temporary print after recording your observations.

Compare changes from the starting readings. The distances are totals since simulation began, not a new measurement for each stick movement. Acceleration and model settings affect the distance traveled; an exact distance in two seconds is not a pass condition.

If the signs disagree, inspect the stick sign and the left/right arithmetic before changing a gear ratio. If the scale looks wrong, check meters, wheel diameter, and motor-to-wheel conversion separately.

---

Create `docs/sim-checks/r07-drive-signs.txt` in the VS Code Explorer and record:

```text
Forward:  left change ___ m, right change ___ m
Reverse:  left change ___ m, right change ___ m
Turn right: left change ___ m, right change ___ m
Stick released: requested volts returned to zero: yes/no
Disabled: requested volts remained zero: yes/no
```

These observations verify the simulation contract. They do not verify motor mounting, follower direction, or encoder signs on the physical robot.

## Check the Drivetrain Result

- The drivetrain works in simulation before another mechanism is added.
- Each subsystem uses a small IO interface.
- Real and simulation details stay in separate implementation files.
- Physical measurements keep their units in the subsystem API.
