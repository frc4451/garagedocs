The robot program starts once. While it runs, WPILib repeatedly calls methods that read inputs and update outputs. The default interval is 20 milliseconds, or about 50 calls each second.

**Teleop** is driver-controlled operation. **Autonomous** runs programmed actions. **Disabled** stops normal motor output while the program continues running.

**Refresher:** [While Loops](/java/fundamentals/while-loops#while-loops-with-conditions). WPILib supplies this repeating loop, so you do not add your own infinite loop.

## Before You Start

Complete R01 with the generated project still building. Review Java methods, [Overriding Methods](/java/fundamentals/inheritance#overriding), conditions, and [While Loops](/java/fundamentals/while-loops#while-loops-with-conditions). This lesson runs only in simulation. One pass through the loop is a **tick**. A **callback** is a method the framework calls. The **scheduler** tracks subsystems, triggers, and commands.

## `TimedRobot` and the 20 ms Tick

The `Robot` class extends `TimedRobot`. With its default period, WPILib calls the periodic methods about every **20 ms**, or 50 times per second. Your code goes in those methods.

You do not write the loop. WPILib writes the loop. You write the *body* of one iteration.

```
boot → Robot() constructor runs once →

  every 20 ms:
    one of {disabledPeriodic, autonomousPeriodic, teleopPeriodic, testPeriodic}
      depending on current mode
    then robotPeriodic()

  on a mode change:
    {old mode}Exit()  → {new mode}Init()
```

The `*Init` methods run on a transition. The `*Periodic` methods run every tick while in that mode. `robotPeriodic` runs every tick *regardless* of mode.

---

## Robot Modes

| Mode | When it's active | Init runs when | Exit runs when |
|---|---|---|---|
| **Disabled** | Driver Station says "Disabled" or the robot has booted | Disabled mode begins | Enable, or mode change |
| **Autonomous** | Driver station says "Autonomous" + Enable | Autonomous begins | Disable, or mode change |
| **Teleop** | Driver station says "Teleop" + Enable | Teleop begins | Disable, or mode change |
| **Test** | Driver station says "Test" + Enable | Test begins | Disable, or mode change |

The robot only enters one mode at a time. If you're in autonomous, `teleopPeriodic` is not running.

The `Robot()` constructor runs **once** at boot, before normal periodic processing begins. That's where the generated template constructs your `RobotContainer`. Older templates did the same work in `robotInit()`, which `TimedRobot` still calls once, right after the constructor.

---

## Callback Responsibilities

| Method | Use it for | Don't use it for |
|---|---|---|
| `Robot()` constructor | Constructing `RobotContainer`, starting telemetry (`DataLogManager.start()`) | Hardware-specific setup (do that in subsystem constructors, see [R04](/kit-bot/r04-subsystems)) |
| `robotPeriodic` | `CommandScheduler.getInstance().run()`, and nothing else by default | Subsystem-specific work (use the subsystem's `periodic()` instead) |
| `disabledInit` | Nothing, usually | Anything that depends on the robot being enabled |
| `disabledPeriodic` | Nothing, usually | Active control: motors are stopped while disabled |
| `autonomousInit` | Grabbing the chosen auto command and scheduling it | Reading joysticks (the driver isn't supposed to be driving) |
| `autonomousPeriodic` | Almost nothing: the scheduler does the work | Manual `if/else` state machines (use commands instead) |
| `teleopInit` | Cancelling the auto command if it's still running | |
| `teleopPeriodic` | Almost nothing: the scheduler does the work | |

The pattern across all of these: **the scheduler does the work; your job is to make sure it ticks**. We'll see what that means in [R05](/kit-bot/r05-commands-and-triggers).

## Run the Command Scheduler

The command framework depends on this call inside `robotPeriodic()`:

```java
@Override
public void robotPeriodic() {
    CommandScheduler.getInstance().run();
}
```

On each scheduler pass, this call:

1. Runs `periodic()` on every registered subsystem.
2. Polls every registered `Trigger` (button presses, conditions). New `Trigger` events fire their bound commands.
3. Runs `execute()` on every currently-running command.
4. Calls `end()` on commands that finished during this tick (their `isFinished()` returned `true`).
5. Schedules default commands on idle subsystems.

If buttons or subsystem updates do nothing, confirm that this line remains in `robotPeriodic()`.

## Course `Robot.java`

This is a complete example of `src/main/java/frc/robot/Robot.java`. Compare it with your generated file; keep the generated version if it already performs these jobs.

```java
package frc.robot;

import edu.wpi.first.wpilibj.TimedRobot;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.CommandScheduler;

public class Robot extends TimedRobot {
    private Command m_autonomousCommand;
    private RobotContainer m_robotContainer;

    public Robot() {
        m_robotContainer = new RobotContainer();
    }

    @Override
    public void robotPeriodic() {
        CommandScheduler.getInstance().run();
    }

    @Override
    public void autonomousInit() {
        m_autonomousCommand = m_robotContainer.getAutonomousCommand();
        if (m_autonomousCommand != null) {
            CommandScheduler.getInstance().schedule(m_autonomousCommand);
        }
    }

    @Override
    public void teleopInit() {
        if (m_autonomousCommand != null) {
            CommandScheduler.getInstance().cancel(m_autonomousCommand);
        }
    }

    // disabledInit/Periodic, autonomousPeriodic, teleopPeriodic, test* left empty
}
```

Read the file in your project. Trace what runs when you click Enable in autonomous, then switch to teleop. Confirm: `autonomousInit` fires once, `autonomousPeriodic` fires repeatedly, then on the switch `teleopInit` runs (cancelling the auto command), and `teleopPeriodic` takes over the tick column.

## Timing in Practice

50 Hz means you have **20 milliseconds** of compute budget per tick. That's a lot of time for "set a motor voltage," but it is not infinite. A few things to watch:

- **No `Thread.sleep`** in periodic code. Sleeping freezes the whole robot.
- **No while-loops that wait for hardware**. Same problem.
- **Spread timed work across ticks.** A `for` loop can process a short list in one call. To count elapsed robot ticks, increase a field once per call instead. About 100 ticks take two seconds.

Periodic code does a small amount of work, saves its state, and returns before the next tick. Later commands use the same pattern without blocking the robot loop.

## Observe Mode Changes

1. Open `Robot.java`.
2. Inside `teleopPeriodic()`, add `System.out.println("teleop tick");`. If that method is absent, add this partial snippet inside the `Robot` class:

```java
@Override
public void teleopPeriodic() {
    System.out.println("teleop tick");
}
```

3. Save, then run **WPILib: Simulate Robot Code**.
4. Select Teleoperated and enable. The message repeats in the terminal.
5. Disable. The teleop message stops, although `robotPeriodic()` continues.
6. Select Autonomous and enable. The teleop message stays absent.
7. Disable, stop simulation, and remove the temporary print.

The default rate is about 50 lines per second. You do not need to count a fast-scrolling terminal to pass this check.
