A **pose** describes where the robot is and which way it faces. A two-dimensional pose has three values:

- **x**, the distance along the field's length, in metres
- **y**, the distance across the field, in metres
- **angle**, the direction the robot faces, in degrees

WPILib's field coordinates start at the blue alliance wall's right corner as viewed from the blue driver stations. Positive x points away from the blue wall. Positive y points to the left. An angle of 0° points along positive x, and positive angles turn counter-clockwise.

For example, `(x = 2 m, y = 1 m, angle = 90°)` means the robot is 2 metres along positive x, 1 metre along positive y, and facing positive y.

**Odometry** updates the pose from the left wheel distance, right wheel distance, and heading. This lesson uses the pose as a visual check. The timed autonomous routine does not steer from it.

## Before You Start

Complete [R07 Part 2: Make It Drive](/kit-bot/r07-drive-io-part-2) and [R13 Part 1: AdvantageScope](/kit-bot/r13-telemetry-with-advantagescope). Confirm that both drive distances change with the expected signs in simulation and that AdvantageScope can connect to the Simulator source.

Use [AdvantageScope: Poses on the Field](/tools/advantagescope-poses-on-the-field) for a larger explanation of field coordinates and the 2D Field controls.

You will make small insertions in these existing files:

- `src/main/java/frc/robot/subsystems/drive/DriveIO.java`
- `src/main/java/frc/robot/subsystems/drive/DriveIOSim.java`
- `src/main/java/frc/robot/subsystems/drive/Drive.java`

The canonical pose topic in this lesson is `Drive/Pose`. Capitalization is part of the topic name.

## Add Heading to the IO Inputs

Open `DriveIO.java`. Add this import with the other measure imports:

```java
import edu.wpi.first.units.measure.Angle;
```

Merge `Degrees` into the file's existing static imports from `edu.wpi.first.units.Units`.

Find the nested `DriveInputs` class. Insert this field beside its position and velocity fields:

```java
public Angle heading = Degrees.zero();
```

Every `DriveInputs` object now starts with a heading of zero degrees. The simulator will replace that value every tick. `DriveIOReal` will leave it at zero because this curriculum's physical Kit Bot has no heading sensor yet.

## Read the Simulated Heading

Open `DriveIOSim.java`. Merge `Degrees` into the existing static imports from `edu.wpi.first.units.Units`.

Find `updateInputs(DriveInputs inputs)`. Keep `sim.update(0.020)` first. Insert this line after the simulator update, beside the existing position readings:

```java
inputs.heading = Degrees.of(sim.getHeading().getDegrees());
```

The simulator advances one 20 millisecond tick before the code reads heading and wheel distances. That keeps all three odometry inputs from the same simulated tick.

Save both IO files. In the Command Palette, run **WPILib: Build Robot Code**. Continue when the terminal ends with `BUILD SUCCESSFUL`.

## Create Odometry in Drive

Open `Drive.java`. Add these imports with the other imports:

```java
import edu.wpi.first.math.geometry.Pose2d;
import edu.wpi.first.math.geometry.Rotation2d;
import edu.wpi.first.math.kinematics.DifferentialDriveOdometry;
import edu.wpi.first.networktables.NetworkTableInstance;
import edu.wpi.first.networktables.StructPublisher;
```

Merge `Degrees` and `Meters` into the file's existing static imports from `edu.wpi.first.units.Units`.

Insert these two fields inside `Drive`, near the existing `io` and `inputs` fields:

```java
private final DifferentialDriveOdometry odometry =
    new DifferentialDriveOdometry(Rotation2d.kZero, 0.0, 0.0);

private final StructPublisher<Pose2d> posePublisher =
    NetworkTableInstance.getDefault()
        .getStructTopic("Drive/Pose", Pose2d.struct)
        .publish();
```

The constructor starts the pose at `(0 m, 0 m, 0°)`. `Pose2d.struct` identifies the data as one structured pose so AdvantageScope can read x, y, and angle together.

## Update and Publish the Pose

Find the existing `periodic()` method in `Drive.java`. Keep `io.updateInputs(inputs)` and `io.setVoltages(leftVoltage, rightVoltage)`. Insert this block immediately **after** `io.updateInputs(inputs)` and before the existing output call:

```java
odometry.update(
    Rotation2d.fromDegrees(inputs.heading.in(Degrees)),
    inputs.leftPosition.in(Meters),
    inputs.rightPosition.in(Meters));

posePublisher.set(odometry.getPoseMeters());
```

The update uses three measurements:

1. heading, in degrees
2. left wheel distance, in metres
3. right wheel distance, in metres

When both distances increase together and heading stays near 0°, x should increase while y stays near zero. During a turn, the heading changes and the pose curves in the direction of travel. You do not need trigonometry for this lesson; `DifferentialDriveOdometry` performs the coordinate update.

Save `Drive.java`, then run **WPILib: Build Robot Code**.

1. In WPILib VS Code, run **WPILib: Simulate Robot Code** with **Sim GUI** selected.
2. Assign a controller or keyboard to Joystick 0. Select **Teleoperated** and **Enabled**.
3. Open AdvantageScope and connect to the Simulator source as you did in Part 1.
4. In AdvantageScope, choose **+ → 2D Field**.
5. In the field tree, find the exact struct topic `Drive/Pose`. Drag it into the **Poses** list in the control pane.
6. Set its object type to **Robot** if AdvantageScope did not choose it automatically.
7. Choose the current season's field. Pan or zoom until the origin at `(0 m, 0 m)` is visible.

If the topic does not appear as a pose, check that the code uses `getStructTopic("Drive/Pose", Pose2d.struct)`. Untyped numbers cannot provide the structured pose type that the field view expects.

## Check Three Motions

Use short stick movements so the icon stays near the origin:

1. Drive forward with the turn stick centered. The robot icon should move mostly along positive x.
2. Drive backward over the same path. The x value should move back toward its earlier value.
3. Center the forward stick and command a turn. The robot icon should rotate, and its angle should change.

The simulation checks that the model's heading, wheel distances, odometry update, struct publication, and field view connect correctly. It does not establish physical encoder signs, wheel scale, gyro installation, or real-world accuracy.

## Understand the Real-Robot Limit

`DriveIOReal` does not supply a heading measurement in this curriculum. Its `heading` value therefore remains at the default 0°. On a physical robot, straight wheel motion may change x, but any turn makes the published angle and later position estimate wrong.

Treat `Drive/Pose` as unsupported on the physical robot until a gyro is installed, its units and direction are checked, and `DriveIOReal.updateInputs(...)` writes that measured heading. A gyro alone does not make the pose exact. Wheel slip, encoder scale, and sensor offsets can still create error.
