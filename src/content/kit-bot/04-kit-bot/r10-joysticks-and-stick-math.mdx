The Drive subsystem from R07 takes `speed` and `rotation` values in `[-1, 1]`. Xbox sticks report values in the same range, but raw readings can make the robot creep at rest and respond too sharply near the center.

This module adjusts stick input so the driver can make small movements near the center. For practice with the same calculation outside a robot project, use [A08](/java/assignments/a08-stick-curve-calculator).

Three things go wrong if you skip stick math:

1. **A centered stick can report a small nonzero value.** Check your own controller in the Sim GUI. That reading can request motion when the driver expects the robot to stay still.
2. **Small movements are too sensitive.** A 10% stick deflection becomes a 10% drive command, too much for precise lining-up.
3. **The Y axis is upside-down.** Push the stick *forward* (up on the controller) and `getLeftY()` returns a *negative* number. Negating this reading makes forward positive.

Three fixes, in order:

- **Negate Y** at the read site.
- **Deadband** small absolute values to zero.
- **Apply a curve**: square the input while preserving sign so small motions stay small but full deflection still gives full drive.

The helper below performs the deadband and curve steps.

---

### A small helper class

Create `src/main/java/frc/robot/subsystems/drive/StickCurve.java` with this complete file.

```java
package frc.robot.subsystems.drive;

public final class StickCurve {

    /**
     * Standard stick conditioning: negate Y if needed, deadband, square-with-sign,
     * clip to maxOutput. Returns a value in [-maxOutput, +maxOutput].
     */
    public static double shape(double rawStick, double deadband, double maxOutput) {
        if (Math.abs(rawStick) < deadband) {
            return 0.0;
        }
        double sign = Math.signum(rawStick);
        double scaled = sign * Math.pow(Math.abs(rawStick), 2);
        double capped = Math.max(-maxOutput, Math.min(maxOutput, scaled));
        return capped;
    }

    private StickCurve() {}
}
```

The helper checks the raw input against the deadband, squares its size, restores its sign, and clamps the result. The deadband check goes first: squaring a small input makes it smaller and could otherwise put it below the threshold.

Notice everything here stays a plain `double`: `rawStick`, `deadband`, `maxOutput` are all dimensionless fractions of full stick deflection, not a physical quantity WPILib's Units library has a type for. That's the same distinction R03 drew between `Distance` and `MAX_DRIVE_PERCENT`, and R07 drew between `arcadeDrive`'s `speed`/`rotation` and its internal `Voltage` math. Units typing stops where the physical quantity does.

Keep exponent `2` for this project so your checks use the same calculation.

---

### Where the math lives

Three options for where to call `StickCurve.shape`:

| Place | Verdict |
|---|---|
| Inside `Drive` (the subsystem) | **No.** The subsystem shouldn't know about joysticks. |
| Inside the default command | **Yes.** That command's whole job is "translate driver input into a drive command." |
| Inside `arcadeDrive` itself | **No.** `arcadeDrive(speed, rotation)` takes a normalized value. Joystick conditioning happens *before* you call it. |

The default command is the right home. The `Drive` subsystem stays unaware of where its commands come from, which makes the same code work for joystick driving, autonomous time-based moves, and any future command you write.

---

### Updated default command

Replace only the `drive.setDefaultCommand(...)` call inside `RobotContainer.configureBindings()` with this partial snippet. Keep every launcher, D-pad, and characterization binding. Import `DriveConstants` and `StickCurve` from `frc.robot.subsystems.drive`.

```java
drive.setDefaultCommand(
    Commands.run(
        () -> {
            double rawY = -driver.getLeftY();         // negate Y
            double rawRot = driver.getRightX();      // positive X requests a right turn

            double speed = StickCurve.shape(
                rawY,
                DriveConstants.TELEOP_DEADBAND,
                1.0                                     // full [-1, 1]; arcadeDrive applies MAX_DRIVE_PERCENT
            );
            double rotation = StickCurve.shape(
                rawRot,
                DriveConstants.TELEOP_DEADBAND,
                1.0                                     // full [-1, 1]; arcadeDrive applies MAX_DRIVE_PERCENT
            );

            drive.arcadeDrive(speed, rotation);
        },
        drive
    )
);
```

What changed from the R07 version:

- Stick reads are conditioned through `StickCurve.shape` before reaching `arcadeDrive`.
- Deadband comes from `DriveConstants.TELEOP_DEADBAND`. Adjusting the feel is a constants edit, not a code edit.
- `shape` is called with a max output of `1.0`, not `DriveConstants.MAX_DRIVE_PERCENT`. `arcadeDrive`'s own doc comment (R07) says it takes `speed` and `rotation` in the full `[-1, 1]` range, then applies `MAX_DRIVE_PERCENT` itself when it converts that to volts. Capping to `MAX_DRIVE_PERCENT` a second time here, before the value ever reaches `arcadeDrive`, would compound the two caps and leave full stick deflection well under 10.2 V.
- The lambda still ends in `drive.arcadeDrive(...)`: the subsystem's API is unchanged. The IO files do not need to change.

### Try it

Add `StickCurve.java`. Update the default command in `configureBindings` with the snippet above. Build and sim.

Plug in an Xbox controller. Slowly push the left stick forward from rest. The robot should:

1. Not move at all until the stick crosses about 5% deflection.
2. Move slowly at 20–30% deflection.
3. Move at full commanded speed at full deflection; `arcadeDrive` still caps the resulting voltage at 10.2 V through `MAX_DRIVE_PERCENT`.

For a numeric check, `shape(0.03, 0.05, 1.0)` should be zero. The helper squares 0.30, so `shape(0.30, 0.05, 1.0)` is 0.09. This is an output fraction, not a measured speed.

If a centered stick requests motion, inspect its raw reading and confirm the command calls `shape`. If small inputs remain too large, check the deadband and exponent before changing motor settings.

---

### When to revisit these values

The values in `DriveConstants` are starting points. Test these items with the same driver and route when real hardware is available:

- **Deadband 0.05** is conservative. Some controllers stay tighter and can use 0.02–0.03; older ones may need 0.10.
- **MAX_DRIVE_PERCENT 0.85** caps voltage at 10.2 V. It's applied inside `Drive.arcadeDrive` (R07), not inside `StickCurve.shape`, so this is a `Drive` edit, not a `StickCurve` edit. Some teams run 0.7 in early drive practice and ratchet up to 1.0 as the driver gets comfortable.
- **Exponent of 2** is a good starting point. A cubic (`Math.pow(abs, 3)`) is gentler near the centre and helps brand-new drivers; experienced drivers often prefer 2.

Change one variable at a time and have the same person drive the same route both ways before deciding.
