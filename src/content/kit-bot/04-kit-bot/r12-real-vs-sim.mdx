R07 and R08 left a TODO: `new DriveIOSim()` is hard-coded in `RobotContainer`. That's fine for development but useless on a real robot. This module finishes the IO pattern: the runtime decision of which implementation to construct.

The decision uses one `if`. Its location matters because the rest of the project should depend on the IO interfaces rather than the runtime environment.

---

### What WPILib gives you

[`RobotBase.isReal()`](https://github.wpilib.org/allwpilib/docs/release/java/edu/wpi/first/wpilibj/RobotBase.html#isReal()) returns `true` when the JVM is running on the roboRIO and `false` when it's running in simulation.

```java
import edu.wpi.first.wpilibj.RobotBase;

boolean realRobot = RobotBase.isReal();
```

There's also `RobotBase.isSimulation()`, the exact inverse. Pick whichever reads better at the call site.

This check is the *only* thing the IO selection needs. No env variables, no build flags. Whatever environment WPILib boots into, this method tells you which one.

---

### Where the `if` lives

It lives in `RobotContainer`'s constructor. Specifically, in the place where IOs and subsystems get constructed.

```java
package frc.robot;

import edu.wpi.first.wpilibj.RobotBase;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.button.CommandXboxController;

import frc.robot.Constants.OperatorConstants;
import frc.robot.commands.TeleopDrive;
import frc.robot.subsystems.drive.Drive;
import frc.robot.subsystems.drive.DriveIO;
import frc.robot.subsystems.drive.DriveIOReal;
import frc.robot.subsystems.drive.DriveIOSim;
import frc.robot.subsystems.launcher.Launcher;
import frc.robot.subsystems.launcher.LauncherIO;
import frc.robot.subsystems.launcher.LauncherIOReal;
import frc.robot.subsystems.launcher.LauncherIOSim;

public class RobotContainer {

    private final Drive drive;
    private final Launcher launcher;
    private final CommandXboxController driver =
        new CommandXboxController(OperatorConstants.DRIVER_CONTROLLER_PORT);

    public RobotContainer() {
        DriveIO driveIO;
        LauncherIO launcherIO;

        if (RobotBase.isReal()) {
            driveIO    = new DriveIOReal();
            launcherIO = new LauncherIOReal();
        } else {
            driveIO    = new DriveIOSim();
            launcherIO = new LauncherIOSim();
        }

        drive    = new Drive(driveIO);
        launcher = new Launcher(launcherIO);

        configureBindings();
    }

    private void configureBindings() {
        drive.setDefaultCommand(new TeleopDrive(
            drive,
            () -> -driver.getLeftY(),
            () -> -driver.getRightX()));

        driver.rightBumper().whileTrue(launcher.launchFuel());
        driver.leftBumper().whileTrue(launcher.intakeFuel());
        driver.a().whileTrue(launcher.ejectFuel());
    }

    public Command getAutonomousCommand() {
        return null;
    }
}
```

A few things worth pointing out:

- **`Drive drive` is still `final`**. `final` means "assigned exactly once". The assignment happens inside the constructor, not at the field declaration site. That's perfectly legal.
- **The `if` is at one place**. Not inside `Drive`, not inside `DriveIOReal`. The subsystem and the IO impls have no idea where they got picked. That's the whole point of the pattern.
- **The branches are symmetric**. Each one assigns both IOs. If you later add another mechanism, add its real and simulation IO assignments here. The pairs are visible in one place and stay in sync.

### A slightly tidier variant: a factory

Some teams move the `if` into a tiny static method to keep the constructor short:

```java
private static DriveIO driveIO() {
    return RobotBase.isReal() ? new DriveIOReal() : new DriveIOSim();
}

private static LauncherIO launcherIO() {
    return RobotBase.isReal() ? new LauncherIOReal() : new LauncherIOSim();
}

public RobotContainer() {
    drive    = new Drive(driveIO());
    launcher = new Launcher(launcherIO());
    configureBindings();
}
```

Same logic, slightly less clutter at the call site. Either form is fine architecturally: both keep the real-vs-sim decision inside `RobotContainer` and invisible everywhere else. One note if you're aiming for the capstone checklist: it asks for "exactly one `if (RobotBase.isReal())` block," which describes the inline form above literally. The factory form replaces that single `if` with two `RobotBase.isReal()` ternaries, one per factory method. That still satisfies the underlying rule (single source of truth, still inside `RobotContainer`), but if your mentor is checking the checklist item by its literal wording, use the inline form or mention the substitution.

### Try it

Confirm both modes work.

1. **Sim**: press `F5` to launch the sim. The console doesn't say which IO it picked; add `System.out.println("IO: " + (RobotBase.isReal() ? "real" : "sim"))` to the constructor if you want confirmation. Drive around. Same behaviour as R11.
2. **Real (with a mentor)**: use a Kit Bot that has passed its electrical inspection, then deploy with `Ctrl+Shift+P` and `WPILib: Deploy Robot Code`. Drive should work identically. Stick math feels the same. The only difference is real motors and real wheels.

If both work, the IO pattern is paying off. If sim works but real doesn't, the bug is in `DriveIOReal`: CAN IDs, inversion, or current limit. The subsystem code didn't change.

---

### Why runtime selection comes after both implementations

R07 and R08 kept the simulation implementation selected while you built and tested both sides of the interface. Adding runtime selection earlier would have introduced the interface, two implementations, and the selector at the same time. By keeping the IO hard-coded to sim through R07–R11, you got to focus on:

- The first interface and implementation pair on the drivetrain (R07).
- Repeating the pattern for the launcher (R08).
- How each subsystem consumes its interface (R07 and R08).
- How commands consume the subsystem (R11).

Now that all those layers are concrete, the runtime selection lands in a place where you can clearly see what it changes (the IO impl chosen) and what it doesn't (everything else).

This is also why we held off on telemetry until R13. Same kind of thing. One concept at a time.
