After the [capstone](/kit-bot/rc-capstone), choose a follow-up project from a behavior you can observe in your working robot. This catalog is optional; selecting a project does not add a requirement to the simulation capstone or Badge 1.

## Before You Start

Keep the working capstone as a reference before changing it. Use a [Git branch](/tools/branching-and-merging) to keep the experiment separate, and ask a mentor to review the proposed change. If the project needs new wiring or equipment, read the relevant [Hardware guide](/hardware) with that mentor before buying, connecting, or operating it.

The links below introduce topics beyond this course. Start with one row and its first experiment. A **feedback controller** compares a measurement with a target and changes the output to reduce the difference. A sensor supplies the measurement; adding the sensor alone does not create that control behavior.

## Choose a Project

| Observed Need | Project and Preparation | First Experiment |
|---|---|---|
| Timed autonomous runs stop at different distances | Use wheel-distance measurements with [feedback control](https://docs.wpilib.org/en/stable/docs/software/advanced-controls/controllers/pidcontroller.html). Review R07's distance units and stopping behavior. | In simulation, graph the target and measured distance. Choose a tolerance with a mentor, then repeat the run and record the stopping error. |
| The drivetrain does not hold its heading | Add a measured heading and a heading controller. [Differential-drive odometry](https://docs.wpilib.org/en/stable/docs/software/kinematics-and-odometry/differential-drive-odometry.html) combines a gyro angle and wheel distances to estimate pose; it does not steer the robot. | Use R13's simulated heading to compare a target angle with the measured angle. Test a correction at limited output before choosing a physical gyro. |
| Launcher speed falls when fuel enters | Add a velocity target with [feedforward and feedback](https://docs.wpilib.org/en/stable/docs/software/advanced-controls/controllers/combining-feedforward-feedback.html). Review R09's units and launcher RPM telemetry. | Graph target and measured velocity during a simulated speed change. Fuel contact and recovery still need a supervised physical test. |
| You want to rerun code against recorded inputs | Investigate [AdvantageKit IO interfaces](https://docs.advantagekit.org/data-flow/recording-inputs/io-interfaces/). Review the existing IO classes and R13 logging first. | Migrate one subsystem on a branch and compare its recorded inputs during replay. This changes the logging architecture; opening a WPILOG in AdvantageScope only replays the recorded display. |
| The launcher needs settings for more distances | Extend the table from [R08's Distance Table](/kit-bot/r08-launcher-calibration). Its entries pair distance with requested voltage. [A10: Shooter Lookup Table](/java/assignments/a10-shooter-lookup-table) offers related Java practice. | Check interpolation between two new entries and behavior outside the table. Simulation cannot establish which voltage scores fuel at a real field location. |
| A mechanism needs a position reference after reboot | Compare an absolute encoder, such as [CANcoder](https://v6.docs.ctr-electronics.com/en/latest/docs/hardware-reference/cancoder/index.html), with a homing routine that moves to a known reference. Review travel limits and sensor mounting with a mentor. | Simulate startup at several positions, including a missing reference. Confirm the mechanism does not move until the program has the information it needs. Choose hardware only after that review. |
| The robot needs to detect fuel or a travel limit | Read a beam break or limit switch through a [digital input](https://docs.wpilib.org/en/stable/docs/software/hardware-apis/sensors/digital-inputs-software.html). Review the selected sensor's wiring and meaning of true and false. | Simulate both input states and confirm the intended response. Check actual polarity and the physical limit under mentor supervision. |
| Drivers need visible robot-state feedback | Add [addressable LEDs](https://docs.wpilib.org/en/stable/docs/software/hardware-apis/misc/addressable-leds.html). Define the states and their priority before selecting the strip or power connection. | Test which pattern each state selects, including two simultaneous states. Have a mentor check the power and signal wiring before connecting LEDs. |
| You need to investigate low voltage or high current | Add [power-distribution telemetry](https://docs.wpilib.org/en/stable/docs/software/can-devices/power-distribution-module.html) for the device installed on the robot. Review [AdvantageScope graphs](/tools/advantagescope-tour#make-a-first-graph). | Test the graph layout with available simulated or recorded values. On hardware, record voltage and current during a supervised run; a current spike alone does not identify its cause. |

## Write a Proposal

Create a Markdown file named `next-project.md` in the project folder. Use these headings to organize a proposal for your mentor:

1. **Observed Behavior:** Describe one run and link its log or screenshot.
2. **Baseline:** Record the current measurement, its units, and the test conditions.
3. **Proposed Change:** Name the smallest change you will try and the primary documentation you will use.
4. **Simulation Check:** State the input, expected result, and how you will measure it. Agree on any tolerance before testing.
5. **Hardware Check:** Identify the equipment and mentor review needed before physical testing.
6. **Return to the Baseline:** Record the working branch or commit so the experiment can be set aside without losing the capstone.

For example: "Our timed drive command stops at different distances under the conditions recorded in these logs. We will compare a distance target with the wheel-distance readings and test a command that stops near that target. We will record the error from repeated simulation runs before planning a physical test."

## Trace a Reference

Read one example from the documentation linked in your chosen row. Identify its inputs, outputs, units, dependencies, and stop conditions. Then compare those with your IO interface and subsystem. A matching class name does not mean an example can replace your file unchanged.

Record the documentation version and date in the proposal. Separate general behavior from season-specific hardware settings. Check the applicable rules and electrical design with a mentor before choosing equipment.
