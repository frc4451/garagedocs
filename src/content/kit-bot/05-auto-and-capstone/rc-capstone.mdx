The capstone brings your existing Kit Bot work into one demonstration. You will run the project in simulation, show the evidence you collected in earlier lessons, and explain how a command reaches a subsystem and its IO implementation. The capstone does not add a new mechanism or calculation.

## Before You Start

Complete the simulation path from R00 through R14. R00 Parts 2 and 3 and R12 Part 2 are physical-hardware work and are not prerequisites for this simulation capstone. Keep your R09 calculation notes, saved WPILOG, and evidence files available.

Open the Kit Bot repository folder in WPILib VS Code. Close unrelated projects so the Explorer and build task point to the Kit Bot. Your project should already have:

- teleop-only driver controls from R11;
- `IO: sim` runtime selection from R12;
- launcher telemetry and simulated pose from R13;
- the three Glass autonomous options from R14.

Real-hardware operation is [Badge 1 Step 7](/badges/badge-1-hardware). Simulation can verify code paths, command sequencing, software motor models, telemetry, and pose updates. It cannot verify physical motor direction, CAN health, braking distance, or fuel movement.

## Required Behavior

| Check | Observable Result |
|---|---|
| Build | `./gradlew build` finishes with `BUILD SUCCESSFUL`. |
| Teleop drive | A controller requests forward, reverse, and turning motion. Centered sticks stay inside the deadband. Drive controls do nothing outside teleop. |
| Launcher and intake | Left bumper intakes, right bumper launches, and A ejects during teleop. The feeder and intake-launcher motors follow the sequence from R08 and both requests return to zero on release. Two D-pad settings produce different launch requests. |
| Characterization | The drivetrain and launcher show the accepted samples and `kS` and `kV` results already required by R09. One result is checked with the saved hand-written sample table. |
| Runtime selection | Simulation prints `IO: sim`. `RobotContainer` also contains the real-hardware branch; that branch is code-review evidence until a hardware deployment. |
| Telemetry and pose | AdvantageScope separates RPM, current, and applied voltage for both launcher motors. Its field view shows `Drive/Pose` translating and rotating. |
| Autonomous | Glass lists **Do nothing**, **Drive forward**, and **Drive then shoot**. Each produces its named behavior and every request stops. Driver controls stay inactive during autonomous. |
| Repository | The project has a README and is pushed to its own Kit Bot repository by following [A00: Practice Repository Setup](/java/assignments/a00-practice-repository-setup). The `<yourname>Badge01` assignments repository stays separate. |

## Map the Project

Before demonstrating, fill in this table in your notes or README with the names used by your project. This organizes existing code; it is not another graded artifact.

| Responsibility | File or Class to Find | What to Explain |
|---|---|---|
| Robot lifecycle | `Robot.java` | Where the scheduler runs and autonomous starts and stops |
| Construction and bindings | `RobotContainer.java` | Where IO is selected, triggers are gated, and the chooser is published |
| Drivetrain boundary | Drive subsystem and IO files | How one drive request reaches the real or simulated implementation |
| Launcher boundary | Launcher subsystem and IO files | How one launcher command controls both simulated motors |
| Driver logic | `TeleopDrive` | Why controller input stays outside `Drive` |
| Autonomous composition | `AutoRoutines` | How existing subsystem commands form one sequence |

Names may differ. Extra files are acceptable when you can explain their responsibility. Remove abandoned experiments and unused classes before the demonstration.

## Review the Code

### Java and Project Basics

- [ ] Package declarations match folder paths.
- [ ] Fields are private unless they are constants or public measurements in an IO inputs class.
- [ ] Overridden methods use `@Override`.
- [ ] Stored objects are `private final` when the field is not reassigned.
- [ ] VS Code reports no unused imports.
- [ ] `.gitignore` excludes build output and local editor files.

### IO Boundary

- [ ] Real IO files contain REVLib calls, and simulation IO files contain WPILib simulation calls.
- [ ] Subsystems depend on their IO interfaces.
- [ ] `RobotContainer` selects real or simulation implementations.

### Command Ownership and Modes

- [ ] Left bumper uses `launcher.intakeFuel()`, right bumper uses `launcher.launchFuel()`, and A uses `launcher.ejectFuel()`.
- [ ] Commands for one mechanism are created by that subsystem and require it.
- [ ] `RobotContainer` chooses triggers without repeating mechanism voltage or stop logic.
- [ ] Every driver trigger uses the R11 teleop gate.
- [ ] `AutoRoutines` composes subsystem commands outside the subsystems.
- [ ] `Robot.java` schedules the chooser result in `autonomousInit()` and cancels it in `teleopInit()`.

### Existing Evidence

- [ ] Teleop drive and both launcher outputs stop when their commands end or the robot is disabled.
- [ ] Autonomous drive and launcher requests stop at their timeouts.
- [ ] Telemetry topic names include units.
- [ ] A saved WPILOG opens after simulation ends.
- [ ] Drivetrain and launcher samples and recorded metadata match the requirements in R09.
- [ ] One `kS` and `kV` result includes the four regression sums from R09 Part 2.
- [ ] `Drive/Pose` moves and rotates in AdvantageScope's field view.

## Prepare the README

At the repository root, open `README.md`. It should guide another student through these existing steps:

1. Open the repository folder in WPILib VS Code.
2. Build the project and identify `BUILD SUCCESSFUL`.
3. Start simulation and identify `IO: sim`.
4. Assign a controller to joystick port 0, or use the documented keyboard mapping.
5. Open AdvantageScope, connect to simulation, and find the saved launcher and pose views.
6. Open Glass, set **NetworkTables Settings** → **Team/IP** to `localhost`, find `SmartDashboard` → `Auto Chooser`, and run the three options.
7. Find the R09 console output, calculation notes, and evidence files.

Link to the GarageDocs lessons for full explanations. Include the dependency or vendor-library versions another student needs to open the project. Follow [A00: Practice Repository Setup](/java/assignments/a00-practice-repository-setup) when you save and share the repository.

## Check the Evidence Files

Keep the three simulation results already required by the curriculum in the repository, or link them from the README:

1. An AdvantageScope screenshot with separate feeder and intake-launcher RPM, current, and applied voltage during intake and launch.
2. The drivetrain and launcher characterization output, including accepted samples and calculated `kS` and `kV` values.
3. A Glass screenshot showing the selected autonomous option, paired with an AdvantageScope trace showing motion settling to a stop. You can graph the position fields within `Drive/Pose`; the temporary R11 console check is also useful for distinguishing a zero request from coasting. The routine does not print a completion message by default.

Use descriptive names with dates, such as `2026-09-24-launcher-telemetry.png`. Before the demonstration, follow each README link and confirm the file opens from the repository folder.

When a physical Kit Bot and mentor are available, Badge 1 Step 7 adds the labeled CAN-ID photo, drive video, and intake-and-launch side view. Those files do not block the simulation capstone.

## Run the Demonstration

The time suggestions help you rehearse. They are not additional requirements.

### Show the Project Map (1 Minute)

In the VS Code Explorer, point to one subsystem, its IO interface, and its real and simulation implementations. Trace one command call to the subsystem method and then to the selected IO object.

### Show Runtime Selection (1 Minute)

Open `RobotContainer.java` and point to the real/simulation branch. Start simulation and show `IO: sim` in the terminal. State that this proves the simulation branch was constructed; the physical branch needs the later hardware check.

### Drive, Intake, and Launch (2 Minutes)

In the Sim GUI, enable teleop. Drive forward, reverse, and turn, then center the sticks. Hold and release the left bumper, right bumper, and A. Demonstrate both D-pad distance settings. In AdvantageScope, show all six launcher topics and the moving `Drive/Pose` field object. Describe these as software-model results, not fuel scoring or physical direction.

### Show the Characterization Record (2 Minutes)

Open the saved R09 output and your calculation notes. For one mechanism, show the four regression sums and compare your hand-calculated `kS` and `kV` with the Java output. State the velocity unit and explain why physical hardware needs its own samples.

### Run Autonomous (2 Minutes)

Open Glass, set **Team/IP** to `localhost`, and confirm the title bar shows a connection. While disabled, select and run **Do nothing**, **Drive forward**, and **Drive then shoot**, disabling between selections. Use the R11 console output and launcher telemetry to show that targets return to zero. Start one routine again and switch to teleop before it finishes to show cancellation.

### Explain One Failure Check (2 Minutes)

Choose one prompt below. Describe the observation first, the first place you would check, and the evidence that would confirm or reject that possible cause. The prompt does not prescribe one answer because several causes can produce the same symptom.

- A driver button produces no motor request.
- A forward request produces opposite left and right wheel motion.
- One telemetry topic remains at zero during its command.
- An autonomous request continues past its timeout.

## Separate Badge 1 Fresh-Clone Check

The [Badge 1 simulation check](/badges/badge-1-simulation#badge-check) later requires a formal fresh-clone demonstration. It is separate from this capstone's Done When conditions. A fresh clone is a new copy in a different folder; running it checks that another student can retrieve the repository's tracked files and documented dependencies.

If it fails, keep the first error visible. Check whether it names a missing file, vendor library, WPILib version, or unavailable download before changing code.
