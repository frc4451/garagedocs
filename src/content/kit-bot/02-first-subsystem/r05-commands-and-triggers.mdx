A **command** is an action the robot takes. A **trigger** is a condition that schedules a command. Buttons are the most common triggers. This module is where the heartbeat module from R04 finally gets a button to press.

If you remember [A22: Command-Binding Lab](/assignments/a22-command-binding), you built a miniature version of this whole system. WPILib's framework is the production version. The shapes are the same (`Runnable`, `BooleanSupplier`, `Trigger`), just better wired.

---

### What a command is

A command is an object that does work, optionally over multiple ticks. It has four hook methods the scheduler calls in order:

| Hook | When it runs | What it's for |
|---|---|---|
| `initialize()` | Once when the command starts | Resetting state, capturing the start time |
| `execute()` | Every scheduler tick while running | Doing the work, usually calling subsystem methods |
| `isFinished()` | Every tick after `execute()` | Returns `true` to stop the command |
| `end(boolean interrupted)` | Once when the command stops | Cleanup: stop motors, reset flags |

The full `Command` interface has a few more methods (`getRequirements`, `runsWhenDisabled`), but those four are the lifecycle.

For the Kit Bot, you'll almost never write a command class by hand. WPILib provides factory methods on `Commands` that build common shapes from a lambda. It's the same pattern A22 modelled.

---

### `Commands.runOnce`: fire and forget

The simplest command: do one thing, then end.

```java
import edu.wpi.first.wpilibj2.command.Commands;

Command resetHeartbeat = Commands.runOnce(() -> heartbeat.reset(), heartbeat);
```

Read it: "build a command that runs the lambda once, then ends. It requires the `heartbeat` subsystem."

The lambda is a `Runnable`. The second argument is the subsystem the command needs. Passing it here tells the scheduler "no other command can use `heartbeat` while this one is running." For a one-shot command this requirement is moot, but it's good hygiene.

This is exactly the `Runnable` argument shape from A22's `Button.onTrue`. WPILib just provides the factory method.

### `Commands.run`: run every tick until interrupted

```java
Command spamHeartbeat = Commands.run(() -> heartbeat.reset(), heartbeat);
```

Same lambda, but this command's `execute()` runs the lambda **every tick**, and `isFinished()` returns `false`, so it keeps going until something else cancels it. Use this for "while the button is held, do this work continuously."

### What a `Trigger` is

A `Trigger` is a `BooleanSupplier` with sugar on top: it polls the supplier every scheduler tick and fires bound commands on edges.

You almost never construct one by hand. You get them from a `CommandXboxController`:

```java
import edu.wpi.first.wpilibj2.command.button.CommandXboxController;

private final CommandXboxController driver = new CommandXboxController(0);

// driver.a() returns a Trigger that's true while the A button is held
driver.a().onTrue(Commands.runOnce(() -> heartbeat.reset(), heartbeat));
```

The CommandXboxController exposes every button as a `Trigger`. The four common bindings:

| Binding | When it fires |
|---|---|
| `.onTrue(command)` | Once, when the trigger goes from false to true (rising edge) |
| `.onFalse(command)` | Once, when the trigger goes from true to false (falling edge) |
| `.whileTrue(command)` | When trigger becomes true, schedule command. When it becomes false, cancel command. |
| `.whileFalse(command)` | The inverse of `whileTrue`. Rarely needed. |

You'll use `onTrue` for "do one thing on press" and `whileTrue` for "keep doing this while the button is held."

### Wiring it up in `RobotContainer`

The full version of the heartbeat-resetting `RobotContainer`:

```java
package frc.robot;

import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.Commands;
import edu.wpi.first.wpilibj2.command.button.CommandXboxController;
import frc.robot.Constants.OperatorConstants;
import frc.robot.subsystems.heartbeat.Heartbeat;

public class RobotContainer {

    private final Heartbeat heartbeat = new Heartbeat();
    private final CommandXboxController driver =
        new CommandXboxController(OperatorConstants.DRIVER_CONTROLLER_PORT);

    public RobotContainer() {
        configureBindings();
    }

    private void configureBindings() {
        driver.a().onTrue(
            Commands.runOnce(() -> heartbeat.reset(), heartbeat)
        );

        driver.b().onTrue(
            Commands.runOnce(() ->
                System.out.println("tick=" + heartbeat.getTickCount()),
                heartbeat)
        );
    }

    public Command getAutonomousCommand() {
        return null;
    }
}
```

Three patterns to absorb:

1. **One field per controller**. Driver is port 0; operator (for the launcher later) will be port 1.
2. **One method for all bindings: `configureBindings()`**. Lives in `RobotContainer`'s constructor flow. Every button on every controller gets its binding here. When you can't remember "what does A do?", this is the only file you have to read.
3. **The lambda goes in `Commands.runOnce` / `Commands.run`**. The second arg is the subsystem. The trigger sits in front: `driver.a().onTrue(...)`.

### Default commands

A subsystem can have a **default command**: the command that runs whenever no other command is using it. This is how teleop drive works: "when nothing else is driving, read the sticks and drive."

```java
heartbeat.setDefaultCommand(
    Commands.run(() -> {
        if (heartbeat.getTickCount() % 100 == 0) {
            System.out.println("idle heartbeat at " + heartbeat.getTickCount());
        }
    }, heartbeat)
);
```

`setDefaultCommand` is a method on `SubsystemBase`. The command you give it has the subsystem as a requirement (the second argument) and is scheduled automatically whenever the subsystem isn't being used by another command.

We'll use this pattern in R11 to make stick input the default drivetrain behaviour, once the drivetrain itself is built in R08.

---

### Reading the sticks

For triggers like the A button, you call `driver.a()` and bind it. For analog stick values, you read them on demand inside a `Commands.run` lambda:

```java
heartbeat.setDefaultCommand(
    Commands.run(() -> {
        double y = -driver.getLeftY();   // forward is up on the stick, but +Y is down
        // do something with y...
    }, heartbeat)
);
```

The `-` sign on `getLeftY()` is the classic FRC gotcha: Xbox stick Y is positive *down*. Negate at the read site to make "forward" positive.

Stick math (deadband, scaling) belongs in the command, not the subsystem. The subsystem just gets a clean voltage or speed. We refine this in R10 once we have a real drivetrain to drive.

### Try it

In your project:

1. Add the `CommandXboxController driver` field to `RobotContainer` and the two bindings from the snippet above.
2. Build and simulate (`F5`).
3. In the sim GUI, drag a keyboard from the **Joystick** list onto **Joystick 0** so the keyboard acts as the driver's controller. (The sim's default mappings vary; in many builds the "A" button is `1` on the keypad.)
4. Enable in teleop. Watch the console. Heartbeat ticks roll up automatically. Press the A-button equivalent: the count resets to 0. Press B: the current count prints.

If the sim's keyboard mapping is confusing, plug a real Xbox controller via USB. The sim picks it up.
