A **subsystem** is a Java class responsible for one robot capability. This Kit Bot has a drivetrain subsystem and a launcher subsystem that also handles intake. Its **state** is the information it remembers in fields. Its **public API** is the set of methods other code can call.

A subsystem is a Java class, so the class owns its fields and methods. WPILib's `SubsystemBase` adds the connection to the command scheduler. If inheritance is new, read [Inheritance](/java/fundamentals/java-inheritance#sharing-what-is-common) before continuing. [A16](/java/assignments/a16-subsystem-family) provides extra practice with the same shape.

---

### What `SubsystemBase` actually gives you

<ReferenceImage
  src="/media/kit-bot/traditional-subsystem.png"

  caption="A subsystem presents public robot capabilities while keeping control logic and hardware details inside."

  contain
/>

```java
public class Drive extends SubsystemBase {
    @Override
    public void periodic() {
        // runs every 20 ms while the scheduler is ticking
    }
}
```

By extending [`SubsystemBase`](https://github.wpilib.org/allwpilib/docs/release/java/edu/wpi/first/wpilibj2/command/SubsystemBase.html) you get four things:

1. **`periodic()` is called every scheduler tick** (every 20 ms). You override it to do per-tick work.
2. **The scheduler tracks "requirements"**. When a command says it requires this subsystem, the scheduler ensures only one command at a time owns it.
3. **Default-command support**. You can register a "this is what to do when nothing else is happening" command, like "drive with sticks" for the drivetrain. The scheduler runs it automatically.
4. **Sendable hooks for telemetry**. `SubsystemBase` implements [`Sendable`](https://github.wpilib.org/allwpilib/docs/release/java/edu/wpi/first/util/sendable/Sendable.html), which lets dashboard tools display information about the subsystem. R13 shows how to publish the measurements we want to graph in AdvantageScope.

You will write one class per mechanism. Each class extends `SubsystemBase`. That's the entire pattern.

### A subsystem's three jobs

Every subsystem you write has the same three responsibilities. Holding to them keeps the code understandable.

| Job | What it looks like |
|---|---|
| **Own its hardware** | `private final` fields for motor controllers, sensors. Initialized in the constructor. Nothing outside the class touches them. |
| **Expose a small public API** | Query methods return measurements. Action methods such as `launchFuel()` return a `Command` that already requires the subsystem. |
| **Run its periodic work** | `@Override periodic()` updates internal state, runs control loops, publishes telemetry. Never reads from joysticks or makes decisions about *what* to do, only *how*. |

What it does **not** do:

- Read joysticks. (Joysticks live in `RobotContainer`, see [R05](/kit-bot/r05-commands-and-triggers).)
- Decide when a command should run. Triggers and autonomous routines schedule the commands.
- Talk directly to other subsystems. Commands that coordinate several mechanisms compose their subsystem commands outside the subsystems.

This separation is what lets you change the hardware implementation in R07 and R08 and test one mechanism at a time. R05 adds command-returning methods to `Heartbeat`; R08 uses the same pattern for `Launcher.launchFuel()`.

### The simplest possible subsystem (no hardware)

Before we talk to a motor, let's prove the scheduler is calling `periodic()` and the subsystem is being constructed. We'll build a subsystem whose only job is to count up.

Create `src/main/java/frc/robot/subsystems/heartbeat/Heartbeat.java`:

```java
package frc.robot.subsystems.heartbeat;

import edu.wpi.first.wpilibj2.command.SubsystemBase;

public class Heartbeat extends SubsystemBase {

    private long tickCount = 0;

    @Override
    public void periodic() {
        tickCount++;
        if (tickCount % 50 == 0) {                  // every ~1 second at 50 Hz
            System.out.println("heartbeat: " + tickCount + " ticks");
        }
    }

    public long getTickCount() {
        return tickCount;
    }

    public void reset() {
        tickCount = 0;
    }
}
```

It has the three jobs:

- **Owns state**: the `tickCount` field. 
- **Public API**: `getTickCount()` and `reset()`.
- **Periodic work**: increments the counter every tick.

Replace `src/main/java/frc/robot/RobotContainer.java` with this complete file. It removes the template example bindings. Remove unused `ExampleCommand.java` and `ExampleSubsystem.java` only after confirming nothing refers to them.

```java
package frc.robot;

import frc.robot.subsystems.heartbeat.Heartbeat;

public class RobotContainer {

    private final Heartbeat heartbeat = new Heartbeat();

    public RobotContainer() {
        configureBindings();
    }

    private void configureBindings() {
        // we'll bind buttons here in the next module
    }

    public edu.wpi.first.wpilibj2.command.Command getAutonomousCommand() {
        return null;   // no auto yet
    }
}
```

Two things to notice:

- The subsystem is a `private final` field on `RobotContainer`. Constructed once, never reassigned. Same pattern as A14 (Robot + Battery) and A16 (subsystem fleet).
- We don't do anything explicit to "register" the subsystem with the scheduler. `SubsystemBase`'s constructor registers itself. As long as the subsystem is *constructed* somewhere, the scheduler will call its `periodic()`.

---

### Run it

Build and start simulation. Leave it disabled at first. After about one second, the console should start printing:

```
heartbeat: 50 ticks
heartbeat: 100 ticks
heartbeat: 150 ticks
...
```

If you disable the robot, the prints keep going. `CommandScheduler.run()` lives in `robotPeriodic()`, which executes in every mode, and subsystem `periodic()` methods run on every scheduler tick regardless of whether the robot is enabled. (This is different from commands, most of which stop running when the robot disables.) Confirm this matches what you see: the tick count should keep climbing whether the robot is enabled or not.

If the prints don't start at all, the most common cause is the subsystem isn't being constructed. Open `RobotContainer.java` and make sure `private final Heartbeat heartbeat = new Heartbeat();` is there. The constructor running is what registers the subsystem with the scheduler.

### What a real subsystem will look like

R07 adds a `DriveIO` field to a drivetrain subsystem. `DriveIO` is an **interface**: a list of methods the subsystem can call. One implementation talks to real controllers; another talks to a simulation.

Keep the `Heartbeat` project working for now. No drivetrain code is needed in this lesson.

### Why subsystems are classes

A subsystem groups the fields and methods for one capability.

1. The scheduler tracks the actual subsystem object. Two commands that require that object cannot run together.
2. Private fields keep other classes from changing the mechanism's settings or outputs directly.
3. An IO interface lets the same subsystem logic use real or simulated hardware.

Requirements organize command access. They do not replace electrical protection, physical guarding, or a person ready to disable the robot.

### Try it

If you haven't yet, do the exercise inline above:

1. Create the `Heartbeat` subsystem class.
2. Construct it as a `private final` field in `RobotContainer`.
3. Build, sim, enable in teleop, watch the console.

Then, while it's running, look at the structure on disk. You should have:

```
src/main/java/frc/robot/
├── Constants.java
├── Main.java
├── Robot.java
├── RobotContainer.java
└── subsystems/
    ├── drive/
    │   └── DriveConstants.java
    └── heartbeat/
        └── Heartbeat.java
```

That's the shape every subsystem will follow.
