### The idea

A recursive method solves a problem by calling itself on a smaller version of the same problem, until the problem is small enough to answer directly.

```java
public static int factorial(int n) {
    if (n <= 1) return 1;             // base case
    return n * factorial(n - 1);      // recursive case
}
```

`factorial(4)` cannot answer immediately, so it asks for `factorial(3)`, which asks for `factorial(2)`, and so on. Once `factorial(1)` returns `1`, the answers multiply back up the chain.

Every recursive method needs both parts:

<ContentTable
  headers={["Part", "Purpose", "Missing it causes"]}
  rows={[
    ["Base case", "A size small enough to answer directly", "Infinite recursion &rarr; <code>StackOverflowError</code>"],
    ["Recursive case", "Reduce the problem and call again", "Never progresses"],
    ["Progress toward the base", "Each call must get closer", "Infinite recursion"]
  ]}
/>

The third is the one people forget. A base case is useless if the recursive call does not move toward it.

### Tracing it

Working a small case by hand is the fastest way to build intuition. For `factorial(4)`:

```
factorial(4) = 4 * factorial(3)
             = 4 * (3 * factorial(2))
             = 4 * (3 * (2 * factorial(1)))
             = 4 * (3 * (2 * 1))
             = 24
```

Notice the multiplications happen on the way *back up*. Nothing is computed until the base case is reached; the calls stack up first, then resolve in reverse.

### The call stack

Each call gets its own copy of the parameters and local variables, stored in a stack frame. That is why `n` is different in each call even though they share a name.

```
factorial(1)   <- top, returns first
factorial(2)
factorial(3)
factorial(4)   <- bottom, returns last
```

This is a literal [stack](/java/fundamentals/stacks#last-in-first-out), the same last-in-first-out structure, which is why running out of space is a `StackOverflowError`.

<RulesBox title="Java's recursion depth limit">

Java does not specify one maximum recursion depth. The available stack size and the size of each call frame determine when a program runs out of stack space:

```
Exception in thread "main" java.lang.StackOverflowError
```

Deep recursion can throw StackOverflowError. Use small inputs while learning. For a task that can grow deeply, use an iterative algorithm, with an explicit stack if needed. Iteration avoids a growing chain of method calls, but the program still has memory limits.


</RulesBox>

### Recursion versus iteration

Anything recursive can be written as a loop, and vice versa. The question is which is clearer.

```java
// iterative: better here
public static int factorialLoop(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++) {
        result *= i;
    }
    return result;
}
```

For factorial, the loop is simpler and does not add a new stack frame per iteration. Recursion earns its place when the *problem itself* branches.

<RulesBox title="When recursion is the right choice">

- **The data structure is recursive.** A [tree](/java/fundamentals/trees#recursive-measurements) node contains subtrees, which are trees. Recursion mirrors the shape.
- **The problem splits into several sub-problems.** Exploring both branches of a decision, or all four directions on a grid.
- **You do not know the depth in advance.** Nested folders, or a search whose length depends on input.

When the problem repeats one step in a straight line, use a loop.

</RulesBox>

### Sum an array recursively

```java
public static int sumFrom(int[] values, int index) {
    if (index == values.length) return 0;
    return values[index] + sumFrom(values, index + 1);
}
```

Call `sumFrom(new int[] {2, 4, 6}, 0)`. It returns `12`. Each call handles one value, then delegates the rest of the array. The base case represents an empty remaining range.

This example assumes `0 <= index && index <= values.length`. A loop uses less call-stack space for a long array. [Tree Traversals](/java/fundamentals/tree-traversals) applies recursion to branching data.

### Watch out for accidental exponential work

Some innocent-looking recursion does enormous amounts of repeated work:

```java
public static int fib(int n) {
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);
}
```

This is correct but recomputes the same values constantly; `fib(40)` makes hundreds of millions of calls. The fix is to remember results you have already computed, covered in [Memoization and Dynamic Programming](/java/fundamentals/memoization-and-dynamic-programming#memoization).

Correct and fast are separate questions. Recursive code can produce the correct answer and still run too slowly to use.

### Helper methods

Often the natural recursion needs extra parameters the caller should not supply. Use a wrapper:

```java
public static int countMatches(int[] values, int target) {
    return countFrom(values, target, 0);       // caller-friendly
}

private static int countFrom(int[] values, int target, int index) {
    if (index == values.length) return 0;
    int here = (values[index] == target) ? 1 : 0;
    return here + countFrom(values, target, index + 1);
}
```

The public method has a clean signature; the private one carries the position. This pattern appears constantly.

<RulesBox title="Common mistakes">

- **No base case**, or one that is unreachable.
- **Not reducing the problem**, so it recurses forever with the same argument.
- **Forgetting to return the recursive call's result.** Calling `factorial(n - 1)` without using the value discards the work.
- **Modifying shared state without undoing it.** See [Backtracking](/java/fundamentals/backtracking#choose-recurse-undo).
- **Assuming recursion is free.** Each call costs a stack frame.
- **Recomputing the same sub-problem** exponentially.

</RulesBox>

<ExerciseBox title="Practice" description="Write each recursively first, then decide whether a loop would be clearer.">

1. Sum the integers from 1 to `n`.
2. Reverse a `String`.
3. Count the digits in a positive integer.
4. Compute the greatest common divisor of two numbers.
5. Print every subset of an `int[]`.

<details>
<summary>Hints</summary>

1. Base case `n <= 0` returns 0; otherwise `n + sumTo(n - 1)`.
2. Base case: a string shorter than 2 is its own reverse. Otherwise the reverse of everything after the first character, plus that character at the end.
3. Base case `n < 10` returns 1; otherwise `1 + countDigits(n / 10)`.
4. `gcd(a, b)` is `a` when `b` is 0, otherwise `gcd(b, a % b)`. Two lines, and it terminates because the remainder always shrinks.
5. At each index you either include the element or skip it: two recursive calls. This is the shape behind backtracking.

</details>

</ExerciseBox>
