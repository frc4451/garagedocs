### The question Big-O answers

Two methods both take a millisecond on today's data. One will take ten milliseconds on ten times the data; the other will take a hundred. Big-O is the notation for *which one you have*, and it is the difference between code that survives the season and code that mysteriously gets slower every event.

The notation describes how running time **grows** as the input size `n` grows. It ignores constants (a loop that does three things per element and a loop that does thirty are both O(n)) because past a certain `n`, the growth shape dominates any constant.

That third column is the practical one. If you can measure a method at two sizes, you can usually tell which row it is on.

### Reading the shapes

The skill is looking at five lines and recognising the shape without counting anything. Here are the ones that cover almost every method you will write.

**No loop: O(1).** However big the array, this does two reads.

```java
public class Main {
    static int endsSum(int[] arr) {
        return arr[0] + arr[arr.length - 1];
    }

    public static void main(String[] args) {
        System.out.println(endsSum(new int[] { 3, 9, 4, 7 }));   // 10
    }
}
```

**One pass: O(n).** Every element visited once. A second sequential loop over the same array is still O(n): two passes is 2n, and the 2 drops out.

```java
public class Main {
    static int sum(int[] arr) {
        int total = 0;
        for (int x : arr) total += x;
        return total;
    }

    public static void main(String[] args) {
        System.out.println(sum(new int[] { 3, 9, 4, 7 }));   // 23
    }
}
```

**Halving: O(log n).** Each step throws away half of what is left, so 1,000 elements take about 10 steps and 1,000,000 take about 20. This is binary search from [Searching](/java/fundamentals/java-searching#binary-search).

```java
public class Main {
    static int halvings(int n) {
        int count = 0;
        while (n > 1) {
            n /= 2;
            count++;
        }
        return count;
    }

    public static void main(String[] args) {
        System.out.println(halvings(1000));      // 9
        System.out.println(halvings(1000000));   // 19
    }
}
```

**A loop inside a loop: O(n²).** Every element paired with every element. The inner loop starting at `i + 1` instead of `0` does about half the work, and half of n² is still O(n²).

```java
public class Main {
    static int pairs(int[] arr) {
        int count = 0;
        for (int i = 0; i < arr.length; i++)
            for (int j = i + 1; j < arr.length; j++)
                count++;
        return count;
    }

    public static void main(String[] args) {
        System.out.println(pairs(new int[10]));    // 45
        System.out.println(pairs(new int[20]));    // 190: 4x for 2x the input
    }
}
```

**A loop around a halving: O(n log n).** Multiply the shapes: n times log n. This is also the cost of every good sort, which is why "sort it, then scan it" is so often the right plan.

```java
public class Main {
    static int mixed(int n) {
        int total = 0;
        for (int k = 0; k < n; k++)
            for (int j = 1; j < n; j *= 2)
                total++;
        return total;
    }

    public static void main(String[] args) {
        System.out.println(mixed(16));   // 64  (16 × 4)
    }
}
```

**Branching recursion: O(2ⁿ).** Each call makes two more. `fib(30)` makes over a million calls; `fib(40)` makes over a billion. [Memoization](/java/fundamentals/java-memoization-and-dynamic-programming#the-repeated-work-problem) is the fix.

```java
public class Main {
    static int fib(int n) {
        if (n <= 1) return n;
        return fib(n - 1) + fib(n - 2);
    }

    public static void main(String[] args) {
        System.out.println(fib(20));   // 6765, and about 22,000 calls to get it
    }
}
```

### The hidden loop

The shapes above are visible in the code. The one that catches people is the loop **inside a method call**.

```java
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

public class Main {

    static List<Integer> distinctSlow(int[] arr) {
        List<Integer> result = new ArrayList<>();
        for (int x : arr) {
            if (!result.contains(x)) result.add(x);   // contains walks the whole list
        }
        return result;
    }

    static List<Integer> distinctFast(int[] arr) {
        List<Integer> result = new ArrayList<>();
        Set<Integer> seen = new HashSet<>();
        for (int x : arr) {
            if (seen.add(x)) result.add(x);           // add is a hash lookup
        }
        return result;
    }

    public static void main(String[] args) {
        int[] data = { 5, 3, 5, 9, 1, 3, 9 };
        System.out.println(distinctSlow(data));   // [5, 3, 9, 1]
        System.out.println(distinctFast(data));   // [5, 3, 9, 1]
    }
}
```

Both versions look like one loop. However, `List.contains` also loops over the list, so the first version is O(n²). `HashSet.add` is O(1) on average, so the second version is O(n).

The programs return the same answer and have a similar shape on the page. Their costs differ because of the library calls inside the loop. Reading real code requires knowing the cost of those calls.

### Best, average, worst

A linear search returns as soon as it finds the target. Finding the target in the first element is O(1). Finding it in the last element, or failing to find it, is O(n).

When someone says "O(n)" without qualification, they usually mean the **worst case**. The worst case determines whether the loop fits within your time budget.

For most code the three cases are the same and you do not mention them. Say so when they differ; it is the difference between "this is fine" and "this is fine unless the target is missing".

### Checking a guess with a stopwatch

Tags are cheap to get wrong. The check is empirical: time the method at two sizes and compare the ratio with the table's third column.

```java
public class Main {
    static int pairs(int[] arr) {
        int count = 0;
        for (int i = 0; i < arr.length; i++)
            for (int j = i + 1; j < arr.length; j++)
                count++;
        return count;
    }

    static long[] samples = new long[5];

    static long medianMicros(Runnable task) {
        for (int i = 0; i < samples.length; i++) {
            long start = System.nanoTime();
            task.run();
            samples[i] = (System.nanoTime() - start) / 1000;
        }
        long[] sorted = samples.clone();
        java.util.Arrays.sort(sorted);
        return sorted[sorted.length / 2];
    }

    public static void main(String[] args) {
        int[] small = new int[4000];
        int[] large = new int[8000];
        medianMicros(() -> pairs(large));   // warm-up: let the JIT compile pairs first
        long t1 = medianMicros(() -> pairs(small));
        long t2 = medianMicros(() -> pairs(large));
        System.out.println(small.length + ": " + t1 + "us, " + large.length + ": " + t2 + "us");
        System.out.println("ratio about " + (t1 == 0 ? "?" : String.valueOf(t2 / (double) t1)));
    }
}
```

Take the **median** of several runs instead of trusting one reading. **Warm up first** because the first call to a method is slower while the just-in-time (JIT) compiler processes it. Other work on the computer can also disturb a single measurement.

Without the warm-up line above, the small input receives the slow first call and may produce a misleading ratio. After warming up, doubling the input should produce a ratio near 4 for O(n²) work and near 2 for O(n) work.

<RulesBox title="What this looks like on a robot">

`periodic()` runs every 20 ms. Anything O(n²) over a growing collection inside it is a bug that has not happened yet: fine with 50 samples, 25 ms with 1,000, and the symptom is loop-overrun warnings in the driver station log, never a stack trace.

The usual fixes are the ones above: a `HashSet` instead of `List.contains`, a ring buffer instead of `remove(0)`, or doing the expensive part once outside the loop and reading the result inside it.

</RulesBox>

<RulesBox title="Common mistakes">

- **Counting the inner loop's smaller bound as a smaller class.** n²/2 is O(n²).
- **Missing the loop inside a library call.** `contains`, `indexOf`, `remove(0)`, `substring` all walk or copy.
- **Reporting the best case.** A search that "usually returns early" is still O(n).
- **Timing one run** and trusting it. Median of several, ignoring the first.
- **Sorting inside a loop.** O(n log n) done n times is O(n² log n). Sort once, outside.
- **Optimising an O(n) loop that runs once** while an O(n²) one runs fifty times a second goes unnoticed.

</RulesBox>
