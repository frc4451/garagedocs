### Two different questions

`static` and `final` show up next to each other so often that people learn them as one thing. They answer two unrelated questions:

- **`static`**: does this belong to the *class*, or to each *object*?
- **`final`**: can this be *reassigned* after it is first set?

You can have either without the other. Understanding them separately is what makes `public static final` readable instead of a phrase you copy.

### static: one copy, shared

An ordinary field lives inside each object. Make ten `Robot`s and there are ten `name` fields. A `static` field lives in the class itself. There is exactly one, no matter how many objects exist, and it exists even if there are none.

```java
public class Robot {
    public static int built = 0;       // one counter for the whole class
    public String name;                // one name per robot

    public Robot(String name) {
        this.name = name;
        built++;                // every constructor bumps the same counter
    }
}

Robot a = new Robot("Drive");
Robot b = new Robot("Launcher");
Robot c = new Robot("Intake");

System.out.println(Robot.built);   // 3
System.out.println(a.name);        // Drive
```

Notice the access: `Robot.built`, through the class name. You *can* write `a.built`, and it compiles, but it misleads, because it looks like the value belongs to `a`. Read a static through the class it belongs to.

### static methods

A static method has no this reference. It can use its parameters, static members, and local variables. To access an instance field, it needs a reference to an object, such as a parameter.

```java
public class Units {
    public static double feetToInches(double feet) {
        return feet * 12;
    }
}

System.out.println(Units.feetToInches(2.5));    // 30.0
```

That is what `Math.abs`, `Math.max` and `Integer.parseInt` are: static methods on classes you never instantiate. It is also why `main` is static: the JVM calls it before any object of your class exists.

<RulesBox title="The error everyone hits once">

```java norun
public class Robot {
    public String name;

    public static void main(String[] args) {
        System.out.println(name);   // error: non-static variable name
                                    // cannot be referenced from a static context
    }
}
```

`main` is static, so there is no `this`. The `name` field belongs to a `Robot` object, but no object was created. Create a `Robot` and read that object's name.

Making `name` static would hide the design error. When this compiler error appears, identify which object should own the value.

</RulesBox>

### final: set once

A `final` variable can be assigned exactly once. After that, any attempt to reassign it is a compile error.

```java
public class Main {
    public static void main(String[] args) {
        final int MAX_SPEED = 100;
        int current = 40;

        current = 60;          // fine
        // MAX_SPEED = 120;    // error: cannot assign a value to final variable

        System.out.println(MAX_SPEED + " " + current);   // 100 60
    }
}
```

For a field, "once" can mean in the declaration or in the constructor; the compiler checks that every constructor assigns it and nothing else ever does.

```java
public class Motor {
    public final int canId;            // assigned in the constructor, never again
    public double output;              // changes all the time

    public Motor(int canId) {
        this.canId = canId;
    }
}

Motor left = new Motor(10);
left.output = 0.5;
// left.canId = 11;             // error
System.out.println(left.canId);   // 10
```

This is the most useful `final` there is. A motor's CAN ID does not change while the robot runs; marking the field `final` makes the compiler enforce it, and tells the next reader *this is identity, not state* without a comment.

### final does not mean immutable

`final` stops you reassigning the *variable*. It says nothing about the object the variable points to.

```java
import java.util.ArrayList;
import java.util.List;

final List<String> subsystems = new ArrayList<>();
subsystems.add("Drive");          // fine: the list changed, the variable did not
subsystems.add("Launcher");
// subsystems = new ArrayList<>(); // error: this would reassign the variable

System.out.println(subsystems);   // [Drive, Launcher]
```

A final reference cannot be reassigned, but its object can still change. List.of creates an unmodifiable list; Collections.unmodifiableList creates an unmodifiable view. Neither freezes mutable elements, and the backing list of a view can still change. [ArrayLists](/java/fundamentals/java-arraylists) explains these collection examples.

### Putting them together: constants

A value that is the same for every object *and* never changes is both `static` and `final`. That is a **constant**, and Java's convention names it in `UPPER_CASE`:

```java
public class DriveConstants {
    public static final int LEFT_LEADER_CAN_ID = 10;
    public static final int RIGHT_LEADER_CAN_ID = 12;
    public static final double MAX_SPEED_MPS = 3.5;
    public static final double DEADBAND = 0.08;
}

System.out.println(DriveConstants.LEFT_LEADER_CAN_ID);   // 10
System.out.println(DriveConstants.MAX_SPEED_MPS * 2);    // 7.0
```

`static` because a CAN ID is a fact about the robot, not about any particular object, so there is one copy. `final` because it must not change while the program runs. `UPPER_CASE` so that anyone reading `DEADBAND` three files away knows it is a constant without looking it up.

The alternative is a `0.08` typed directly where it is used, a **magic number**. It works until you need to change it and cannot find the four other places you typed it. Constants have one home.

<RulesBox title="Reading public static final">

A constant shared with other classes can be public static final. Use private static final when only its own class needs it:

- `public`: any class can read it
- `static`: accessed as `DriveConstants.DEADBAND`, no object needed
- `final`: the compiler rejects any attempt to change it

Three keywords, three separate decisions, and now each one means something.

</RulesBox>

<RulesBox title="Common mistakes">

- **Making a field `static` to silence "non-static variable cannot be referenced from a static context".** Create the object instead.
- **Reading a static through an object.** `a.built` compiles but lies about ownership. Use the class name.
- **Assuming `final` freezes the object.** It freezes the variable; a `final` list still accepts `add`.
- **A `final` field the constructor forgets to set.** The compiler will tell you, which is the point.
- **Magic numbers.** `0.08` in three places is three bugs waiting for the day it becomes `0.1`.
- **`UPPER_CASE` on something that is not a constant.** Reserve it for `static final` values; using it for ordinary variables makes real constants harder to spot.

</RulesBox>
