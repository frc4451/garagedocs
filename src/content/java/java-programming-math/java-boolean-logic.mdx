Boolean logic describes statements that can be true or false and the rules for combining them. Badge 1 assigns this lesson before Java Fundamentals, so the first sections use words, symbols, and arithmetic examples. The later Java section applies the same ideas to code.

## Statements that Can Be True or False

A **proposition** is a statement with one truth value: true or false. For example, “12 is greater than 5” is true, and “8 is an odd number” is false. A question or instruction is not a proposition because it does not claim something that can be true or false.

Letters such as `p` and `q` are short names for propositions. If `p` means “12 is greater than 5,” then `p` has the value true. The letters do not stand for numbers in this lesson. They stand for complete statements and their truth values.

A statement with a value still missing is a **predicate**. For example, “`x` is greater than 5” can be true or false depending on `x`. After `x` is given a value, such as 12, the predicate becomes a proposition that can be evaluated.

## Boolean Operators

An **operator** combines or changes truth values. Logic textbooks and Java use different symbols for some of the same operations.

<ContentTable
  title="Boolean Operators"
  headers={["Logic", "Name", "Meaning", "Java form"]}
  rows={[
    ["<code>¬p</code>", "NOT", "Reverse one truth value", "<code>!p</code>"],
    ["<code>p ∧ q</code>", "AND", "True when both propositions are true", "<code>p &amp;&amp; q</code>"],
    ["<code>p ∨ q</code>", "OR", "True when at least one proposition is true", "<code>p || q</code>"],
    ["<code>p ⊕ q</code>", "XOR", "True when exactly one proposition is true", "<code>p ^ q</code>"],
    ["<code>p → q</code>", "Implication", "False only when <code>p</code> is true and <code>q</code> is false", "No Java implication operator"],
    ["<code>p ↔ q</code>", "Biconditional", "True when both propositions have the same truth value", "<code>p == q</code> for boolean values"]
  ]}
/>

In logic, **OR** is inclusive: `p ∨ q` is true when `p` is true, `q` is true, or both are true. XOR means “one or the other, but not both.”

## Truth Tables

A **truth table** lists every possible set of input values and calculates the result for each set. With two propositions, there are four combinations. Keep the rows in a regular order so none are missed: true/true, true/false, false/true, false/false.

<ContentTable title="Two-Input Truth Table" headers={["p", "q", "¬p", "p ∧ q", "p ∨ q", "p ⊕ q"]} rows={[
  ["true", "true", "false", "true", "true", "false"],
  ["true", "false", "false", "false", "true", "true"],
  ["false", "true", "true", "false", "true", "true"],
  ["false", "false", "true", "false", "false", "false"]
]} />

Read one row at a time. In the second row, `p` is true and `q` is false. Therefore, `p ∧ q` is false because both inputs are not true, while `p ∨ q` is true because at least one input is true.

Three propositions have eight combinations. To build the input columns, keep `p` true for four rows and false for four rows. Change `q` every two rows and `r` every row.

<ContentTable title="Three-Input Row Pattern" headers={["p", "q", "r"]} rows={[
  ["true", "true", "true"],
  ["true", "true", "false"],
  ["true", "false", "true"],
  ["true", "false", "false"],
  ["false", "true", "true"],
  ["false", "true", "false"],
  ["false", "false", "true"],
  ["false", "false", "false"]
]} />

For a compound expression, add a column for each inner part. For `p ∧ (¬q ∨ r)`, calculate `¬q` first, then `¬q ∨ r`, and finally the complete expression. In the first row, `¬q` is false, `false ∨ true` is true, and `true ∧ true` is true.

## Implication and Its Relatives

The implication `p → q` means that whenever `p` is true, `q` must also be true. It is false only when `p` is true and `q` is false.

<ContentTable title="Implication and Biconditional" headers={["p", "q", "p → q", "p ↔ q"]} rows={[
  ["true", "true", "true", "true"],
  ["true", "false", "false", "false"],
  ["false", "true", "true", "false"],
  ["false", "false", "true", "true"]
]} />

The last two implication rows can feel unusual. When `p` is false, the requirement “whenever `p` is true, `q` is true” has not been broken. The table therefore marks both rows that begin with false as true. This definition also makes `p → q` equivalent to `¬p ∨ q`.

Use an arithmetic example to compare an implication with related statements:

- `p`: an integer is a multiple of 4.
- `q`: the integer is even.

<ContentTable title="Statements Related to an Implication" headers={["Form", "Symbol", "Statement", "Equivalent to the original?"]} rows={[
  ["Original", "<code>p → q</code>", "If an integer is a multiple of 4, then it is even", "Yes"],
  ["Contrapositive", "<code>¬q → ¬p</code>", "If an integer is not even, then it is not a multiple of 4", "Yes"],
  ["Converse", "<code>q → p</code>", "If an integer is even, then it is a multiple of 4", "No; 6 is a counterexample"],
  ["Inverse", "<code>¬p → ¬q</code>", "If an integer is not a multiple of 4, then it is not even", "No; 6 is a counterexample"]
]} />

Only the contrapositive is guaranteed to match the original implication. The converse and inverse need their own evidence.

## Equivalent Expressions

Two expressions are **equivalent** when every row of their truth tables matches.

<ContentTable title="Boolean Equivalences" headers={["Name", "First expression", "Equivalent expression", "Use"]} rows={[
  ["Double negation", "<code>¬¬p</code>", "<code>p</code>", "Remove a repeated negation"],
  ["Identity", "<code>p ∧ true</code><br /><code>p ∨ false</code>", "<code>p</code><br /><code>p</code>", "Remove a value that cannot change the result"],
  ["Domination", "<code>p ∧ false</code><br /><code>p ∨ true</code>", "<code>false</code><br /><code>true</code>", "Find a result that is already fixed"],
  ["De Morgan's first law", "<code>¬(p ∧ q)</code>", "<code>¬p ∨ ¬q</code>", "Negate an AND expression"],
  ["De Morgan's second law", "<code>¬(p ∨ q)</code>", "<code>¬p ∧ ¬q</code>", "Negate an OR expression"],
  ["Implication", "<code>p → q</code>", "<code>¬p ∨ q</code>", "Write implication with NOT and OR"],
  ["Contrapositive", "<code>p → q</code>", "<code>¬q → ¬p</code>", "Reason backward from a missing result"]
]} />

De Morgan's laws change both operators: negate each proposition, then swap AND with OR or OR with AND. A truth table can verify a law by showing that the two result columns match on every row.

## Rules of Inference

An **argument** starts with one or more **premises**, statements accepted as true for that argument. Its **conclusion** is the statement that follows from those premises. An **inference rule** gives a valid pattern for moving from true premises to a conclusion.

<ContentTable title="Common Inference Rules" headers={["Rule", "Premises", "Conclusion"]} rows={[
  ["Modus ponens", "<code>p → q</code><br /><code>p</code>", "<code>q</code>"],
  ["Modus tollens", "<code>p → q</code><br /><code>¬q</code>", "<code>¬p</code>"],
  ["Hypothetical syllogism", "<code>p → q</code><br /><code>q → r</code>", "<code>p → r</code>"],
  ["Disjunctive syllogism", "<code>p ∨ q</code><br /><code>¬p</code>", "<code>q</code>"]
]} />

Inference rules are only as reliable as their premises. For example: “If a number is a multiple of 4, then it is even. The number is a multiple of 4. Therefore, it is even.” This is modus ponens. The conclusion follows when both premises are true.

<RulesBox title="Optional Robot Context">

Robot examples are applications, not extra Badge 1 requirements. A premise such as “If a sensor is connected, then data arrives” is an assumed model, not a hardware guarantee. A delayed packet, a logging error, or a second fault can make that premise incomplete. Debugging still requires checking what the program and hardware establish.

</RulesBox>

## Tautologies and Contradictions

<ContentTable headers={["Kind", "Meaning", "Example", "What it can suggest in code"]} rows={[
  ["Tautology", "Always true", "<code>p ∨ ¬p</code>", "A branch that always runs"],
  ["Contradiction", "Always false", "<code>p ∧ ¬p</code>", "A branch that cannot run"]

When a long condition appears always true or always false, build its truth table. The table can expose the row where an assumption fails or confirm that the expression has the same result on every row.

## Practice

These checks are ungraded practice. Badge 1 still uses the separate paper worksheet and its existing sign-off requirements.

1. Build the eight input rows for `ready ∧ (¬fault ∨ override)`. Use `ready` as `p`, `fault` as `q`, and `override` as `r` in the three-input row pattern. Add columns for `¬fault`, `¬fault ∨ override`, and the complete expression. The first complete-expression result is true.
2. Use De Morgan's laws to rewrite `¬(enabled ∧ connected)` without negating a grouped AND expression. Verify the rewrite with a four-row truth table.
3. Label each argument as modus ponens, modus tollens, hypothetical syllogism, or disjunctive syllogism.
   1. If an integer is a multiple of 4, then it is even. The integer is a multiple of 4. Therefore, it is even.
   2. If a whole number is greater than 10, then it is greater than 5. The number is not greater than 5. Therefore, it is not greater than 10.
   3. If a whole number is greater than 10, then it is positive. If it is positive, then its square is positive. Therefore, if it is greater than 10, then its square is positive.
   4. The integer is even or odd. The integer is not even. Therefore, it is odd.
4. Explain why the converse of “if an integer is a multiple of 4, then it is even” is not guaranteed. Give one counterexample.

## Implication and Java If

This and the next section apply the logic to Java after the Badge 1 worksheet material. If you are following Badge 1 before Java Fundamentals, finish the practice above, complete the assigned paper worksheet, and return here after Java Fundamentals.

A logical implication is a proposition with a truth value. A Java `if` statement is an instruction that evaluates a condition and may execute a block of code. The `if` statement does not claim that one proposition implies another.

Java has no implication operator. After you reach [Conditionals](/java/fundamentals/java-conditionals), you can represent the truth value of `p → q` with `!p || q`. You can use that expression as an `if` condition, but the expression and the `if` statement still have different jobs.

## Java Evaluation

For the four Java Boolean operators used here, precedence runs from highest to lowest: `!`, `^`, `&&`, then `||`. Precedence tells Java which operation groups first when parentheses are absent. The earlier operator table was organized for learning and did not state precedence. Use parentheses when the intended grouping would otherwise be hard to see.

Java evaluates the left operand before the right operand. The `&&` and `||` operators also **short-circuit**:

- For `p && q`, Java skips `q` when `p` is false because the result is already false.
- For `p || q`, Java skips `q` when `p` is true because the result is already true.
- For Boolean `p ^ q`, Java evaluates both operands.

```java
public class Main {
    public static void main(String[] args) {
        boolean enabled = true;
        boolean connected = false;

        boolean first = !(enabled && connected);
        boolean equivalent = !enabled || !connected;

        System.out.println(first);      // true
        System.out.println(equivalent); // true
    }
}
```

A matching truth table proves that two expressions return the same Boolean result for the same input values. It does not prove that two Java expressions evaluate the same parts in the same order. If an operand calls a method, changes a variable, or can throw an exception, a rewrite may change program behavior. Apply these equivalences directly to Boolean variables and comparisons. Analyze evaluation order separately for expressions with other effects.
