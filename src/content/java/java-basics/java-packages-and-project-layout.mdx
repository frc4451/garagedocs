### One file is not a project

A package groups related Java types and gives them a shared name prefix. In the project layout used here, source folders match the package name beneath the source root.

```java norun
// File: src/main/java/frc/robot/subsystems/Drive.java
package frc.robot.subsystems;

public class Drive {
    // ...
}
```

The package declaration determines the type’s full name. Keep its folder path aligned with that package so VS Code and the build tools can find it consistently.

A public top-level class also needs a matching filename. A folder mismatch and a filename mismatch are different problems; javac can compile an explicitly supplied source file from a different folder.

A class's full name is its package plus its name: `frc.robot.subsystems.Drive`. Two classes can both be called `Drive` as long as they live in different packages, which is how your `Drive` and a library's `Drive` coexist.

### import

Inside a package, classes see each other by their short names. Anything from a *different* package has to be named in full, or brought in with `import`:

```java norun
package frc.robot;

import frc.robot.subsystems.Drive;          // one class
import edu.wpi.first.wpilibj.TimedRobot;    // one class from a library
import java.util.List;                      // one class from the JDK

public class Robot extends TimedRobot {
    private final Drive drive = new Drive();
    private final List<String> log = new java.util.ArrayList<>();   // full name inline, no import needed
}
```

`import` does not copy or load anything. It is a note to the compiler: *when I say `Drive`, I mean `frc.robot.subsystems.Drive`.* That is all. The class still has to exist somewhere the compiler can find it.

Two things you do not import: anything in `java.lang` (`String`, `Math`, `System`, always visible), and anything in the same package as the file you are writing.

<RulesBox title="Wildcard imports">

`import java.util.*;` brings in every class in `java.util`. It is convenient in a scratch file and discouraged in a real one: a reader cannot tell which classes the file uses, and when two packages both have a `List`, the compiler cannot tell either. Name what you use.

</RulesBox>

### What the layout looks like

This is the standard Gradle Java source layout used by WPILib projects. Build configuration can customize it; check the source-root settings if another project differs:

```
my-robot/
├── build.gradle              what to build and which libraries to fetch
├── settings.gradle
├── src/
│   ├── main/
│   │   ├── java/             ← the source root: packages start here
│   │   │   └── frc/robot/
│   │   │       ├── Main.java
│   │   │       ├── Robot.java
│   │   │       ├── RobotContainer.java
│   │   │       ├── Constants.java
│   │   │       └── subsystems/
│   │   │           ├── Drive.java
│   │   │           └── Launcher.java
│   │   └── deploy/           files copied to the robot as-is
│   └── test/
│       └── java/             tests, same package layout as main
└── build/                    generated; never edit, never commit
```

Three things to notice:

1. **`src/main/java` is the root.** `package frc.robot.subsystems` means `src/main/java/frc/robot/subsystems/`. The `src/main/java` part is not in the package name.
2. **Packages group by purpose.** `subsystems` holds subsystems, `commands` holds commands. When a package has fifteen unrelated files, it wants splitting.
3. **`build/` is output.** It is regenerated on every build. It belongs in `.gitignore`, and if something in it looks wrong, the fix is in `src/`.

### Naming

Package names are lowercase, dot-separated, and conventionally start with something that identifies the owner: `com.company.product` for commercial code, `frc.robot` for a WPILib project, `org.team1234` for a team library. Class names are `UpperCamelCase`, one public class per file, file named after it.

The convention exists so that any two projects in the world can be combined without a name collision. For a robot project the important part is smaller: put things where the next person will look for them.

### Visibility follows packages

Use explicit visibility in GarageDocs examples: public for types and methods other classes need, and private for internal fields and helpers.

```java
package frc.robot.subsystems;

public class Drive {
    private double lastCommandedSpeed;

    public void arcadeDrive(double speed) {
        lastCommandedSpeed = speed;
    }
}
```

Another class can call arcadeDrive but cannot read lastCommandedSpeed directly. Java also supports package-private access when a modifier is omitted. Recognize it in outside code; the examples here state their intended access explicitly.


<RulesBox title="Common mistakes">

- **File in the wrong folder for its package**, or the wrong package for its folder. Check the source root and package declaration as well as the message from your editor or build tool.
- **Filename that does not match the public class**, including case: `drive.java` holding `class Drive` fails.
- **Editing files under `build/`.** They are overwritten on the next build.
- **Forgetting the `import`** and reading "cannot find symbol" as if the class were missing. The class exists, but the compiler was not told where to look.
- **`import java.util.*;` in a file that also uses `java.awt.List`.** An ambiguity error that a specific import would have avoided.
- **Everything in one package.** A twenty-file `frc.robot` with no sub-packages is a project nobody can navigate.

</RulesBox>

<ExerciseBox title="Practice">

1. Create `src/main/java/team/util/Clamp.java` with package `team.util` and a public static clamp method. Create `src/main/java/team/Main.java` with package `team` and a public static main that imports and calls Clamp.
2. From the project root, run `javac -d out src/main/java/team/util/Clamp.java src/main/java/team/Main.java`. Then run `java -cp out team.Main`. These commands work in PowerShell and bash.
3. Test clamp with a value below, inside, and above its range. Print the three results.
4. Add a private field to Clamp. Try to read it from Main, identify the access error, then remove that invalid access.
5. Open a WPILib project and identify the source root and the packages containing Robot, RobotContainer, and its subsystems.

The -d out option puts compiled classes in an output folder with the appropriate package structure. Keep source files in folders matching their package declarations.

</ExerciseBox>
