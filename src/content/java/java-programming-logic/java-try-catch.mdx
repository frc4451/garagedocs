## Follow A Failure Path

Some valid Java programs encounter a problem while they run. You saw one example in [Console Input](/java/fundamentals/java-console-input#read-input-failures): `Integer.parseInt("twelve")` cannot produce an `int`, so it throws a `NumberFormatException`.

An **exception** is an object that reports this kind of runtime failure. When a statement inside a `try` block throws an exception, Java stops that path through the block and looks for a matching `catch` block. Without a matching handler, Java continues looking through the active method calls. If none provides one, Java reports the exception and ends these console programs.

A compiler error is different. It means Java could not turn the source into a program, so the program never started. A missing semicolon is a compiler error. Text that cannot be converted to an `int` is a runtime failure in a program that did compile.

## Handle An Expected Failure

Use `try` and `catch` when an operation has a known failure that the program can respond to. This complete `Main.java` file tries two fixed inputs, so both paths are repeatable. To run it locally, replace the entire contents of `Main.java`, save the file, and follow [Compile And Run](/java/fundamentals/java-setup#compile-and-run).

```java
public class Main {
    public static void main(String[] args) {
        printCount("12");
        printCount("twelve");
        System.out.println("Program continues");
    }

    public static void printCount(String countText) {
        try {
            int count = Integer.parseInt(countText);
            System.out.println("Count: " + count);
        } catch (NumberFormatException e) {
            System.out.println("Cannot use as a count: " + countText);
        }
    }
}
```

The output is:

```text
Count: 12
Cannot use as a count: twelve
Program continues
```

For `"12"`, the conversion succeeds, the `catch` block is skipped, and the method ends normally. For `"twelve"`, `parseInt` throws `NumberFormatException`. Java skips the rest of the `try` block and runs the matching handler. After the handler finishes, execution continues after the complete try/catch statement.

The declaration `NumberFormatException e` has two parts:

- `NumberFormatException` is the type this handler catches.
- `e` is a local variable that refers to the caught exception object. The name can be different, but `e` is a common short name.

The first handler does not need to inspect `e`. It prints the value that the program was trying to use, which gives the reader enough context to correct the input.

## Use The Exception Message Carefully

An exception provides a `getMessage()` method. It returns the exception's detail text. Some exceptions have no detail text, in which case the method returns the special value `null`. For now, read that value as “no detail message.” The exact message is useful for a log or investigation, but it is not a stable user instruction to build program logic around.

This partial snippet can replace the try/catch block inside `printCount` from the first program:

```java norun
try {
    int count = Integer.parseInt(countText);
    System.out.println("Count: " + count);
} catch (NumberFormatException e) {
    System.out.println("Could not convert countText to an int");
    System.out.println("Java reported: " + e.getMessage());
}
```

The first line records what the program was doing. The second adds Java's detail. A useful handler can also choose a documented default, skip an optional action, or ask the caller for a new value. The next lesson, [While Loops](/java/fundamentals/java-while-loops), teaches the repetition needed to ask again until an input is valid.

## Catch The Intended Type

A `try` block can have several `catch` blocks. Java checks them in order and runs the first one whose declared type can handle the thrown exception. This complete file has one handler for invalid number text and another for integer division by zero:

```java
public class Main {
    public static void main(String[] args) {
        printShare("12", "3");
        printShare("twelve", "3");
        printShare("12", "0");
    }

    public static void printShare(String totalText, String groupCountText) {
        try {
            int total = Integer.parseInt(totalText);
            int groupCount = Integer.parseInt(groupCountText);
            int share = total / groupCount;
            System.out.println("Share: " + share);
        } catch (NumberFormatException e) {
            System.out.println("Both values must be integers");
        } catch (ArithmeticException e) {
            System.out.println("Group count cannot be zero");
        }
    }
}
```

The output is:

```text
Share: 4
Both values must be integers
Group count cannot be zero
```

Only one handler runs for each call. A `NumberFormatException` reaches the first handler. An `ArithmeticException` from integer division by zero does not match the first type, so Java checks and runs the second handler.

Catch the specific failures the program knows how to handle. A broad `catch (Exception e)` also catches many programming defects and unrelated failures. It can hide the location of a bug or let the program continue with missing results. Let an unexpected exception remain visible unless this part of the program has a deliberate recovery or reporting policy for it.

Fix a preventable mistake at its source when you can. For example, a condition can reject a zero divisor before division. Exception handling does not replace correct conditions, input checks, or debugging.

## Run Cleanup With Finally

An optional `finally` block runs when execution leaves its `try` and `catch` blocks. That includes a normal path, a matching handler, a return, or an unmatched exception that will continue to an outer method. It is useful for cleanup that belongs to this operation. This complete program makes the normal and handled paths visible without a loop:

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Result: " + readCount("12"));
        System.out.println("Result: " + readCount("twelve"));
    }

    public static int readCount(String countText) {
        try {
            return Integer.parseInt(countText);
        } catch (NumberFormatException e) {
            System.out.println("Using a default count");
            return 0;
        } finally {
            System.out.println("Finished count attempt");
        }
    }
}
```

The output is:

```text
Finished count attempt
Result: 12
Using a default count
Finished count attempt
Result: 0
```

Each `return` chooses a value, then the `finally` block runs before control returns to `main`, provided that `finally` finishes normally. The second call also runs its matching `catch` block before `finally`.

`finally` has limits. It may not run if the Java Virtual Machine exits or the process is forcibly stopped while the `try` or `catch` block is running. Code inside `finally` can fail too. A `return` or thrown exception from `finally` can replace the result or failure that was already in progress, so keep control-flow decisions out of cleanup code. These console examples do not control hardware, and a `finally` block by itself is not a robot safety system.

<RulesBox title="Choose A Handler">

- Catch a specific exception type when this code has a planned response to that failure.
- Include the failed operation or value in a diagnostic message when that information is safe and useful.
- Keep unexpected failures visible so they can be debugged.
- Use `finally` for cleanup that should run on normal and handled-failure paths, while respecting its limits.

</RulesBox>
