## Before You Begin

[Command Line Basics](/tools/command-line-basics) teaches you to open the correct shell, identify its prompt, and check your current folder. Complete those steps first. This page uses a disposable folder named `garagedocs-shell-practice` so you can see each file change without risking a project.

Create the practice folder, enter it, and confirm its name before continuing:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
cd ~
if (Test-Path garagedocs-shell-practice) {
  Write-Warning "Stop: garagedocs-shell-practice already exists. Inspect it or choose another name."
} else {
  New-Item -ItemType Directory garagedocs-shell-practice
  Set-Location garagedocs-shell-practice
  Get-Location
}
```

</CodeTab>
<CodeTab label="Terminal">

```bash
cd ~
if [ -e garagedocs-shell-practice ]; then
  printf '%s\n' 'Stop: garagedocs-shell-practice already exists. Inspect it or choose another name.'
else
  mkdir garagedocs-shell-practice && cd garagedocs-shell-practice && pwd
fi
```

</CodeTab>
</CodeTabs>

Continue only when the final line ends in `garagedocs-shell-practice`. If the warning appears, nothing was created and the command did not enter that folder. Inspect the existing folder or repeat the block with a different empty name.

Create the small files used by the examples below. These commands write only inside the practice folder:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
New-Item -ItemType Directory src
Set-Content src\Intake.java 'public class Intake { void setVoltage(double volts) {} void run() { setVoltage(4.0); } }'
Set-Content build.log 'starting build','error: sample motor error','build stopped'
Set-Content old.txt 'practice file'
Get-ChildItem -Recurse
```

</CodeTab>
<CodeTab label="Terminal">

```bash
mkdir -p src
printf '%s\n' 'public class Intake { void setVoltage(double volts) {} void run() { setVoltage(4.0); } }' > src/Intake.java
printf '%s\n' 'starting build' 'error: sample motor error' 'build stopped' > build.log
printf '%s\n' 'practice file' > old.txt
find . -print
```

</CodeTab>
</CodeTabs>

The listing should contain `src`, `src/Intake.java`, `build.log`, and `old.txt`. Stop here and check the location if those names appear somewhere else.

Choose the PowerShell or Terminal tab for your shell. Similar command names can accept different options and produce different output.

## Find Files

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
Get-ChildItem -Recurse -Filter *.java              # every .java file below here
Get-ChildItem -Recurse -Filter *.java | Select-Object -First 5
Get-ChildItem -Recurse | Where-Object Name -like "*Intake*"   # by part of the name
```

</CodeTab>
<CodeTab label="Terminal">

```bash
find . -name "*.java"                  # every .java file below here
find . -name "*.java" | head -5
find . -iname "*intake*"               # by part of the name, case-insensitive
```

</CodeTab>
</CodeTabs>

The pattern `*.java` is a **wildcard**. The `*` matches anything. On Terminal, quote it so the shell hands the pattern to `find` instead of expanding it first.

## Search Inside Files

Search for a name or message to find the files that contain it:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
Select-String -Pattern "setVoltage" -Path src\*.java                    # this folder's src directory
Get-ChildItem -Recurse -Filter *.java | Select-String "setVoltage"      # the whole tree
Select-String "error" build.log -Context 2                              # two lines either side
```

</CodeTab>
<CodeTab label="Terminal">

```bash
grep -n "setVoltage" src/*.java                # this folder's src directory, with line numbers
find . -name "*.java" -exec grep -n "setVoltage" {} +   # the whole tree
grep -n -C 2 "error" build.log                 # two lines either side
grep -in "error" build.log                     # case-insensitive
```

</CodeTab>
</CodeTabs>

VS Code's Search view (`Ctrl+Shift+F` / `Cmd+Shift+F`) searches the open project. Shell commands are useful for logs, other folders, or a remote session.

## Read Files in the Terminal

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
Get-Content build.log                    # the whole file ("cat" works too)
Get-Content build.log -TotalCount 20     # first 20 lines
Get-Content build.log -Tail 20           # last 20 lines
Get-Content build.log -Wait              # keep showing new lines as they arrive; Ctrl-C to stop
```

</CodeTab>
<CodeTab label="Terminal">

```bash
cat build.log                 # the whole file
head -20 build.log            # first 20 lines
tail -20 build.log            # last 20 lines
tail -f build.log             # keep showing new lines as they arrive; Ctrl-C to stop
less build.log                # page through it; space for next page, / to search, q to leave
```

</CodeTab>
</CodeTabs>

`tail -f` and `Get-Content -Wait` show new lines as a file grows. Leave one running while reproducing a problem, then interrupt it when finished.

## Practice File Changes

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
New-Item -ItemType Directory logs          # make a folder ("mkdir logs" works too)
Copy-Item build.log logs\                  # copy a file into it
Copy-Item -Recurse src src-backup          # copy a whole folder
Move-Item old.txt new.txt                  # move, which is also how you rename
Get-ChildItem src-backup                    # inspect the practice copy
Remove-Item -Recurse -Confirm src-backup    # delete only that practice copy
```

</CodeTab>
<CodeTab label="Terminal">

```bash
mkdir -p logs                 # make a folder (-p: and any parents; no error if it exists)
cp build.log logs/            # copy a file into it
cp -r src src-backup          # copy a whole folder
mv old.txt new.txt            # move, which is also how you rename
ls src-backup                 # inspect the practice copy
rm -r -i src-backup           # confirm items in that practice copy
```

</CodeTab>
</CodeTabs>

<RulesBox title="Delete Does Not Mean Recycle">

`rm` and `Remove-Item` bypass the Recycle Bin or Trash. Run the location command and list the exact target immediately before deletion. The examples delete only the practice copy created in this section. Do not substitute a project folder.

</RulesBox>

## Save Command Output

Many commands write normal output and errors to separate streams. `>` redirects normal output to a file, replacing its contents. `>>` appends instead.

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
Write-Output "network check" > network.txt    # replace the file with harmless sample output
Write-Output "second check" >> network.txt    # append instead
.\gradlew build > build.log 2>&1               # in a Gradle project: save output and errors
```

</CodeTab>
<CodeTab label="Terminal">

```bash
printf '%s\n' "network check" > network.txt    # replace the file with harmless sample output
printf '%s\n' "second check" >> network.txt    # append instead
./gradlew build > build.log 2>&1                 # in a Gradle project: save output and errors
```

</CodeTab>
</CodeTabs>

The Gradle command is a project example; it will fail in this practice folder because there is no wrapper here. For native programs, `2>&1` combines standard error with standard output. PowerShell also has additional streams; `*>` can redirect all its redirectable streams. If a saved log is incomplete, check which stream the missing messages use.

## Pipes

A **pipe**, written `|`, passes one command's output to another command. Use it to filter, count, sort, or select results.

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
ipconfig | Select-String "IPv4"                          # only the lines that matter
Get-ChildItem -Recurse -Filter *.java | Measure-Object   # how many files
Get-Content build.log | Select-String "error" | Select-Object -First 1   # the first error
git log --oneline | Select-Object -First 10               # the last ten commits
Get-Process | Sort-Object CPU -Descending | Select-Object -First 5       # highest accumulated CPU time
```

</CodeTab>
<CodeTab label="Terminal">

```bash
grep -i "error" build.log                   # only matching lines
find . -name "*.java" | wc -l               # how many files
grep -i "error" build.log | head -1         # the first error
git log --oneline | head -10                # in a Git repository: the last ten commits
ps aux | sort -k3 -nr | head -5             # what is eating the CPU
```

</CodeTab>
</CodeTabs>

Read the first command's output before adding a filter. Then add commands such as `Select-String`, `grep`, or `Select-Object` to select the information you need.

The Git examples require a Git repository, and the Gradle example requires a project containing its wrapper. Run them in the intended project only after checking the current folder; use the practice-folder examples for the exercise on this page.

bash and zsh pipes carry byte streams, commonly text. PowerShell commands can pass structured objects. For example, `Get-Process` produces objects with properties that `Sort-Object` can use.

## Environment Variables

The **environment** contains named values that a process can pass to programs it starts. `JAVA_HOME` commonly identifies a JDK for build tools, and `PATH` lists directories searched for executable programs.

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
$env:JAVA_HOME                              # show one
Get-ChildItem env:                          # show them all
$env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-25"   # set for this window only
```

</CodeTab>
<CodeTab label="Terminal">

```bash
echo $JAVA_HOME                             # show one
env                                         # show them all
export JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-25.jdk/Contents/Home   # this window only
```

</CodeTab>
</CodeTabs>

A setting made in the shell affects that process and programs it starts. To retain it across sessions, use Windows user environment settings or the startup file for your bash/zsh configuration. Restart applications that need the new environment. Substitute your installed JDK path in these examples; the Terminal path shown is for macOS.

## PATH and Command Not Found

When resolving an external command such as `java`, the shell searches directories in **PATH**. Aliases, functions, and built-in commands may take precedence. A command-not-found error means the shell could not resolve the entered command; check its spelling, installation, and search path.

Inspect PATH and the command it resolves:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
$env:PATH -split ";"                     # which folders, in order
Get-Command java                         # which java would run, and from where
Get-Command java -All                    # every java on the PATH: the first one wins
```

</CodeTab>
<CodeTab label="Terminal">

```bash
echo $PATH | tr ":" "\n"                 # which folders, in order
which java                               # which java would run, and from where
which -a java                            # every java on the PATH: the first one wins
```

</CodeTab>
</CodeTabs>

The outcomes and what they mean:

<ContentTable
  headers={["What you see", "Meaning", "Fix"]}
  rows={[

    ["Found, but the wrong version", "Two installs; the older one's folder comes first", "Reorder PATH, or uninstall the one you do not want"],

/>

Add a directory without deleting the existing PATH entries. In Windows user environment settings, edit Path and add a new entry. In your shell startup file, `export PATH="$PATH:/the/new/folder"` appends a directory. Order matters when several directories contain the same command.

When the current folder is not on PATH, run a local program with an explicit path: `./gradlew` in bash/zsh or `.\gradlew` in PowerShell. This selects the project's wrapper rather than another command found through PATH.

## Install Software

A package manager can install and update programs from configured sources. The examples below show common choices; install the appropriate package manager first if it is not available. Review the package and version before installing or upgrading.

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
winget search temurin                              # find the package name
winget install Git.Git                             # Git
winget install Microsoft.VisualStudioCode          # VS Code
winget install EclipseAdoptium.Temurin.25.JDK      # a JDK for the Java lessons
```

</CodeTab>
<CodeTab label="Terminal">

```bash
# macOS: install Homebrew first from https://brew.sh
brew install git
brew install --cask visual-studio-code
brew install --cask temurin@25             # Java 25 for the Java lessons

# Debian / Ubuntu Linux
sudo apt update && sudo apt install git
```

</CodeTab>
</CodeTabs>

Use the WPILib installer for the robot toolchain and follow [R00](/kit-bot/r00-wpilib-setup#step-1-install-wpilib). It supplies the supported tools and JDK for that WPILib version.

<RulesBox title="Common Mistakes">

- **<code>rm -r</code> without looking first.** <code>pwd</code>, <code>ls</code>, then delete.
- **A log with no errors in it.** You forgot <code>2>&1</code>. The errors went to the screen and scrolled away.
- **Editing PATH and testing in the same window.** Persistent settings do not update existing processes. Open a new shell; a direct shell assignment takes effect there immediately.
- **Typing <code>gradlew</code> and getting <em>not found</em>.** Use <code>./gradlew</code> because the program is in the current directory rather than on the PATH.
- **Unquoted wildcards on Terminal.** <code>find . -name *.java</code> can fail confusingly when the current folder happens to contain a .java file. Quote the pattern.

</RulesBox>
