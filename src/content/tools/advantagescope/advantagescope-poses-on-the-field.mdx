Field views place pose data on a coordinate system. Use them to compare estimates, trajectories, targets, and mechanism geometry. A surprising picture is evidence to investigate alongside the numeric data and configuration.

Before using this page, open a known data source and practice selecting a field in the [AdvantageScope Tour](/tools/advantagescope-tour). To create the Kit Bot's `Drive/Pose` topic, follow [R13: Pose and Field View](/kit-bot/r13-pose-and-field-view). A log or live source needs pose data before a field view can show a robot.

## Pose and Coordinates

A **pose** combines position and orientation. For `Pose2d`, WPILib uses x, y, and a `Rotation2d`. A coordinate system defines where measurements start and which directions are positive. The following convention applies to the 2026 FRC field with the **Blue Wall** origin. Confirm that the data producer and AdvantageScope use the same convention:

- The origin is the **blue alliance's** right-hand corner as the blue drivers see it. **+X** runs *away* from the blue wall, down the field toward red. **+Y** runs to the *left* as blue looks at the field. Units are **metres**.
- **Rotation** is counter-clockwise positive, and **0°** points down +X, toward the red wall. A robot facing its own blue driver station has a heading of 180°.
- In 3D, **+Z** is up, and a `Pose3d` adds height and a full `Rotation3d` (roll, pitch, yaw).

For example, `(1.5 m, 4.0 m, 90°)` is 1.5 m along +X, 4.0 m along +Y, with its heading toward +Y. Confirm the field origin and units against the [WPILib coordinate documentation](https://docs.wpilib.org/en/stable/docs/software/basic-programming/coordinate-system.html).

## Publish a Pose

AdvantageScope recognizes WPILib struct types for geometry and other supported data. The topic type lets the field view interpret a `Pose2d`, `Pose3d`, or array. Create publishers once and update their values during operation. A **struct** packages named pieces, such as x, y, and angle, into one typed value.

These are **partial reference snippets**, not files to paste into an empty project. The WPILib example assumes an existing subsystem with an `odometry` object and a `Pose2d[]` named `trajectoryPoses`. Merge the update statements into its existing `periodic()` method. The AdvantageKit example assumes an AdvantageKit project and application-provided pose variables/methods. Those illustrative names are not a claim that Cobra exposes those exact methods. Use the complete [R13 pose procedure](/kit-bot/r13-pose-and-field-view#update-and-publish-the-pose) for your first implementation:

<CodeTabs>
<CodeTab label="WPILib (Kit Bot)">

```java
import edu.wpi.first.math.geometry.Pose2d;
import edu.wpi.first.networktables.NetworkTableInstance;
import edu.wpi.first.networktables.StructArrayPublisher;
import edu.wpi.first.networktables.StructPublisher;

// Open once, as fields: never inside periodic()
private final StructPublisher<Pose2d> posePub = NetworkTableInstance.getDefault()
    .getStructTopic("Drive/Pose", Pose2d.struct).publish();
private final StructArrayPublisher<Pose2d> pathPub = NetworkTableInstance.getDefault()
    .getStructArrayTopic("Drive/Trajectory", Pose2d.struct).publish();

@Override
public void periodic() {
  posePub.set(odometry.getPoseMeters());   // one robot
  pathPub.set(trajectoryPoses);            // a Pose2d[]: drawn as a line
}
```

With `DataLogManager.start()` running and its default NetworkTables logging enabled, updates to these topics are recorded in the `.wpilog` ([R13, step 1](/kit-bot/r13-telemetry-with-advantagescope#start-the-log)).

</CodeTab>
<CodeTab label="AdvantageKit Pattern">

```java
import org.littletonrobotics.junction.Logger;

Logger.recordOutput("Odometry/Global", drive.getGlobalPose());          // Pose2d
Logger.recordOutput("Odometry/Trajectory", trajectory.getPoses());      // Pose2d[]
Logger.recordOutput("Vision/Cameras/Front/Pose", frontCameraPose);      // Pose3d
Logger.recordOutput("Vision/TagPoses", tagPoses);                       // Pose3d[]
```

These appear under `RealOutputs/…` in the tree (`ReplayOutputs/…` in [log replay](/frc/log-replay)). AdvantageKit inputs marked with a struct type, such as a `Pose2d` field in an `@AutoLog` class, are recorded the same way. An `@AutoLogOutput` on a getter that returns a pose is the one-line version.

</CodeTab>
</CodeTabs>

Use typed struct publishing for new pose data. `Field2d` remains useful for SmartDashboard-compatible consumers but uses its own published representation and object structure.

## Show a 2D Pose

Add a tab with **+ → 2D Field**. Then:

<StepsBox title="Robot on the Field">

1. Drag a pose key such as `Drive/Pose` or `RealOutputs/Odometry/Global` into the **Poses** list in the control pane. The field name appears in the list. For a saved log, select a time when that field has data.
2. Click the coloured icon beside the key (or right-click the name) to choose its **object type** and colour. Choose **Robot** for the first pose; the `?` icon lists every type with the data types it accepts.
3. In the control pane, set **Field** to the game matching the data. The documented **Size** choices are 30, 27, or 24 inches for the square robot drawing. Choose a useful approximation; this drawing is not an exact bumper model or a clearance check. **Orientation** rotates the drawing so the field is the way you are standing.
4. For a saved log, press play or click the timeline to select a recorded time. For live simulation, command a short movement using R13 and observe the icon. If it does not move, compare the numeric pose before changing the view.

</StepsBox>

Common visualization choices are listed below. Use the **?** beside the object list to check the installed version's supported data types and child-object requirements before adding an unfamiliar type:

Add several keys to compare the estimated pose, reference path, targets, or alternative estimates. Give each a clear label and color, then export the layout if the team will reuse it.

**Check the first result.** Start with R13's three short simulation motions. If the icon seems wrong, expand `Drive/Pose` in the sidebar and inspect its numeric components. Check whether position or angle changes at all. Next confirm metres versus other distance units, then degrees versus radians at the code's conversion. Finally compare the field/origin setting with the producer's coordinate system. Changing a display orientation does not repair incorrect coordinates.

**Reading the view.** If a pose jumps, compare raw odometry, accepted vision measurements, timestamps, and uncertainty before changing filters. If heading or mirroring looks wrong, check units, gyro offsets, coordinate frames, and alliance transformations one at a time.

## Explore a 3D Pose

**+ → 3D Field** displays supported 2D and 3D geometry on a rendered field. Use it for camera poses, AprilTags, robot components, and other data with height or three-dimensional orientation.

Begin only after the 2D pose works. Add a **3D Field** tab and drag the same pose into its **Poses** list. Choose its Robot object settings and field model in the control pane. A built-in model is sufficient for pose work. A [custom asset](https://docs.advantagescope.org/more-features/custom-assets/) can show the team robot after its model and configuration have been validated.

These are optional next steps. A **child** object belongs to a Robot or Ghost entry in the object list. Check **?** for the accepted type and parent requirement; mechanism components use robot-relative poses, while a Camera Override uses a field-relative pose.

**Camera controls.** Right-click the view to choose a field, robot, Driver Station, or configured camera perspective. Use a camera view to inspect geometry; it does not prove that a physical camera can detect a target under real lighting and exposure conditions.

**Rendering.** Choose the rendering mode based on the laptop's performance and power needs. If playback stutters, compare the lower-power mode before treating the data as irregular.

## Use Simulation

The same field controls work with compatible live or recorded sources. Start with [R13: Check Three Motions](/kit-bot/r13-pose-and-field-view#check-three-motions). Its current physical-robot pose is unsupported without a checked heading sensor; a moving simulation icon does not remove that limitation. [Simulation in AdvantageScope](/frc/simulation-in-advantagescope#the-2d-and-3d-field) covers team simulation data, and [Vision Simulation](/frc/vision-simulation) covers simulated camera geometry.

<RulesBox title="Common Blockers">

- **Publishing separate scalar values.** Use a supported pose type when the field should interpret them as one pose.
- **Wrong angle units.** Construct `Rotation2d` with the conversion that matches the source.
- **Wrong coordinate frame.** Label frames and apply alliance transforms in one documented location.
- **Creating publishers repeatedly.** Keep publisher handles as fields and close them according to the project lifecycle.
- **Missing component data.** Log mechanism or component geometry if the model should move.
- **Invalid custom asset.** Check the asset configuration with a built-in model as a known comparison.

</RulesBox>
