## Start With Evidence

You do not need to memorize every Java or robot-library method. You need a repeatable way to find accurate information, compare it with the project in front of you, and test what you learned.

When something fails, save the exact message before changing the code. The message, file, line, project version, and action that produced the failure are evidence. They help you separate an observed problem from a guess about its cause.

Before starting, use [VS Code Tour](/tools/vscode-tour) if opening a project folder or finding the editor panels is unfamiliar. [Introduction to Version Control](/tools/introduction-to-version-control) explains repositories and commits. You can read the examples here without running a robot or writing a program.

## Choose a Source

An **API** (application programming interface) describes the operations a library makes available to your code. A **method** is a named operation. A **dependency** is another library or tool your project relies on. Different sources answer different questions. A search result is a route to a source, not evidence by itself.

Start with a guide when the task is unfamiliar. Use an API reference when you know the class or method and need exact details. Read source and tests when you need implementation evidence. Use issue discussions to form a hypothesis, then confirm it against your project and its version.

## Look Up a Java Method

Suppose you have the text `"auto-ready"` and need to check whether it contains `"ready"`. You can use the Java API reference even if you do not know the method name.

1. Open the Java 25 [`String` page](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html). `String` is the class, which means it describes Java text values and the operations available on them.
2. Use the browser's Find command, `Ctrl+F` on Windows/Linux or `Cmd+F` on macOS, and search for `contains`.
3. In **Method Summary**, find `boolean contains(CharSequence s)`. A **parameter** is an input to a method. Here, `s` is the text to find. The return type `boolean` means the result is either `true` or `false`.
4. Open the method name and read **Method Details**. The detail says what counts as a match and lists any documented exceptions or special cases.
5. Check the documentation version. This page is for Java 25. A robot project may use a different Java version supplied by WPILib.

For this example, `contains` reports `true` because `"ready"` occurs inside `"auto-ready"`. `CharSequence` is an input type that accepts text such as a `String`; you do not need to learn interfaces to use this lookup. An **exception** reports a failure while a program runs.

The summary is an index of documented members, not a tutorial. The detail for one method may contain a full explanation, a short sentence, or only generated information. Inherited methods may appear in a separate list that links to a parent class.

A **constructor** creates an object. A **signature** identifies a method or constructor and its input types; **overloads** share a name but accept different input lists. Constructor summaries work the same way. Each constructor signature is a different accepted set of inputs. One overload may offer a convenience default, while another may accept different data or behave differently. Read the detail for each candidate instead of assuming the extra parameters are optional.

VS Code can also show documentation when you hover over a name or choose **Go to Definition**. `F12` is a common default shortcut, but keybindings can change. A dependency may open source, generated information, or decompiled code depending on what the library and editor have available. Confirm behavior in the versioned online reference when the editor view is incomplete.

## Check the Version

Before using an example, find the dependency version in the project. For a robot project, vendor dependencies are recorded in files under `vendordeps`, and WPILib has its own yearly release. Compare that version with the guide or API page.

On GitHub, a tag marks a point in repository history, and a release can add notes and downloadable files around a tag. Projects choose how they use tags and releases, so a dependency version may not have a matching public release name. Follow the vendor's documentation for mapping an installed version to source.

## Read a Guide

Find the page's prerequisites before copying an example. Check which application or project should be open, which library version it uses, and whether the code is a complete program or only part of one. Read each line and identify names supplied elsewhere, such as imports, constants, or existing objects. Typing a sample yourself is optional; understanding what it requires is the useful step.

Follow one small part of the example in a practice project, compare the result with the guide, and record any difference. If the page does not explain where the code belongs, look for its surrounding example project or ask a mentor before changing robot code.

## Read a Repository

Open the repository's **Code** page and read its README, the introductory document usually displayed below the file list. Look for setup instructions, supported versions, and links to documentation. A missing instruction is a gap to resolve, not proof that the project is broken.

Use **Go to file** to find a known filename. Open the file and inspect nearby declarations and comments. GitHub's [Code Navigation guide](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github) explains file navigation and the **Blame** view. Blame identifies changes associated with lines; their commit messages and linked discussions may explain the reason, but the author's name alone does not.

Compare the selected branch or tag with your dependency version before treating the file as evidence. Read linked issues, pull requests, and release notes for context. Source shows an implementation in that revision; tests cover particular cases and do not prove every possible use works.

## Read an Error

VS Code shows diagnostics as underlines in the editor and as entries in the Problems panel. Open **View → Problems**, or press `Ctrl+Shift+M` on Windows/Linux or `Cmd+Shift+M` on macOS. Select a problem to open its file and line. To copy one diagnostic, right-click its Problems entry and choose **Copy Message**. For build output, open **View → Terminal** and choose the terminal that ran the build. Drag across the relevant lines to select them. Copy with `Ctrl+C` on Windows, `Ctrl+Shift+C` on Linux, or `Cmd+C` on macOS. Select the text first: without a selection, `Ctrl+C` can stop a running command. Paste into a new text document and check that the error and its surrounding lines are present.

Start with the first relevant error. One mistake can cause several later messages, so fix or investigate one cause before treating the entire list as separate problems.

This illustrative compiler output shows a misspelled method name. It assumes a text variable named `mode` already exists. The filename and line number will differ in your project:

```text
Robot.java:18: error: cannot find symbol
    boolean ready = mode.contain("ready");
                        ^
  symbol:   method contain(String)
  location: variable mode of type String
```

Read it from top to bottom:

1. `Robot.java:18` identifies the file and line where the compiler could not continue.
2. `cannot find symbol` is the error category. A **symbol** is a name in the program, such as a class, variable, or method.
3. The caret `^` points near the text the compiler could not resolve.
4. `method contain(String)` says Java looked for a method named `contain` that accepts a `String` input.
5. `variable mode of type String` says the lookup happened on a `String` value named `mode`.

Those lines establish that the compiler cannot find that method on `String`. They do not yet establish why. Check the spelling in the Java `String` reference. The documented method is `contains(CharSequence s)`, with an `s` at the end. Change the name, rebuild, and use the new result as evidence that the change worked.

A **stack trace** lists the method calls involved in a failure; each listed call is a **frame**. Runtime failures need a similar reading process. For a Java stack trace, read the exception type and message, then find the first relevant frame in code you own. That frame shows where the failure became visible. Caller frames show how execution reached it; the value that caused the problem may have originated earlier. Follow [Read a Java Stack Trace](/tools/shell-troubleshooting#read-a-java-stack-trace) for a worked example.

## Search the Exact Message

Search after you have read and saved the error. Begin with a quoted, distinctive part of the message:

```text
"cannot find symbol" "method contain(String)" Java
```

Quotes ask a search engine to keep those words together. If the full query finds nothing, remove one quoted part and keep the error category, missing name, language, and relevant library. Add the season or library version for FRC tools, such as `WPILib 2026` or `Phoenix 6 26.1.0`.

Leave out changing details that will not help another person find the same problem, such as timestamps and your full home-folder path. Keep class names, method names, exception types, and the lines around the failure.

For GitHub issues, use the repository's Issues search and include the exact message. Read the issue's status, closing reason, linked pull requests, comments, affected versions, and evidence. A matching title alone does not show that the same cause applies to your project.

## Ask for Help

Keep one complete local copy of the evidence. When sharing in a public forum, make a second copy and redact private information such as passwords, access tokens, personal names in file paths, private server addresses, and code that FRC 4451 has not made public. Mark replacements clearly, such as `<user>` or `<private address>`, so readers know text was removed. Do not rewrite the technical message or remove version information that someone needs to diagnose the failure.

Include these details when asking a teammate, mentor, or community:

Copy this template into your question and replace each bracketed instruction. Paste the error as text below it:

```text
Goal: [What I expected to do]
Project and versions: [Project, Java, libraries, and operating system]
Steps: [The actions that produced the problem]
Expected: [What I expected to see]
Observed: [What happened, including the exact error]
Location: [File, line, and relevant code]
Tried: [One change and its result]
```

After solving the problem, record the observed failure, cause, change, versions, and check that passed. Link the source that supported the decision. This gives the next student a tested starting point.

<RulesBox title="Investigation Check">

- Save the original error before changing code.
- Open the named file and line, then read the whole message.
- Check the official guide or API reference for the project's version.
- Treat source, tests, and issue discussions as evidence from a specific revision and context.
- Change one relevant thing, repeat the failing action, and record the result.
- Keep complete evidence locally and redact private details only in the copy shared publicly.

</RulesBox>
