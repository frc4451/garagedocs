## Inspect a Running Program

A debugger can pause a program before a selected statement runs. While paused, you can inspect variables and the chain of method calls that reached that point. Start with a small local Java program. Use WPILib VS Code 2026 only when you later apply these controls to a 2026 robot project.

Before creating the example, complete [VS Code: Tour](/tools/vscode-tour#open-the-folder-not-the-file) and the stock-editor steps in [Java Setup](/java/fundamentals/setup). You need stock VS Code with Java support and the curriculum's Java 25 JDK. The example does not use WPILib or robot hardware.

## Make a Safe Practice Program

Create a new folder named `debug-practice`, open that folder in stock VS Code, and create `Main.java`. This example is independent of robot hardware:

```java
public class Main {
    public static void main(String[] args) {
        int total = 0;
        for (int count = 1; count <= 3; count++) {
            total = total + count;
            System.out.println(total);
        }
    }
}
```

Save the file. Wait for Java loading to finish. **Run | Debug** should appear above `main`; if it does not, confirm that the containing folder is open, the file ends in `.java`, and the Java extensions are installed.

## A First Session

<StepsBox title="First Debug Session">

1. Select line 5, `total = total + count;`.
2. Click in the gutter to the left of that line number. A red breakpoint dot appears. You can also use **Run → Toggle Breakpoint**.
3. Select **Debug** above `main`. If that link is not visible, select **Run and Debug** in the Activity Bar (the play symbol with a bug), then choose **Run and Debug** and select **Java** if VS Code asks for a debugger. The program runs until it reaches the breakpoint.
4. Confirm that line 5 is highlighted. The highlight marks the **next statement to execute**. At the first pause, `count` is `1` and `total` is `0` in the Variables view.
5. Select **Step Over** in the Debug toolbar or press `F10`. Line 5 runs, the highlight moves to line 6, and `total` becomes `1`.
6. Select **Step Over** again. The first number prints in the Terminal, and execution advances through the loop.
7. Select **Continue** or press `F5`. The debugger stops again when the next loop iteration reaches the breakpoint.
8. Select **Stop** or press `Shift+F5`. The debug toolbar disappears.

</StepsBox>

If execution never pauses, confirm that the breakpoint dot is solid, the debugger started rather than a normal Run, the saved source matches the program, and execution reaches that line.

## Stepping

- **Variables** shows values available at the selected stack frame. Expand an object to inspect its fields.
- **Watch** reevaluates expressions at each pause. Add `total + count` with the plus button. Prefer expressions that do not call methods or change state.
- **Call Stack** shows which methods called the current method. Select a frame to see its source and variables.
- **Breakpoints** lists pause points. Clear a checkbox to disable a breakpoint without deleting it.
- **Debug Console** evaluates expressions in the paused program. Method calls can have side effects, so begin with arithmetic and comparisons.

If the Side Bar does not show these sections while paused, select **Run and Debug** in the Activity Bar. Select the small arrow beside a collapsed section name such as **Variables** to open it.

**Step Over** runs the highlighted statement and stops at the next statement in the same frame. **Step Into** enters a method call when the debugger has usable source. **Step Out** finishes the current method and returns to its caller. **Continue** runs until another breakpoint or program completion.

## Use Conditional Breakpoints and Logpoints

Right-click a breakpoint and choose **Edit Breakpoint...**. Choose **Expression** to pause when a Java expression such as `count == 3` is true, or **Hit Count** to pause after the line has been reached a selected number of times.

A **logpoint** writes to the Debug Console without pausing or editing source. To replace the practice breakpoint, first right-click its red dot and choose **Remove Breakpoint**. Then right-click the gutter beside the same line, choose **Add Logpoint...**, enter `count is {count}, total is {total}`, and press Enter. A diamond-shaped logpoint marker replaces the red breakpoint dot. Start debugging again and open **Debug Console** in the bottom Panel. The message should appear for each loop iteration without pausing. Java logpoints use braces around expressions. Logpoints still add debugger work and can change timing in a frequent loop.

If a condition never fires, confirm the expression uses names available on that line and that the workspace contains the correct Java project. In a workspace with multiple Java projects, the debugger may need an explicit project configuration for expression evaluation.

## Stop on Exceptions

The **Breakpoints** section can include exception breakpoints. Enable **Uncaught Exceptions** to stop when an exception would leave the current code without being handled. Enable **Caught Exceptions** only for a specific investigation because libraries may throw and handle many exceptions during normal work. When the debugger stops, read the exception type and message, then select the first relevant frame in your own code.

## Debug Robot Code Safely

Robot code has timing requirements and can command hardware. Practice in desktop simulation first. Follow [Running the Simulator](/frc/running-the-simulator) and use its documented debug path. A breakpoint pauses the Java program; other processes or wall-clock-driven simulation may continue. A paused session is not evidence of normal loop timing.

WPILib also supports **Debug Robot Code**, which deploys and attaches to the roboRIO. Treat this as a supervised hardware procedure:

- Disable the robot and mechanically secure every mechanism before attaching.
- Keep a mentor at the Driver Station Disable control.
- Do not rely on a breakpoint or motor-safety timeout to make hardware safe. The last commanded output may persist, and other processes may continue.
- Stop the debug session before returning the robot to normal operation.

These are safety requirements for following this lesson. The WPILib documentation establishes deploy-and-attach behavior and that breakpoints pause execution; it does not promise that pausing Java makes every actuator safe.

## Practice Without Losing Work

Copy the `Main.java` example to `MainBroken.java`, rename its class to `MainBroken`, and make the intentional mistake only in the copy. Change `count <= 3` to `count <= 4`, then add a conditional breakpoint for `count == 4`. Inspect the values, stop the session, and undo the change. Keep `Main.java` as the known-good copy.

<RulesBox title="Recovery Checks">

- A hollow or grey breakpoint can mean the running code does not match the saved source.
- Unexpected stepping can come from step filters or generated code. Use Step Out to return to your code.
- After editing during a session, stop and restart unless you deliberately use and understand Hot Code Replace.
- Remove or disable practice breakpoints before a shared simulation session.

</RulesBox>
