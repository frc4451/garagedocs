### What this view is

VS Code's **Source Control** view shows Git changes and provides controls for staging, committing, and synchronizing. It operates on the same repository as command-line Git.

Open it with `Ctrl+Shift+G` (the same on macOS) or the branching icon in the Activity Bar. This lesson assumes you know what a commit, a branch and a remote are. If you do not, start with [Local Git Workflow](/tools/local-git-workflow#understanding-the-three-areas-of-git).

The Status Bar, bottom left, is the view's summary: the current branch name, a sync icon with how many commits are waiting to go each way (`↓2 ↑1`), and a spinner while Git is doing something.

### The letters and colours

Every file in *Changes* carries a letter, and the same letter and colour appear next to the file in the Explorer and on its editor tab:

A **U** marks an untracked file. Check whether the project needs it, then stage it if it belongs in the commit. Colours can vary with the theme.

### Seeing what changed

Open a file under **Changes** to compare unstaged edits with the staged version. Open a file under **Staged Changes** to compare the staged version with the current commit. Read both when a file has edits in each group.

The **gutter** beside the line numbers marks changes. Select a marker to inspect that change and use the available staging or reverting controls.

### Staging

Staging selects the versions that the next commit will record:

Unstaging is the same in reverse: the `−` on a file under *Staged Changes*, or on the heading. Unstaging keeps the file edits.

**Discard Changes** removes selected working changes. This differs from unstaging, which keeps the file edits. Treat discard as destructive and check the confirmation and affected file before proceeding; do not rely on automatic recovery.

### Committing

Type the message in the box and press `Ctrl+Enter` (`Cmd+Enter`), or click ✓. The first line is the summary; leave a blank line and keep writing for the body. [Writing Good Commit Messages](/tools/version-control-best-practices#writing-good-commit-messages) is the standard to hold it to.

Two commit options need care:

- **Nothing staged:** smart-commit behavior depends on settings. Stage the intended files explicitly before committing.
- **Amend:** replaces the latest commit with a new version. Use it for local history you intend to revise; coordinate before amending a commit others may have used.

### Branches

The branch name in the Status Bar is a button. Click it for the branch picker:

- **Create new branch…**: type a name; you are switched to it immediately. Follow [Branch Naming](/tools/version-control-best-practices#branch-naming-and-organization).
- **Create new branch from…**: the same, but starting from a branch other than the current one. Use it to start a fix from `main` while you are in the middle of a feature.
- Select any listed branch to switch to it (`git switch`). Remote branches you have not checked out yet appear as `origin/name`; picking one creates a local copy.

Uncommitted changes may follow a branch switch or prevent it if files would be overwritten. Check which branch the work belongs on before committing or stashing it.

The `…` menu → *Branch* has the rest: rename, delete, merge another branch into this one, and *Publish Branch* for a branch that does not exist on GitHub yet.

### Sync, pull, push, fetch

**Sync Changes** pulls remote work and then pushes local commits. Use it when you intend both operations. To fetch, pull, or push separately, choose the corresponding action from the `…` menu.

The `…` menu → *Pull, Push* separates them, and adds **Fetch**: ask GitHub what is new *without* merging it into your branch. After a fetch, the Graph shows the remote's commits alongside yours, which is the safe way to look before you pull.

Authentication depends on the remote URL and configured credential method. Use the team's supported setup; [GitHub and remote repositories](/tools/github-remotes#authentication-methods) explains the options.

### Stash

The Stash menu saves unfinished changes locally. Check whether you selected an option that includes untracked files. Give the stash a descriptive message, and inspect the Changes list afterward. [Advanced Git](/tools/advanced-git#stashing-work) explains apply, pop, and conflicts.

### Merge conflicts

When Git cannot combine changes automatically, inspect the conflicted files in Source Control. Overlapping text edits are one cause; file deletion and rename conflicts can also occur.

**In the editor**, text conflict markers separate the competing changes. Use the comparison controls, read both sides, and edit the intended combined result. Current and incoming labels depend on the operation, particularly during rebase.

**In the Merge Editor**, compare both inputs and edit the Result pane. Selecting both sides is appropriate only if the combined code makes sense.

For a regular merge, stage the resolved files, build and check the result, then complete the merge commit. During a rebase, use its continuation workflow instead. Aborting an operation is not a substitute for preserving local changes before starting it.

[Conflict Resolution](/tools/branching-and-merging#conflict-resolution) explains what a conflict is and how to avoid most of them.

### History

The **Graph** shows commits and how branches relate. Select a commit to inspect its files and diffs.

For one file, the **Timeline** at the bottom of the Explorer lists every commit that touched the file that is open. Click one for the diff at that point.

Use file history or blame to find the last recorded change to a line. Read the commit and related discussion to understand the reason. GitLens is an optional extension for additional history views.

### Ignoring files

Use **Add to .gitignore** for generated or temporary files that should remain untracked. Review the rule before committing it. Ignoring a file does not stop Git tracking it if it was already committed.

<RulesBox title="Common mistakes">

- **Committing without reading the diff.** The <code>println</code>, the commented-out block, the file you did not mean to touch. All are visible in one click.
- **Missing the green U.** A new file is not in the commit until it is staged. Look before you commit.
- **Discard when you meant unstage.** Unstage keeps the change; discard destroys it. The icons are different. The curved arrow discards the change.
- **Amending a pushed commit.** History diverges from GitHub, and the next push is refused. Make a new commit instead.
- **Leaving a merge half done.** Files with a <strong>C</strong> stay conflicted until staged and committed. The Status Bar says <em>merging</em> until then.
- **Treating the view as the only way.** When something looks wrong, <code>git status</code> in the integrated terminal tells you what the view is summarizing.

</RulesBox>

<ExerciseBox title="Practice">

On a scratch repository, not the robot:

1. Change three files. Stage one whole file, then stage only two lines of the second from the diff editor. Commit. Confirm the third file is still under *Changes*.
2. Make a new file. Note the **U**. Stage it and confirm it moves to Staged Changes before committing.
3. Create a branch from the Status Bar, edit a line, commit. Switch to `main`, edit the *same* line differently, commit. Merge the branch (`…` → *Branch* → *Merge*) and resolve the conflict in the Merge Editor. Stage, commit.
4. Make a change, stash it, confirm the file is back to the committed version, pop it.
5. Open the Graph, click your merge commit, and open the diff of the conflicted file.

</ExerciseBox>
