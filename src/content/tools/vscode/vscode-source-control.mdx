## Before You Start

Complete [Local Git Workflow](/tools/local-git-workflow#the-three-areas) first. A **repository** is a project folder whose history Git tracks. A **staged change** is selected for the next **commit**, which is a named local snapshot. A **branch** is a movable line of commits. A **remote** is another copy of the repository, often on GitHub.

Git must be installed, and the repository folder must be open through **File → Open Folder...**. VS Code and command-line Git use the same repository; there is no separate import step.

## The Layout

Select the Source Control icon in the Activity Bar, choose **View → Source Control**, or press `Ctrl+Shift+G` on every supported platform. The repository name appears above its changes. If the view says no source control provider is registered, confirm that Git is installed and that you opened the repository folder rather than one file.

If Graph is not visible, use **Source Control Graph** from the Command Palette. For one file, Explorer's **Timeline** is another built-in history view.

## Read File Status

Lead with the letter and status name because theme colors differ. **M** means modified, **U** untracked, **A** added, **D** deleted, **R** renamed, and **C** conflicted. Open a file under **Changes** to compare working edits with the staged or committed version. Open it under **Staged Changes** to inspect what the next commit will record.

An untracked file is not included until staged. Before staging it, decide whether it is required project content or generated output that belongs in `.gitignore`.

## Staging

<StepsBox title="Review and Stage">

1. Select a file under **Changes**. A diff editor opens.
2. Read the old and new lines. Confirm the change belongs in this commit.
3. To stage the whole file, return to Source Control, hover over the file, and select **Stage Changes** (`+`). The file moves to **Staged Changes**.
4. To stage selected lines, select them in the diff editor, right-click, and choose **Stage Selected Ranges**. Only the selected change moves to the staged side.
5. Reopen the file under **Staged Changes** and read the staged diff. Any remaining edits stay under **Changes**.

</StepsBox>

**Unstage Changes** moves a staged change back to **Changes** and keeps the edit. **Discard Changes** removes working edits. Before choosing Discard, stop, read the confirmation, verify the exact file or range, and make sure you have another copy if the work matters. Do not use Discard as an unstaging shortcut.

## Commit and Confirm

Type a message that names the behavior, such as `Fix launcher speed limit`. Stage the intended changes explicitly, then select **Commit**. The default keyboard action is `Ctrl+Enter` on Windows/Linux or `Cmd+Enter` on macOS, but use the named button if the configured behavior is unclear.

After a successful commit, the staged files disappear from **Staged Changes**. Uncommitted edits remain under **Changes**. Open Graph or run `git status` in the integrated terminal to confirm the commit and remaining work. A commit is local until pushed.

Avoid **Amend** unless you intend to replace the latest local commit. If that commit has already been shared, create a new commit unless the collaborators have agreed to rewrite history.

## Create or Switch Branches

Select the branch name in the lower-left Status Bar. Choose **Create new branch...**, enter the name, and press Enter. The Status Bar should change to the new name. Before editing or committing, read it again.

When switching branches, VS Code may carry edits that apply cleanly or block the switch when it would overwrite work. Stop and read the message. Keep the work on its current branch by committing it, or follow [Stashing Work](/tools/advanced-git#stash-work-safely) after verifying whether untracked files are included.

## Sync, Pull, Push, Fetch

- **Fetch** asks the remote for updated branch information without integrating it into the current branch.
- **Pull** fetches and integrates remote commits into the current branch.
- **Push** uploads local commits.
- **Sync Changes** pulls and then pushes. Use it only when you intend both operations.

Choose separate actions from the Source Control `...` menu when you need one operation. After a push, outgoing-commit indicators should clear. If a push is rejected, read the complete message. Incoming work, authentication, permissions, and branch protections require different fixes.

## Merge Conflicts

Conflicted files appear under **Merge Changes** or with a conflict status. Open each file. VS Code may show inline conflict controls or a three-way Merge Editor. Read both inputs and edit the Result into the intended combined code. Labels such as current and incoming depend on whether the operation is a merge or rebase, so identify the branches before choosing a side.

Save the resolved file, stage it with **Stage Changes**, and verify that no conflict status remains. For a merge, build or test the combined result before completing the merge commit. Use the operation-specific continue or abort control for a rebase. See [Conflict Resolution](/tools/branching-and-merging#conflict-resolution) before practicing this workflow.

## Stash Unfinished Work

The Source Control `...` menu includes **Stash** actions. A stash stores unfinished local changes so the working tree can return to the current commit. Before creating one, inspect `git status` in the integrated terminal and decide whether untracked files must be included. Give the stash a description, then confirm the intended paths disappear from Changes.

Use **Apply Stash** to restore an entry while keeping the saved stash. Inspect every restored file before choosing **Drop Stash**. **Pop Stash** combines apply and removal after success, so separate apply, inspect, and drop steps are safer while learning. See [Advanced Git: Stash Work Safely](/tools/advanced-git#stash-work-safely).

## Inspect History

Open **Source Control Graph** from the Command Palette to inspect commits and branch relationships. Select a commit to inspect its changed files. For one file, open it in the editor, expand **Timeline** at the bottom of Explorer, and select an entry to compare that revision.

History and blame identify the recorded commit that changed a line. Read the commit message and related pull request before assuming why the author changed it.

## Ignore Generated Files

Some Source Control context menus offer **Add to .gitignore** for an untracked path. Review the exact pattern before committing it. An ignore rule affects untracked paths; it does not stop Git from tracking a file already committed. Follow [`.gitignore`](/tools/gitignore) for tracked-file and credential cases.

## Practice in a Scratch Repository

Use the scratch repository created in [Local Git Workflow](/tools/local-git-workflow#command-reference), not a robot repository. Change two files. Stage and commit one, then confirm the other remains under Changes. Create a branch, confirm the Status Bar name, make one commit, and return to the starting branch. Use the linked Git lesson for each command-line setup step. To abandon the practice, close VS Code and remove only the scratch folder through your file manager after verifying its full path.

<RulesBox title="Recovery Checks">

- If Source Control is empty, check the open folder and run `git status` in that same folder.
- If a new file is missing from a commit, look for its **U** status and stage it deliberately.
- If the wrong content is staged, use **Unstage Changes**, then stage the intended lines again.
- If an operation reports a conflict, stop normal commits until every conflict is resolved or the operation is safely aborted.

</RulesBox>
