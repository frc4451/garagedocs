## Prepare for the Loop

Complete [VS Code: Tour](/tools/vscode-tour), [Local Git Workflow](/tools/local-git-workflow#the-three-areas), and [VS Code: Source Control](/tools/vscode-source-control) first. This page condenses those procedures into one work session.

In this loop, **fetch** checks for remote commits, **pull** integrates them, a **branch** holds a line of work, **stage** selects changes, **commit** records a local snapshot, **push** uploads commits, and a **pull request** asks collaborators to review and merge a branch.

For a 2026 robot project, start **WPILib VS Code 2026**. It supplies the matching Java 17 robot toolchain. Stock VS Code with Java 25 remains the environment for this site's standalone Java curriculum.

## Open and Inspect

<StepsBox title="Start a Work Session">

1. Choose **File → Open Recent** and select the project. If it is absent, use **File → Open Folder...** and select the root containing `build.gradle`.
2. In Explorer, confirm the project name and `build.gradle`.
3. Open Source Control and read the branch name in the Status Bar.
4. Inspect every existing item under **Changes** and **Staged Changes** before updating. Preserve work whose owner or purpose is unclear.
5. Choose **Fetch** from the Source Control `...` menu to learn about remote commits without integrating them.
6. If the branch should receive those commits, choose **Pull**. Read and resolve any message before editing.

</StepsBox>

A pull can report that the branch is already up to date, integrate commits, or stop for a conflict. Use [Conflict Resolution](/tools/branching-and-merging#conflict-resolution) when Git cannot combine changes.

## Create the Work Branch

Select the branch name in the Status Bar, choose **Create new branch...**, and enter the agreed name. The Status Bar should show the new branch immediately. Confirm its starting branch before editing.

If VS Code blocks a branch switch, read the named files. It may allow edits to follow a switch when they apply cleanly and block the switch when they would be overwritten. Commit work that belongs to the current branch or follow the team's stash procedure. Do not discard work to force the switch.

## Edit and Save

Save each file with **File → Save**, `Ctrl+S`, or `Cmd+S`. Review relevant Problems messages, but do not treat a clear Problems panel as a successful build. Open Source Control periodically and inspect the diff so accidental edits remain small and recognizable.

## Build or Simulate

For a standalone Java lesson file with a `main` method, select **Run** above `main` and confirm the expected output in the Terminal.

For a robot project, open the Command Palette and type `WPILib:`. You can also select the WPILib extension control in the editor title area; its icon can vary, so use the tooltip or accessible label rather than identifying it only by shape.

## Review, Stage, and Commit

1. Open Source Control and select each changed file to read its diff.
2. Remove temporary prints, commented experiments, secrets, and unrelated edits.
3. Stage only the files or ranges that belong to one change. They move to **Staged Changes**.
4. Reopen each staged diff and compare it with the intended behavior.
5. Enter a descriptive message and select **Commit**.
6. Confirm that the staged list clears. Intended unfinished edits may remain under **Changes**.

If the commit reports that nothing is staged, return to the diff and stage the intended content. Avoid settings that silently stage everything for a beginner workflow.

## Push and Request Review

Choose **Publish Branch** when the branch has no remote counterpart, or **Push** when it does. After success, outgoing-commit indicators clear. If the push is rejected, read the full message before choosing Pull, Sync, or a credential fix.

Open GitHub and use the new-branch banner, or follow [Creating a Pull Request](/tools/pull-requests#creating-a-pull-request). Confirm the source branch and destination branch. Describe the behavior, reason, and checks performed. After creation, the pull request page displays those branches and its review status. Read [GitHub Actions Results](/tools/github-actions#open-a-pull-request-result) and address failures connected to the change.

## Shared Editor Files

Files under `.vscode/` apply to the project that contains them:

- `settings.json` can override editor settings for that workspace.
- `extensions.json` can recommend extensions.
- `launch.json` can define debug configurations.

Presence and contents vary by repository. Inspect the current project rather than assuming that generated Kit Bot and Cobra settings match. WPILib supplies the normal robot tooling. Before adding an extension, check its publisher, purpose, permissions, and compatibility with the WPILib workflow; disable it and repeat the check if it appears to cause a conflict.

Do not enable Settings Sync between stock VS Code and WPILib VS Code. WPILib warns that sharing those settings can break either installation.

## Practice the Loop

Use a scratch repository already created through [Local Git Workflow](/tools/local-git-workflow#command-reference). Fetch only if it has a remote. Create `practice/your-name`, confirm the branch in the Status Bar, edit and save one file, inspect its diff, stage it, commit it, and confirm the staged list clears. Publish only if the scratch repository is yours and its remote was intentionally configured. Otherwise, stop after the local commit.

<RulesBox title="Before You Finish">

- Confirm the current branch before editing and before committing.
- Record the build, simulation, or other checks that apply to the change.
- Use Fetch, Pull, Push, or Sync according to the operation you intend.
- Leave unrelated edits unstaged and tell their owner where they remain.
- Return to the base branch and update it only after the pull request is merged or the work is deliberately closed.

</RulesBox>
