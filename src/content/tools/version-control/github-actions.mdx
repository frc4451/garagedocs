### What the tick means

A pull request or commit can show a status icon for GitHub Actions checks. Open the check details to see which workflow and job produced the result. FRC 4451's robot repository runs a build workflow on pushes and pull requests.

This automated build is an example of **continuous integration** (CI): changes are checked on a separate runner as they are shared.

### FRC 4451's workflow

FRC 4451's robot repository defines this workflow in `.github/workflows/build.yml`:

```yaml
name: Build

on:
  push:
  pull_request:

jobs:
  build:
    name: Build
    runs-on: ubuntu-latest
    container: wpilib/roborio-cross-ubuntu:2024-22.04
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Grant execute permission
        run: chmod +x gradlew
      - name: Build robot code
        run: ./gradlew build
```

The YAML file defines the events that start the workflow and the steps the runner executes. A `run:` entry executes a shell command; a `uses:` entry invokes a published action. The result covers only the commands in the workflow.

### Reading a result

Open the check details from the commit or pull request. Select the job and expand the failed step to read its output. Interface labels can change, so use the Actions tab if the status menu is unclear.

For a compile failure, find the first relevant `error:` line. For another Gradle failure, read the failing task and the `What went wrong` block. Download the log when you need to preserve or share the complete output.

A pending status means the check has not finished. A skipped, cancelled, neutral, or stale status has a different meaning; open the details instead of inferring the cause from the icon alone.

The runner starts from a checkout of the committed files. It cannot see an uncommitted file or an unsaved editor buffer. Build and review the intended commit locally before pushing, then use the remote result as another check.

### Why a red cross matters

A failed check reports that one or more workflow steps failed. Repository rules can require selected status checks before a pull request is merged. Check the repository rules rather than assuming every failure blocks the merge.

Treat required formatting, compilation, and test failures as work to resolve or explain before merge.

### Anatomy, for when you need to change it

Edit workflow files when the automation itself needs to change. Review the repository's current file and documentation first:

- **Run the tests only, or a second job.** Add another item under `jobs:` with its own `steps:`; jobs run in parallel on separate machines.
- **The container tag.** The image tag (`2024-22.04` above) is a WPILib year. FRC 4451's file still pins 2024 and builds 2026 code fine, because GradleRIO downloads the roboRIO toolchain it needs during the build; what the image really provides is a JDK that WPILib is happy with. When WPILib changes its Java version, update the tag. Available tags are listed on [Docker Hub](https://hub.docker.com/r/wpilib/roborio-cross-ubuntu/tags).
- **Cache Gradle downloads when repeated downloads are a measured bottleneck.** A `uses: gradle/actions/setup-gradle@v4` step before the build keeps dependencies between runs and can reduce download time; measure the workflow before and after.
- **Secrets.** Put private values such as tokens and passwords in *Settings → Secrets* and is referenced as `${{ secrets.NAME }}`, never typed into the file. The file is public to everyone who can read the repository.

Workflow files are YAML, so indentation controls structure. GitHub reports workflow syntax and configuration problems in the Actions interface.

<RulesBox title="Common mistakes">

- **Reading only the status icon.** Open the job and identify the failed step.
- **Pushing without local checks.** Run the checks relevant to the change and review the committed files.
- **Reading only the bottom of a build log.** Locate the failing task and its first relevant error.
- **Testing workflow edits only on the default branch.** Use a branch or pull request when the workflow triggers there.
- **Putting credentials in YAML.** Store secrets through repository or environment settings and limit their permissions.

</RulesBox>
