## What an Organization Does

A GitHub organization owns repositories and manages access for a group of individual accounts. It lets the Automation Team retain code and documentation as students graduate and mentors change. Each person uses a personal account; never share an organization-owner or student login.

Organization membership, public membership visibility, and repository access are separate:

- **Membership** means an account belongs to the organization.
- **Public or private membership visibility** controls whether that membership appears on the person's public profile.
- **Repository access** determines which private repositories and actions the person can use.

A private membership can still have repository access. Seeing an organization on a public profile does not prove access to a particular repository.

## Student Member Tasks

Most students do not create or administer the organization. Their normal path is:

1. Create and secure a personal GitHub account through [Creating Your GitHub Account](/tools/creating-your-github-account).
2. Give the organization owner the exact username, never a password or authentication code.
3. Open and accept the invitation while signed in to the intended account. Invitations expire after seven days.
4. Open the repository named by the mentor. Confirm that its page loads and that the expected actions, such as reading code or creating a branch, are available.
5. If access is missing, report the account username, organization, repository, and visible message. Do not send credentials or recovery codes.

An organization that requires two-factor authentication requires it before an invited person can join. Membership visibility can be changed separately and does not grant or remove repository permissions.

## Repository Roles

GitHub provides repository roles from least to most access: **Read**, **Triage**, **Write**, **Maintain**, and **Admin**. An organization owner can also set a base permission that applies to all organization members.

Use the least access that supports the person's work:

| Need | Role to Consider | Limit |
|---|---|---|
| View and discuss code | Read | Cannot push code. |
| Manage issues and pull requests without pushing | Triage | Does not grant code write access. |
| Push branches and contribute code | Write | Does not grant repository administration. |
| Manage a repository without sensitive or destructive administration | Maintain | Broader than normal student contribution. |
| Manage security, access, or destructive settings | Admin | Reserve for people responsible for those settings. |

The table explains GitHub's built-in roles; it does not define FRC 4451 policy. Organization owners should document which role each Automation Team responsibility receives.

## Teams and Outside Collaborators

A GitHub **team** groups organization members so repository access and review requests can be managed together. Teams can contain organization members; an **outside collaborator** has access to selected repositories without being an organization member and cannot join an organization team.

Before adding nested teams or broad permissions, inspect the access inherited by every member. A parent team's repository access can flow to child-team members. Use direct, understandable groups such as a current-season Automation Team only when they match a real access need.

## Mentor and Owner Tasks

Creating an organization, selecting a plan, transferring repositories, changing base permissions, inviting members, and assigning owners are administrative actions. A responsible owner should:

- Keep at least two current, trusted owners as an FRC 4451 continuity practice. GitHub does not require this; it reduces dependence on one unavailable account.
- Require each owner to secure a personal account, retain recovery methods, and use two-factor authentication.
- Grant repository roles and team access according to documented responsibilities.
- Review owners, members, teams, outside collaborators, installed apps, and repository access when people join, change roles, or leave.
- Remove access that is no longer needed without deleting the person's account or rewriting their past contributions.
- Record who will assume owner responsibilities before a mentor or student owner leaves.

When removing a member, inspect GitHub's removal and reinstatement options first. Repository forks, outside-collaborator access, team membership, and private-repository access can be affected differently. Keep a handoff record outside any one person's account.

## Security and Visibility

Choose public or private repository visibility according to what FRC 4451 intends to share. A private repository limits who can read it, but it is not secret storage. Keep tokens, passwords, private keys, and recovery codes out of repositories.

Organization owners can require two-factor authentication for members and outside collaborators. Review the current GitHub warning and affected accounts before enabling or changing enforcement because people who do not comply can lose access.

## Optional Education Programs

GitHub Free already supports private repositories. GitHub Education programs have separate eligibility rules and changing benefits. Treat [GitHub Education](https://education.github.com/) and [GitHub Classroom](https://classroom.github.com/) as optional programs; verify current eligibility and features before planning a team workflow around them.

<RulesBox title="Access Check">

- The student signs in with a personal account and can open the mentor-named repository.
- The assigned role permits the needed action without unnecessary administration rights.
- Private membership visibility is not mistaken for missing membership.
- At least two responsible owners and a successor plan are recorded as FRC 4451 policy.
- Credentials and recovery methods remain private and outside repositories.

</RulesBox>
