## Before You Start

Complete [Branching and Merging](/tools/branching-and-merging) and [GitHub Remotes](/tools/github-remotes) first. You need a feature branch with at least one commit pushed to GitHub. The branch must differ from the branch that should receive the work.

A pull request (PR) proposes merging the **compare branch**, which contains the proposed work, into the **base branch**, which should receive it. A pull request gives reviewers one place to inspect the diff, discuss behavior, see automated checks, and record the decision.

## Creating A Pull Request

1. In a browser, sign in to GitHub and open the repository.
2. If GitHub shows a banner for your recently pushed branch, select **Compare & pull request**. If no banner appears, select the **Pull requests** tab, then select **New pull request**.
3. In the **base** menu, select the destination branch, usually `main`. In the **compare** menu, select your feature branch.
4. Read the comparison before continuing. If GitHub reports no changes, confirm that you pushed the intended feature branch and selected it as **compare**.
5. Enter a title that states the result of the change. In the description, explain the problem, resulting behavior, tests performed, and any remaining hardware check.
6. Select a reviewer if the repository allows you to request one. Link a related issue when one exists.
7. Select **Create pull request**. Use **Create draft pull request** when you want early feedback and the work is not ready to merge.

The resulting PR page should show the base and compare branch names, your title and description, the changed commits and files, and any checks configured for the repository. New commits pushed to the compare branch update the same pull request.

If the wrong files appear, do not merge. Return to the feature branch locally, inspect its commits and diff, and ask a mentor for help separating unrelated work.

## Read The Pull Request

Start on **Conversation** and read the description, linked issue, discussion, and checks. Select **Commits** to inspect the commit sequence and **Files changed** to inspect the complete diff.

Automated checks may appear beside commits or near the merge area. [GitHub Actions](/tools/github-actions) explains how to open a failed check. A passing check confirms only the work that check performed; it does not prove the robot behaves correctly.

For a robot change, compare the claim with simulation output and note any physical-robot test still required. Keep the request focused enough that a reviewer can understand and test its purpose.

## Reviewing Pull Requests

On **Files changed**, select the blue comment icon beside a line to start a line review. Use **Start a review** to keep line comments pending until you submit them together. A single comment posted outside a review appears immediately and does not itself approve or request changes.

These examples express different outcomes:

| Review Need | Example Comment | Review Outcome |
|---|---|---|
| Clarifying question | “Does this limit apply before or after the motor inversion?” | **Comment** while the reviewer gathers information. |
| Required correctness change | “This comparison uses encoder rotations, but the limit is documented in mechanism rotations. Convert the units before comparing.” | **Request changes** when repository policy and reviewer permission make the correction a merge requirement. |
| Optional suggestion | “Consider naming this value `maximumArmRotations` so its unit is visible.” | **Comment** or clearly label it optional. |

After reviewing the files, select **Review changes**, enter a summary, and choose:

- **Comment** for feedback without explicit approval or a formal change request.
- **Approve** when the proposed work is ready under the repository's standards.
- **Request changes** when required work remains.

Then select **Submit review**. A requested-changes review blocks merging only when the applicable branch protection or ruleset and the reviewer's permissions make it blocking. Read the repository's merge area rather than assuming every comment has the same effect.

## Respond To A Review

Read every comment before editing. Reply with the change made, a question, or the reason for keeping the current approach. Make corrections on the same feature branch, commit them, and push that branch. The PR updates automatically.

Resolve a conversation only after the concern is addressed according to the repository's process. If the scope changes, update the PR title and description so they explain the final behavior.

## Check Merge Requirements

The merge area on the **Conversation** tab reports conflicts, required reviews, unresolved conversations, and required status checks. Branch protections and rulesets can prevent merging until those requirements pass. They can also restrict who may push or merge.

GitHub repositories can enable one or more merge methods:

| Method | Result On The Base Branch |
|---|---|
| Create a merge commit | Adds the feature commits and a merge commit that joins the histories. |
| Squash and merge | Combines the pull request's commits into one new commit on the base branch. |
| Rebase and merge | Adds each feature commit onto the base branch without a merge commit; GitHub creates new commit identifiers. |

The available button reflects the repository's configuration and branch rules. Use the method the repository owner selected. Do not rewrite or force-push shared work to make a method available without coordinating with collaborators.

In the Badge 1 Git check, the student opens the pull request and responds to review. The mentor merges it. The student should not select a merge button unless the mentor has explicitly assigned that responsibility for another repository.

## Confirm The Result

After an authorized person merges the PR:

1. Confirm that GitHub labels the pull request **Merged** and names the base branch.
2. Open the repository's base branch and confirm that the changed files show the intended result.
3. Update any related issue or documentation required by the project.
4. Delete the feature branch only when the repository's process allows it and no later work depends on it.
5. Update the local repository before starting more work on the base branch.

If GitHub says the branches cannot merge automatically, do not select a different base to hide the conflict. Update the feature branch from the intended base, resolve the conflict with the mentor or other author, test the combined result, and push the resolution.
