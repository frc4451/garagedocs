## Write Useful Commit Messages

A commit message should let another student understand the recorded change without opening every file. Name the behavior or purpose in the first line.

| Weak Message | Useful Message | Why It Helps |
|---|---|---|
| `updates` | `Add launcher ready-speed check` | Names the added behavior. |
| `fix stuff` | `Fix drivetrain inversion in teleop` | Names the affected system and failure. |
| `more changes` | `Document encoder units for arm setpoint` | Names the documentation and the value it protects. |

Use an imperative verb such as **Add**, **Fix**, **Remove**, or **Document** for consistency. A short first line is easier to scan in a log. Git does not impose a 50-character summary limit, so preserve the specific behavior instead of cutting useful meaning.

The following are separate examples, not a sequence to run:

```text
git commit -m "Add autonomous scoring sequence"
git commit -m "Fix drivetrain calibration in teleop"
```

When the reason or tradeoff is not clear from the summary, write a body after a blank line through your editor or pull-request description. Include an issue, requirement, or test result when it helps future readers understand why the change exists.

## Name Focused Branches

Names such as `feature/autonomous-scoring` and `fix/drivetrain-inversion` identify the work. Follow the repository's established convention. Add a season or subsystem only when it helps distinguish the branch.

Keep one branch focused enough that a reviewer can explain its purpose and run the relevant checks. Before editing, read the branch name in VS Code's Status Bar or run `git branch --show-current`. Before deleting a merged branch, confirm that its work is present on the intended destination branch.

## Update With Intent

Read [GitHub Remotes](/tools/github-remotes#fetch-pull-and-push) before updating from a remote. Use **fetch** when you want updated remote information without changing the current branch. Use **pull** when you intend to fetch and integrate remote commits into the current branch.

Before either action, inspect the current branch and `git status`. Preserve unfinished work before switching branches or integrating commits. If Git reports a conflict or would overwrite local work, stop and read the named paths instead of forcing the operation.

## Make Reviewable Commits

Build a commit around one behavior, correction, or documentation purpose when practical. Related code, tests, configuration, and documentation can belong together because they are needed for the same result. Unrelated formatting or feature work is easier to review in a separate commit.

Before committing:

1. Save the files.
2. Run `git status` and identify every path.
3. Read the unstaged and staged diffs.
4. Stage explicit files or selected ranges.
5. Confirm that new files needed for the build are staged.
6. Run the checks appropriate to the change and record the actual result.

Simulation can check supported robot behavior before hardware. It cannot verify wiring, motor direction, mechanism limits, or real-world performance. Record what still needs hardware confirmation.

<RulesBox title="Record Robot-Affecting Changes">

Document hardware replacements, configuration changes, units, coordinate frames, calibration procedures, and the evidence used to choose a value. A later student should be able to tell what the setting controls and when it must be measured again.

</RulesBox>

## Protect Project Files and Credentials

Use [`.gitignore`](/tools/gitignore) for generated build output and local machine files. `.gitignore` does not make a credential safe: tracked files remain in history, and anyone can bypass an ignore rule.

Keep passwords, personal access tokens, private keys, and recovery codes out of project files. Use the supported credential manager for Git authentication and GitHub's secrets settings for automated workflows. If a credential is committed or pushed, revoke or rotate it first, then follow [GitHub's sensitive-data removal procedure](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) with the repository owner.

The repository README should explain the project, how to build it, and where a new contributor should start. Keep required source, build scripts, vendordep files, and shared configuration under version control.

## Review Before Sharing

Use this checklist before a push or pull request:

- Confirm the current branch and the remote destination.
- Read the staged diff and commit list.
- Confirm each commit message describes its change.
- Build, simulate, or run the relevant checks and record their results accurately.
- State any known limitation or check still needed.
- Check that no credential, generated output, or unrelated file is included.

Push normally. If a push is rejected, read the complete message and check for incoming commits, authentication, permissions, or branch rules. Do not answer an unexplained rejection with a force push. See [Push Troubleshooting](/tools/github-remotes#troubleshooting-a-push) for the first check for each symptom.

## Prepare a Pull Request

Confirm the compare branch contains your work and the base branch is where it should merge. Describe the resulting behavior, why the change is needed, the checks performed, and what remains unverified. Keep follow-up fixes on the same branch so reviewers can see the updated result.

After GitHub Actions runs, open the check rather than reading only the icon. A passing workflow proves only the commands configured in that workflow. Reviewer feedback and hardware checks can still identify issues outside that automation.
