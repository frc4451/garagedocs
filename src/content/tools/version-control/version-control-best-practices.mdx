### Writing good commit messages

Describe the behavior or purpose of the change. Use a short first line, followed by a blank line and details when the reason or tradeoff needs explanation.

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git commit -m "Add autonomous scoring sequence"
git commit -m "Fix drivetrain calibration in teleop"
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git commit -m "Add autonomous scoring sequence"
git commit -m "Fix drivetrain calibration in teleop"
```

</CodeTab>
</CodeTabs>

These are separate message examples, not commands to run in sequence. Use an imperative verb such as "Add" or "Fix" for consistency. About 50 characters is a useful target for the summary, not a Git requirement. Reference an issue or test result when it helps explain the change.

### Branch naming and organization

Names such as `feature/autonomous-scoring` and `fix/drivetrain-issue` identify the work. Choose a convention with the team and follow it. Add a season to the name only when it helps distinguish the work.

Keep each branch focused enough to review and test. Delete a merged branch when it is no longer needed.

### Team workflow practices

Before starting new work, inspect the current branch and local changes, then fetch or pull as appropriate. Preserve unfinished work before switching branches or integrating changes.

Make focused commits as the work progresses. Before proposing a merge, run the relevant checks and explain the results in the pull request. For robot behavior, develop and check it in simulation before hardware confirmation. Keep `main` aligned with the team's review and testing policy.

<RulesBox title="Record changes that affect the robot">

Document hardware replacements, configuration changes, units, and calibration procedures alongside the code. Record the reason and evidence so a later student can understand the setting instead of copying it without context.

</RulesBox>

### File and repository organization

Use [`.gitignore`](/tools/gitignore) for generated build output and temporary files. Keep
source code and configuration files that the project needs under version control.
Organize them so a reader can find related code and settings together.

The README should explain the project, how to build it, and where to start. Keep credentials such as tokens and passwords out of tracked files. Use the platform's supported credential or secret storage.

### Review before sharing

- Read the staged diff and check that it contains only the intended change.
- Include new files required to build the project.
- Explain the reason for changes that are not clear from the diff.
- Record what was tested and what still needs checking.
- Push the commits so teammates can access them.
