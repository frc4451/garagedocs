## Before You Start

Read [Introduction to Version Control](/tools/introduction-to-version-control), [Local Git Workflow](/tools/local-git-workflow), and [GitHub Remotes](/tools/github-remotes) first. GitHub Desktop provides visible controls for the same repository, branch, staging, commit, fetch, pull, and push concepts.

Ask the computer's owner or administrator before installing software. Download GitHub Desktop only from the [official GitHub Desktop site](https://desktop.github.com/). Installation and account sign-in require a human walkthrough on the actual Windows or macOS computer because prompts can vary.

## Open The Correct Repository

After GitHub Desktop opens, use one of these paths:

- To copy a GitHub repository that is not on this computer, select **File → Clone repository**, choose the repository, select its local path, and select **Clone**.
- To use a repository already on the computer, select **File → Add local repository**, choose its folder, and select **Add repository**.

The repository bar at the top shows **Current Repository** and **Current Branch**. Select **Current Repository** and confirm the repository name. Select **Repository → Show in Explorer** on Windows or **Repository → Show in Finder** on macOS to see the exact local folder.

If Desktop says the selected folder is not a Git repository, do not initialize an unrelated folder. Compare the path with the repository folder you intended to add.

## Make A Commit

Use a disposable practice repository that is already connected to a GitHub remote and that your account may write to. Do not use an Automation Team robot repository for the first Desktop exercise. If you have only the local `git-workflow-practice` repository, you can complete the commit and History steps below, but **Push origin** and **Publish branch** will not appear until an approved remote is configured.

1. In the repository bar, select **Current Repository** and choose the practice repository.
2. Select **Current Branch** and confirm the branch that should receive the commit.
3. Open the repository in your editor, edit one text file, and save it.
4. Return to GitHub Desktop. In the left sidebar, select **Changes**. The saved file should appear in the changed-files list.
5. Select the file and read its diff on the right. Checked files and selected changed lines are included in the commit; unchecked files and unselected lines remain for later.
6. Enter a short result in **Summary**. Add useful context in **Description** when the summary is not enough.
7. Read the button below the message. It should say **Commit to BRANCH**, where `BRANCH` is the intended branch. Select it only after the branch, files, and message are correct.
8. After the commit, inspect **Changes**. Any file left there was not included. Select **History** and confirm that the new commit and its diff appear. Do not push while unexpected changes remain.

A successful local commit does not immediately appear on GitHub. In a remote-enabled practice repository, the repository bar should offer **Push origin** when the branch has commits to share. Confirm the current repository, branch, and clean **Changes** view before selecting it. Then open the repository on GitHub and confirm that the branch shows the commit. A local-only repository correctly has no Push origin button.

If **Changes** stays empty after an edit, confirm the file was saved and that the editor and Desktop have the same local repository folder open.

## Create And Publish A Branch

1. Select **Current Repository** and choose the remote-enabled practice repository. Confirm that **Changes** is empty before switching or creating a branch.
2. Select **Current Branch** and confirm the branch that should be the starting point.
3. Select **New branch**, enter a focused name, and create the branch.
4. Confirm the new name now appears under **Current Branch** before editing or committing.
5. After making at least one commit and confirming the **Changes** view is clean, select **Publish branch** to create the corresponding branch on GitHub.

Creating a local branch requires read access to the repository. Publishing it requires write access. If publication is rejected, read the message and check repository access or rules instead of recreating the branch.

## Switch With Uncommitted Changes

When you switch branches while saved, uncommitted changes exist, GitHub Desktop asks what to do. Read the branch names in the dialog:

- **Leave my changes on CURRENT-BRANCH** keeps the changes associated with the current branch while you switch away.
- **Bring my changes to NEW-BRANCH** moves the saved changes into the working view of the branch you are entering.
- Stashing temporarily removes saved changes from the files so you can switch, then restore them later on the original branch.

GitHub Desktop supports one stash at a time. To create it, right-click the changed-files heading and select **Stash All Changes**. To restore it, return to that branch, select **Stashed Changes** in the **Changes** sidebar, and select **Restore**.

Before choosing, ask which branch should own the unfinished work. If you are uncertain or the dialog reports a conflict, cancel the switch and commit or discuss the work first.

## Keep Recovery Actions Separate

These actions solve different problems:

| Action | Use | Important Result |
|---|---|---|
| Discard changes | Remove selected uncommitted edits from working files. | Desktop places discarded changes in a dated file in the system Trash until the Trash is emptied. Review the confirmation list first. |
| Undo a commit | Return the newest unpushed commit's changes to the working directory. | The changes become editable again; this is unavailable after the commit is pushed. |
| Reset to commit | Move the branch back to a selected commit and restore later commit changes to the working directory. | Use only for local history up to the newest commit already pushed. Inspect the selected commit first. |
| Revert a commit | Create a new commit that reverses an earlier commit. | This preserves shared history and is the appropriate Desktop option for a pushed commit. |
| Delete branch | Remove a branch reference. | Desktop says branch deletion cannot be undone. Verify the branch is merged and no longer needed. |

Avoid changing the history of commits already pushed. Other collaborators may have based work on those commits. When the correct recovery action is unclear, stop and show the **History** view and repository state to a mentor.

## Open A Pull Request

After publishing a feature branch, GitHub Desktop can show **Preview Pull Request**. Select it, confirm the **base** branch that should receive the change, and inspect the preview diff. Select **Create Pull Request** to open GitHub in the browser, where you enter the title and description.

Follow [Pull Requests](/tools/pull-requests) for the browser review and merge process. In the Badge 1 check, the mentor merges the pull request.

## Confirm Every Tool Matches

Desktop, VS Code, and a terminal can operate on the same local repository. Before moving between them, compare:

1. **Folder:** In Desktop, use **Repository → Show in Explorer/Finder**. In VS Code, read the folder at the top of the Explorer. In the terminal, read the prompt or check the current folder as taught in Command Line Basics.
2. **Branch:** Read **Current Branch** in Desktop, the branch indicator in VS Code, and the branch named by `git status` in a terminal.
3. **File state:** Save editor files, then compare Desktop **Changes** with `git status` when the views seem inconsistent.

Do not commit until the repository path and branch agree across the tools you are using.
