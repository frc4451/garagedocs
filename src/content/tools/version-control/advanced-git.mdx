### Choosing an operation

Use this page after the local, branch, and remote workflows. Check `git status` and the relevant commits before undoing work. Practice unfamiliar history operations in a scratch repository.

### Undoing changes

The following are alternatives, not a sequence. `HEAD` names the current commit; `HEAD~1` names its first parent. The reset examples require a previous commit and should be used only for local history you intend to revise.

| Command | Effect |
|---|---|
| `git reset --soft HEAD~1` | Move the branch back one commit; leave the index and working files unchanged. |
| `git reset --mixed HEAD~1` | Move the branch back and reset the index; keep working files. |
| `git reset --hard HEAD~1` | Move the branch back and replace the index and working files. This discards tracked changes and can remove untracked files that obstruct the reset. |
| `git revert HEAD` | Create a new commit that reverses the current commit's changes. Conflicts may need resolution. |
| `git checkout -- filename` | Replace a working file with its staged version, discarding unstaged changes to that file. |

For shared history, prefer a reverting commit so teammates can follow the correction. Read the [reset](https://git-scm.com/docs/git-reset) and [revert](https://git-scm.com/docs/git-revert) references before choosing an operation.

### Stashing work

A stash saves unfinished changes locally. By default it includes changes to tracked files; `-u` also includes untracked files, but not ignored files.

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git stash push -u -m "Intake adjustment in progress"
git stash list
git stash apply
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git stash push -u -m "Intake adjustment in progress"
git stash list
git stash apply
```

</CodeTab>
</CodeTabs>

`apply` restores the latest stash while retaining the saved entry. `pop` restores it and removes the entry on success. If applying causes conflicts, resolve them before deleting the stash. Use `git stash drop` only when the saved entry is no longer needed. See the [stash reference](https://git-scm.com/docs/git-stash).

### Rebasing for clean history

Rebase replays commits on a different base. Interactive rebase can combine commits, reorder them, or edit their messages. Because this creates new commit identities, coordinate with teammates before rebasing work they may already have used.

Use the linked rebase guide for a worked procedure. For a shared branch, merging is often the more straightforward way to preserve the existing history.

### Tags and releases

A tag names a particular commit, such as the version used at an event. An annotated tag also records a message and tagger information:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git tag -a v1.0 -m "Competition version"
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git tag -a v1.0 -m "Competition version"
```

</CodeTab>
</CodeTabs>

Run this only when the current commit is the version you intend to label. The tag is local until it is pushed. GitHub releases can attach notes and downloadable files to a tag. Record the event, configuration, and known limits in the release notes.

### Advanced branching strategies

Feature branches keep individual changes separate until review. Trunk-based development integrates small changes frequently into a shared main line. Git flow adds develop, release, and hotfix branches for a more structured release process.

Feature flags select behavior in the code; they are not a branching strategy by themselves. Environment branches separate deployments such as development and production, but add coordination work. Choose extra branches only when they solve a problem the team actually has.
