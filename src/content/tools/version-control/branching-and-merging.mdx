### Working with branches

A branch lets you develop a change separately from another line of work. For example, you can test an autonomous routine on a feature branch while the team continues using `main`.

`main` is a branch name, not a guarantee that code is tested. Keeping it ready for the robot is a team policy supported by reviews and checks.

### Branch operations

Start in a practice repository with a commit on `main` and no uncommitted changes:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git status
git checkout -b autonomous-improvements
git branch
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git status
git checkout -b autonomous-improvements
git branch
```

</CodeTab>
</CodeTabs>

`checkout -b` creates a branch from the current commit and switches to it. `git branch` lists local branches and marks the current one with `*`. To create a branch without switching, use `git branch branch-name`; to switch to an existing branch, use `git checkout branch-name`.

### Merging workflows

After committing and testing the feature, switch to the branch that should receive it:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git checkout main
git merge autonomous-improvements
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git checkout main
git merge autonomous-improvements
```

</CodeTab>
</CodeTabs>

If `main` has no separate new commits, Git can move it forward to the feature's latest commit. This is a fast-forward. If both branches have new commits, a merge can record how their histories combine in a merge commit.

For shared team code, use a [pull request](/tools/pull-requests) when the team's review policy requires one. The commands above demonstrate a local merge.

<RulesBox title="Robotics branching examples">

Use names that describe the work: `autonomous-improvements`, `teleop-enhancements`, or `fix-drivetrain-issue`. Keep unrelated changes on separate branches when that makes them easier to test and review.

</RulesBox>

### Conflict resolution

A conflict occurs when Git cannot combine changes automatically. Overlapping edits to the same lines are one cause; deleting a file that another branch modified is another.

1. Run `git status` to identify conflicted files.
2. Open each file or use the editor's merge tool. Decide what the combined result should do.
3. Remove conflict markers and save the resolved files.
4. Stage each resolved file with `git add filename`.
5. Build and check the result, then complete the merge with `git commit`.

If you are unsure which behavior to keep, ask the author of the other change. Selecting one side without reading it can remove needed work.

### Understanding branch management

Once the work is merged and no longer needed as a separate local branch, `git branch -d branch-name` deletes that local branch. It does not delete the remote branch. Keep branches focused and review their changes before merging.
