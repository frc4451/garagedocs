## Before You Start

Complete the [Local Git Workflow](/tools/local-git-workflow) first. Use its `git-workflow-practice` repository for this lesson. Do not practice merging in GarageDocs or a robot repository.

Open `git-workflow-practice` in VS Code, select **Terminal → New Terminal**, and run `git status`. Continue only when the output says you are on `main` and the working tree is clean. If Git lists changed or untracked files, save and commit intended practice work or ask a mentor what to do with it before switching branches.

## What A Branch Does

A branch names a line of development and points to its newest commit. New commits move the current branch forward. For example, you can test an autonomous change on a feature branch while `main` remains at an earlier commit.

`main` is a branch name. It does not guarantee that code is tested. Keeping `main` ready for the robot is a team policy supported by reviews and checks.

## Create A Feature Branch

Run the commands one line at a time:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git status
git switch -c autonomous-improvements
git branch
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git status
git switch -c autonomous-improvements
git branch
```

</CodeTab>
</CodeTabs>

`git switch -c` creates a branch at the current commit and switches to it. `git branch` lists local branches. The line beginning with `*` should be `autonomous-improvements`.

If Git says the branch already exists, do not create another spelling of it. Run `git branch`, then use `git switch autonomous-improvements` if that is the branch you meant to continue.

Open `notes.txt`, add `Test autonomous changes in simulation.` on a new line, and save the file. Then run:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git diff
git add notes.txt
git diff --staged
git commit -m "Add autonomous test note"
git status
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git diff
git add notes.txt
git diff --staged
git commit -m "Add autonomous test note"
git status
```

</CodeTab>
</CodeTabs>

The final status should name `autonomous-improvements` and report a clean working tree.

## Merge The Feature

Switch to the branch that should receive the change, then merge the feature branch into it:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git switch main
git merge autonomous-improvements
git log --oneline --decorate -4
git status
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git switch main
git merge autonomous-improvements
git log --oneline --decorate -4
git status
```

</CodeTab>
</CodeTabs>

Because `main` did not receive another commit after the feature branch was created, Git should report a **fast-forward**. It moves `main` to the feature's newest commit. The log should show `main` and `autonomous-improvements` beside the same commit, and the final status should be clean.

If both branches have new commits, Git may create a merge commit that records how their histories join. For shared work, follow the repository's policy and use a [pull request](/tools/pull-requests) when review is required.

<RulesBox title="Choose Focused Branch Names">

Use names that describe the work, such as `autonomous-improvements`, `teleop-controls`, or `fix-drivetrain-current-limit`. Keep unrelated changes on separate branches when that makes them easier to test and review.

</RulesBox>

## Create A Practice Conflict

A conflict occurs when Git cannot combine changes automatically. This exercise changes the same line differently on two branches so the result is predictable.

On `main`, create `mode.txt` in the VS Code Explorer. Type `Selected mode: disabled`, save it, and commit it:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git add mode.txt
git commit -m "Add selected mode note"
git switch -c practice-conflict
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git add mode.txt
git commit -m "Add selected mode note"
git switch -c practice-conflict
```

</CodeTab>
</CodeTabs>

On `practice-conflict`, replace the line with `Selected mode: autonomous`, save it, and commit:

```text
Selected mode: autonomous
```

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git add mode.txt
git commit -m "Set autonomous practice mode"
git switch main
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git add mode.txt
git commit -m "Set autonomous practice mode"
git switch main
```

</CodeTab>
</CodeTabs>

On `main`, replace the line with `Selected mode: teleop`, save it, and commit:

```text
Selected mode: teleop
```

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git add mode.txt
git commit -m "Set teleop practice mode"
git merge practice-conflict
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git add mode.txt
git commit -m "Set teleop practice mode"
git merge practice-conflict
```

</CodeTab>
</CodeTabs>

The merge should stop with a conflict in `mode.txt`. Git has not completed the merge.

## Conflict Resolution

1. Run `git status`. It should list `mode.txt` as both modified.
2. Open `mode.txt`. VS Code shows both versions and may display controls such as **Accept Current Change**, **Accept Incoming Change**, and **Accept Both Changes**. Read the text before choosing. **Current** is the version on `main`; **incoming** is the version from `practice-conflict`.
3. For this exercise, replace the entire file with `Selected mode: chosen by the driver station`. Remove every line containing `<<<<<<<`, `=======`, or `>>>>>>>`, then save the file.
4. Stage and inspect the resolution, then complete the merge:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git add mode.txt
git diff --staged
git commit -m "Resolve practice mode conflict"
git status
git log --oneline --graph --decorate -7
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git add mode.txt
git diff --staged
git commit -m "Resolve practice mode conflict"
git status
git log --oneline --graph --decorate -7
```

</CodeTab>
</CodeTabs>

The status should be clean. The graph should show the two lines of work joining at the merge commit.

If you are unsure how to resolve a real conflict, stop before staging. Run `git merge --abort` to return to the state before the merge, then ask the other author or a mentor which behavior the combined file needs. Do not choose one side only because its button looks convenient.

## Delete A Merged Branch

Before deleting a local branch, confirm that you are on `main` and that the branch's work is present there. Then run `git branch -d branch-name`, replacing the placeholder with the exact merged branch name. The lowercase `-d` refuses to delete some unmerged work.

Deleting a local branch does not delete a remote branch. The practice branches can also remain until a mentor reviews the exercise.
