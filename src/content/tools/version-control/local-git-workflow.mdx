## Before You Start

Complete [Installing Git](/tools/installing-git) first. You need Git, a configured commit name and email address, and VS Code.

This lesson creates a new practice repository containing only text files. Do not run the setup commands inside GarageDocs, a robot project, or another existing project. If terminal prompts and folders are unfamiliar, read [The Prompt](/tools/command-line-basics#the-prompt) and [Move Between Folders](/tools/command-line-basics#moving-around) first.

## The Three Areas

| Area | What It Contains |
|---|---|
| Working directory | The files you edit and save in the project folder. |
| Staging area, also called the index | The saved file versions selected for the next commit. |
| Repository history | Snapshots already recorded as commits. |

Saving a file changes the working directory. Staging selects the file's current saved version. A commit records the staged version. If you edit and save a file after staging it, stage it again to include the later edit.

## Create A Practice Folder

1. Open VS Code.
2. Select **File → Open Folder**.
3. In the folder chooser, go to a location where you keep school projects, such as **Documents**. Look for a folder named `git-workflow-practice` before creating anything.
4. If the folder does not exist, select **New Folder**, name it `git-workflow-practice`, and open it. If it already exists and you intend to resume that practice, open it without deleting or replacing anything. Otherwise, create an empty folder with a numbered name such as `git-workflow-practice-2`.
5. Check the Explorer on the left side of VS Code. Its top folder should show the practice folder you chose.
6. Select **Terminal → New Terminal**. A terminal panel opens at the bottom of VS Code.

The terminal prompt should end with the practice folder's name or show that folder immediately before the cursor. The prompt is information from the shell; do not type it as part of a command.

If VS Code opened a different folder, close the terminal, select **File → Open Folder**, and open `git-workflow-practice` before continuing.

## Initialize The Repository

Click after the terminal prompt, type the following command, and press **Enter**:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git init -b main
git status
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git init -b main
git status
```

</CodeTab>
</CodeTabs>

The first command creates an empty Git repository whose initial branch is named `main`. The `-b main` option requires Git 2.28 or newer. The second command should report that you are on `main`, that there are no commits yet, and that there is nothing to commit.

If Git says `unknown option` for `-b`, check `git --version` and ask a mentor to update Git or help name the initial branch. If Git says the folder is already a repository, stop. Confirm that you created and opened the separate practice folder rather than continuing in an existing project.

## Create The First File

1. In the VS Code Explorer, select the **New File** icon beside `git-workflow-practice`.
2. Type `README.md` and press **Enter**. The complete filename is uppercase `README`, followed by `.md`.
3. Type these two lines in the editor:

```markdown
# Git Workflow Practice

This repository contains my Git practice files.
```

4. Select **File → Save**. A filled circle on the editor tab changes to an `×` when the file is saved.

Return to the terminal and run:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git status
git diff
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git status
git diff
```

</CodeTab>
</CodeTabs>

`git status` should list `README.md` under **Untracked files**. Ordinary `git diff` prints nothing for an untracked file because Git has no earlier tracked version to compare. A command that succeeds can produce no output.

## Stage And Commit

Run each command after the previous one finishes:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git add README.md
git status
git diff --staged
git commit -m "Describe the practice project"
git log --oneline
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git add README.md
git status
git diff --staged
git commit -m "Describe the practice project"
git log --oneline
```

</CodeTab>
</CodeTabs>

`git add README.md` normally prints no output. The next status should list `README.md` under **Changes to be committed**. The staged diff should show the heading and sentence you wrote with `+` signs. The plus signs describe added lines; they are not part of the file.

The commit command records the staged file with the message between the quotation marks. The final log should show one shortened commit identifier followed by `Describe the practice project`. The commit is local until you push it to a remote repository.

If the commit says Git cannot identify you, return to [Configure And Check Git](/tools/installing-git#configure-and-check-git), set the intended name and email address, and run the commit again. Your staged work remains staged after this identity error.

## Make Two More Commits

Create a file named `notes.txt` in the Explorer. Type `Practice notes` on its first line, save the file, and run:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git status
git add notes.txt
git diff --staged
git commit -m "Add practice notes"
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git status
git add notes.txt
git diff --staged
git commit -m "Add practice notes"
```

</CodeTab>
</CodeTabs>

Then open `README.md`, add this line at the end, and save it:

```markdown
I can inspect changes before I commit them.
```

Run:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
git status
git diff
git add README.md
git diff --staged
git commit -m "Record the review step"
git log --oneline
git status
```

</CodeTab>
<CodeTab label="Terminal">

```bash
git status
git diff
git add README.md
git diff --staged
git commit -m "Record the review step"
git log --oneline
git status
```

</CodeTab>
</CodeTabs>

The log should now show three commits, newest first. The final status should report that the working tree is clean. If it still lists a changed file, read its path before doing anything else. Confirm that the file was saved and that you staged the file you intended.

## Command Reference

| Command | Use |
|---|---|
| `git init -b main` | Create a repository in the current folder with an initial branch named `main`. |
| `git clone repository-url` | Copy an existing repository. Replace `repository-url` with its URL. |
| `git status` | Check the current branch and file states. |
| `git add filename` | Select a file's current saved version for the next commit. |
| `git diff` | Compare unstaged changes in tracked files with the staging area. |
| `git diff --staged` | Compare staged changes with the current commit. |
| `git commit -m "message"` | Record staged changes with the message inside the quotation marks. |
| `git log --oneline` | Show a compact commit history. |

Use explicit file paths when staging so unrelated changes stay out of the commit. Check [`.gitignore`](/tools/gitignore) before staging generated files such as build output.
