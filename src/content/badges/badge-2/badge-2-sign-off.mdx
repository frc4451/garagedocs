Step 15 closes Badge 2 after the integrated capstone and successful replay. The student completes
the post-test and reviews the accumulated evidence with a mentor. A passing written score does not
replace the practical work.

## Required Sheet

The [sign-off sheet (PDF)](/documents/badges/badge-2/badge-2-sign-off.pdf) and
[assessment (PDF)](/documents/badges/badge-2/badge-2-pretest.pdf) match the current fifteen-step
curriculum. The sign-off sheet summarizes the fifteen steps and provides spaces for mentor
signatures and dates. Each signature confirms the full requirements in the linked lesson. The mentor
records the assessment version as described in [Pretest](/badges/badge-2-pretest#printed-test).

The mentor prints a fresh sign-off sheet or provides a working copy. The student records evidence
locations in the repository README; the mentor signs and dates completed steps on the sheet. The
repository README links the same evidence by row identifier. The student does not need to transcribe
the requirement text.

Row identifiers are stable evidence labels and do not always match lesson numbers. Step 4 contains
hardware rows HW.1, 3.8 and HW.2. Row 3.7 belongs to Step 5 with software rows 4.1–4.7. Row HW.3
belongs to Step 7 with the simulation work; rows 6.11–6.12 cover the two CTRE roller simulation
checks, and controller-binding rows 8.9–8.10 are in Step 7 so the bindings are tested in simulation
before the physical check. The badge uses three robot projects: `Badge2Bench` for individual
mechanisms, `Badge2KitBot` and `Badge2Swerve`. Row 3.6, the controller subclass, is in Step 6
because the class is built in `Badge2Bench`, which Step 5 creates. Rows 10.30–10.31 in Step 11
verify the Step 9 mechanisms and controller already in `Badge2Swerve`. Row 11.12 in Step 12 checks
that vision runs before the drivetrain. Row 4.5 checks builder construction, defaults and generated
null checks without requiring delombok inspection.

Existing evidence is retained when it proves the current behavior. The mentor checks the work rather
than transferring a signature solely because a row number matches. Newly required physical work and
any missing current checks are completed separately. A mistake during practice does not erase
completed evidence.

The mentor reviews the physical roller evidence and selects one motor setting to trace from the
builder through configuration tests, IO construction, vendor application, and its verification
evidence. The student distinguishes Lombok-generated construction code from AdvantageKit-generated
input logging and explains one configuration test or unit conversion. The capability table
distinguishes four general models, both CTRE roller device simulations, the selected physical
controller and the CTRE pivot profile comparison. The elevator review includes drum diameter, the
radius passed to `ElevatorSim`, a predicted travel change, limits, and the saved motion log.

The student must build the roller, flywheel, pivot and elevator 2D visualizations in Step 8 and
reuse them in the three local superstructure visualizers in Step 9. Viewing the finished solution
alone does not satisfy these requirements. The mentor reviews the student's local visualizer source,
reused helpers, subsystem update calls and tests, then asks the student to trace a measured input to
a displayed line. The README links that implementation and its saved-log evidence.

The Step 8 review includes all four student-built 2D line drawings and their numeric plots. The
composition review follows Cobra, Ember, then Riptide and verifies ports 0, 1 and 2. It includes a
refused clearance transition, the component views for all three parents with measured/goal
comparisons where goals apply, and the Ember-style `EmberSuperStructure` in `Badge2Swerve`, and
feeding refused without valid possession or measured pivot and flywheel readiness. Required
controller input and binding checks remain passing. Optional rumble or extra assemblies do not
replace a required check.

The mentor reviews the differential comparison log and both complete swerve routines, two-camera
vision, one derived robot fact, safe interruption, and successful replay with a new output. The
autonomous capstone remains in simulation; the bench project supplies physical mechanism evidence.

During the existing Step 8 mechanism review, discuss the
[Math Behind PID](/badges/badge-2-mechanism-library#the-math-behind-pid): one signed error-rate
calculation, one accumulated-error calculation, and their meaning on the mechanism graph. This is
guided practice, with no separate worksheet or sign-off row. Formal calculus is taught in
[Badge 3](/badges/badge-3-calculus).

The mentor also asks the student to name one library design they would change after using it and
explain the tradeoff. A specific reason matters more than choosing a particular redesign.

## Cross-Step Questions

The student may use notes for these practical-review questions. Answers belong in the student's own
words.

1. **Ownership:** A shooter command wants to change the intake roller directly because it knows the
   shooter is ready. Trace the owning subsystem and show how the readiness fact can influence an
   allowed command.
2. **Frames:** Vision observations are consistently displaced relative to the robot. Name the
   transform and frame evidence to check, then describe a test that distinguishes a sign error from
   using the inverse transform.
3. **Control:** The physical FX, FXS or Nova roller responds differently from its simulation. Name
   two configuration, conversion, supply, or model differences to inspect and the evidence that
   would confirm each.
4. **Autonomous:** Run from the drawn start and from an offset. Explain each follower's inputs,
   progress model, and recovery using the observed logs. Do not assume one follower must fail or
   recover identically in every case.
5. **Java and Tests:** Show a record, callback, or collection from the project. Use the controller
   subclass to explain an override and runtime dispatch. Explain who owns its data, when it is read,
   and one test that could detect a mistake in that behavior.

If an explanation needs work, the mentor reviews the relevant lesson and tries another example.
Completed checks remain complete.

## Assessment and Signature

Use a fresh copy of the [ten-question assessment](/badges/badge-2-pretest). The student scores at
least 18 of 20 without notes or internet. The mentor compares the first and final papers with the
student after scoring the second sitting. For a paper using the temporary 26-point version, retain
that paper and use the questions 1–10 subtotal out of 20; calculus questions do not affect Badge 2
completion.

| # | Work | Done When |
| --- | --- | --- |
| 14.1 | Post-test | The final score is at least 18 of 20 and is recorded beside the initial score, with each test version identified |
| 14.2 | Evidence review | Every current required row in Steps 2–14 is signed and links to evidence in the README; retired and optional rows are excluded |
| 14.3 | Cross-step explanation | The student answers the five practical questions and explains one design improvement |
| 14.4 | Final signature | The mentor records the completion date after confirming the capstone and successful replay |

## After Badge 2

Badge 2 introduces FX, FXS and Nova, includes both CTRE roller simulation paths and the
Nova physics adapter with shared ThriftyNova conversion helpers, and records which
controller was demonstrated physically. Badge 3 refines that foundation with torque-current control,
characterization, advanced sensing and reference work. Before advanced physical FX work, review the
actual fixture and establish or reuse a matching voltage baseline. A student who used Nova or FXS
physically completes that fixture-specific bridge without repeating the controller-introduction
lesson.

The supplied Badge 3 base may contain additional mechanism families and vendor implementations. The
mentor distinguishes those supplied assets from the four families required here. The saved Badge 2
elevator log supports the calculus application.

A student with Badge 2 can begin contributing to FRC 4451's competition code with a mentor.
[State-Driven Robot Code](/frc/why-state-machines) extends composed subsystems into a
superstructure. BLine remains the path-following standard for the next badge.
[Badge 3](/badges/badge-3) continues with mechanism refinement, hardware, object detection,
autonomous acquisition, simulator experiments, and leadership evidence.
