In Step 7, the student expands the working Talon FX roller from [Step 6](/badges/badge-2-first-mechanism) into a library of reusable **components** inside `Badge2Robot`, under `org/<name>/mechanisms/`. A component is a plain Java object that a subsystem owns; it does not extend `SubsystemBase` and does not create commands. Each family gets a component class, an IO boundary, a Talon FX implementation, a Talon FXS implementation, a simulation for each, and one focused test. The five FRC lessons on mechanism components teach the contracts and the arithmetic; this step adds the CTRE implementations and the simulation matrix they do not carry.

Step 6 established the student's first CTRE path. The student now adds the Talon FXS roller, then repeats the understood pattern for the other four families. The hardware pages cover Phoenix Tuner X and the two controllers; the mechanism library is written so the same component runs on either.

## Library Contract

Every family under `org/<name>/mechanisms/<family>/` contains:

- the component class (`Roller`, `Flywheel`, `Pivot`, `Elevator`, `LinearRail`);
- an IO interface (`RollerIO` and so on) with default no-op methods, which is also the replay implementation;
- an AdvantageKit inputs class annotated `@AutoLog`;
- a Talon FX implementation (`RollerIOTalonFX`);
- a Talon FXS implementation (`RollerIOTalonFXS`);
- a Talon FX simulation that extends the Talon FX implementation and drives `TalonFXSimState` (`RollerIOSimTalonFX`);
- a Talon FXS simulation that extends the Talon FXS implementation and drives `TalonFXSSimState` (`RollerIOSimTalonFXS`);
- configuration records that carry units and conversion values (gear reduction, drum radius, rigging, limits, tolerance);
- one focused simulation test.

The component owns mechanism behavior and logging: goals, limits, `atGoal`, and `Logger.processInputs` under a log path the parent subsystem assigns. The IO implementation owns vendor configuration and control requests. Nothing above the IO knows which controller is attached.

The simulation classes follow the [vendor-sim-state pattern](/frc/talonfx-simulation#two-objects-two-jobs): the real IO's constructor runs unchanged, so the same configuration and the same control request run in simulation, and a background loop carries values between the Phoenix sim state and a WPILib physics model. The exact class names are `TalonFXSimState` and `TalonFXSSimState`; nothing in the library is called `TalonFXSim`.

## Voltage Control

Every Badge 2 implementation sends a voltage-output request. Open-loop effort is `VoltageOut`, closed-loop velocity is `VelocityVoltage`, and profiled position is `MotionMagicVoltage`. The [Control Requests](/frc/control-requests#the-grid) lesson describes the torque-current column, and the Rollers lesson offers a torque-current method; Badge 2 leaves both out. Two reasons: `TorqueCurrentFOC` requests need a Pro licence, and CTRE's control documentation states that the Talon FXS does not support them. A library whose Talon FXS implementation could not honour a request its Talon FX implementation accepts is not one library.

| Component | Control behavior | Request | Physics model |
|---|---|---|---|
| Roller | Open-loop effort | `VoltageOut` | `DCMotorSim` |
| Flywheel | Closed-loop angular velocity | `VelocityVoltage` | `FlywheelSim` |
| Pivot | Profiled angular position | `MotionMagicVoltage` | `SingleJointedArmSim`, or `DCMotorSim` for a vertical axis |
| Elevator | Profiled linear position, after conversion | `MotionMagicVoltage` | `ElevatorSim` with gravity |
| Linear rail | Profiled linear position, after conversion | `MotionMagicVoltage` | `ElevatorSim` without gravity |

A roller does not get `MotionMagicVoltage`; it has no position goal. A flywheel is not a position mechanism. The pivot, elevator and rail all send the same request; what differs is the conversion between rotor rotations and the mechanism unit, and the gravity model in `Slot0Configs`.

## Component Behavior

**Roller.** Accepts a voltage and a stop request. Reports position, velocity, applied voltage and current. The student can explain gear reduction, surface speed, output torque and contact force from the [Rollers](/frc/roller-example#calculate-torque-and-contact-force) lesson.

**Flywheel.** Accepts an angular-velocity goal. Reports measured velocity and `atGoal` with an explicit tolerance. The student can explain gear reduction, wheel surface speed, feedforward and stored rotational energy from the [Flywheels](/frc/shooter-example#understand-acceleration-and-stored-energy) lesson. The simulation shows spin-up and coast-down.

**Pivot.** Accepts an angle goal through `MotionMagicVoltage`. Enforces a minimum and a maximum angle before the goal reaches the IO. Supports a horizontal axis with `GravityType.Arm_Cosine` and a nonzero `kG`, and a vertical-axis use, such as a turret, with `kG` of zero. The simulation shows angle, velocity and the gravity response.

**Elevator.** Accepts a distance goal through `MotionMagicVoltage`. Converts motor rotations through the reduction (driven teeth divided by driver teeth) and the drum radius, and includes a rigging factor when the carriage does not move one-to-one with rope travel. Enforces lower and upper travel limits. The simulation shows carriage height and gravity.

**Linear rail.** Accepts a distance goal through `MotionMagicVoltage`. Documents one conversion model from the [Linear Rails](/frc/linear-rail-example) lesson: belt and pulley, chain and sprocket, rack and pinion, or lead screw. Uses a horizontal model with no gravity term. The component's documentation states that a vertical rail is an elevator problem and needs gravity compensation. Enforces retracted and extended limits.

## Talon FXS

The Talon FXS is a separate controller with a motor attached by connector, so its IO sets the `MotorArrangement` before anything else, as the [Talon FXS](/hardware/ctre-talon-fxs#set-the-motor-arrangement-first) page describes. In simulation, `TalonFXSSimState` carries two orientation fields where `TalonFXSimState` has one: `MotorOrientation` for the motor and its commutation sensor, and `ExtSensorOrientation` for an external sensor on the data port. A brushless motor such as the Minion reports rotor position through its commutation sensor, so the sim loop writes `setRawRotorPosition` and `setRotorVelocity` as it does for a Talon FX. A brushed motor with a quadrature or pulse-width encoder on the data port reports through that sensor, so the sim loop writes `setRawQuadraturePosition` and `setQuadratureVelocity`, or `setPulseWidthPosition` and `setPulseWidthVelocity`, and the feedback source in `ExternalFeedbackConfigs` names which. The Badge 2 library uses a brushless arrangement for every Talon FXS implementation, so rotor units apply throughout; the student documents that choice in the README.

## Simulation Checks

For each of the ten controller-and-component combinations, the student shows, on a graph or in a test:

1. Supply voltage enters the vendor sim state (`setSupplyVoltage(RobotController.getBatteryVoltage())`).
2. Motor voltage from the sim state (`getMotorVoltage()`) drives the WPILib physics model.
3. The model's position and velocity return to the sim state in **rotor** units: mechanism value times the reduction.
4. `SensorToMechanismRatio` is applied once, in the device configuration, and nowhere else.
5. Positive output moves the mechanism in the documented positive direction.
6. Each simulation publishes its current draw to the shared simulation owner. That owner sums all active mechanism currents and updates the one robot battery through `BatterySim` and `RoboRioSim.setVInVoltage` once per simulation cycle.
7. The component receives simulated inputs through the same `updateInputs` as on the robot, with no simulation-only branch in component code.

There is one simulated battery for the robot. An individual mechanism notifier must not call `RoboRioSim.setVInVoltage` from its own current alone once several mechanisms exist, because whichever notifier writes last would erase the other loads. Each simulation IO reports its latest current draw. A simulation-level owner, such as the `Badge2Robot` simulation harness, collects those values, passes all active currents to `BatterySim.calculateDefaultBatteryLoadedVoltage(double...)`, and writes the result once. Every device sim state reads that shared battery voltage on its next update.

The ROBOTZ Garage library's `SingleRoller` family in Cobra shows this plumbing and is worth reading for it: `SingleRollerIOSimTalonFX` and `SingleRollerIOSimTalonFXS` are the two sim classes Step 7 asks each family to have.

Its architecture is not the student's library design. In Cobra, `SingleRoller` is the base component and `Flywheel`, `Pivot` and `Elevator` all extend it, so one class carries every mechanism's behavior and each subclass narrows it. The Badge 2 library is five independent families instead, each with its own component, IO and configuration record. The tradeoff is real in both directions: Cobra's chain removes duplication and means a change to `SingleRoller` reaches everything, while five families let a student change the elevator's conversion without reading the flywheel's code. Building them separately first is what makes the tradeoff visible, which is the point of item 12 on the [sign-off](/badges/badge-2-sign-off#final-review).

## Badge Check

<StepsBox title="Mechanism Library Badge Check">

1. From a clean clone, the student runs the library tests (`./gradlew test`). All pass.
2. The student simulates `Badge2Robot` with a test binding for each family and graphs goal, setpoint and measured value for one Talon FX family and one Talon FXS family in AdvantageScope. The measured line follows the profile; `AppliedVoltage` sags as current rises.
3. The mentor picks one family and asks for the conversion from rotor rotations to the mechanism unit, on paper, with the reduction and radius the student configured. The student's number matches the logged value.
4. The mentor asks why every implementation uses voltage control and which request each family sends. The student answers from the table above and names the Talon FXS limitation.
5. The student opens the README capability matrix and shows the class and test behind one cell the mentor chooses.

</StepsBox>
