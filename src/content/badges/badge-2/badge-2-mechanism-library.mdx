Step 8 extends the working roller into four families: roller, flywheel, pivot, and elevator. Each component is a plain Java object with its own IO contract, configuration, logs, and tests. The student completes one family at a time and explains the result before starting the next.

The required library has a general WPILib simulation for each family and the provided-controller roller implementation from Step 7. The FX and FXS roller simulation paths from Step 7 remain required. The student also completes one CTRE pivot simulation to compare a software profile with Motion Magic. Additional hardware adapters are extensions; Badge 2 does not require every family on every controller. Linear rail is outside the required library. The elevator remains required even when no physical elevator is used.

## Library Contract

Each family under `org/<name>/mechanisms/<family>/` contains a component, an IO interface, an `@AutoLog` inputs class, configuration records, a general simulation, and a focused test. The component owns goals, limits, readiness, and logging. The IO owns measurements, actuator requests, and the selected control implementation. Each input snapshot is processed by AdvantageKit before the component reads it.

The parent subsystem supplies a log path and calls the component once per robot loop. The same public methods serve REAL, SIM, and REPLAY. Only the constructor selection changes. A hardware adapter exists only for a controller that has been implemented; selecting an unavailable hardware configuration produces a clear startup failure instead of silently constructing empty IO. Empty IO is the deliberate REPLAY choice.

## Reuse the Configuration Pattern

Extend the [motor configuration pattern from Step 7](/badges/badge-2-first-mechanism#configuration-to-hardware) as each family is added. Keep controller-specific records for settings whose meaning depends on the vendor. Reuse a shared value record only when its units, meaning, and validation agree across the consumers. The required physical adapter remains the provided-controller roller; this exercise does not add another hardware port.

Keep mechanism geometry and operating goals separate from device setup. Elevator drum radius, travel limits, and mass belong with the elevator model or mechanism configuration. CAN identity and supported controller settings belong with the hardware adapter. Give simulation records their model parameters and validate them before constructing the model. The student tests changed validation rules and traces any new setting to the code that consumes it.

## Typed Mechanism Contracts

| Family | Goal | Measurements | General Model |
| --- | --- | --- | --- |
| Roller | `Voltage` | `Angle`, `AngularVelocity`, voltage and current | `DCMotorSim` |
| Flywheel | `AngularVelocity` | Speed, voltage and current | `FlywheelSim` |
| Pivot | `Angle` | Angle, angular velocity, voltage and current | `SingleJointedArmSim` with gravity |
| Elevator | `Distance` | Height, `LinearVelocity`, voltage and current | `ElevatorSim` with gravity |

Limits and tolerances use the same measurement types as their goals. Gear reduction and rigging multipliers are dimensionless. Numeric controller gains carry a written unit convention. Conversion occurs at the numeric model or vendor API boundary.

Before motion tests, the student proves equivalent inputs: 90 degrees and 0.25 rotations produce the same pivot goal; 1 foot and 12 inches produce the same elevator goal. A second assertion checks the number sent across the IO boundary. Typed inputs alone do not catch an incorrect conversion inside the adapter.

## Component Behavior

The roller retains Step 7's voltage and stop behavior. The flywheel accepts a speed goal and reports readiness from measured speed within a named tolerance. After a new goal, readiness reflects the new error. The student plots spin-up and coast-down and distinguishes a requested speed from a measured speed.

The pivot accepts a bounded angle goal. Its general simulation uses a software motion profile, voltage-producing feedback, and arm feedforward. The model's geometry and gravity setting match the chosen axis. The student tests an invalid goal and both finite travel limits before a normal move.

The elevator accepts a bounded height goal, reports measured height and velocity, and includes gravity in its general simulation. Its software profile and feedback produce voltage in the IO implementation. The student documents the starting reference, positive direction, reduction, loaded drum radius, mass, and travel limits. A simulated reference is an initial condition; it is not evidence that a physical elevator has been referenced.

## Software Profile Before Motion Magic

The student first builds a general `PivotIOSim` following [Trapezoidal Motion Profiling](/frc/trapezoidal-motion-profiling). Each update advances one profile, calculates voltage from its intermediate reference and measured state, bounds the voltage, advances the physics once, and publishes the new inputs. The log contains final goal, profile reference, and measured angle as separate signals.

The student then follows [TalonFX Simulation](/frc/talonfx-simulation) to build one CTRE pivot path using Talon FXS or Talon FX in simulation. That IO sends `MotionMagicVoltage`; the device generates the intermediate reference. The student removes the external software profile from that selected path and keeps the same component goals. The selected CTRE pivot can run without that controller attached.

The vendor simulation retains the documented supply, motor-voltage, rotor-feedback, direction, and ratio checks. Reuse the concurrency preparation and update-ownership checks completed for the two CTRE roller simulations in Step 7 before using its 5 ms notifier. The callback uses measured elapsed time and coordinated shared access; logging stays on the main thread. Tests use the vendor's timing procedure and close the notifier and devices. The general simulation keeps its own fixed-step test procedure.

Motion Magic is a CTRE capability. A Nova hardware adapter is not expected to implement it. A student using Nova for the physical roller still completes this separate simulation comparison and explains the difference in ownership.

## Elevator Conversion

The [Elevators](/frc/elevator-example) lesson provides the worked conversion. The student distinguishes motor rotor revolutions, drum revolutions, cable travel, and carriage travel. Let <Equation tex="N" /> be motor revolutions, <Equation tex="G" /> be motor revolutions per drum revolution, <Equation tex="D" /> be effective drum diameter in metres, and <Equation tex="S" /> be carriage travel divided by cable travel. Carriage displacement <Equation tex="h" /> in metres is:

<Equation display tex="h = \frac{N}{G}\,\pi D\,S" />

This equation assumes constant effective diameter and no slip. For direct rigging, <Equation tex="S=1" />. Ten motor revolutions through a 10:1 reduction turn the drum once. With a 0.04 m diameter, carriage travel is approximately 0.126 m. These values are a calculation example, not the physical fixture's settings.

WPILib's geometry-based `ElevatorSim` constructor accepts drum radius in metres. The student converts diameter to radius once, with <Equation tex="r=D/2" />, and identifies that value in the model configuration. The motor rotor's diameter is not the drum diameter. A belt pulley uses its effective pitch diameter; a wound cable uses its loaded drum diameter.

The student predicts and tests three separate changes: double diameter, double reduction, and change the rigging multiplier. For the same motor revolutions, doubling diameter doubles travel; doubling reduction halves travel. The rigging multiplier describes carriage motion relative to cable motion. It also changes the load seen at the drum, so changing a distance conversion alone is not a complete new physics model.

The required dynamic simulation uses direct rigging. Other rigging layouts are checked with conversion calculations; extending the physics to them requires a consistent load and travel model. The student also explains why cable building up in layers changes effective diameter and can make a constant conversion inaccurate.

## Establish a Simulation Baseline

A baseline is a saved configuration that completes a stated test. The mentor helps establish it before the student compares changes.

1. The student records motor model, reduction, inertia or mass, dimensions, gravity, reference, supply, and travel range. A bounded open-loop check establishes direction and conversion first.
2. The student and mentor select a reachable goal, tolerance, and maximum test time. Position moves start with conservative profile velocity and acceleration. Initial integral gain is zero.
3. Following [Feedforward](/frc/feedforward), the student identifies the effort needed for motion or gravity. Flywheel feedforward relates voltage to speed; arm and elevator feedforward account for their different gravity behavior. Gains use the units of the selected loop.
4. The mentor helps add proportional feedback. The student compares goal, profile reference where present, measured response, voltage, and current. Enable state, direction, units, gravity, and output saturation are checked before changing gains.
5. The student saves the configuration and passing log. A change to gearing, diameter, mass, or inertia requires another baseline check. General and vendor-controlled simulations may need different numeric gains; values are not copied without checking their units.

For example, 3 V at 20 rotations per second and 6 V at 40 rotations per second give a two-point slope of 0.15 V per rotation per second. That is an illustrative starting estimate from steady, unsaturated samples. Independent characterization and performance refinement come in Badge 3.

## The Math Behind PID

The student and mentor use a fixed position setpoint to discuss two calculations from [PID Control](/frc/pid-control#the-three-terms). Error is requested position minus measured position.

- Error falling from +0.20 m to +0.10 m in 0.5 s has an average rate of minus 0.20 m/s. For a positive D gain, that decreasing error gives a negative D contribution.
- Error staying at +0.10 m for 2 s adds +0.20 metre-seconds to an accumulation that starts at zero. Later zero error stops further accumulation but does not erase the stored amount.

The student explains the signs and units beside an existing mechanism graph. These are guided calculations, not instructions to enable I or D. Formal derivatives, integrals, and the worksheet remain in Badge 3. The student saves a timestamped elevator log with setpoint, position, and velocity for that later application.

## Simulation Checks

For every required family, tests use the public measurement path, check direction and conversion, and exercise its relevant goal and limit behavior. All active models report current to one battery owner. REPLAY constructs no motor, physics model, or notifier. The capability table distinguishes general simulations, the FX and FXS roller device simulations, selected CTRE pivot simulation, and physical FX, FXS or Nova roller, and unimplemented extensions.
