Step 5 traces how the robot selects its IO and prepares a motor configuration for the roller. The student starts with a validated record, then uses Lombok to generate a builder with named settings. The mode-selection code chooses the IO implementation, and that implementation applies the configuration. AdvantageKit generates the input logging and replay support through a separate annotation processor.

## Before You Start

Complete [Step 4: Hardware Setup and Utilization](/badges/badge-2-hardware). Use the fixture record and observed hardware behavior to explain what the software must configure, request and measure. Review [AdvantageKit](/frc/advantagekit), [Physics in the IO Layer](/frc/physics-in-the-io-layer), [Log Replay](/frc/log-replay), and [Lombok](/frc/lombok).

## Prepare the Bench Project

The mentor supplies `Badge2Bench`, a minimal AdvantageKit robot project with a recorded release, build instructions, mode selection, logging and bounded commands that start stopped. Its devices match the secured fixture recorded in Step 4. Build it unchanged and record its revision. Keep the swerve template's shipped device IDs and constants in simulation.

The student identifies the selected vendor dependency and follows one supplied request to a device call and one sensor value into the log. Compare device identities and configuration values with the Step 4 setup sheet. This is a source-code trace; powered robot-code checks follow in Step 7 after simulation and tests.

## Keep the Boundary Explicit

The component requests mechanism behavior through `RollerIO` and reads logged measurements. The selected adapter owns vendor calls. REAL uses the fixture's controller, SIM selects the general model or a named CTRE device simulation, and REPLAY restores recorded inputs without devices or physics. Swapping the implementation keeps the component contract stable, while supported capabilities and configuration remain explicit.

The student will apply this boundary to `RollerIOTalonFX`, `RollerIOTalonFXS` and, when supplied, `RollerIONova`. The two CTRE adapters also serve their simulation paths. A vendor simulation can wrap or extend its voltage IO adapter, keeping configuration and measurement code shared. Simulation wiring stays inside that path; the component never calls `getSimState()`.

## Guided IO Trace

Start in `KitBotPathPlanner`:

1. Open `Constants.java` and find `currentMode`. On the roboRIO it selects `REAL`; on a desktop it uses the configured simulation mode.
2. Open `RobotContainer.java`. Trace the `REAL`, `SIM`, and `REPLAY` branches to the object each branch constructs.
3. Open `Robot.java`. Match each mode to its logger setup.
4. Draw three short arrows in the evidence notes: mode, constructed IO class, logger source or receiver.

In the 2026 Kit Bot template, the branches construct `DriveIOTalonSRX`, `DriveIOSim`, or an empty `DriveIO() {}`. The logger adds `WPILOGWriter` and `NT4Publisher` for `REAL`, `NT4Publisher` for `SIM`, and a `WPILOGReader` replay source for `REPLAY`.

Repeat the trace in `Badge2Robot`. Its drivetrain uses `ModuleIOTalonFX`, `ModuleIOSim`, or an empty `ModuleIO() {}` in the corresponding branches. The exact surrounding source remains the template version recorded in Step 3.

## Replay a Template Log

Replay needs an existing `.wpilog`; the empty template repository does not supply one. The unmodified v26.0.2 template publishes through NT4 in `SIM` and does not write a simulation log. Use either a short log from a robot running the same template or make the logging-only change below to record a desktop simulation log with the same input schema.

This partial snippet replaces the `SIM` branch of `Robot.java`'s logger setup. The template already imports both receiver classes. Add the writer before `Logger.start()`:

```java
case SIM -> {
    Logger.addDataReceiver(new NT4Publisher());
    Logger.addDataReceiver(new WPILOGWriter("logs"));
}
```

Keep `simMode` set to `SIM`, start **Simulate Robot Code**, drive the template chassis for at least ten seconds, and stop the simulation. The new `.wpilog` appears under the project's `logs/` folder. This change adds a file receiver; it does not change the drivetrain IO classes, logged input fields, or control logic. Record the template release and logging-only change in the evidence notes. Keep this writer in the `SIM` branch for later mechanism and autonomous logs. Add it to both simulation projects when each needs a saved simulation log; it does not belong in the replay branch, which already writes its replay result.

Set `Constants.simMode` to `REPLAY`. Open the original log in AdvantageScope, then start **Simulate Robot Code**. `LogFileUtil.findReplayLog()` first checks `AKIT_LOG_PATH`, then the file open in AdvantageScope, then prompts for a file. The template disables the simulation GUI by default for replay. A successful run reads the original log with `WPILOGReader` and writes a new file with `_sim` added to its name.

Open the replay result in AdvantageScope. Confirm that the original input table is present and that `ReplayOutputs` advances through the whole log. Restore `Constants.simMode` to `SIM` before the next step. This exercise proves the template path with a known log; the student records their own mechanism logs after Step 7 adds a mechanism.

## Extend the Mode Selection

The mechanism components use the same typed interface in every mode. One construction point in `RobotContainer` or a factory selects the implementation. The student records the selected model or controller in run metadata.

| Mode | Required Mechanism Implementation | Evidence |
| --- | --- | --- |
| `REAL` | The provided FX, FXS or Nova roller IO, constructed in `Badge2Bench` | Step 7 physical log and mentor demonstration. |
| `SIM` | General WPILib physics for all four families; required FX and FXS roller device simulations; one CTRE pivot profile comparison | Model configuration, tests, and saved logs in `Badge2Robot`. |
| `REPLAY` | Empty implementation of the same IO interface | Recorded inputs restored by AdvantageKit; no motor, model, or notifier constructed. |

The student traces the bench's REAL mode alongside the template traces. An unavailable physical mechanism has no REAL configuration to select. A startup check reports that unsupported choice instead of silently substituting replay IO. The general simulation is a mechanism model; it is not a claim to emulate Nova firmware.

Before Step 7, the student opens a template inputs class annotated with `@AutoLog`, builds, and locates its generated `InputsAutoLogged` class under the build output. The student identifies how the generated class records and restores input fields. This is AdvantageKit's annotation processing. The motor configuration exercise below uses Lombok to generate a builder for constructing settings. Neither generated output is edited by hand or committed.

## Guided Lombok Example

The task is to describe the provided roller's motor setup in one record and pass it into the IO constructor. The record states the requested configuration; constructing it does not contact or configure a motor. The IO implementation owns the vendor calls that apply it.

Bring the plain `RollerConfig` practice from Step 2 into `Badge2Robot`. Use it as the starting point for one controller-specific record, with the proposed name `TalonFXConfig`, `TalonFXSConfig` or `ThriftyNovaConfig`, matching the fixture chosen in Step 4. Keep the original practice file as evidence. First construct the new record directly and explain each argument. Start with the provided controller's record. In Step 7, add the corresponding FX and FXS records needed for the two CTRE simulations, reusing shared value records only where meanings and units agree.

Use named components for the device ID, reduction, direction, neutral behavior, and the approved current limits the adapter will apply. Define reduction as motor revolutions per mechanism revolution. Distinguish supply current from stator current wherever both are used. Add the feedback selection and, for FXS, motor arrangement required by the fixture. Use explicit units in component names or the project's immutable unit values. Required settings are explicit; each optional setting has a documented default and meaning. Device identity and required selections must not silently inherit an omitted builder value. A boxed ID with a non-null check can distinguish an omitted ID from a valid zero ID; validate its range against the selected controller's documentation.

Keep the record constructor free of hardware creation and vendor calls. It validates required values, finite positive reduction, and the fixture's approved current-limit bounds. Reject an invalid value with a useful message instead of silently increasing a requested current limit. The record contains configuration values; it does not own a motor, mutable control request, or running controller. A record containing a mutable object still shares that object's state, so use small value components for this exercise.

As the constructor gains arguments, add named construction methods with Lombok. Follow [Lombok: Adding It to a Project](/frc/lombok#adding-it-to-a-project) and use the plugin version supported by the recorded template release. Add the `io.freefair.lombok` plugin to `Badge2Robot`, refresh the Java project, and build before adding `@Builder` to the motor configuration record. Replace one direct constructor call with a builder call that supplies the same values. Both constructions must pass through the record's validation and produce equal values.

Lombok's ordinary builder leaves unspecified values at zero, `false`, or `null`. The student identifies what happens if each required setting is omitted and defines defaults only where omission has a deliberate meaning. Records already supply component accessors, so this exercise needs no separate class made only to demonstrate `@Getter`. Do not add `@Data` or generated setters to mechanism state.

Run the `delombok` task, then open the source and its expanded result under `build/delombok/` side by side. Trace `builder()`, one named setting method, and `build()` into the record constructor. Identify the validation written by the student and the construction code generated by Lombok. The generated folder is build output and is not committed.

The record and builder are prepared here without creating hardware. In [Step 7: One Complete Mechanism](/badges/badge-2-first-mechanism#configuration-to-hardware), the student passes the finished record to the selected roller IO constructor and traces each setting into its application. Use the same source revision and compatible Lombok setup in the bench project when transferring that implementation.
