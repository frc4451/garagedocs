In Step 9, the student composes the components from
[Step 8: Mechanism Library](/badges/badge-2-mechanism-library) into an elevator-and-conveyor parent
subsystem and a smaller flywheel-and-feed exercise in `Badge2Bench`.
[Step 11](/badges/badge-2-path-following#bring-the-mechanisms-into-badge2swerve) copies these
parents into `Badge2Swerve` for the autonomous routines. The parent subsystem owns its components,
calls each component's `periodic()` once, assigns the log paths, creates the commands, carries the
WPILib requirement, and coordinates the interlocks between components. Commands belong to the parent
and call component methods; a component never creates a command.

The required elevator assembly follows Riptide's design intent. The flywheel exercise isolates
measured readiness and possession. The pivoting intake below is an optional extension. These are
simulation tasks; the required physical roller work was completed in Step 7.

## Elevator, Pivot, and Conveyor

The first required assembly contains an elevator, a pivot and a conveyor roller. This will be
a recreation of Riptide's `SuperStructure`, which owns an `Elevator`, a coral `Pivot` and 
a `Shooter` roller that pairs an elevator height with a pivot angle in each value of 
its `SuperStructureModes` enum. Riptide's code sets both goals together and reports `isAtMode` 
when both are near; it does not enforce a clearance rule between them. The three interlocks 
below are Badge 2 requirements added on top of that design.

Required interlocks:

- The pivot may leave its starting angle only when the elevator is above a named clearance height.
- The elevator may move below the clearance height only when the pivot is at its starting angle.
- The conveyor may run only at two approved elevator-and-pivot setpoint pairs.
- The approved pairs are named records or enum values, as Riptide's modes are. Placeholder names
  such as `X`, `Y`, `A` and `B` do not appear in the code.
- The conveyor checks measured elevator height and pivot angle against the approved pair tolerances;
  requesting an approved goal is not evidence of reaching it.
- A rejected request stops safely and produces a useful log entry or an `Alert`, naming what was
  requested and which interlock refused it.

"Stops safely" means the component keeps or returns to a defined goal and the conveyor is stopped;
it does not mean the subsystem throws an exception or leaves a goal half-applied.

The interlock tests (rows 8.5 and 8.6) construct each parent with the general WPILib simulation IO
from Step 8. Those models advance one fixed step each time `scheduler.run()` calls the parent's
`periodic()`, and `SimHooks.stepTiming` controls the command timing, so the test decides exactly how
far everything moves. The CTRE device simulations run on their own notifier against Phoenix's
real-time clock and cannot be stepped that way; keep them for the Step 7 and Step 8 device checks.

## Work Through One Clearance Move

For the first simulation, use named example values: `STOWED` is 0.10 m and 0 degrees; `SCORE_LOW` is
0.60 m and 45 degrees. Clearance is 0.30 m, with a staging height of 0.35 m, a height tolerance of
0.01 m and an angle tolerance of 2 degrees. Confirm these values fit the Step 8 simulation ranges.
They are teaching values, not physical fixture settings.

| Phase | Requested Behavior | Measured Condition Before Continuing |
| --- | --- | --- |
| Raise | Hold the pivot at its start; raise to the staging height; stop conveyor. | Elevator is above clearance and at staging height. |
| Position | Hold elevator above clearance; move pivot and elevator to `SCORE_LOW`. | Both measurements match the approved pair within tolerance. |
| Convey | Allow conveyor effort while the approved pair remains measured. | Stop conveyor immediately if either measurement leaves tolerance. |
| Return Pivot | Stop conveyor; keep elevator at or above staging; request the starting angle. | Pivot is within the starting-angle tolerance. |
| Lower | Keep pivot at its start; lower to `STOWED`. | Both measurements match `STOWED`. |

A `Trigger` is a Boolean condition the scheduler can read repeatedly.
[Riptide's `isAtMode()`](https://github.com/frc4451/Riptide2025/blob/main/src/main/java/frc/robot/subsystems/superstructure/SuperStructure.java)
exposes measured readiness this way. Riptide pairs goals; the clearance rules above are the badge's
addition.

This partial snippet belongs in the student's parent subsystem. `elevatorAtStaging()` and
`pivotAtStart()` read measured values with the tolerances above. `requestStaging()`,
`requestScoreLow()` and `holdSafely()` are parent methods that apply the table's goals. Import
WPILib's `Trigger`, `Command` and `Commands`.

```java
private final Trigger clearanceReady = new Trigger(this::elevatorAtStaging);
private final Trigger pivotHome = new Trigger(this::pivotAtStart);

public Command scoreLowCommand() {
  return Commands.sequence(
          runOnce(this::requestStaging),
          Commands.waitUntil(clearanceReady),
          runOnce(this::requestScoreLow),
          Commands.waitUntil(this::atScoreLow))
      .withTimeout(5.0)
      .finallyDo(interrupted -> {
        if (interrupted) holdSafely();
      });
}
```

The parent-created `runOnce` commands carry its requirement, so the sequence owns that parent. The
trigger is a condition inside the sequence; it does not schedule a competing command. Normal
completion retains the approved pair with the conveyor stopped, ready for a separate convey command.
Interruption or timeout invokes the safe holding policy. Use `pivotHome` for the return sequence
before lowering. The student implements that return and a second approved pair independently.

The parent's periodic interlocks remain active throughout the move. A one-time wait is not enough if
clearance is later lost. Refuse or suspend an unsafe goal before sending it to a component, stop the
conveyor, and log the reason. Define `holdSafely()` using the current phase: hold the elevator above
clearance while returning a displaced pivot to its start; do not blindly lower both goals together.
Tests cover interruption in each phase and a measurement that leaves its allowed region. On disable,
actuator effort stops; gravity may still move the model, so disabled motion is not evidence of
active holding.

## Intake to Flywheel

The required version uses one feed roller, one flywheel, and a scripted possession input in a small
parent subsystem. A separate floor-intake mechanism is optional. The historical example explains the
wider arrangement; the student proves the readiness boundary without rebuilding the whole intake
path.

A floor-intake roller, a feed roller and a flywheel, after Ember 2024. Ember split these across
`IntakeSubsystem`, `FeederSubsystem` and `ShooterSubsystem`; its intake and feeder each read a beam
break, the feeder's `setVelocityBeambreakCommand` runs until the beam break is obstructed and so
holds the game piece before the shooter, and the shooter exposes a `shooterNearTarget()` trigger
that is true when both flywheel velocities are within 1 rotation per second of their targets. The
focused Badge 2 version composes the feed roller and flywheel into one parent subsystem built from
the student's `Roller` and `Flywheel` components.

Required behavior:

- A scripted IO input changes from no piece to a piece at the feed roller. An added floor-intake
  roller is an extension.
- The feed roller holds the game piece before the flywheel. A beam break, as in Ember, or a
  simulated boolean input standing in for one, is the hold condition; the parent reads it through an
  IO input.
- The flywheel receives a velocity goal.
- The feed roller stays stopped until the possession input is valid and reports a piece, the
  flywheel reports `atGoal`, and a shoot command is active. A missing or invalid possession input
  refuses feeding.
- Releasing or interrupting the command leaves every component in a defined safe state: rollers
  stopped, flywheel at its documented idle or stopped.

## Draw Measured Position Against the Goal

Add a logged mechanism drawing for the elevator-and-pivot assembly. Follow
[Mechanisms per Subsystem](/frc/mechanisms-per-subsystem) to build its canvas and roots, then
[Measured Against Goal](/frc/measured-against-goal) for two distinguishable chains. One chain uses
measured elevator height and pivot angle; the other uses their goals. Use names and different line
widths as well as color. Convert the typed height and angle only at the drawing API boundary.

Update the drawing from the parent subsystem after its components process their inputs. Record it
with AdvantageKit so it can be inspected from a saved log. Keep ordinary plots of goal, profile
setpoint, and measurement beside the drawing; the drawing shows geometry while the plots show timing
and error.

Request a valid move with the saved baseline constraints. The goal changes before the measurement
reaches it. Pause the log during that movement and explain the gap. Then request a refused
transition and show that the measured mechanism stays within the interlock rules. Do not drive both
drawing chains from the goal accessor; that would conceal a mechanism that never moved.

## Bind the Composed Subsystems

The controller bindings and their tests were built in
[Step 7: One Complete Mechanism](/badges/badge-2-first-mechanism#extend-the-controller-bindings) for
the roller. Bind the same controller to commands from the elevator-assembly and feed parents, using
the same test setup. Keep the interlocks in the parents: a controller request that breaks an
interlock reaches the parent's command and is refused there. If the student completed the optional
rumble extension, bind it to a simulated readiness transition, such as the flywheel reaching its
goal.

The student explains how the Step 6 input processing reaches a composed command and why the parent
subsystem still owns its interlocks.

## Pivoting Intake

This is an optional extension after the required work. It adds no required sign-off row.

A pivot and a roller, after Cobra 2026's `Intake`. That subsystem owns two library components, a
`Pivot` named `endeffector` and a `Flywheel` named `rollers`, names its pivot positions in an
`EndeffectorState` enum (`STARTING`, `DEPLOYED`, `LIFTED`, `SQUEEZE`), calls both components'
`periodic()` from its own, and exposes one command factory per position plus factories that run the
rollers. The [composition lesson](/frc/composing-mechanism-subsystems#build-a-pivoting-intake) has a
version built on the same component types.

Two differences from Cobra to keep in mind. Cobra's roller is typed `Flywheel` because that class
adds velocity control on top of the roller behavior; the Badge 2 version uses the student's
`Roller`, since the intake roller has no velocity goal. Cobra runs its rollers on percent output and
torque current, while Badge 2 uses voltage throughout for the reasons in
[Step 8: Mechanism Library](/badges/badge-2-mechanism-library#voltage-control).

For this extension, the behavior is:

- Named `STOWED`, `INTAKE` and `EJECT` pivot positions, as constants or an enum.
- Roller requests for intake, eject, hold and stop, each a voltage from a named constant.
- A command that deploys the pivot and runs the roller to intake.
- A command that stops the roller and stows the pivot.
- Completion based on the measured pivot angle through `atGoal`, not on a timer.
- One requirement, the parent `Intake`, on every command.

## Badge Check

<StepsBox title="Composition Badge Check">

1. From a clean clone, the student runs the tests. Every interlock test and the unsafe-transition
   test pass.
2. The student simulates `Badge2Bench` and demonstrates each subsystem from controller bindings,
   with AdvantageScope showing component goals and measured values under the parent's log path.
3. The mentor chooses one interlock and asks the student to violate it from the controller. The
   request is refused, the mechanisms hold, and the log or alert names the refused request.
4. The mentor interrupts a running command in the elevator assembly or feed exercise. Every
   component enters its documented safe state.
5. The student opens the saved mechanism drawing, pauses during movement, and explains its
   goal/measurement gap beside the numeric plots.
6. The student operates a composed subsystem from the Step 7 controller bindings, then traces a
   processed input through its binding into the owning parent.
7. The student explains why the components are plain objects and why every command requires the
   parent subsystem, in their own words.

</StepsBox>
