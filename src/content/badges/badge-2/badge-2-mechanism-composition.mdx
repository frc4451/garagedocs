In Step 8, the student composes the components from [Step 7](/badges/badge-2-mechanism-library) into three parent subsystems in `Badge2Robot`. The parent subsystem owns its components, calls each component's `periodic()` once, assigns the log paths, creates the commands, carries the WPILib requirement, and coordinates the interlocks between components. Commands belong to the parent and call component methods; a component never creates a command.

Each example follows the design intent of one FRC 4451 robot. The intent is named and cited; the interlocks are Badge 2's requirements, and where they go past what the cited code does, this page says so.

## Pivoting Intake

A pivot and a roller, after Cobra 2026's `Intake`. That subsystem owns two library components, a `Pivot` named `endeffector` and a `Flywheel` named `rollers`, names its pivot positions in an `EndeffectorState` enum (`STARTING`, `DEPLOYED`, `LIFTED`, `SQUEEZE`), calls both components' `periodic()` from its own, and exposes one command factory per position plus factories that run the rollers. The [composition lesson](/frc/composing-mechanism-subsystems#build-a-pivoting-intake) has a version built on the same component types.

Two differences from Cobra to keep in mind. Cobra's roller is typed `Flywheel` because that class adds velocity control on top of the roller behavior; the Badge 2 version uses the student's `Roller`, since the intake roller has no velocity goal. Cobra runs its rollers on percent output and torque current, while Badge 2 uses voltage throughout for the reasons in [Step 7](/badges/badge-2-mechanism-library#voltage-control).

Required behavior:

- Named `STOWED`, `INTAKE` and `EJECT` pivot positions, as constants or an enum.
- Roller requests for intake, eject, hold and stop, each a voltage from a named constant.
- A command that deploys the pivot and runs the roller to intake.
- A command that stops the roller and stows the pivot.
- Completion based on the measured pivot angle through `atGoal`, not on a timer.
- One requirement, the parent `Intake`, on every command.

## Elevator and Conveyor

An elevator, a pivot and a conveyor roller, after Riptide 2025's `SuperStructure`, which owns an `Elevator`, a coral `Pivot` and a `Shooter` roller and pairs an elevator height with a pivot angle in each value of its `SuperStructureModes` enum. Riptide's code sets both goals together and reports `isAtMode` when both are near; it does not enforce a clearance rule between them. The three interlocks below are Badge 2 requirements added on top of that design.

Required interlocks:

- The pivot may leave its starting angle only when the elevator is above a named clearance height.
- The elevator may move below the clearance height only when the pivot is at its starting angle.
- The conveyor may run only at two approved elevator-and-pivot setpoint pairs.
- The approved pairs are named records or enum values, as Riptide's modes are. Placeholder names such as `X`, `Y`, `A` and `B` do not appear in the code.
- A rejected request stops safely and produces a useful log entry or an `Alert`, naming what was requested and which interlock refused it.

"Stops safely" means the component keeps or returns to a defined goal and the conveyor is stopped; it does not mean the subsystem throws an exception or leaves a goal half-applied.

## Intake to Flywheel

A floor-intake roller, a feed roller and a flywheel, after Ember 2024. Ember split these across `IntakeSubsystem`, `FeederSubsystem` and `ShooterSubsystem`; its intake and feeder each read a beam break, the feeder's `setVelocityBeambreakCommand` runs until the beam break is obstructed and so holds the game piece before the shooter, and the shooter exposes a `shooterNearTarget()` trigger that is true when both flywheel velocities are within 1 rotation per second of their targets. The Badge 2 version composes the same three roles into one parent subsystem built from the student's `Roller` and `Flywheel` components.

Required behavior:

- The floor-intake roller moves the game piece into the system.
- The feed roller holds the game piece before the flywheel. A beam break, as in Ember, or a simulated boolean input standing in for one, is the hold condition; the parent reads it through an IO input.
- The flywheel receives a velocity goal.
- The feed roller stays stopped until the flywheel reports `atGoal` and a shoot command is active.
- Releasing or interrupting the command leaves every component in a defined safe state: rollers stopped, flywheel at its documented idle or stopped.

## Badge Check

<StepsBox title="Composition Badge Check">

1. From a clean clone, the student runs the tests. Every interlock test and the unsafe-transition test pass.
2. The student simulates `Badge2Robot` and demonstrates each subsystem from controller bindings, with AdvantageScope showing component goals and measured values under the parent's log path.
3. The mentor chooses one interlock and asks the student to violate it from the controller. The request is refused, the mechanisms hold, and the log or alert names the refused request.
4. The mentor interrupts a running command (Example C's shoot, or Example A's intake). Every component enters its documented safe state.
5. The student explains why the components are plain objects and why every command requires the parent subsystem, in their own words.

</StepsBox>
