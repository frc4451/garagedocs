In Step 9, the student composes the components from [Step 8: Mechanism Library](/badges/badge-2-mechanism-library) into an elevator-and-conveyor parent subsystem and a smaller flywheel-and-feed exercise in `Badge2Robot`. The parent subsystem owns its components, calls each component's `periodic()` once, assigns the log paths, creates the commands, carries the WPILib requirement, and coordinates the interlocks between components. Commands belong to the parent and call component methods; a component never creates a command.

The required elevator assembly follows Riptide's design intent. The flywheel exercise isolates measured readiness and possession. The pivoting intake below is an optional extension. These are simulation tasks; the required physical roller work was completed in Step 7.

## Elevator and Conveyor

The first required assembly contains an elevator, a pivot and a conveyor roller, after Riptide 2025's `SuperStructure`, which owns an `Elevator`, a coral `Pivot` and a `Shooter` roller and pairs an elevator height with a pivot angle in each value of its `SuperStructureModes` enum. Riptide's code sets both goals together and reports `isAtMode` when both are near; it does not enforce a clearance rule between them. The three interlocks below are Badge 2 requirements added on top of that design.

Required interlocks:

- The pivot may leave its starting angle only when the elevator is above a named clearance height.
- The elevator may move below the clearance height only when the pivot is at its starting angle.
- The conveyor may run only at two approved elevator-and-pivot setpoint pairs.
- The approved pairs are named records or enum values, as Riptide's modes are. Placeholder names such as `X`, `Y`, `A` and `B` do not appear in the code.
- The conveyor checks measured elevator height and pivot angle against the approved pair tolerances; requesting an approved goal is not evidence of reaching it.
- A rejected request stops safely and produces a useful log entry or an `Alert`, naming what was requested and which interlock refused it.

"Stops safely" means the component keeps or returns to a defined goal and the conveyor is stopped; it does not mean the subsystem throws an exception or leaves a goal half-applied.

## Intake to Flywheel

The required version uses one feed roller, one flywheel, and a scripted possession input in a small parent subsystem. A separate floor-intake mechanism is optional. The historical example explains the wider arrangement; the student proves the readiness boundary without rebuilding the whole intake path.

A floor-intake roller, a feed roller and a flywheel, after Ember 2024. Ember split these across `IntakeSubsystem`, `FeederSubsystem` and `ShooterSubsystem`; its intake and feeder each read a beam break, the feeder's `setVelocityBeambreakCommand` runs until the beam break is obstructed and so holds the game piece before the shooter, and the shooter exposes a `shooterNearTarget()` trigger that is true when both flywheel velocities are within 1 rotation per second of their targets. The focused Badge 2 version composes the feed roller and flywheel into one parent subsystem built from the student's `Roller` and `Flywheel` components.

Required behavior:

- A scripted IO input changes from no piece to a piece at the feed roller. An added floor-intake roller is an extension.
- The feed roller holds the game piece before the flywheel. A beam break, as in Ember, or a simulated boolean input standing in for one, is the hold condition; the parent reads it through an IO input.
- The flywheel receives a velocity goal.
- The feed roller stays stopped until the possession input is valid and reports a piece, the flywheel reports `atGoal`, and a shoot command is active. A missing or invalid possession input refuses feeding.
- Releasing or interrupting the command leaves every component in a defined safe state: rollers stopped, flywheel at its documented idle or stopped.

## Draw Measured Position Against the Goal

Add a logged mechanism drawing for the elevator-and-pivot assembly. Follow [Mechanisms per Subsystem](/frc/mechanisms-per-subsystem) to build its canvas and roots, then [Measured Against Goal](/frc/measured-against-goal) for two distinguishable chains. One chain uses measured elevator height and pivot angle; the other uses their goals. Use names and different line widths as well as color. Convert the typed height and angle only at the drawing API boundary.

Update the drawing from the parent subsystem after its components process their inputs. Record it with AdvantageKit so it can be inspected from a saved log. Keep ordinary plots of goal, profile setpoint, and measurement beside the drawing; the drawing shows geometry while the plots show timing and error.

Request a valid move with the saved baseline constraints. The goal changes before the measurement reaches it. Pause the log during that movement and explain the gap. Then request a refused transition and show that the measured mechanism stays within the interlock rules. Do not drive both drawing chains from the goal accessor; that would conceal a mechanism that never moved.

## Extend the Controller Bindings

Reuse the `BadgeCommandXboxController` built in [Step 3: Project Setup](/badges/badge-2-project-architecture#build-a-robot-controller-class) and tested in [Step 6: Testing Fundamentals](/badges/badge-2-testing#test-the-controller-inputs). The processed axes and OOP demonstration are already complete. This step adds commands and driver feedback.

Add `leftX()` returning a `Trigger` whose callback reads whether the processed axis is nonzero. Build and bind it during container setup so the callback reads changing input during scheduler polling.

Override the no-argument `leftTrigger()` to delegate to the inherited overload that takes the configured threshold. The student explains why overriding that signature and calling a different overload are separate Java operations.

Timed rumble is an optional extension. For that extension, add `rumble(strength)` with `Commands.startEnd`: start sets both rumble outputs, and end clears them. Add `rumbleSeconds(strength, seconds)` by applying `withTimeout` to that command. Use a strength between zero and one and a positive duration. Keep one rumble command active at a time in the exercise; these factories do not claim a mechanism subsystem, so subsystem requirements alone will not prevent competing rumble commands.

In `RobotContainer`, use an inherited button and one added trigger to schedule existing parent-subsystem commands. Demonstrate a processed axis setting a roller voltage through a command that requires its parent, with stop behavior on release or interruption. Keep interlocks in the parent. The controller class processes operator input and produces driver feedback; it does not construct mechanisms or reach into their IO. If the student completes the rumble extension, bind it to a simulated readiness transition or another documented feedback event.

### Prove the Behavior

Use `XboxControllerSim` with the controller's underlying HID and notify new input data before polling. Reuse the paused-clock scheduler setup from [Unit Tests in Simulation](/frc/unit-tests-in-simulation). Robot hardware and a physical gamepad are not required.

- Keep the Step 6 axis and runtime-dispatch tests passing.
- Check the added stick trigger at rest and during movement, the analog trigger below and above its configured threshold, and one inherited button binding.
- For the optional rumble extension, schedule timed rumble, inspect both simulated rumble outputs while active, and verify zero after timeout. Repeat with early cancellation and with robot disable. Enable simulated teleop for the active-command checks and restore scheduler, Driver Station, and simulation state during teardown.
- Operate the simulated subsystem through the student's controller class. Show the input, command request, and measured response, then release or interrupt the command and show the documented safe state.

The README links the added bindings, tests, and simulation evidence. The student explains how the Step 3 input processing reaches a command and why the parent subsystem still owns its interlocks.

## Pivoting Intake

This is an optional extension after the required work. It adds no required sign-off row.

A pivot and a roller, after Cobra 2026's `Intake`. That subsystem owns two library components, a `Pivot` named `endeffector` and a `Flywheel` named `rollers`, names its pivot positions in an `EndeffectorState` enum (`STARTING`, `DEPLOYED`, `LIFTED`, `SQUEEZE`), calls both components' `periodic()` from its own, and exposes one command factory per position plus factories that run the rollers. The [composition lesson](/frc/composing-mechanism-subsystems#build-a-pivoting-intake) has a version built on the same component types.

Two differences from Cobra to keep in mind. Cobra's roller is typed `Flywheel` because that class adds velocity control on top of the roller behavior; the Badge 2 version uses the student's `Roller`, since the intake roller has no velocity goal. Cobra runs its rollers on percent output and torque current, while Badge 2 uses voltage throughout for the reasons in [Step 8: Mechanism Library](/badges/badge-2-mechanism-library#voltage-control).

For this extension, the behavior is:

- Named `STOWED`, `INTAKE` and `EJECT` pivot positions, as constants or an enum.
- Roller requests for intake, eject, hold and stop, each a voltage from a named constant.
- A command that deploys the pivot and runs the roller to intake.
- A command that stops the roller and stows the pivot.
- Completion based on the measured pivot angle through `atGoal`, not on a timer.
- One requirement, the parent `Intake`, on every command.

## Badge Check

<StepsBox title="Composition Badge Check">

1. From a clean clone, the student runs the tests. Every interlock test and the unsafe-transition test pass.
2. The student simulates `Badge2Robot` and demonstrates each subsystem from controller bindings, with AdvantageScope showing component goals and measured values under the parent's log path.
3. The mentor chooses one interlock and asks the student to violate it from the controller. The request is refused, the mechanisms hold, and the log or alert names the refused request.
4. The mentor interrupts a running command in the elevator assembly or feed exercise. Every component enters its documented safe state.
5. The student opens the saved mechanism drawing, pauses during movement, and explains its goal/measurement gap beside the numeric plots.
6. The student demonstrates the controller exercise and passing checks, then traces a processed input through its binding into the owning subsystem.
7. The student explains why the components are plain objects and why every command requires the parent subsystem, in their own words.

</StepsBox>
