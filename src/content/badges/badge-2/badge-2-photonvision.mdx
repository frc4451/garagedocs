In Step 12, the student builds a real and a simulated AprilTag vision IO in `Badge2Swerve` and
connects accepted observations to the swerve template's pose estimator. The step reuses the
vocabulary of [Step 10: Pose, Frames, and Odometry](/badges/badge-2-math): the filter is a set of
named predicates, the residual is a vector magnitude, and every rejected observation is logged with
its reason. Object detection is out of scope for Badge 2. Pages that mention it are read for their
AprilTag content only.

## Prepare the Camera Data

The student first completes
[Step 10's camera preparation](/badges/badge-2-math#complete-the-work-in-two-stages), rows 9.6–9.10
and 9.12. This puts 3D transforms and filter calculations beside the camera code that uses them.

Before processing observations, the student reads the `Optional` part of
[Streams](/java/fundamentals/streams#questions-with-short-answers) and practices an empty and a
present `Optional`: the empty value supplies no pose, and the present value is inspected only after
its presence check. The student then collects two observation records in a list, converts the list
to the input array, and explains when the consumer callback runs. Arrays, lists, records, and
callbacks were introduced in the earlier Java work; `Optional` is new here, and this exercise
connects all of them to the vision contract.

Continue the [Vision Worksheet (PDF)](/documents/badges/badge-2/badge-2-vision-worksheet.pdf)
from Step 10. Section 2C covers the camera transform chain; Sections 3 through 5 cover residuals,
filter decisions, per-camera timestamps, and missing poses. The student records predictions before
running code, then completes the final project check with a test or log from the implementation.

Install PhotonLib 2026.3.2 in `Badge2Swerve` from the release's vendordep file,
[`photonlib-v2026.3.2.json`](https://github.com/PhotonVision/photonvision/releases/tag/v2026.3.2).
Do not use the online "latest" vendordep URL: it can serve a 2027 prerelease, which does not build
against WPILib 2026. Record the PhotonLib version in the root README beside the other vendor
versions.

### Architecture

Four classes and a plain Java observation family:

- `AprilTagVision`: the vision subsystem. It owns one IO per camera, calls `updateInputs` and
  `Logger.processInputs` for each, and passes the accepted observations on. It extends
  `VirtualSubsystem`, as Cobra's does; the next section explains why.
- `AprilTagIO`: the data contract. Its `@AutoLog` inputs carry `Observation[]` and
  `RejectedObservation[]` arrays produced during that loop. `Logger.processInputs` records those
  arrays on the robot and restores them from the log during replay. The interface's default
  `updateInputs` method leaves replayed values in place.
- `AprilTagIOPhoton`: one real PhotonVision camera. It owns a `PhotonCamera`, a
  `PhotonPoseEstimator`, the camera's `robotToCamera` transform and the field layout.
- `AprilTagIOPhotonSim`: extends `AprilTagIOPhoton` and adds the camera to a `VisionSystemSim`. The
  real class's constructor runs first, so the estimator, the transform and the filter are the ones
  the robot uses; only the source of pixels changes. This is the
  [vendor-sim-state pattern](/frc/physics-in-the-io-layer#the-vendor-sim-state-pattern) from Step 7,
  applied to a camera.
- Plain Java observation records with the timestamp, pose candidate, tag count, ambiguity, and
  uncertainty the estimator needs. A rejected observation uses an enum for its first failed
  predicate. AdvantageKit serializes custom record arrays as structs when every record component is
  a primitive, enum, struct-compatible WPILib type, or another compatible record. Array-valued
  record components are not supported, so tag IDs or other repeated values use a separate top-level
  array.

`AprilTagIOPhoton` reads every unread result once per loop with `getAllUnreadResults()`. For each
result, `PhotonPoseEstimator` returns an `Optional<EstimatedRobotPose>`: empty when no pose could be
calculated. A present value carries `estimatedPose`, a `Pose3d` in the Field frame, and the result's
timestamp. The observation record keeps that pose; the drivetrain converts it with `toPose2d()` when
it hands the observation to the 2D pose estimator. The implementation may collect results in a
`List` while processing, then converts them to the record arrays stored in the `@AutoLog` inputs.

After `Logger.processInputs` returns, the vision subsystem iterates the restored accepted array and
passes each value to a `Consumer<Observation>`. This ordering makes the same observations flow to
the estimator during replay. The consumer does not drain anything; it offers the observation to a
queue.

As in Cobra, `BobotState` owns that queue. Create the small `BobotState` interface needed now: a
private observation queue, an offer method such as `BobotState.offerVisionObservation(observation)`,
a drain method used only by the drivetrain, and an initialized pose with a getter and a
drivetrain-only update method; the vision subsystem receives `BobotState::offerVisionObservation` as
its `Consumer<Observation>`. [Step 13](/badges/badge-2-robot-state) adds the rest of the class. The
drivetrain is the only class that drains the queue: in its `periodic()`, after the odometry update,
it polls each observation, calls `addVisionMeasurement` once per observation, and then writes its
estimated pose back into `BobotState`. The
[swerve example](/frc/swerve-pose-estimation-example#apply-accepted-observations) shows the drain.

### Run Vision Before the Drivetrain

The vision subsystem has to offer its observations before the drivetrain drains the queue, or every
observation waits a loop. It also has nothing for a command to require: no command should own the
cameras. A [`VirtualSubsystem`](/frc/virtual-subsystem#the-class) gives it a `periodic()` every loop
without registering it with the command scheduler.

1. Write the `VirtualSubsystem` base class from [the lesson](/frc/virtual-subsystem#writing-one):
   its constructor adds the instance to a static list, and a static `runPeriodically()` calls each
   one's `periodic()`.
2. In `Robot.robotPeriodic()`, call `VirtualSubsystem.runPeriodically()` before
   `CommandScheduler.getInstance().run()`. Every virtual subsystem then runs before any scheduler
   subsystem, including the drivetrain.
3. Make `AprilTagVision` extend `VirtualSubsystem` instead of `SubsystemBase`, and construct it once
   in `RobotContainer`.

The drivetrain's `periodic()` runs later in the same loop and drains the observations vision just
offered. [Step 13](/badges/badge-2-robot-state) makes `BobotState` a `VirtualSubsystem` too.

### Filter and Residual

The rejection code names each predicate (`hasTags`, `ambiguityOk`, `onField`, `onFloor`,
`timestampOk`, `residualOk`), calculates the translation residual as
`observed.getTranslation().minus(reference.getTranslation()).getNorm()`, logs the residual for every
observation whether it passes or not, and records the first failed predicate for every rejected one.
The ambiguity and residual limits apply to single-tag observations only. A multi-tag observation
passes both. The residual gate is a Badge 2 addition; Cobra's `AprilTagAlgorithms` uses a single-tag
camera-distance cutoff instead. The badge preserves the single-tag-only policy: several tags solved
together have proved reliable enough in practice, and their distance still raises their uncertainty.
Uncertainty selection is a separate stage after acceptance: the filter decides whether an
observation enters the estimator, and the standard deviations decide how much an accepted one moves
the pose. The student can explain both stages and point at the code for each.

Track the last processed timestamp separately in each camera IO. Use the estimator's time base for
age checks, not wall-clock time. A newer frame can advance that camera's timestamp even if a
geometry predicate rejects it, so an old frame is not reconsidered later. Replay restores the
recorded decisions before publication. No future-timestamp fault exercise is required.

### Simulation

Read these Cobra2026 files alongside the simulation work. Follow how the camera joins the simulated
world, where its configuration comes from, and which class advances the world each loop.

- [`AprilTagIOPhotonSim.java`](https://github.com/frc4451/Cobra2026Private/blob/main/src/main/java/org/robotzgarage/frc2026/subsystems/vision/AprilTagIOPhotonSim.java):
  extends the real camera IO, applies `SimCameraProperties`, constructs `PhotonCameraSim`, and
  registers the camera with its robot-to-camera transform.
- [`VisionConstants.java`](https://github.com/frc4451/Cobra2026Private/blob/main/src/main/java/frc/robot/subsystems/vision/VisionConstants.java):
  defines the shared AprilTag simulation world and selects per-camera configuration.
- [`Robot.java`](https://github.com/frc4451/Cobra2026Private/blob/main/src/main/java/frc/robot/Robot.java):
  adds the field's AprilTags in `simulationInit()`.
- [`AprilTagVision.java`](https://github.com/frc4451/Cobra2026Private/blob/main/src/main/java/org/robotzgarage/frc2026/subsystems/vision/AprilTagVision.java):
  advances the shared world with `aprilTagSim.update(globalPoseSupplier.get())`. Trace this call
  before choosing the update owner in the student's implementation.

`AprilTagIOPhotonSim` uses:

- `VisionSystemSim`, the world: the field's tags and every simulated camera's place on the robot;
- `SimCameraProperties`, one camera's resolution, field of view, frame rate, latency and noise;
- `PhotonCameraSim`, the camera attached to the world;
- the official `AprilTagFieldLayout` for the season;
- a measured or documented `robotToCamera` transform;
- the robot's estimated pose from `BobotState`, passed to `VisionSystemSim.update(pose)` every loop,
  as Cobra's `AprilTagVision` does.

Because the simulated cameras render the field from the estimated pose, the simulation checks
transforms, filtering, logging and the estimator connection. It cannot show vision correcting a
wrong estimate: resetting the estimate moves the simulated cameras with it, and their observations
agree with the wrong pose. That correction is checked on the robot.

A **low-resource option** is required: a configuration flag that calls `enableRawStream(false)` and
`enableProcessedStream(false)` (PhotonLib enables both streams by default) and leaves the wireframe
at its default of off (PhotonLib documents its rendering cost). The student measures robot-loop
timing during a repeatable simulated drive with streams off and records whether the loop stays
within the 20 ms target. AdvantageKit records the timing every loop: `LoggedRobot/FullCycleMS` is
the whole cycle and `LoggedRobot/UserCodeMS` is the robot code's share, both under `RealOutputs` in
a simulation log. Graph `FullCycleMS` for the run and record its maximum. The same run must still
produce AprilTag detections and pose results. The result applies to the measured setup and is not
generalized to every laptop.

### FRC 4451 Reference

The FRC section describes FRC 4451's 2026 vision stack, and this step asks for the same shape: a
maintainable multi-camera AprilTag stack with per-camera configuration, real and simulated IO,
timestamped observations, filtering, uncertainty, logging and estimator integration. Cobra's own
`AprilTagIO`, `AprilTagIOPhoton` and `AprilTagIOPhotonSim` are the model for that shape and are
worth reading. Copying them into the student's project does not satisfy the step; the student writes
the stack in their own package, from the lessons and the vendor documentation.

One place Badge 2 asks for more than Cobra does: `AprilTagIOPhotonSim` there sets
`enableDrawWireframe(true)` and a 10 m sight range with no way to turn the rendering off. Row 11.10
asks the student to make that a configuration choice.

## Badge Check

<StepsBox title="PhotonVision Badge Check">

1. The student simulates `Badge2Swerve` with the streams disabled and drives near a tag.
   AdvantageScope's 2D field shows the camera's pose observations landing on the robot; the 3D field
   shows each camera drawn on the robot where its transform says.
2. The student drives past a single tag and then in view of several, and shows the logged residual
   for both kinds of observation. The mentor tightens the single-tag residual limit below the
   residuals in the log; single-tag observations are then rejected with `residualOk` while multi-tag
   observations are still accepted. The student restores the limit and explains why resetting the
   estimate to a wrong pose would not produce a correction in this simulation.
3. The student opens the log and shows rejected observations with their reasons, then changes one
   filter limit and shows a different predicate rejecting.
4. Before the check, the mentor plants a wrong `robotToCamera` (a swapped sign, or the inverse
   transform). The student finds it on the 3D field, where the camera is drawn in the wrong place or
   facing the wrong way, corrects it, and shows the camera back at the documented mounting position.
   The student explains why the pose observations stayed on the robot in simulation: the same
   transform places the simulated camera and tells the estimator where the camera is, so the two
   errors cancel. On the robot, the camera is where it is bolted, and the same wrong transform moves
   the observations off the robot.
5. The student explains why `AprilTagIOPhotonSim` extends the real implementation instead of copying
   it, and what would go wrong if the simulation had its own filter.

</StepsBox>
