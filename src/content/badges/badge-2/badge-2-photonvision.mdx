In Step 11, the student builds a real and a simulated AprilTag vision IO in `Badge2Robot` and connects accepted observations to the swerve template's pose estimator. The step reuses the vocabulary of [Step 9](/badges/badge-2-math): the filter is a set of named predicates, the residual is a vector magnitude, and every rejected observation is logged with its reason. Object detection is out of scope for Badge 2. Pages that mention it are read for their AprilTag content only.

## Guided Example

Build and test one camera before adding the second. The first pass proves the observation contract, ownership boundary, filter, estimator connection, and simulation update with one name and one transform.

### Architecture

Three classes and a plain Java observation family:

- `AprilTagIO`: the data contract. Its `@AutoLog` inputs carry `Observation[]` and `RejectedObservation[]` arrays produced during that loop. `Logger.processInputs` records those arrays on the robot and restores them from the log during replay. The interface's default `updateInputs` method leaves replayed values in place.
- `AprilTagIOPhoton`: one real PhotonVision camera. It owns a `PhotonCamera`, a `PhotonPoseEstimator`, the camera's `robotToCamera` transform and the field layout.
- `AprilTagIOPhotonSim`: extends `AprilTagIOPhoton` and adds the camera to a `VisionSystemSim`. The real class's constructor runs first, so the estimator, the transform and the filter are the ones the robot uses; only the source of pixels changes. This is the [vendor-sim-state pattern](/frc/physics-in-the-io-layer#the-vendor-sim-state-pattern) from Step 6, applied to a camera.
- Plain Java observation records with the timestamp, pose candidate, tag count, ambiguity, and uncertainty the estimator needs. A rejected observation uses an enum for its first failed predicate. AdvantageKit serializes custom record arrays as structs when every record component is a primitive, enum, struct-compatible WPILib type, or another compatible record. Array-valued record components are not supported, so tag IDs or other repeated values use a separate top-level array.

`AprilTagIOPhoton` reads every unread result once per loop with `getAllUnreadResults()`. Each result becomes an `Optional<Observation>` after pose calculation and filtering. The implementation may collect results in a `List` while processing, then converts them to the record arrays stored in the `@AutoLog` inputs. After `Logger.processInputs` returns, the vision subsystem iterates the restored accepted array and passes each value to a `Consumer<Observation>`. This ordering makes the same observations flow to the estimator during replay. The callback itself does not drain anything. If the integration uses a queue, the drivetrain owns that queue, the consumer appends to it, and the drivetrain drains it before calling `addVisionMeasurement` once per accepted observation, as the [swerve example](/frc/swerve-pose-estimation-example#apply-accepted-observations) does.

### Filter and Residual

The rejection code names each predicate (`hasTags`, `ambiguityOk`, `onField`, `onFloor`, `timestampOk`, `residualOk`), calculates the translation residual as `observed.getTranslation().minus(reference.getTranslation()).getNorm()`, logs the residual for every observation whether it passes or not, and records the first failed predicate for every rejected one. Uncertainty selection is a separate stage after acceptance: the filter decides whether an observation enters the estimator, and the standard deviations decide how much an accepted one moves the pose. The student can explain both stages and point at the code for each.

### Simulation

`AprilTagIOPhotonSim` uses:

- `VisionSystemSim`, the world: the field's tags and every simulated camera's place on the robot;
- `SimCameraProperties`, one camera's resolution, field of view, frame rate, latency and noise;
- `PhotonCameraSim`, the camera attached to the world;
- the official `AprilTagFieldLayout` for the season;
- a measured or documented `robotToCamera` transform;
- the simulated drivetrain's pose, passed to `VisionSystemSim.update(pose)` every loop and kept separate from the estimated pose that vision is correcting.

A **low-resource option** is required: a configuration flag that calls `enableRawStream(false)` and `enableProcessedStream(false)` (PhotonLib enables both streams by default) and leaves the wireframe at its default of off (PhotonLib documents its rendering cost). The student measures robot-loop timing during a repeatable simulated drive with streams off and records whether the loop stays within the 20 ms target. The same run must still produce AprilTag detections and pose results. The result applies to the measured setup and is not generalized to every laptop.

### FRC 4451 Reference

The FRC section describes FRC 4451's 2026 vision stack, and this step asks for the same shape: a maintainable multi-camera AprilTag stack with per-camera configuration, real and simulated IO, timestamped observations, filtering, uncertainty, logging and estimator integration. Cobra's own `AprilTagIO`, `AprilTagIOPhoton` and `AprilTagIOPhotonSim` are the model for that shape and are worth reading. Copying them into the student's project does not satisfy the step; the student writes the stack in their own package, from the lessons and the vendor documentation.

One place Badge 2 asks for more than Cobra does: `AprilTagIOPhotonSim` there sets `enableDrawWireframe(true)` and a 10 m sight range with no way to turn the rendering off. Row 11.10 asks the student to make that a configuration choice.

## Independent Change

After the first camera passes its check, add a second camera with a different name and measured transform. Keep each camera's inputs and logs separate while both publish through the same drivetrain-owned integration boundary.

## Badge Check

<StepsBox title="PhotonVision badge check">

1. The student simulates `Badge2Robot` with the streams disabled and drives near a tag. AdvantageScope's 2D field shows the camera's pose observations landing on the robot; the 3D field shows each camera drawn on the robot where its transform says.
2. The student resets the estimator to a deliberately wrong pose. Accepted observations pull the estimate back; the log shows the residual shrinking.
3. The student opens the log and shows rejected observations with their reasons, then changes one filter limit and shows a different predicate rejecting.
4. Before the check, the mentor plants a wrong `robotToCamera` (a swapped sign, or the inverse transform). The student finds it from the field view, names the symptom, corrects it, and shows the observations landing on the robot again.
5. The student explains why `AprilTagIOPhotonSim` extends the real implementation instead of copying it, and what would go wrong if the simulation had its own filter.

</StepsBox>
