In Step 14, the student integrates the work already in `Badge2Swerve` (the composed mechanisms
copied from `Badge2Bench` in Step 11, the paths, vision and robot state) and explains the data flow
through it. Both swerve routines come from Step 11; the capstone registers them with the chooser and
demonstrates them together with the existing mechanisms, cameras, and derived state. The only added
diagnostic is the output used to prove replay. The project is demonstrated from a clean clone,
twice, without a source change between runs.

The template builds its chooser from `AutoBuilder.buildAutoChooser()`, which lists the PathPlanner
autos. Add the BLine routine as one more option with the chooser's `addOption` method. A command
object can belong to only one composition: registering one object with `NamedCommands` and also
placing it in the BLine sequence throws an error that names the composition. Keep a command factory
when both followers need the same behavior. Call it separately for each API that takes a `Command`;
pass the factory itself only when the API asks for a `Supplier<Command>`. For example, this partial
wiring uses the student's feed-parent factory:

```java
Supplier<Command> makeFeed = feedParent::feedCommand;
NamedCommands.registerCommand("Feed", makeFeed.get());
Command feedInBLine = makeFeed.get();
```

Import `java.util.function.Supplier`, WPILib's `Command`, and PathPlanner's `NamedCommands`. The two
factory calls produce separate objects. Bound their lifetimes using the
[BLine action example](/frc/bline#events); a factory alone does not stop a scheduled action.

Row 13.7 does not use the teleop trigger from Step 13; a surrounding command composition may already
require the Step 9 subsystem, and a trigger that schedules another command on it interrupts the
routine. Put the fact inside the routine: `Commands.either(onTrue, onFalse, fact)` chooses between
two commands when that point in the routine is reached, and `command.onlyIf(fact)` skips one.

Row 13.10 depends on the project keeping the template's replay structure. If a `Timer` read outside
an IO, a random value, or a background thread makes replay differ, the student fixes that boundary
and repeats the replay. A successful replay is required for the badge.

The mentor also checks rows 6.9–6.10 for the physical roller and 6.11–6.12 for the FX/FXS device
simulations. These earlier checks remain required even when the integrated routine selects general
mechanism models. The integrated autonomous demonstration remains simulation-only.

Keep the [controller class](/badges/badge-2-testing#build-a-robot-controller-class) and the
composed-subsystem bindings that
[Step 11](/badges/badge-2-path-following#bring-the-mechanisms-into-badge2swerve) copied into
`Badge2Swerve`. Before the autonomous runs, demonstrate one teleop binding on a composed subsystem
and the defined stop behavior. This reuses the bindings from Step 7 (rows 8.9–8.10) as extended in
Step 9; no additional controller implementation is required.

## Independent Change

Integrate the Step 11 BLine routine without changing its route and action points or the mechanisms,
camera integration, and robot-state interfaces it uses. The chooser must run either existing swerve
routine from the same clean clone. The earlier path-following evidence includes the guided
differential comparison and both complete swerve routines. The physical FX, FXS or Nova roller
evidence remains in the bench project and is reviewed alongside this simulation capstone.

### Data-Flow Explanation

The student explains the data flow, not only runs the program. The chain, in the student's words and
with a file named for each arrow:

```text
simulated hardware
  -> IO inputs
  -> component or subsystem
  -> pose and vision observations
  -> BobotState derived facts
  -> command decision
  -> IO request
  -> simulation state
```

The last arrow closes the loop: the request reaches the selected simulation IO, advances its physics
model through its one owner, and appears in the next loop's inputs. The student names whether that
configuration uses general WPILib control, a CTRE roller device simulation or the CTRE pivot
comparison.

## Badge Check

<StepsBox title="Capstone Badge Check">

1. The mentor clones `<yourname>Badge02` into a new folder and builds `Badge2Swerve`. No edits.
2. The student selects the PathPlanner routine in the chooser, enables autonomous in the Sim GUI,
   and the routine runs to a stop. AdvantageScope shows the path, the mechanism actions, the camera
   observations and the derived state on one timeline.
3. The student selects the BLine routine and runs it the same way, without touching source.
4. The student demonstrates a timeout and a cancellation while the simulated robot remains enabled,
   then the mentor repeats the interruption by disabling. The drivetrain stops, every mechanism
   enters its documented safe state, and no action remains scheduled. Run the routine again to show
   that event flags and commands did not leak from the previous run. The student identifies each
   outcome in the log.
5. The student walks the data-flow chain above from one simulated encoder to the sim state, naming
   the file at each arrow.
6. The student identifies the selected mechanism simulation configuration and explains why replay
   creates no motor or physics objects.
7. The student replays the saved log successfully through the current code in `REPLAY` mode and
   shows the newly recorded output in the replayed log.

</StepsBox>
