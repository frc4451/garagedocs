In Step 12, the student builds one deliberately shared object in `Badge2Robot`: a `BobotState`-style class that stores robot-wide observations and derived facts. It holds the pose, velocity, accepted vision observations, at least one target-relative calculation, and at least one field-zone predicate. It exposes them through narrow getters, records, and `Trigger`s. Mutable collections are copied on entry with `List.copyOf`, and getters return the stored unmodifiable snapshot instead of the caller's list or the drivetrain's queue. A record with another mutable component makes a defensive copy in its constructor and accessor. `BobotState` does not own a motor, component, or subsystem, and nothing calls it to set an output. Subsystems keep their local state (the intake's deployment, the flywheel's readiness), while `BobotState` may combine those facts into a derived readiness condition without setting their motors.

## Guided Example

Start with estimated pose and one fixed field target. Derive the robot-to-target distance once per loop, log the value, expose it through a narrow getter, and build one `Trigger` from a stated range condition.

### What the Object Does

Once per robot loop, through the [`VirtualSubsystem`](/frc/virtual-subsystem#the-class) pattern, the Badge 2 `BobotState`:

- receives the current estimated pose and the robot-relative or field-relative velocity from the drivetrain, which is the only writer of the pose;
- receives accepted vision observations from Step 11; if the integration uses a queue, the drivetrain owns and drains that queue while the vision callback only appends observations;
- calculates at least one target-relative transform or distance (`fieldToHub.relativeTo(fieldToRobot)` and its translation's `getNorm()`, in the [VARC](/frc/varc#what-a-varc-holds) shape);
- calculates at least one field-zone predicate (inside the alliance zone, within shooting range of the hub);
- copies mutable inputs on entry and exposes only narrow values or unmodifiable snapshots, never the drivetrain's queue or a caller-owned mutable collection;
- publishes the derived values to AdvantageKit logs with `Logger.recordOutput`;
- provides one or more `Trigger`s built on derived facts, for `RobotContainer` to bind;
- makes no motor, component or subsystem output call.

The [Why State Machines](/frc/why-state-machines) lesson explains where a full state-driven superstructure would take this next. Badge 2 stops before it: the object derives facts, and commands and triggers decide what to request.

### Lombok Applied on Purpose

Step 3 added Lombok to the project. Here it is used where it removes routine code without hiding a decision:

- `@Builder` constructs immutable configuration or observation records.
- `@Getter` exposes read-only derived state.
- `@NonNull` guards required construction inputs.
- No broad generated setters. A `@Setter` on `BobotState`, if one exists, marks exactly the fields the drivetrain writes and nothing else.
- `./gradlew delombok` runs before the mentor check, and the student reads the generated result.

## Badge Check

The evidence is one trace, in code and in a log.

<StepsBox title="Robot state badge check">

1. The student picks one value that starts at a sensor or simulation input (a module encoder, a gyro, a simulated camera) and traces it through the IO inputs, the pose estimator, into `BobotState`, into a derived fact, into a `Trigger`, and into the command that trigger schedules, pointing at each line of code.
2. The student opens a saved log and shows the same trace: the input, the pose, the derived value, the trigger's state and the command's start, on one AdvantageScope timeline.
3. The student runs `./gradlew delombok` and shows the generated code for one `@Builder` record and one `@Getter`.
4. The mentor names a value and asks whether it belongs in `BobotState` or in a subsystem. The student answers with the three tests from [Adding to it without ruining it](/frc/bobot-state#adding-to-it-without-ruining-it).
5. The mentor asks what happens if a command calls a setter on `BobotState` to "fix" the pose. The student explains why the log would stop explaining the robot.

</StepsBox>
