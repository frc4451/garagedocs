Step 7 builds one roller from a command to a measured response. The student first proves the component in simulation, then runs the same component on the provided Talon FX, Talon FXS or Thrifty Nova. The mentor helps with the first setup and asks the student to explain one independent change.

Complete [Testing Fundamentals](/badges/badge-2-testing) and the [hardware preparation in Step 4](/badges/badge-2-hardware#complete-the-setup-sheet). Talon FX is one of the supported Badge 2 physical routes. The drivetrain template remains a simulation project; the mechanism's physical check uses the mentor-provided bench project prepared in [Step 5](/badges/badge-2-io-and-generated-code#prepare-the-bench-project).

## Prepare for Simulation

The student distinguishes a general physics model from a simulated vendor device. All students implement a general roller plus Talon FX and Talon FXS vendor simulation paths. Those paths exchange device output and sensor feedback with physics; they do not prove wiring, mechanical assembly or physical configuration. No Nova firmware-simulation API is assumed for this curriculum's recorded release.

The two CTRE simulations use corresponding FX and FXS voltage IO adapters even when Nova is supplied physically. Each configuration runs separately with its documented motor model, reduction and sensor arrangement. Extra physical controller ports and additional mechanism-by-controller combinations remain extensions.

## Guided Example

The student builds the roller under `org/<name>/mechanisms/roller/` in `Badge2Robot`. These are proposed student class names:

- `Roller` owns the requested voltage, stop behavior, cached measurements, and log path.
- `RollerIO` defines requests and the input snapshot.
- `RollerIOInputsAutoLogged` is generated from the inputs class annotated with `@AutoLog`.
- `RollerIOSim` implements the interface using WPILib's `DCMotorSim`.
- `RollerIOTalonFX` and `RollerIOTalonFXS` supply the voltage IO used by the required CTRE simulations; the supplied physical controller selects one of those or `RollerIONova`.
- `RollerIOSimTalonFX` and `RollerIOSimTalonFXS` connect those adapters to their corresponding simulated device and physics model.
- `RollerTest` checks behavior through the same measurements that the component reads.

The component is a plain Java object. A small parent subsystem calls its `periodic()` once per robot loop and gives its commands one WPILib requirement. Step 9 extends that ownership pattern. The component contains no vendor imports and does not create a motor controller or a command.

## Start with the Physics Model

`RollerIOSim` owns a `DCMotorSim` configured with the selected motor model, reduction, and load inertia. The student uses `Voltage` for requests, `Angle` for position, `AngularVelocity` for speed, and `Current` for current. Numeric conversions belong at the model or vendor boundary. For example, a voltage becomes a number in volts only when a method needs that number.

On each 20 ms input update, the simulation applies the bounded voltage request, advances the model once, and copies its measurements into the inputs. Disabled operation applies zero voltage. The student identifies that one update owner; advancing the same model again in `simulationPeriodic()` would advance its motion twice.

The simulation reports current draw to one robot-level battery owner. That owner sums the active mechanism loads, calculates loaded voltage with `BatterySim`, and updates `RoboRioSim.setVInVoltage` once per cycle. Each model reads the shared supply on its next update. A component does not overwrite the battery with its own load alone.

The first demonstration is positive voltage, reverse voltage, stop, and disable. Positive voltage should produce positive measured velocity under the documented direction convention. Stop removes applied effort; a roller may continue coasting. A second run changes reduction or inertia after the student predicts the effect.

## IO and Logging

`Roller.periodic()` calls `io.updateInputs(inputs)` and then `Logger.processInputs(logPath, inputs)`. The component reads the resulting snapshot. In REPLAY, the empty IO constructs no hardware or physics, and AdvantageKit restores recorded measurements before the component uses them.

The student logs requested voltage separately from feedback. The input record identifies position, velocity, supply information, current, device status, and whether an applied-voltage value is measured or estimated. Unsupported feedback has an explicit validity flag or documented absence. A requested voltage copied into a feedback field does not establish the motor's applied voltage.

## Configuration to Hardware

Carry the tested motor configuration record from Steps 5 and 6 into the roller implementation. The proposed constructor is `RollerIOTalonFX(TalonFXConfig config)`, `RollerIOTalonFXS(TalonFXSConfig config)` or `RollerIONova(ThriftyNovaConfig config)`. The robot's construction code supplies the fixture's named settings through the builder and passes the completed record into that constructor. The component continues to depend only on `RollerIO`.

Before constructing or enabling the hardware, the student and mentor compare those settings with the Step 4 fixture record. The IO constructs the device and translates the record into the pinned vendor API's configuration calls. For every required setting, keep an evidence table with the record component, units, application point, and available readback or physical check. A setting controlled only through a vendor tool is identified in the fixture record; an unused record field does not count as an applied setting. Apply and verify configuration using the selected release's documented status or readback support, report failure clearly, and keep output disabled until the startup checks pass.

The student traces one setting from the builder method through constructor validation to its application and observed result. Building the record prepares values; constructing and initializing the IO applies them. Normal voltage commands and measurements still pass through the existing IO methods and logged inputs.

`RollerIOSim` receives its own model configuration, including motor model, reduction, and inertia. Shared physical values agree with the hardware setup, but a simulation record does not need a CAN ID. REPLAY constructs neither motor nor model. Record the selected configuration values or a reproducible configuration revision with the run evidence so the logs can be compared later.

Copy the vendor-independent component and selected physical IO from `Badge2Robot` into `Badge2Bench`, preserving package names and recording the source revision. Carry its configuration record and compatible Lombok setup with it. Rebuild the bench project after each deliberate transfer; it constructs only the actual fixture devices.

## Implement the Provided Controller

The student reads all three controller introductions. Implement FX and FXS voltage adapters for their simulation paths and the supplied-controller route for the physical check. One physical controller demonstration is required; physical demonstrations on additional controllers are extensions.

For Talon FX and Talon FXS, the IO configures the actual motor and feedback arrangement, direction, current limits and reduction. FXS additionally requires its supported motor arrangement to be selected explicitly. The voltage request uses `VoltageOut`. The student explains whether a reported position is already in mechanism units before applying another reduction. The device and the component must not both divide the same measurement by the reduction.

For Thrifty Nova, the IO uses the pinned ThriftyLib release and the motor selection established with Thrifty Config. The student identifies the encoder source and checks its position and velocity units against that release. The mentor reviews one rotation-to-mechanism conversion before the powered check.

Nova's documented `setPercent` request is a fraction of output, not volts. For a release whose selected adapter uses percent output, the student implements voltage compensation at the IO boundary: read the supply voltage, reject a nonfinite or nonpositive supply, clamp the voltage request to the approved bound and available supply, then divide it by supply voltage to obtain a fraction between minus one and one. Invalid input produces zero output and a recorded fault. Stop sends zero. The student records the source of the supply reading; using roboRIO battery voltage is an approximation of the controller's supply. Requested duty multiplied by that supply is an estimated output, and the log names it accordingly.

The student tests that conversion independently: a 3 V request with a 12 V supply produces a 0.25 fraction; the same request at 10 V produces 0.30. The negative cases preserve direction. A zero or invalid supply produces zero, and a request beyond the configured bound is limited. If the pinned release provides a verified native voltage method, the student can use it and cite that exact API instead. A numeric voltage is never passed unchanged to `setPercent`.

## Simulation Loop

First prove the general `RollerIOSim` and its fixed 20 ms update. Then follow [TalonFX Simulation](/frc/talonfx-simulation), including its FXS section, to implement both `RollerIOSimTalonFX` and `RollerIOSimTalonFXS`. These are required paths for every student, including a student using Nova physically. They reuse the matching voltage IO configuration and measurement code. Apply the Step 6 constructor/builder validation tests to any configuration records added for these adapters. Select one path at a time; do not advance several models for one roller.

For each CTRE path, record the supported device/motor arrangement, supply, reduction, direction and model inertia. Read the device's simulated motor voltage into the physics model, advance that model through one owner, and feed rotor position and velocity back through the appropriate `SimState`. The general model's mechanism-side rotation must be converted to rotor rotation with the documented reduction; the device then applies its configured feedback ratio. Check the orientation and avoid applying the reduction twice.

Before using a background notifier, complete [Threads and Concurrency](/java/fundamentals/threads-and-concurrency) and [Race Conditions and Synchronization](/java/fundamentals/race-conditions-and-synchronization). Follow the reference's vendor timing procedure, measure elapsed time, coordinate shared-state access and log on the main thread. Close the notifier and device resources after the run. The general simulation retains its separate fixed-step procedure.

For both CTRE paths, demonstrate positive voltage, reverse voltage, stop, disable, and a changed reduction. Record requested and device-reported output, rotor feedback and mechanism measurements with units. Predict the conversion before running. Compare each result with a general model using matching motor and load parameters; FX and FXS may use different motors, so equal traces between those devices are not an acceptance criterion.

These simulations establish the IO/device/physics connection and its tests. The physical demonstration establishes the actual fixture behavior. The general WPILib model does not emulate Nova firmware, and no Nova-specific simulation API is required.

## First Test

The student initializes the WPILib test environment as described in [Unit Tests in Simulation](/frc/unit-tests-in-simulation), supplies enabled or disabled Driver Station state, and advances the general model through its normal 20 ms path. A fixed-step general model does not need Phoenix's real-time device test setup. Both required CTRE simulations use the vendor's documented timing procedure separately. Run their checks with distinct device identities and clean up every device and notifier after each test.

The assertions read cached inputs or public component accessors. They check positive and negative motion, zero applied effort after stop, and zero applied effort while disabled. Each test restores Driver Station and battery state and closes resources it created. The test also checks the reduction and unit conversion using expected values calculated before running.

## Check the Result

The mentor and student complete the Step 4 fixture record before applying power. The mechanism is secured, its travel is clear, its limits are configured, and the mentor identifies the disable operator and power disconnect. The student deploys only the bench project configured for the actual fixture. The simulated swerve template's device IDs and constants are not a bench configuration.

The student demonstrates a bounded positive request, stops, then demonstrates a bounded reverse request. The mentor checks motor direction and feedback direction separately. Controller bindings then prove stop on release, interruption, and disable. The student saves the physical log and compares requested effort, measured speed, and available current and supply readings with the simulation log.

An unexpected sign or scale is a reason to stop and check configuration and conversion. The mentor helps identify the cause; the student repeats the affected check after the correction. A successful vendor-tool or Motor Runner test does not replace the robot-code demonstration.

## Independent Change

The student changes reduction or inertia in simulation, predicts the result, and explains the saved comparison. On the physical fixture, the mentor selects a permitted output bound or command duration to change. The student predicts and demonstrates that change without altering unrelated configuration.

## Badge Check

<StepsBox title="One Complete Mechanism Badge Check">

1. The student builds from a clean clone and runs the general, FX and FXS simulation checks and conversion tests, naming each selected implementation.
2. The student traces a builder setting through record validation, the selected IO constructor, and its application evidence, then traces a command through the component, measurement, and log.
3. The student shows the simulation prediction and explains the changed response.
4. With the mentor, the student runs the physical checks using the recorded fixture configuration.
5. The mentor selects a signal from the physical log. The student explains its units, source, and whether it is measured or estimated.
6. The student explains what the simulation established and what required the physical check.

</StepsBox>
