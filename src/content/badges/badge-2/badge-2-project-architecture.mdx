Step 3 creates the repository and applies Java inheritance in a student-written driver-controller class. The student starts two separate GradleRIO projects from AdvantageKit's 2026 templates, records where each project came from, and copies the completed Java practice into the repository.

## Before You Start

Complete [Step 2: Java Foundations](/badges/badge-2-java) first. Keep the local `Badge2JavaPractice` folder until the copied version has been checked inside the repository.

Review [GitHub Remotes](/tools/github-remotes), [Cobra Repository Tour](/frc/cobra-repository-tour), and the setup sections of the [AdvantageKit Kit Bot template](https://docs.advantagekit.org/getting-started/template-projects/kitbot-template/) and [TalonFX(S) swerve template](https://docs.advantagekit.org/getting-started/template-projects/talonfx-swerve-template/).

Before driving the swerve template, read [Tank and Swerve](/frc/tank-and-swerve). It introduces steering modules and forward, sideways, and turning requests. The remaining Drivetrain Fundamentals lessons supply the worked calculations during Step 10; setup here asks the student to build and drive the supplied template.

Create the repository outside a synchronized OneDrive folder. Open each GradleRIO project as its own folder in WPILib VS Code. The WPILib build and simulation commands act on the project folder that is open.

The root `README.md` records the exact AdvantageKit release tag and template name for both projects, the WPILib 2026 patch version, and the vendor versions preserved in `vendordeps/`. Keep those versions fixed while comparing mechanism behavior. It also contains one evidence table for the full badge. Each row links to the folder, source file, test, log, or explanation that satisfies the requirement. Later steps add rows to the same table.

## Guided Setup

Use a WPILib 2026-compatible AdvantageKit release linked by the template documentation. Do not copy the current contents of a moving default branch and describe them as a release. For each downloaded project:

1. Preserve the template's Gradle wrapper, `vendordeps/`, source tree, and license files.
2. Set the FRC team number where the template instructions specify it.
3. Open the project folder in WPILib VS Code and run **Build Robot Code** before making structural changes.
4. Run **Simulate Robot Code** and confirm the template starts with its shipped simulation constants.
5. Record the template name, release tag, download URL, and first successful build date in the root README.

For `Badge2Robot`, the shipped `generated/TunerConstants.java` describes a specific robot and is sufficient for every Badge 2 simulation row. A student who later deploys to a real swerve chassis generates constants for that chassis with Phoenix Tuner X as the template instructions describe. Physical swerve setup is outside Badge 2.

## Build a Robot Controller Class

The student recreates a focused part of Cobra's [GarageCommandXboxController](https://github.com/frc4451/Cobra2026Private/blob/main/src/main/java/org/robotzgarage/frc2026/util/GarageCommandXboxController.java) in `Badge2Robot`. This connects Java inheritance to a robot behavior the student can operate and test. Review [Inheritance](/java/fundamentals/inheritance), [Runtime Polymorphism](/java/fundamentals/runtime-polymorphism), and [RobotContainer and Bindings](/frc/robot-container-and-bindings) first.

Cobra's class extends `CommandXboxController`, overrides stick getters to apply a deadband, adds sign-preserving squared getters and stick-motion triggers, changes the default trigger threshold, and supplies rumble commands. The student builds a smaller `BadgeCommandXboxController` in the project's own utility package. Step 3 implements two processed stick axes and demonstrates their Java behavior. Step 6 adds automated input tests. Step 9 adds command bindings and a configured analog-trigger threshold. Timed rumble is an optional extension. Four-axis coverage and repeating rumble are also optional.

### Follow One Input

With the mentor, trace Cobra's left-X path from `super.getLeftX()` through the private deadband helper to `getLeftX()` and `getLeftXSquared()`. A deadband removes small inputs around center; WPILib's `MathUtil.applyDeadband` also rescales the remaining range. Squaring with `Math.abs(value) * value` preserves direction while reducing intermediate magnitudes.

The student then writes the corresponding left-X behavior in their own class:

1. Extend `CommandXboxController` and pass the Driver Station port to `super(port)` in the constructor. Keep deadband and trigger threshold in named constants or validated constructor configuration.
2. Override `getLeftX()` with `@Override`, reading the parent implementation through `super.getLeftX()` and applying the deadband once. Calling the overriding method from inside itself would recurse.
3. Add `getLeftXSquared()` using the already processed getter and a private sign-preserving helper. Keep the raw, deadbanded, and squared values distinguishable in the demonstration; do not apply another deadband in the consumer.

Use an illustrative deadband of 0.10 for the check. Raw inputs 0.05 and -0.05 produce zero. Raw inputs 0.55 and -0.55 produce approximately 0.50 and -0.50 after rescaling, then 0.25 and -0.25 after signed squaring. A tolerance-based assertion handles floating-point rounding. The values are dimensionless controller inputs; conversion to a mechanism's typed voltage request belongs at the command boundary.

### Independent Controller Change

Add the same deadband and signed-squaring behavior for left Y without copying the complete Cobra class. Use private helpers to keep the shared input policy in one place.

Finally, assign the same controller object to a variable declared as `CommandXboxController`. Calling `getLeftX()` through that variable still runs the student's override. The student explains this runtime dispatch and why the added `getLeftXSquared()` method is unavailable through that declared type without changing the reference type. The mentor then asks which method would need updating if the deadband changed.

### Show the Inputs

After the unmodified template builds and simulates, create one instance of the student controller on a documented Driver Station port. Use simulated joystick inputs and temporary diagnostic output to compare the raw HID value, processed getter, and squared getter. Demonstrate centered input, both signs, the deadband boundary, and full-scale input on both axes. No physical gamepad or new mechanism is required. Keep the template's drive bindings working; inspect its existing input shaping before connecting processed axes so the deadband is not applied twice.

Record the source and observed values in the README. This step checks the implementation and explanation interactively. [Step 6: Testing Fundamentals](/badges/badge-2-testing#test-the-controller-inputs) turns those observations into automated assertions, and [Step 9: Mechanism Composition](/badges/badge-2-mechanism-composition#extend-the-controller-bindings) uses the controller with the student's subsystems.

## Badge Check

A **clean clone** is a fresh copy of the repository in a new folder. Building from one proves that the repository contains the files another student needs.

<StepsBox title="Project Setup Badge Check">

1. The student clones `<yourname>Badge02` into a new folder and compiles `java-practice/ConfigPractice.java` there.
2. The student opens `KitBotPathPlanner` from the clean clone. **Build Robot Code** and **Simulate Robot Code** succeed with no edits.
3. The student opens `Badge2Robot` from the same clone. **Build Robot Code** succeeds with no edits, and **Simulate Robot Code** drives the swerve chassis from a controller in the Sim GUI.
4. The student opens the root README and shows the template name, exact release tag, and source link for each project.
5. The student demonstrates the controller inputs and predicts a getter call through a parent-typed reference, then verifies the result.
6. The mentor chooses one completed evidence row. The student follows its link to the named file or result.

</StepsBox>

If a clean clone fails to build, start with the first error. Check whether a source file or `vendordeps/` JSON was omitted, whether both computers use the same WPILib release, and whether a dependency download needs network access.
