In Step 9, the student connects selected Java lessons to the pose, path, and vision code used in Steps 10 through 12. [Discrete Math Foundations](/java/fundamentals/java-discrete-math) supplies the language for a **filter**: a set of observations, each admitted only when every predicate is true. [Vector Math](/java/fundamentals/java-vector-math) supplies the language for a **residual**: the vector from a reference position to an observed one, and its magnitude. [Pose Geometry](/frc/pose-geometry) supplies the WPILib types used to express those ideas. These Java lessons are reviewed here, when the project first needs them, instead of as a separate survey of every Java topic.

Start with [Tank to Swerve](#tank-to-swerve) to connect the familiar Kit Bot drivetrain to the swerve project. Then use the geometry, filter, and odometry work below to explain the measurements both drivetrains produce.

### A Vision Filter Is a Set of Predicates

A PhotonVision camera produces a stream of candidate robot poses. Only the ones the robot can trust reach the pose estimator. In the language of [sets](/java/fundamentals/java-discrete-math#sets), the accepted observations are a subset of all observations, and membership is decided by predicates. An observation is in the accepted set only when every required predicate is true:

| Predicate | True when |
|---|---|
| `hasTags` | The observation used at least one AprilTag |
| `ambiguityOk` | The single-tag ambiguity is below the configured limit; a multi-tag observation passes by definition |
| `onField` | The estimated position is inside the field boundary |
| `onFloor` | The estimated height is plausible for a robot on the carpet |
| `timestampOk` | The timestamp is newer than the last accepted one and inside the estimator's usable history |
| `residualOk` | The translation residual is below the configured gate |

`accepted = hasTags ∧ ambiguityOk ∧ onField ∧ onFloor ∧ timestampOk ∧ residualOk`. Written as Boolean logic the rule is one line; written as code it is one method that returns the **first predicate that failed**, or nothing. Logging that name is what lets a student open a log and say why a sample was thrown out. The discrete-math lesson's [relations and functions](/java/fundamentals/java-discrete-math#cartesian-products-and-relations) describe the same thing: the filter is a function from observations to `{accepted, rejected-for-reason}`. Its [probability](/java/fundamentals/java-discrete-math#probability-and-expected-value) section explains why a gate is not proof: an observation that passes every predicate can still be wrong, and the estimator's uncertainty weights, not the filter, decide how much an accepted observation moves the pose. The introductory lesson does not derive WPILib's estimator, and this step does not ask the student to.

### A Residual Is a Vector

The **residual** is the difference between where the camera says the robot is and where the reference (odometry, or the current estimate) says it is. In the language of [Vector Math](/java/fundamentals/java-vector-math#points-and-displacement-vectors):

1. Both positions are points in the Field frame, in metres.
2. Their difference, observed minus reference, is a displacement vector, `referenceToObserved`.
3. Its [magnitude](/java/fundamentals/java-vector-math#magnitude-and-normalization) is the translation error, a single distance.
4. Normalize it only when the code needs the direction without the distance; the residual gate does not.
5. A [dot product](/java/fundamentals/java-vector-math#dot-products) answers a later question, such as whether the residual points along the robot's motion or across it.
6. The frame and the unit stay attached to the vector's name and its log key.

The residual threshold is a gate whose limit can depend on observation quality. The code logs the residual whether the sample passes or fails so the student can inspect the chosen limit against the tag count, distance, and resulting estimate.

### Vector Ideas in WPILib Types

The student does not write a vector class for the robot; WPILib supplies the translation and geometry types below. What the Vector Math lesson taught by hand appears in them like this:

| Vector-math idea | WPILib representation | Odometry use |
|---|---|---|
| Two components in a named frame | `Translation2d` | Robot position on the field, or displacement between two positions |
| Vector subtraction | `end.getTranslation().minus(start.getTranslation())` | Translation change, or a vision residual |
| Vector magnitude | `translation.getNorm()` | Distance travelled, or residual size |
| Scaling | `translation.times(scale)` | Scale a displacement without changing its direction |
| Rotating a vector | `translation.rotateBy(rotation)` | Convert a translation between orientations |
| Orientation | `Rotation2d` | Robot heading from the gyro or the pose estimate |
| Position plus orientation | `Pose2d` | The robot's estimated state on the field |
| Finite change in position and orientation | `Transform2d` | The difference between two poses, or a change applied to a pose |
| Small motion along an arc | `Twist2d` | The increment odometry integrates with the pose exponential |
| Velocity components in a named frame | `ChassisSpeeds` | Robot-relative or field-relative motion for drive control and estimation |

The boundaries matter as much as the correspondences:

- A `Translation2d` behaves like a two-dimensional vector, and its meaning still depends on the named frame. `fieldToRobot.getTranslation()` and `robotToCamera.getTranslation()` are both `Translation2d`; the axes differ.
- A `Rotation2d` is an orientation or an angular change. It is not a two-component vector, even though it stores a cosine and a sine.
- A `Pose2d` is a state: a translation and a rotation from a fixed frame.
- A `Transform2d` is the finite change that connects two poses.
- A `Twist2d` is a small body-frame motion, integrated along an arc.
- `ChassisSpeeds` is a rate. It is not a position or a displacement, and dividing a `Twist2d` by the loop time is how one becomes the other.

### Measures and Geometry

WPILib has two families that both hold numbers with meaning. A **measure** is a physical amount with a unit. A **geometry type** is a position, orientation or change in a named frame. The units API holds the first, the geometry types hold the second, and the conversion happens once, at the edge where a distance becomes a coordinate:

| Type family | Meaning | Examples |
|---|---|---|
| Units and measures | A physical amount with a unit | `Distance`, `Angle`, `AngularVelocity`, `Voltage`, `Current` |
| Translation | Position offset or displacement without orientation | `Translation2d`, `Translation3d` |
| Rotation | Orientation or angular change | `Rotation2d`, `Rotation3d` |
| Transform | Change from one pose or frame to another | `Transform2d`, `Transform3d` |
| Pose | Position and orientation together | `Pose2d`, `Pose3d` |

An elevator's height is a `Distance`. A camera's place on the robot is a `Transform3d`. A tag's place on the field is a `Pose3d`. The mount height inside that transform was measured as a `Distance` and converted once, with `.in(Meters)`, when the transform was built. [Math Toolbox: Units and Interpolation](/frc/math-toolbox-units-and-interpolation#the-units-library) has the convert-at-the-edge rule.

### From Encoders to a Pose

The vector operations describe the values that flow through WPILib's odometry. The student uses the library classes and reads the numbers:

1. Encoders measure wheel or module motion.
2. Kinematics converts those measurements into robot motion (`DifferentialDriveKinematics` or `SwerveDriveKinematics`).
3. The gyro supplies the heading, or constrains it.
4. Odometry integrates the measured change into a new `Pose2d`: `DifferentialDriveOdometry.update(gyroAngle, leftMeters, rightMeters)` for the Kit Bot; `SwerveDriveOdometry.update(gyroAngle, modulePositions)` for the swerve robot.
5. A pose estimator (`DifferentialDrivePoseEstimator`, `SwerveDrivePoseEstimator`) starts from that odometry result and can apply timestamped vision corrections.
6. The vision filter compares a new observation with the reference pose by subtracting translations and measuring the residual vector.

Students use WPILib's tested geometry, kinematics, odometry and estimator classes. The vector work explains the values moving through those APIs and helps the student catch a frame, sign or unit error. It is not an instruction to replace odometry with handwritten integration.

## Badge Check

The evidence is a small runnable check in `Badge2Robot`: a JUnit test under `src/test/java`, as [Unit Tests in Simulation](/frc/unit-tests-in-simulation#where-tests-live-and-how-they-run) sets one up, or a `main` method the student runs from VS Code. The expected numbers are written in the test before the code runs.

<StepsBox title="Pose and motion badge check">

1. The student opens the check and shows the expected values written as literals beside each assertion, with the frame named in each variable.
2. The check runs green. It contains one differential odometry update and one swerve odometry update, each from stated wheel or module values and a gyro angle.
3. The check contains at least one accepted observation, at least one rejected observation with its failed predicate named, and one calculated translation residual.
4. The mentor changes one input (a wheel distance, a module position, the gyro angle, a pose, a transform, or a filter limit) and asks the student to predict the new result before running the check again.
5. The student explains, in the words of this page, what a residual is, what the gate does, and why passing the gate is not proof the observation is correct.

</StepsBox>
