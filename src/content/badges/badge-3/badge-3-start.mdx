The student starts from the mentor-supplied `Badge3Starter`, the same recorded source every student
receives, and completes the full migration in an individual fork; the Starter itself stays
unchanged. The migration rebuilds Cobra's reusable code in the ROBOTZ Garage library's new package,
`org.robotzgarage.frc2027`. Step 1 traces the code and plans the work; the migration itself proceeds
across Steps 3–12. Students can collaborate on review and experiments; each student owns every
required change in their own fork.

Badge 2 or mentor-verified equivalent work is the prerequisite. Badge 2 supplies:

- four general simulated mechanism families: roller, flywheel, pivot, and elevator
- a physical roller demonstrated on the supplied FX, FXS or Nova fixture, FX and FXS roller device
  simulations, and a SimThriftyNova physics adapter
- configuration records and builders
- 2D mechanism drawings and a CTRE pivot profile comparison
- composition, two-camera AprilTag IO, robot state, paths, tests, and replay

The Starter also contains vendor adapters that Cobra does not construct, such as
`SingleRollerIONova`. The student explains the parts each step uses. Supplied code does not count as
the student's evidence, and the student does not need to have learned it in Badge 2. The Starter's
simulation constants describe a teaching model; each physical fixture gets its own measured
settings.

## Start with the Diagnostic

The mentor gives the [Written Checks](/badges/badge-3-written-checks) diagnostic before instruction.
It has no passing score; its result shows which topics the student should practice. The mentor keeps
the correction record open while the student learns those topics. After Step 14, the student scores
100% on an independent mastery attempt using an equivalent form (the same questions with changed
numbers and scenarios). The separate 100% final follows in Step 15. The technical steps start
without waiting for either attempt, and a mistake on a written check does not erase practical rows
already completed.

## Establish the Baseline

1. Obtain `Badge3Starter` from the mentor, create the student's fork, and clone it to a local folder
   outside OneDrive, as the Starter README directs. Change no code yet. Record the release, Java
   version, WPILib version, and vendordeps in the fork's README.
2. Open `README.md` and `BASELINE.md` in the clone. The Starter's current source keeps the
   pre-migration API and robot logic; the README lists its dated revisions.
   `WORKING-SOURCE-MANIFEST.json` records its current hashes; `SOURCE-MANIFEST.json` is the
   historical record of the original files.
3. Run the verification command in the README. It tests that source with build metadata explicitly
   marked as non-release and runs 50 disabled simulation loops. Save its test report and log.
4. Inspect the baseline log and record its exact scope. A disabled startup check shows that the code
   starts; it says nothing about an autonomous path.
5. Change the fork's project name, preserve the original version record, and create the evidence
   directory. Keep the baseline logs for later comparisons.

Then record an enabled baseline: from the unchanged code, run the selected autonomous routine in
simulation ([Autonomous Simulation](/frc/autonomous-simulation)), and record the routine, mode,
initial pose, enabled duration, outcome, and requested versus measured traces in the fork. Until
that run exists, the README marks the enabled baseline as pending; the disabled check does not stand
in for it.

## Read the Migration Target

`Badge2MechanismReference`, supplied by the mentor, is the finished Badge 2 bench solution, and it
remains available for comparison throughout the migration. Its `RobotContainer` shows the target
wiring: it chooses each mechanism's configuration record once, from the robot mode, and passes that
record to both the IO adapter and the subsystem, as in
`ElevatorSubsystem(ElevatorConfig, ElevatorIO)`.
[Bench Integration](/badges/badge-2-mechanism-library#bench-integration) describes that project's
layout.

In the Starter, Cobra's reusable code is in the ROBOTZ Garage library's `org.robotzgarage.frc2026`
package; [The Two Packages](/frc/cobra-repository-tour#the-two-packages) explains the split. Across
Steps 3–12, the student moves active reusable code to the ROBOTZ Garage library,
`org.robotzgarage.frc2027`. The fork keeps the original `org.robotzgarage.frc2026` classes alongside
the migrated library until the student retires them. The drivetrain and robot-specific shooting
policy stay in the robot project.

Begin by tracing one roller, the feeder tower, with
[One Mechanism, End to End](/frc/cobra-repository-tour#one-mechanism-end-to-end) as the reading
guide. In the fork, follow `Feeder.runFeederVoltage()` into the tower. Cobra builds the tower as a
`Flywheel`, which extends `SingleRoller`, so `runVolts()` is the inherited
`SingleRoller.runVolts()`. A class named `Flywheel` that only receives effort requests is still a
roller. Continue to the `SingleRollerIO` contract and the two tower adapters that `RobotContainer`
constructs. In REAL it builds `SingleRollerIOTalonFX` from `FeederConstants.towerConfig`; in SIM it
builds `SingleRollerIOSimTalonFX` from `FeederConstants.towerConfigSim`, a record made from
`towerConfig` plus the motor model and moment of inertia.
[Constructing Subsystems](/frc/robot-container-and-bindings#constructing-subsystems) explains that
`switch`.

When the student migrates this roller, each mechanism family stays an explicit type, and a
mechanism's commands go in the subsystem that owns it, as the tower's commands live in `Feeder`. Add
abstractions only when they make that path easier to explain.

## First Readiness Experiment

Before the mechanism steps, find out how Cobra decides it is ready to feed. In the fork, open
`RobotContainer.java` and find the operator controller's (port 1) A-button binding.
[Composing Triggers](/frc/robot-container-and-bindings#composing-triggers) explains its form:
holding A starts `feeder.runFeederVoltage()` while `BobotState.shouldStopFeedingFuelToShooter()` is
false, and `onFalse` stops the feeder when A is released or `shouldStopFeedingFuelToShooter()`
becomes true. Read that condition in `bobot_state/BobotState.java`, with
[Zones and Game Logic as Triggers](/frc/bobot-state#zones-and-game-logic-as-triggers) beside it. It
checks the field zone, the shooter's position relative to the hub, and trench proximity
(`isNearTrench`). Teleop feeding never reads the measured flywheel speed or hood angle.

Then open `autonomous/AutonomousManager.java` and read `handleInterpolateShooterToHub`, using
[Waiting Without Blocking](/frc/command-groups#waiting-without-blocking) for its
`Commands.waitUntil`. Autonomous waits until the robot is far enough from the hub and
`Shooter.isNearHubVelocity` reports the flywheel within 2 rotations per second of its interpolated
speed, then feeds until the shot's time runs out. It checks once: a speed drop after feeding starts
does not stop the feeder.

Record, for each feed path (teleop and autonomous), which measurements permit feeding and which are
ignored. Predict what happens when the operator holds A before the flywheel reaches speed, and when
the flywheel slows during an autonomous shot. Once the enabled baseline above is recorded, check one
prediction in simulation.

For the autonomous prediction, follow
[Autonomous Simulation](/frc/autonomous-simulation). For the teleop prediction, map a keyboard or
USB controller to joystick slot 1 in the Sim GUI
([The Sim GUI](/frc/running-the-simulator#the-sim-gui)) and enable Teleoperated; Keyboard 0's `Z`
key is button 1, which the Xbox controller class reads as A.

Graph these keys from the enabled simulation run on one time axis. The names are written as they
appear in the Starter's log:

- `//Feeder/Tower/AppliedVoltage`: the tower's applied voltage, an input logged by
  `SingleRoller.periodic()`.
- `/RealOutputs//Shooter/Shooter/Leader/VelocityRPS` and
  `/RealOutputs//Shooter/Shooter/VelocitySetpointRPS`: the measured and requested flywheel speed in
  rotations per second, recorded by `FlywheelFollower.periodic()`.
- `/RealOutputs/BobotState/Zoning/ShouldStopFeeding`: the teleop feed condition.

The doubled slash comes from the leading slash in Cobra's subsystem names, such as `"/Feeder"`.
These are observations of the supplied code, not hardware settings.

For the B3-01.2 independent change, add one readiness condition to one feed path in the fork, such
as a settling time before the autonomous wait ends, and make no other change. Predict the new feed
time, run the related test or simulation, and save a comparison with the unchanged enabled baseline.
Step 9 turns the same question into subsystem-owned states with refusal reasons, and that evidence
extends into B3-09.2.

## Plan the Work

For each step, the student records the supplied behavior, planned change, relevant files,
anticipated result, and evidence location. Record simulation configuration separately from hardware
configuration. Define an acceptable error, settling interval, overshoot, and repeatability target
before tuning; use units and describe how each quantity will be measured. List the equipment and
hardware appointments each physical demonstration needs, and which steps depend on one another.

Compare `WORKING-SOURCE-MANIFEST.json` and the Starter README with the current site requirements.
Record which files are supplied, which the student changes, and which belong to optional extensions.
Preserve both manifests. Where an older packet disagrees with the site, attach the
[curriculum revision record](/badges/badge-3-sign-off#curriculum-revision-record); the current
required outcomes govern completion.

The mentor provides Talon FX hardware for the advanced Badge 3 work. Badge 2 introduced the Talon FX
and covered FXS and Nova setup and the two CTRE roller simulation paths. At entry, the mentor
reviews the student's Badge 2 physical motor controller and saved physical voltage baseline. Before
each advanced physical demonstration, the student completes the
[setup sheet](/badges/badge-3-hardware#complete-the-setup-sheet) for that fixture and the relevant
simulation checks. The student reuses a matching physical FX voltage baseline or establishes one on
the actual fixture before current-control comparisons. These checks happen as each mechanism is
ready; Step 13 reviews them at the end.

Open the [leadership requirements](/badges/badge-3-review) now. Plan opportunities to diagnose a
saved run, review code, and help a Badge 1 or 2 student. Record evidence as those opportunities
occur.

## Badge Check

S means simulation, W means written reasoning, and M means mentor-observed review. The student
records an evidence link and an explanation in the student's own words for each row in the fork's
README. The mentor asks the student to explain a change and its result, checks each row, then signs
and dates the step on the [sign-off sheet](/documents/badges/badge-3/badge-3-sign-off.pdf).

| Row | Work | Done When |
| --- | --- | --- |
| B3-01.1 | Diagnostic and correction | W/M: Record the initial diagnostic at entry, correct missed reasoning during instruction, and score 100% on an independent mastery attempt on an equivalent form after Step 14. The row closes before the separate Step 15 final. |
| B3-01.2 | Preserve and explain the base | S/M: Build the supplied release, run its baseline checks, explain configuration and ownership, and record the starting version before Step 3 begins the individual migration. Predict and demonstrate one independent readiness condition in the student's fork. |
| B3-01.3 | Plan the work | W/M: Identify supplied behavior, planned changes and their files, anticipated results, performance targets with units, equipment and hardware appointments, dependencies between steps, leadership opportunities, and evidence locations. |

## For the Mentor

The Starter has no migrated test suite. The mentor solution, `Badge3MentorSolution`, is the worked
answer to this badge; `TRAINING-MATERIALS.md` maps each step to its reference file and test, and the
focused `curriculum-reference` examples stay mentor-side.

After the student records their own readiness condition and predictions, compare them with
`frc.robot.subsystems.feeder.FeedPolicy` and `FeedPolicyTest` in `Badge3MentorSolution`.
`TRAINING-MATERIALS.md` maps this experiment to those files; the test holds the policy's cases and
expected outcomes. Run it from the mentor solution's folder:

```powershell
.\gradlew.bat test --tests "*FeedPolicyTest"
```

```sh
./gradlew test --tests "*FeedPolicyTest"
```
