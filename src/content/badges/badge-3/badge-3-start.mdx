The student starts with the mentor-supplied `Badge3Starter`, preserves that baseline, and completes
the full migration in an individual fork. Collaborate on review and experiments while retaining
individual ownership of every required change. Everyone begins from the same recorded source.

Badge 2 or mentor-verified equivalent work is the prerequisite. Badge 2 supplies four general
simulated mechanism families, including an elevator, one provided-controller roller, FX and FXS
roller device simulations, a Nova roller approximation, configuration records and builders, 2D
mechanism drawings, a CTRE pivot profile comparison, composition, two-camera AprilTag IO, robot
state, paths, tests, and replay. The supplied Cobra base may also contain other assemblies and
vendor adapters. The student explains the parts each step uses; supplied code is neither student
evidence nor an extra Badge 2 prerequisite. Its simulation constants describe a teaching model, and
each physical fixture gets its own measured settings.

## Start with the Diagnostic

The mentor administers [Written Checks](/badges/badge-3-written-checks) before instruction. The
initial result identifies topics to practice. Keep the correction record open while the student
learns the assessed topics. Complete the independent equivalent mastery attempt at 100% after the
relevant instruction, before the separate 100% final in Step 15. The technical lessons start without
waiting for either attempt. A mistake does not erase practical rows already completed.

## Establish the Baseline

1. Obtain `Badge3Starter` from the mentor. Record the release, Java version, WPILib version, and
   vendordeps in the student's README. Use a local folder outside OneDrive, as the Starter README
   directs.
2. Open `Badge3Starter/README.md` and `BASELINE.md`. The working copy keeps the pre-migration API
   and robot logic; the README lists its dated revisions. `WORKING-SOURCE-MANIFEST.json` records
   its current hashes; `SOURCE-MANIFEST.json` is the historical record of the original files. Run
   the verification command in the README. It tests the working copy with explicitly non-release
   build metadata and runs 50 disabled simulation loops. Save its test report and log.
3. Inspect the baseline log and record its exact scope. A disabled startup check shows that the
   code starts; it says nothing about an autonomous path. Before comparing an autonomous change,
   record the selected routine, mode, initial pose, enabled duration, outcome, and requested versus
   measured traces in the student fork. Keep that enabled baseline pending until it has been
   observed.
4. Create the student fork and working copy. Change its project name, preserve the original version
   record, and establish an evidence directory. Keep baseline logs for later comparisons.

The independent change for B3-01.2 is the readiness condition in
[First Readiness Experiment](/badges/badge-3-start#first-readiness-experiment) below: one bounded
change to an interlock in the student copy. Make only that one change. Predict its effect, run the
related test or simulation, and save a comparison with the unchanged baseline.

`Badge2MechanismReference`, supplied by the mentor, is the finished Badge 2 bench solution, and it
remains available for comparison throughout the migration. Its `RobotContainer` shows the target
wiring: it chooses each mechanism's configuration record once, from the robot mode, and passes that
record to both the IO adapter and the subsystem, as in `ElevatorSubsystem(ElevatorConfig,
ElevatorIO)`. [Bench Integration](/badges/badge-2-mechanism-library#bench-integration) describes
that project's layout.

The Starter's reusable code is in Cobra's `org.robotzgarage.frc2026` package;
[The Two Packages](/frc/cobra-repository-tour#the-two-packages) explains the split. Move active
reusable code to the ROBOTZ Garage library's new package, `org.robotzgarage.frc2027`. Keep
drivetrain and robot-specific shooting policy in the robot project.

Begin with one roller, using
[One Mechanism, End to End](/frc/cobra-repository-tour#one-mechanism-end-to-end) as the reading
guide. In the fork, follow `Feeder.runFeederVoltage()` into the tower. Cobra builds the tower as a
`Flywheel`, which extends `SingleRoller`, so `runVolts()` is the inherited
`SingleRoller.runVolts()`. Continue to the `SingleRollerIO` contract and the two tower adapters that
`RobotContainer` constructs. In REAL it builds `SingleRollerIOTalonFX` from
`FeederConstants.towerConfig`; in SIM it builds `SingleRollerIOSimTalonFX` from
`FeederConstants.towerConfigSim`, a record made from `towerConfig` plus the motor model and moment
of inertia. [Constructing Subsystems](/frc/robot-container-and-bindings#constructing-subsystems)
explains that `switch`. A class named `Flywheel` that only receives effort requests is still a
roller. Keep each family explicit and place commands in its parent subsystem. Add abstractions only
when they make that path easier to explain.

## Plan the Work

For each module, the student records the supplied behavior, planned change, relevant files,
anticipated result, and evidence location. Record simulation configuration separately from hardware
configuration. Define an acceptable error, settling interval, overshoot, and repeatability target
before tuning; use units and describe how each quantity will be measured.

Talon FX hardware remains provided for advanced Badge 3 work. Its introduction, FXS and Nova setup,
and the two CTRE roller simulation paths belong to Badge 2. Review the student's selected physical
controller and saved baseline at entry. Before each advanced physical demonstration, complete the
[fixture-specific preparation](/badges/badge-3-hardware#complete-the-setup-sheet) and relevant
simulation checks. Reuse a matching physical FX voltage baseline or establish one on the actual
fixture before current-control comparisons. Do these checks as each mechanism is ready; Step 13
reviews them at the end.

Open the [leadership requirements](/badges/badge-3-review) now. Plan opportunities to diagnose a
saved run, review code, and help a Badge 1 or 2 student. Record evidence as those opportunities
occur.

Compare `WORKING-SOURCE-MANIFEST.json` and the Starter README with the current site
requirements. Record which files are supplied, which the
student changes, and which belong to optional extensions. Preserve both manifests. Where an older
packet disagrees with the site, attach the
[site revision record](/badges/badge-3-sign-off#curriculum-revision-record); the current required
outcomes govern completion.

## First Readiness Experiment

Before the mechanism steps, find out how Cobra decides it is ready to feed. In the fork, open
`RobotContainer.java` and find the operator controller's (port 1) A-button binding.
[Composing Triggers](/frc/robot-container-and-bindings#composing-triggers) explains its form:
holding A starts `feeder.runFeederVoltage()` while `BobotState.shouldStopFeedingFuelToShooter()` is
false, and `onFalse` stops the feeder when either condition changes. Read that condition in
`bobot_state/BobotState.java`, with
[Zones and Game Logic as Triggers](/frc/bobot-state#zones-and-game-logic-as-triggers) beside it. It
checks the field zone, the shooter's position relative to the hub, and trench proximity
(`isNearTrench`). Teleop feeding never reads the measured flywheel speed or hood angle.

Then open `autonomous/AutonomousManager.java` and read `handleInterpolateShooterToHub`, using
[Waiting Without Blocking](/frc/command-groups#waiting-without-blocking) for its
`Commands.waitUntil`. Autonomous waits until the robot is far enough from the hub and
`Shooter.isNearHubVelocity` reports the flywheel within 2 rotations per second of its interpolated
speed, then feeds until the shot's time runs out. It checks once: a speed drop after feeding starts
does not stop the feeder.

Record, for each path, which measurements permit feeding and which are ignored. Predict what happens
when the operator holds A before the flywheel reaches speed, and when the flywheel slows during an
autonomous shot. Once the enabled baseline above is recorded, check one prediction in simulation,
following [Autonomous Simulation](/frc/autonomous-simulation) for the autonomous run. Graph these
Starter log keys on one time axis, written as they appear in the Starter's own baseline log:

- `//Feeder/Tower/AppliedVoltage`: the tower's applied voltage, an input logged by
  `SingleRoller.periodic()`.
- `/RealOutputs//Shooter/Shooter/Leader/VelocityRPS` and
  `/RealOutputs//Shooter/Shooter/VelocitySetpointRPS`: the measured and requested flywheel speed in
  rotations per second, recorded by `FlywheelFollower.periodic()`.
- `/RealOutputs/BobotState/Zoning/ShouldStopFeeding`: the teleop feed condition.

The doubled slash comes from the leading slash in Cobra's subsystem names, such as `"/Feeder"`.
These are observations of the supplied code, not hardware settings.

This readiness condition is the B3-01.2 independent change. Add one readiness condition to a copy of
one path, such as a settling time before the autonomous wait ends, and predict the new feed time
before running it. Step 9 turns the same question into subsystem-owned states with refusal reasons,
and that evidence extends into B3-09.2.

## Badge Check

S means simulation, H means hardware, W means written reasoning, and M means mentor-observed review.
The student records an evidence link, an explanation in the student's own words, the mentor's
signature, and the date for each row. The mentor asks the
student to explain a change and its result before signing.

| Row | Work | Done When |
| --- | --- | --- |
| B3-01.1 | Diagnostic and correction | W/M: Record the initial diagnostic at entry; correct reasoning through instruction and complete an independent equivalent 100% mastery attempt after the assessed topics. This row closes before the separate final, not before Step 2. |
| B3-01.2 | Preserve and explain the base | S/M: Build the supplied release, run its baseline checks, explain configuration and ownership, and record the starting version before starting the individual migration. Predict and demonstrate one independent core change in the student copy. |
| B3-01.3 | Plan the work | W/M: Identify supplied behavior, assessed changes, equipment, performance targets, dependencies and evidence locations. |

## For the Mentor

The Starter has no migrated test suite. The mentor solution, `Badge3MentorSolution`, is the worked
answer to this badge; `TRAINING-MATERIALS.md` maps each step to its reference file and test, and the
focused `curriculum-reference` examples stay mentor-side.

After the student records their own readiness design and predictions, compare it with
`frc.robot.subsystems.feeder.FeedPolicy` and `FeedPolicyTest` in `Badge3MentorSolution`.
`TRAINING-MATERIALS.md` maps this experiment to those files; the test holds the policy's cases and
expected outcomes. Run it from the mentor solution's folder:
