The student starts with the mentor-supplied `Badge3Starter`, preserves that baseline, and completes
the full migration in an individual fork. Collaborate on review and experiments while retaining
individual ownership of every required change. Everyone begins from the same recorded source.

Badge 2 or mentor-verified equivalent work is the prerequisite. Badge 2 supplies four general
simulated mechanism families, including an elevator, one provided-controller roller, FX and FXS
roller device simulations, a Nova roller approximation, configuration records and builders, 2D
mechanism drawings, a CTRE pivot profile comparison, composition, two-camera AprilTag IO, robot
state, paths, tests, and replay. The supplied Cobra base may also contain other assemblies and
vendor adapters. The student explains the parts each step uses; supplied code is neither student
evidence nor an extra Badge 2 prerequisite. Its simulation constants describe a teaching model, and
each physical fixture gets its own measured settings.

## Start with the Diagnostic

The mentor administers [Written Checks](/badges/badge-3-written-checks) before instruction. The
initial result identifies topics to practice. Keep the correction record open while the student
learns the assessed topics. Complete the independent equivalent mastery attempt at 100% after the
relevant instruction, before the separate 100% final in Step 15. The technical lessons start without
waiting for either attempt. A mistake does not erase practical rows already completed.

## Establish the Baseline

1. Obtain `Badge3Starter` from the mentor. Record the release, Java version, WPILib version, and
   vendordeps in the student's README. Use a local folder outside OneDrive, as the Starter README
   directs.
2. Open `Badge3Starter/README.md` and `BASELINE.md`. The working copy keeps the pre-migration API
   and robot logic; the README lists its dated revisions. `WORKING-SOURCE-MANIFEST.json` records
   its current hashes; `SOURCE-MANIFEST.json` is the historical record of the original files. Run
   the verification command in the README. It tests the working copy with explicitly non-release
   build metadata and runs 50 disabled simulation loops. Save its test report and log.
3. Inspect the baseline log and record its exact scope. A disabled startup check shows that the
   code starts; it says nothing about an autonomous path. Before comparing an autonomous change,
   record the selected routine, mode, initial pose, enabled duration, outcome, and requested versus
   measured traces in the student fork. Keep that enabled baseline pending until it has been
   observed.
4. Create the student fork and working copy. Change its project name, preserve the original version
   record, and establish an evidence directory. Keep baseline logs for later comparisons.

Make one bounded independent change to a core mechanism configuration or interlock in the student
copy. Predict its effect, run the related test or simulation, and save a comparison with the
unchanged baseline. Choose a change the student can explain from the core code alone.

The completed `Badge2MechanismReference`, supplied by the mentor, remains available for comparison
throughout the migration.

Move active reusable code to `org.robotzgarage.frc2027`. Keep drivetrain and robot-specific shooting
policy in the robot project. Begin with one roller: in the fork, follow
`Feeder.runFeederVoltage()` into the tower. Cobra builds the tower as a `Flywheel`, which extends
`SingleRoller`, so `runVolts()` is the inherited `SingleRoller.runVolts()`. Continue to the
`SingleRollerIO` contract, then `SingleRollerIOTalonFX`, which `RobotContainer` constructs from
`FeederConstants.towerConfig`. A class named `Flywheel` that only receives effort requests is still
a roller. Keep each family explicit and place commands in its parent subsystem. Add abstractions
only when they make that path easier to explain.

## Plan the Work

For each module, the student records the supplied behavior, planned change, relevant files,
anticipated result, and evidence location. Record simulation configuration separately from hardware
configuration. Define an acceptable error, settling interval, overshoot, and repeatability target
before tuning; use units and describe how each quantity will be measured.

Talon FX hardware remains provided for advanced Badge 3 work. Its introduction, FXS and Nova setup,
and the two CTRE roller simulation paths belong to Badge 2. Review the student's selected physical
controller and saved baseline at entry. Before each advanced physical demonstration, complete the
[fixture-specific preparation](/badges/badge-3-hardware#complete-the-setup-sheet) and relevant
simulation checks. Reuse a matching physical FX voltage baseline or establish one on the actual
fixture before current-control comparisons. Do these checks as each mechanism is ready; Step 13
reviews them at the end.

Open the [leadership requirements](/badges/badge-3-review) now. Plan opportunities to diagnose a
saved run, review code, and help a Badge 1 or 2 student. Record evidence as those opportunities
occur.

Compare `WORKING-SOURCE-MANIFEST.json` and the Starter README with the current site
requirements. Record which files are supplied, which the
student changes, and which belong to optional extensions. Preserve both manifests. Where an older
packet disagrees with the site, attach the
[site revision record](/badges/badge-3-sign-off#curriculum-revision-record); the current required
outcomes govern completion.

## First Readiness Experiment

Before the mechanism steps, find out how Cobra decides it is ready to feed. In the fork, open
`RobotContainer.java` and find the A-button binding. It runs `feeder.runFeederVoltage()` whenever
`BobotState.shouldStopFeedingFuelToShooter()` is false. Read that condition in
`bobot_state/BobotState.java`: it checks the field zone and the shooter's position near the hub.
Teleop feeding never reads the measured flywheel speed or hood angle.

Then open `autonomous/AutonomousManager.java` and read `handleInterpolateShooterToHub`. Autonomous
waits until the robot is far enough from the hub and `Shooter.isNearHubVelocity` reports the
flywheel within 2 rotations per second of its interpolated speed, then feeds until the shot's time
runs out. It checks once: a speed drop after feeding starts does not stop the feeder.

Record, for each path, which measurements permit feeding and which are ignored. Predict what happens
when the operator holds A before the flywheel reaches speed, and when the flywheel slows during an
autonomous shot. Once the enabled baseline above is recorded, check one prediction in simulation by
comparing the logged feeder output with the measured flywheel speed. These are observations of the
supplied code, not hardware settings.

The independent change adds one readiness condition to a copy of one path, such as a settling time
before the autonomous wait ends, and predicts the new feed time before running it. Save this
exercise under B3-01.2. Step 9 turns the same question into subsystem-owned states with refusal
reasons, and that evidence extends into B3-09.2.

## For the Mentor

The Starter has no migrated test suite. The mentor solution, `Badge3MentorSolution`, is the worked
answer to this badge; `TRAINING-MATERIALS.md` maps each step to its reference file and test, and the
focused `curriculum-reference` examples stay mentor-side.

The readiness gap above is what the mentor's `frc.robot.subsystems.feeder.FeedPolicy` closes. To
show where the student's design can lead after they have recorded their own predictions, run
`FeedPolicyTest` from the mentor solution's folder:

<CodeTabs>
<CodeTab label="PowerShell">

```powershell
.\gradlew.bat test --tests "*FeedPolicyTest"
```

</CodeTab>
<CodeTab label="Terminal">

```sh
./gradlew test --tests "*FeedPolicyTest"
```

</CodeTab>
</CodeTabs>

With possession, reference, clearance, mode and goals valid and the measured angle within 1 degree
of its goal, the default policy uses a 2 rotation per second speed tolerance, a 0.12 second settling
dwell, and a 3 second timeout from the request. A requested 40 rotations per second against a
measured 30 refuses with `SPEED`; raising the measurement to 40 gives `SETTLING`, then `READY` after
the dwell; holding `SPEED` for 3 seconds latches `TIMEOUT`; removing possession refuses at once.
