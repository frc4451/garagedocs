The student starts with the mentor-supplied `Badge3RobotBase`, preserves that copy, and makes the
assessed changes in a separate `Badge3Robot` folder. Everyone begins from the same working robot so
the review can focus on what the student changed and why.

Badge 2 or mentor-verified equivalent work is the prerequisite. Badge 2 supplies four general
simulated mechanism families, including an elevator, one provided-controller roller, FX and FXS
roller device simulations, configuration records and builders, a CTRE pivot profile comparison,
composition, two-camera AprilTag IO, paths, tests, and replay. The supplied base may also contain
linear rail, extra assemblies, and additional vendor adapters. Those are supplied assets, not
evidence that the student implemented them or additional Badge 2 prerequisites. Its simulation
constants describe a teaching model. They are not physical fixture settings.

## Start with the Diagnostic

The mentor administers [Written Checks](/badges/badge-3-written-checks) before instruction. The
initial result identifies topics to practice. Keep the correction record open while the student
learns the assessed topics. Complete the independent equivalent mastery attempt at 100% after the
relevant instruction, before the separate 100% final in Step 13. Neither corrected attempt is an
entry gate for the technical lessons. A mistake does not erase practical rows already completed.

## Establish the Baseline

1. Obtain the base source archive and its `SOURCE-MANIFEST.json` from the mentor. Record the
   release, Java version, WPILib version, and vendordeps in the student's README. Use a local folder
   outside OneDrive because GradleRIO rejects projects inside it.
2. Open the base folder in VS Code using the installed WPILib environment. Follow its README to run
   `gradlew.bat build` on Windows or `./gradlew build` in a terminal. Save the result. Explain one
   mechanism test and one subsystem interlock test.
3. Run the saved baseline autonomous routines. Find the requested path, estimated pose, measured
   mechanism position, and mechanism goal in the log. Explain which IO implementation the selected
   mode constructs.
4. Copy the project to `Badge3Robot`. Change its project name, preserve the original version record,
   and establish a new evidence directory. Keep baseline logs so later changes can be compared.

Make one bounded independent change to a core mechanism configuration or interlock in the student
copy. Predict its effect, run the related test or simulation, and save a comparison with the
unchanged baseline. Do not use a supplied extension as a hidden prerequisite.

The mentor also has a separate `curriculum-reference` project. Its focused examples support
instruction; they are not completed student evidence. The mentor provides an example when its module
begins, then checks an independent adaptation.

## Plan the Work

For each module, the student records the supplied behavior, planned change, relevant files,
anticipated result, and evidence location. Record simulation configuration separately from hardware
configuration. Define an acceptable error, settling interval, overshoot, and repeatability target
before tuning; use units and describe how each quantity will be measured.

Talon FX hardware remains provided for advanced Badge 3 work. Its introduction, FXS and Nova setup,
and the two CTRE roller simulation paths belong to Badge 2. Review the student's selected physical
controller and saved baseline at entry. Before each advanced physical demonstration, complete the
[fixture-specific preparation](/badges/badge-3-hardware#complete-the-setup-sheet) and relevant
simulation checks. Reuse a matching physical FX voltage baseline or establish one on the actual
fixture before current-control comparisons. The hardware evidence review is not a reason to postpone
those checks.

Open the [leadership requirements](/badges/badge-3-review) now. Plan opportunities to diagnose a
saved run, review code, and help a Badge 1 or 2 student. Record evidence as those opportunities
occur.

Compare `SOURCE-MANIFEST.json` and the supplied README with the current site requirements. Record
which files are supplied, which the student changes, and which belong to optional extensions.
Preserve the original archive and manifest. If its README still lists linear rail or maple-sim as
required, attach the [site revision record](/badges/badge-3-sign-off#curriculum-revision-record);
the current required outcomes govern completion.

## Badge Check

S means simulation, H means hardware, W means written reasoning, and M means mentor-observed review.
The student records an evidence link, mentor signature, and date for each row. The mentor asks the
student to explain a change and its result before signing.

| Row | Work | Done When |
| --- | --- | --- |
| B3-01.1 | Diagnostic and correction | W/M: Record the initial diagnostic at entry; correct reasoning through instruction and complete an independent equivalent 100% mastery attempt after the assessed topics. This row closes before the separate final, not before Step 2. |
| B3-01.2 | Preserve and explain the base | S/M: Build the supplied release, run its baseline checks, explain configuration and ownership, and record the starting version before creating `Badge3Robot`. Predict and demonstrate one independent core change in the student copy. |
| B3-01.3 | Plan the work | W/M: Identify supplied behavior, assessed changes, equipment, performance targets, dependencies and evidence locations. |
