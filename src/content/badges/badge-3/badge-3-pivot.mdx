The student refines the pivot while keeping its position reference, travel limits, and profile
ownership explicit. Start after Step 3 and the Badge 2 software-profile baseline. This module can
run alongside flywheel and FuelSim work. Before each physical reference or motion check, complete
the [Step 13 setup sheet](/badges/badge-3-hardware#complete-the-setup-sheet) and
[first enable](/badges/badge-3-hardware#first-enable) for that fixture. Read
[CANcoder Absolute Position](/frc/cancoder-absolute-position),
[Why Motion Magic](/frc/why-motion-magic),
[Trapezoidal Motion Profiling](/frc/trapezoidal-motion-profiling), and
[Exponential Motion Profiling](/frc/exponential-motion-profiling).

Steps 7 and 8 read Cobra's `org.robotzgarage.frc2026` classes in your Badge3Starter fork to learn
what the robot does today, and implement each change in your migrated `org.robotzgarage.frc2027`
pivot from [Step 1](/badges/badge-3-start#establish-the-baseline).

Cobra has two absolute-referenced pivots to start from. In the fork, the intake's `endeffector` is a
`Pivot` on `SingleRollerIOTalonFXWithCANCoder`, and the hood runs on
`SingleRollerIOTalonFXSWithCANCoder`. Both configure `FusedCANcoder` feedback with the
rotor-to-sensor and sensor-to-mechanism ratios from their CANcoder configs. The intake adapter
already holds `MotionMagicVoltage` and `MotionMagicExpoTorqueCurrentFOC` requests; the hood adapter
uses `MotionMagicVoltage`. These adapters run only in REAL. In SIM, `RobotContainer` builds the
endeffector on `SingleRollerIOSimTalonFX` (the `SingleRollerIOSimTalonFXWithCANCoder` line is
commented out) and the hood on `SingleRollerIOSimTalonFXS`, so neither fused feedback nor the Expo
request runs in Cobra's simulation until the student switches those constructions.

Before switching SIM to a CANcoder adapter, predict what fused feedback will report during a
simulated move. Then read `SingleRollerIOSimTalonFXWithCANCoder.updateSimState()`: it writes the
Talon FX rotor position and velocity and never writes the CANcoder's sim state, and the FXS version
has the same gap.
[The Missing Piece: the CANcoder](/frc/talonfx-simulation#the-missing-piece-the-cancoder) explains
what fused feedback does with a CANcoder that never moves. Write the CANcoder's sim state from the
same physics, in sensor rotations, before trusting any fused run in simulation.

## Establish Manual Reference

Write a procedure that begins with the mechanism powered off and placed at its known reference.
After power is restored in the disabled state, the operator explicitly establishes the encoder
reference. Record whether the write succeeded before allowing position requests. Startup must not
move the mechanism automatically to find zero.

Use a pivot with relative feedback for this exercise: your Badge 2 bench pivot, or a SIM pivot on a
rotor-only adapter such as Cobra's `SingleRollerIOSimTalonFX`. Keep Cobra's intake pivot for the
absolute path in B3-07.3. Its feedback is `FusedCANcoder`, and
[Starting Consistently, Every Time](/frc/cancoder-absolute-position#starting-consistently-every-time)
explains why a fused motor is not re-zeroed with `setPosition`.

Reference validity begins false after a power cycle or a known sensor reset. A matching encoder
number alone does not prove the arm is at the reference mark. The subsystem rejects ordinary
position requests until the reference procedure succeeds. Record a refusal reason and preserve a
separate, mentor-controlled bring-up procedure if manual movement is needed.

Cobra's pivots have no reference gate. Nothing in the Starter calls `Pivot.setGoalPosition`.
`Intake` and `Hood` call `setGoal`, which `Pivot` inherits from `SingleRoller`: it records the goal
and calls the adapter's `setGoal`, which sends a `MotionMagicVoltage` request. No step on that path
checks a reference. The adapters' `resetPosition` calls `talon.setPosition(position)` and discards
the returned `StatusCode`, so a failed write goes unnoticed. Add the gate to your migrated pivot:
refuse normal requests until an explicit reference write succeeds, and check that write's result.
Write a test for the refusal and the recovery.

Connect the gate to the controller's reset status, the disabled state, and subsystem requests. On a
Talon FX, Phoenix 6's `ParentDevice.hasResetOccurred()` returns true when the device has reset since
the previous call, so call it from one place each loop and invalidate the reference when it returns
true. A second student follows the written procedure after a power cycle and demonstrates
repeatable goals. No limit switch is required.

## Add Absolute Position Reference

This is a Badge 3 addition to the motor-relative Badge 2 mechanism library. Keep the
relative-feedback path available while adding the absolute sensor configuration and IO.
Complete B3-07.3 with either of these vendor-matched fixtures:

| Controller | Absolute sensor | Reference implementation |
| --- | --- | --- |
| CTRE Talon FX or Talon FXS | CTRE CANcoder | Remote, fused, or synchronized feedback supported by the selected controller and license; demonstrate fused feedback when supported. |
| Thrifty Nova | Thrifty CAN encoder | Read the CAN encoder, initialize Nova's internal position while disabled, verify readback, then use Nova voltage control. This is startup referencing, not CTRE-style fusion. |

Keep Thrifty electronics with Thrifty electronics and CTRE electronics with CTRE electronics.
A Thrifty fixture is a valid hardware option for the absolute-reference and repeatability rows.
The CTRE-specific Motion Magic, torque-current, and Expo simulation comparisons remain separate
requirements; choosing Thrifty hardware does not require a second physical CTRE fixture.

For both paths, record CAN bus and IDs, sensor placement, positive direction, offset, reduction,
sensor-to-mechanism ratio, and permitted travel. Compare physical and reported mechanism angles
at multiple marks before allowing normal motion. A single-turn encoder cannot identify which
turn a multi-turn mechanism occupies. Keep the permitted travel within one sensor turn or use a
separately reviewed referencing strategy. Have the IO refuse to reference when the travel exceeds
one sensor turn, or when the encoder does not share the controller's bus with its own CAN ID, and
report the reason as its reference status.

Before wiring, compute how far each Cobra sensor turns across its pivot's travel. Take the
`minAngle` to `maxAngle` range from `IntakeConstants.pivotConfig` and `HoodConstants.pivotConfig`,
multiply by the sensor-to-mechanism ratio each CANcoder config uses
(`endeffectorReductionSensorToMechanism` and `hoodReductionSensorToMechanism`), and compare each
result with one sensor turn of 360 degrees. Record the margin.

Cobra's CANcoder adapters write `MagnetOffset` as the config's `magnetOffset`, a mechanism angle,
times `sensorToMechanismReduction`. The Thrifty path below keeps its offset in sensor-angle units
from the start. Explain why Cobra multiplies by the ratio, which unit the CANcoder applies its
offset in, and why the Thrifty path needs no multiplication.

### Thrifty CAN Encoder and Nova Startup

Review [Thrifty Nova Control](/frc/thrifty-nova-control) and
[Thrifty Nova Simulation](/frc/thrifty-nova-simulation) first. Cobra and the Starter pin ThriftyLib
2026.0.1 (`com.thethriftybot.frc:ThriftyLib-java`). Its `ThriftyEncoder` class offers position and
zeroing but not the `CanEncoder` status API this exercise uses. Before this
exercise, replace the fork's ThriftyLib vendordep with the 2026.2.2 release Badge 2 used
(`com.thrifty.frc:Thrifty-java`, packages `com.thrifty.*`) and rebuild. The new release replaces the
`ThriftyNova` class with `com.thrifty.nova.Nova` and a new configuration API, so the old Nova
adapter and its configuration types are replaced, not only re-imported. The student's Badge 2
`NovaConfigs` and `NovaMotorConfig` already use the 2026.2.2 API. This CAN device is distinct from
Thrifty's 10-pin encoder; confirm which device the fixture uses before wiring it.

Thrifty's online documentation and Javadoc follow its newest release. The
[Encoders & Feedback](https://docs.thethriftybot.com/software/thriftylib/latest/encoders) page
describes pairing a CAN encoder to the Nova with `NovaConfig.canEncoderId` and the CAN feedback
sensor types; that pairing needs Nova firmware 2027.0.0-beta.4 or newer and is not part of this
exercise. In the pinned 2026.2.2 API, a `CanEncoder` reads the sensor, its `status()` reports
`getPositionAbs()`, `getPositionRel()`, `getVelocity()`, and `getDeviceStatus()`, and
`Nova.setEncoderPosition(rotations, EncoderType.INTERNAL)` seeds the motor's internal position.
Check method names against the pinned library in the project; the online pages describe the newer
release. In VS Code, use Go to Definition on a `com.thrifty` class to open the pinned 2026.2.2 jar's
signatures. Your Badge 2 `PivotIONova`, which seeds the internal encoder with
`setEncoderPosition(..., EncoderType.INTERNAL)` in its constructor and `resetPosition`, is a
starting point for the new IO.

Set the device offset and inversion to zero and false, and apply direction and offset exactly once
in typed host calibration. Keep the offset in sensor-angle units, before division by the
sensor-to-mechanism ratio. Convert the encoder's absolute position to a typed mechanism `Angle`.
Initialize Nova's internal position with that angle times the motor reduction, converted to
rotations only at `setEncoderPosition(..., EncoderType.INTERNAL)`.

1. Start disabled with normal voltage and position requests refused. Read the encoder and verify
   its configuration, finite readings, travel range, and stationary mechanism.
2. Request the absolute reference explicitly. A successful request means the seed was sent, not that
   it succeeded. The write itself must not command motor motion.
3. Call the normal periodic input update. Choose and justify a count of agreeing position
   readbacks, taken while disabled and stationary, that makes the reference valid, and a timeout for
   collecting them. A timeout leaves output stopped. Do not re-zero Nova every loop.
4. Enable and command a bounded goal. Log internal position, absolute position, reference validity,
   refusal/status text, and applied voltage. Compare both angles with the physical marks.
5. Test a missing encoder at startup, disconnect after referencing, bad offset/direction/ratio,
   rejected or ignored seed, restart/reset, and recovery. Faults invalidate the reference and stop
   output. Restoring communication alone must not re-enable motion; reference again while disabled.
   Invalidate the reference after a known Nova reset or reconfiguration.

The pinned status view reports the last device status, `getDeviceStatus()`, but no sample timestamp
or dedicated heartbeat. A successful status is not proof of a fresh reading. Perform the physical
disconnect check and record when the fault is detected. The software comparison also detects
disagreement between motor-relative and absolute position, but that does not prove every reset or
stale-frame case is detected. Hardware evidence must include these limitations.

Write tests for calibration, startup gating, write verification, faults, and recovery. A simulation
that pairs the Nova voltage approximation with WPILib physics and a separate software
absolute-sensor model checks the robot code's path, while the Nova and encoder firmware run only on
hardware, so record physical sensor behavior separately.

## Bound Travel

Reject nonfinite goals and deliberately reject or clamp out-of-range finite goals. Cobra's
`Pivot.setGoalPosition` documents clamping to its minimum and maximum angles, but the clamp is
commented out, and the `setGoal` path Cobra uses has no clamp, so goals reach the IO unbounded. The
Badge 2 library `Pivot` clamps out-of-range goals and logs `GoalClamped`, but WPILib's
`MathUtil.clamp` is built on `Math.max` and `Math.min`, which return NaN when given NaN; check
finiteness before the request. Test both ends and a nonfinite goal in simulation.

Before restoring any clamp, compare each pivot's `minAngle` and `maxAngle` with the goals it
receives. The hood's `PivotConfig` limits, 28 to 50 degrees, are launch elevation. The `Hood`
presets DOWN, MID and UP, 0, 17 and 22 degrees, are displacement from DOWN
([Keep the Hood References Clear](/frc/visualizing-cobra#keep-the-hood-references-clear)). Predict
what DOWN becomes under a clamp to those limits. Then make the limits and the goals use one frame,
record which frame you chose, and check the intake's limits against its `Intake` presets the same
way.

Cobra's `MotorConfigs` default disables both software limits, and both CANcoder adapters apply
whatever their config supplies. `IntakeConstants.endeffectorConfig` keeps a commented-out
`softwareLimitSwitch` built from the pivot's limits and tolerance; read it as a starting point, and
review [Software Limit Switches](/frc/motor-controller-configuration#software-limit-switches).
Configure the selected controller's software limits using its feedback units, with thresholds in the
same frame as the goals, and record their physical interpretation on the fixture sheet before
enabling hardware.

## Compare Profiles on the Same Model

Retain the Badge 2 software trapezoid as a baseline. Compare it with device-generated Motion Magic
voltage control, then Talon FX torque-current Motion Magic. Talon FXS uses voltage. Record final
goal, intermediate profile reference, measured angle and speed, output mode, gains, and limits.

The Starter has no plain torque-current Motion Magic path in use. `SingleRollerIOTalonFX` holds a
`MotionMagicTorqueCurrentFOC` request and the intake CANcoder adapter holds
`MotionMagicExpoTorqueCurrentFOC`, both behind `setGoalTorque`, but nothing in the Starter calls
`setGoalTorque`. Add a `MotionMagicTorqueCurrentFOC` request to your migrated Talon FX pivot IO for
B3-07.1. Its gains are in amps rather than volts, so give it its own slot.

A profiled position request still requires a feedback controller to follow its intermediate
setpoints. Position within tolerance while moving quickly is not settled. The student records both
position error and speed during the chosen settling interval and checks overshoot over the entire
move.

## Compare Expo

With reference validity and travel bounds established, complete the Expo comparison below.

Complete this worksheet before the exponential comparison:

| Prompt | Student Response |
| --- | --- |
| What angle and speed units does the selected feedback report? | Show one conversion from degrees to mechanism rotations. |
| Which object advances the trapezoidal profile, and which advances Motion Magic? | Name the owner and period. |
| What units do `MotionMagicExpo_kV` and `MotionMagicExpo_kA` use? | Distinguish these profile parameters from the Slot 0 voltage gains the comparison uses. |
| What does a larger Expo kA predict under the same available voltage? | Predict before running. |
| How will error, settling, overshoot and repeatability be measured? | Give targets and log fields. |
| Which profile better meets the recorded targets for this model? | Compare traces and state the model's limits. |

Run supported CTRE Expo in simulation against the same initial angle, goal, and model. Use
`MotionMagicExpoVoltage` with the same Slot 0 voltage gains as the Motion Magic voltage run, so the
profile is the only change between runs. State the test model before running. One suitable model is
a Kraken X60 through a 100:1 reduction driving about 342 lb in^2 (0.1 kg m^2, the unit WPILib's
simulation takes) about a vertical axis, so gravity adds no load, over 0 to 90 degrees on a 12 V
supply. These are illustrative settings, not measurements of Cobra's hood or intake.

Cobra's REAL intake adapter holds a `MotionMagicExpoTorqueCurrentFOC` request. Read it as the
installed torque-current variant; it needs torque-current gains, so it is not the voltage comparison
this section asks for. Keep each run's settings and saved trace as evidence. Physical Expo is
optional. The mentor checks all worksheet reasoning, then asks for an independent prediction with a
changed constraint.

## Trace the Reference in Cobra

Start with the intake pivot's request in the fork: trace an `Intake` command such as
`endeffectorDeploy()` to the inherited `SingleRoller.setGoal`, then to the CANcoder adapter's
`setGoal` and its `MotionMagicVoltage` request. Then follow the same request in your migrated pivot.
With the reference gate added, first request an angle with an invalid reference and predict
refusal. Establish the reference explicitly, repeat the same request, and
compare goal, measured angle, speed, and refusal. Connect the gate to the actual student subsystem
before claiming the reference outcome.
