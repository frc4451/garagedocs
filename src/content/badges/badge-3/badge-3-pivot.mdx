The student refines the pivot while keeping its position reference, travel limits, and profile
ownership explicit. Start after Step 3 and the Badge 2 software-profile baseline. This step can run
alongside the flywheel and FuelSim work in Steps 5 and 6. Before each powered reference or motion
check, complete the [Step 13 setup sheet](/badges/badge-3-hardware#complete-the-setup-sheet) and
[first enable](/badges/badge-3-hardware#first-enable) for that fixture.

The student reads Cobra's `org.robotzgarage.frc2026` classes in the Badge3Starter fork to learn what
the robot does today and implements each change in the migrated `org.robotzgarage.frc2027` pivot
from [Step 1](/badges/badge-3-start#establish-the-baseline).

Research these before changing the pivot IO:

- [CANcoder Absolute Position](/frc/cancoder-absolute-position)
- [Why Motion Magic](/frc/why-motion-magic)
- [Trapezoidal Motion Profiling](/frc/trapezoidal-motion-profiling)
- [Exponential Motion Profiling](/frc/exponential-motion-profiling)

## Establish Manual Reference

Write a procedure that begins with the mechanism powered off and placed at its known reference.
After power is restored in the disabled state, the operator explicitly establishes the encoder
reference. Record whether the write succeeded before allowing position requests. Startup must not
move the mechanism automatically to find zero.

Use a pivot with relative feedback for this exercise: the student's Badge 2 bench pivot, or a SIM
pivot on a rotor-only adapter such as Cobra's `SingleRollerIOSimTalonFX`. Keep Cobra's intake pivot
for the absolute path in B3-07.3. Its feedback is `FusedCANcoder`, and
[Starting Consistently, Every Time](/frc/cancoder-absolute-position#starting-consistently-every-time)
explains why a fused motor is not re-zeroed with `setPosition`.

Reference validity begins false after a power cycle or a known sensor reset. A matching encoder
number alone does not prove the arm is at the reference mark. The subsystem rejects ordinary
position requests until the reference procedure succeeds. Record a refusal reason. If manual
movement is needed, keep a separate, mentor-controlled bring-up procedure for it.

Cobra's pivots have no reference gate. Nothing in the Starter calls `Pivot.setGoalPosition`.
`Intake` and `Hood` call `setGoal`, which `Pivot` inherits from `SingleRoller`: it records the goal
and calls the adapter's `setGoal`, which sends a `MotionMagicVoltage` request. No step on that path
checks a reference. The `resetPosition` methods of the intake and hood adapters,
`SingleRollerIOTalonFXWithCANCoder` and `SingleRollerIOTalonFXSWithCANCoder`, call
`talon.setPosition(position)` and discard the returned `StatusCode`, so a failed write goes
unnoticed. Add the reference gate to the migrated pivot and check the result of the reference write.
Write a test for the refusal and the recovery.

Connect the gate to the motor controller's reset status, the disabled state, and subsystem requests.
On a Talon FX, Phoenix 6's `ParentDevice.hasResetOccurred()` returns true when the device has reset
since the previous call. Call it from one place each loop, and invalidate the reference when it
returns true. Another member follows the written procedure after a power cycle and demonstrates
repeatable goals. No limit switch is required.

## Confirm the Trace in Cobra

Start with the intake pivot's request in the fork: trace an `Intake` command such as
`endeffectorDeploy()` to the inherited `SingleRoller.setGoal`, then to the CANcoder adapter's
`setGoal` and its `MotionMagicVoltage` request. Then follow the same request in the migrated pivot.
With the reference gate added, predict the result, then request an angle while the reference is
invalid. Establish the reference explicitly, repeat the same request, and compare goal, measured
angle, speed, and refusal. Connect the gate to the student's own subsystem before claiming the
reference outcome.

## Add Absolute Position Reference

Cobra has two absolute-referenced pivots to start from. In the fork, the intake's `endeffector` is a
`Pivot` on `SingleRollerIOTalonFXWithCANCoder`, and the hood runs on
`SingleRollerIOTalonFXSWithCANCoder`. Both configure `FusedCANcoder` feedback with the
rotor-to-sensor and sensor-to-mechanism ratios from their CANcoder configs. The intake adapter
already holds `MotionMagicVoltage` and `MotionMagicExpoTorqueCurrentFOC` requests; the hood adapter
uses `MotionMagicVoltage`. Expo is CTRE's exponential Motion Magic profile. These adapters run only
in REAL. In SIM, `RobotContainer` builds the endeffector on `SingleRollerIOSimTalonFX` and the hood
on `SingleRollerIOSimTalonFXS`; the `SingleRollerIOSimTalonFXWithCANCoder` line is commented out.
Neither fused feedback nor the Expo request runs in Cobra's simulation until those constructions
are switched.

For B3-07.3 in simulation, switch the endeffector's or the hood's SIM construction to its CANcoder
adapter. Before switching, predict what fused feedback will report during a simulated move. Then
read `SingleRollerIOSimTalonFXWithCANCoder.updateSimState()`: it writes the Talon FX rotor position
and velocity and never writes the CANcoder's sim state, and the FXS version has the same gap.
[The Missing Piece: the CANcoder](/frc/talonfx-simulation#the-missing-piece-the-cancoder) explains
what fused feedback does with a CANcoder that never moves. Write the CANcoder's sim state from the
same physics, in sensor rotations, before trusting any fused run in simulation.

Absolute position reference is a Badge 3 addition to the motor-relative Badge 2 mechanism library.
Keep the relative-feedback path available while adding the absolute sensor configuration and IO.
Complete B3-07.3 with either of these vendor-matched fixtures:

| Controller | Absolute sensor | Reference implementation |
| --- | --- | --- |
| CTRE Talon FX or Talon FXS | CTRE CANcoder | Remote, fused, or synchronized feedback supported by the selected controller and license; demonstrate fused feedback when supported. |
| Thrifty Nova | Thrifty CAN encoder | Read the CAN encoder, initialize Nova's internal position while disabled, verify readback, then use Nova voltage control. This is startup referencing, not CTRE-style fusion. |

Keep Thrifty electronics with Thrifty electronics and CTRE electronics with CTRE electronics.
A Thrifty fixture is a valid hardware option for the absolute-reference and repeatability rows.
The CTRE-specific Motion Magic, torque-current, and Expo simulation comparisons remain separate
requirements; choosing Thrifty hardware does not require a second physical CTRE fixture.

For both paths, record CAN bus and IDs, sensor placement, positive direction, offset,
motor-to-mechanism reduction, sensor-to-mechanism ratio, and permitted travel. Compare physical and
reported mechanism angles at multiple marks before allowing normal motion. A single-turn encoder
cannot tell which of its own turns it is on, so keep the permitted travel within one sensor turn or
use a separately reviewed referencing strategy. Have the IO refuse to reference in two cases: when
the travel exceeds one sensor turn, and when the encoder is not on the controller's CAN bus at its
recorded CAN ID. Have it report the reason as its reference status.

Before configuring the absolute reference, compute how far each Cobra sensor turns across its
pivot's travel. Take the `minAngle` to `maxAngle` range from `IntakeConstants.pivotConfig` and
`HoodConstants.pivotConfig`, and multiply it by the sensor-to-mechanism ratio each CANcoder config
uses (`endeffectorReductionSensorToMechanism` and `hoodReductionSensorToMechanism`). Compare each
result with one sensor turn of 360 degrees, and record the margin.

Cobra's CANcoder adapters write `MagnetOffset` as the config's `magnetOffset`, a mechanism angle,
times `sensorToMechanismReduction`. The Thrifty path in
[Thrifty CAN Encoder and Nova Startup](#thrifty-can-encoder-and-nova-startup) keeps its offset in
sensor-angle units from the start. Explain why Cobra multiplies by the ratio, which unit the
CANcoder applies its offset in, and why the Thrifty path needs no multiplication.

### Thrifty CAN Encoder and Nova Startup

This subsection applies only to a Thrifty Nova fixture; a CTRE fixture skips it. The Thrifty CAN
encoder is distinct from Thrifty's 10-pin encoder; confirm which device the fixture uses before
wiring it. Review [Thrifty Nova Control](/frc/thrifty-nova-control) and
[Thrifty Nova Simulation](/frc/thrifty-nova-simulation) first.

Cobra and the Starter pin ThriftyLib 2026.0.1 (`com.thethriftybot.frc:ThriftyLib-java`). Its
`ThriftyEncoder` class offers position and zeroing but not the `CanEncoder` status API this exercise
uses. The fork already pins the 2026.2.2 release Badge 2 used (`com.thrifty.frc:Thrifty-java`,
packages `com.thrifty.*`), swapped in when the library was copied
([Start the Library](/badges/badge-3-start#start-the-library)). The new release replaces the
`ThriftyNova` class with `com.thrifty.nova.Nova` and a new configuration API, so the student
rewrites the old Nova adapter and its configuration types rather than only changing their imports.
The student's Badge 2 `NovaConfigs` and `NovaMotorConfig` already use the 2026.2.2 API.

Thrifty's online documentation and Javadoc follow its newest release. The
[Encoders & Feedback](https://docs.thethriftybot.com/software/thriftylib/latest/encoders) page
describes pairing a CAN encoder to the Nova with `NovaConfig.canEncoderId` and the CAN feedback
sensor types. That pairing needs Nova firmware 2027.0.0-beta.4 or newer and is not part of this
exercise. In the pinned 2026.2.2 API, a `CanEncoder` reads the sensor, its `status()` reports
`getPositionAbs()`, `getPositionRel()`, `getVelocity()`, and `getDeviceStatus()`, and
`Nova.setEncoderPosition(rotations, EncoderType.INTERNAL)` seeds the motor's internal position.
Check method names against the pinned library in the project. In VS Code, use Go to Definition on a
`com.thrifty` class to open the pinned 2026.2.2 jar's signatures. The student's Badge 2
`PivotIONova`, which seeds the internal encoder with `setEncoderPosition(..., EncoderType.INTERNAL)`
in its constructor and `resetPosition`, is a starting point for the new IO.

Set the device offset and inversion to zero and false, and apply direction and offset exactly once
in the robot code's calibration, using typed units. Keep the offset in sensor-angle units, before
division by the sensor-to-mechanism ratio. Convert the encoder's absolute position to a typed
mechanism `Angle`. Initialize Nova's internal position with that angle times the motor reduction,
converted to rotations only at `setEncoderPosition(..., EncoderType.INTERNAL)`.

1. Start disabled with normal voltage and position requests refused. Read the encoder and verify
   its configuration, finite readings, travel range, and stationary mechanism.
2. Request the absolute reference explicitly. A successful request means the seed was sent, not that
   it succeeded. The write itself must not command motor motion.
3. Call the normal periodic input update. Choose and justify a count of agreeing position
   readbacks, taken while disabled and stationary, that makes the reference valid, and a timeout for
   collecting them. A timeout leaves output stopped. Do not re-zero Nova every loop.
4. Enable and command a bounded goal. Log internal position, absolute position, reference validity,
   refusal/status text, and applied voltage. Compare both angles with the physical marks.
5. Test a missing encoder at startup, disconnect after referencing, bad offset/direction/ratio,
   rejected or ignored seed, restart/reset, and recovery. Faults invalidate the reference and stop
   output. Restoring communication alone must not re-enable motion; reference again while disabled.
   Invalidate the reference after a known Nova reset or reconfiguration.

The pinned status view reports the last device status, `getDeviceStatus()`, but no sample timestamp
or dedicated heartbeat. A successful status is not proof of a fresh reading. Perform the physical
disconnect check and record when the fault is detected. Comparing motor-relative and absolute
position in software also detects disagreement between them, but that does not prove every reset or
stale-frame case is detected. Hardware evidence must include these limitations.

Write tests for calibration, startup gating, write verification, faults, and recovery. A simulation
that pairs the Nova voltage approximation with WPILib physics and a separate software
absolute-sensor model checks the robot code's path. The Nova and encoder firmware run only on
hardware, so record physical sensor behavior separately.

## Bound Travel

Reject nonfinite goals and deliberately reject or clamp out-of-range finite goals. Cobra's
`Pivot.setGoalPosition` documents clamping to its minimum and maximum angles, but the clamp is
commented out, and the `setGoal` path Cobra uses has no clamp, so goals reach the IO unbounded. The
Badge 2 library `Pivot` clamps out-of-range goals and logs `GoalClamped`. WPILib's `MathUtil.clamp`
is built on `Math.max` and `Math.min`, which return NaN when given NaN, so check finiteness before
the request. Test both ends and a nonfinite goal in simulation.

Before restoring any clamp, compare each pivot's `minAngle` and `maxAngle` with the goals it
receives. The hood's `PivotConfig` limits, 28 to 50 degrees, use the reference in which DOWN is 28
degrees. The `Hood` presets DOWN, MID and UP, 0, 17 and 22 degrees, are displacement from the hood's
zero at DOWN
([Keep the Hood References Clear](/frc/visualizing-cobra#keep-the-hood-references-clear)). In
[Step 6](/badges/badge-3-fuelsim-experiment#apply-cobras-hood-and-table-conventions) the student
works out how both references relate to launch elevation. Predict what DOWN becomes under a clamp to
those limits. Then make the limits and the goals use one convention (elevation or displacement),
record the chosen convention, and check the intake's limits against its `Intake` presets the same
way.

Cobra's `MotorConfigs` default disables both software limits, and both CANcoder adapters apply
whatever their config supplies. `IntakeConstants.endeffectorConfig` keeps a commented-out
`softwareLimitSwitch` built from the pivot's limits and tolerance; read it as a starting point, and
review [Software Limit Switches](/frc/motor-controller-configuration#software-limit-switches).
Configure the selected controller's software limits using its feedback units, with thresholds in the
same convention as the goals, and record their physical interpretation on the setup sheet before
enabling hardware.

## Tune the Pivot Live

Cobra's `Pivot` extends `SingleRoller`, which builds the same `FeedBack` and `FeedForward` tunables
as the flywheel in [Step 5](/badges/badge-3-flywheel#tune-gains-live). Carry the same live-tuning
path into the migrated pivot IO for each motor controller the student supports, with separate
voltage and torque-current gain sets on the Talon FX. Two differences from the flywheel matter:

- A gain change reaches the controller while the pivot may be moving or holding against gravity.
  Make changes while the pivot holds a goal inside the travel bounds from
  [Bound Travel](#bound-travel), with the reference gate passing.
- On a Nova, the profile feedforward and the PID are ThriftyLib configuration options. ThriftyLib's
  [Configurations](https://docs.thethriftybot.com/software/thriftylib/latest/configs) page warns
  against large reconfigurations in the periodic loop and says flash settings persist across power
  cycles. Decide how the migrated Nova IO sends a gain change and which units the gains use once
  the profile's sensor-to-mechanism ratio is set. Then decide what returns the Nova to the constants
  at the next startup. Record the answers in the fork's README.

Copy the final values into the constants and repeat the validation run with `tuningMode` off.

## Compare Profiles on the Same Model

Run every comparison in this section and the next on one stated test model. One suitable model is a
Kraken X60 through a 100:1 reduction on a 12 V supply, moving over 0 to 90 degrees. It drives
about <Equation tex="342\;\mathrm{lb}\cdot\mathrm{in}^2" />
(<Equation tex="0.1\;\mathrm{kg}\cdot\mathrm{m}^2" />, the unit WPILib's simulation takes) around a
vertical axis, so gravity adds no load. These are illustrative settings, not measurements of
Cobra's hood or intake.

Retain the Badge 2 software trapezoid as a baseline. Compare it with device-generated Motion Magic
voltage control, then Talon FX torque-current Motion Magic. The Talon FXS comparison uses voltage
control only. Record final goal, intermediate profile reference, measured angle and speed, output
mode, gains, and limits.

The Starter has no plain torque-current Motion Magic path in use. `SingleRollerIOTalonFX` holds a
`MotionMagicTorqueCurrentFOC` request and the intake CANcoder adapter holds
`MotionMagicExpoTorqueCurrentFOC`, both behind `setGoalTorque`, but nothing in the Starter calls
`setGoalTorque`. Add a `MotionMagicTorqueCurrentFOC` request to the migrated Talon FX pivot IO for
B3-07.1. Its gains are in amps rather than volts, so give it its own slot.

A profiled position request still requires a feedback controller to follow its intermediate
setpoints. Position within tolerance while moving quickly is not settled. The student records both
position error and speed during the chosen settling interval and checks overshoot over the entire
move.

With reference validity and travel bounds established, complete this worksheet for the Expo
comparison. Answer the first five prompts before running the comparison and the last one after it.

| Prompt | What the Student Shows |
| --- | --- |

| Which object advances the trapezoidal profile, and which advances Motion Magic? | Name the owner and period. |

| What does a larger Expo kA predict under the same available voltage? | Predict before running. |
| How will error, settling, overshoot and repeatability be measured? | Give targets and log fields. |

`MotionMagicExpoVoltage` with the same Slot 0 voltage gains as the Motion Magic voltage run, so the

Cobra's REAL intake adapter holds a `MotionMagicExpoTorqueCurrentFOC` request. Read it as the
existing torque-current variant; it needs torque-current gains, so it is not the voltage comparison
this section asks for. Keep each run's settings and saved trace as evidence. Physical Expo is
optional.
