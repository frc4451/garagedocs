The student combines the refined mechanisms into behavior owned by a subsystem. Start after the
roller, flywheel and pivot simulation checks in Steps 4, 5 and 7, and the drawing work in Step 8.
FuelSim is needed for the later integrated launch, not for the first state-transition tests.
Hardware demonstrations may be scheduled separately. Read
[Why State Machines](/frc/why-state-machines),
[Subsystem State Machines](/frc/subsystem-state-machines),
[States, Commands and Triggers](/frc/states-commands-and-triggers), and
[Transition Graphs](/frc/transition-graphs).

## Write the Transition Table First

Choose states that describe observable behavior, such as stowed, collecting, holding, preparing to
score, scoring, and faulted. Keep current state separate from requested state. For each transition,
record the request, required observations, outputs while waiting, time bound, and refusal reason.

For example, a request to score while the flywheel is slow moves to preparation. The feeder remains
stopped until possession is confirmed, pivot reference is valid, and measured speed and angle
satisfy readiness for the required interval. A requested goal is not evidence that the mechanism
reached it.

Retain relevant clearance rules from the supplied code. The physical conflict is still there after
the rule moves into a state machine, so the rule moves with it. Identify which measured conditions
permit a transition and which faults require an explicit recovery action.

Cobra's rules are triggers in `RobotContainer`'s operator bindings. While the right bumper is held,
the field zone picks the hood preset: DOWN near the alliance hub, UP in the neutral zone, MID in the
far zone. The hood drops to DOWN near the trench, when the intake is down, or when the bumper is
released. A separate right-bumper binding picks the shooter's table: the hub table near the alliance
hub and the dropoff table elsewhere, without the trench check. `RobotContainer` also defines
`configureHoodBindings` with a different automatic mapping, but nothing calls it. Write these rules
into the transition table before replacing them.

## Connect Commands to Requests

Commands request behavior from the subsystem and declare its requirement. The subsystem evaluates
guards and owns actuator outputs. Avoid one command writing the roller while another subsystem loop
writes a different roller output in the same cycle.

Write the transition policy first as a class that receives observations as arguments, so a test can
drive it deterministically without motors or a field. Then adapt it into the subsystem, connect
logged IO, and define outputs for every state, including failure and interruption.

## Exercise the Refusals

Start from a known state for each test. Request a valid transition, a clearance violation, a
transition with invalid reference, and scoring before readiness. Demonstrate timeout, cancellation,
disable, and explicit recovery. Log requested state, current state, elapsed time, guard values,
refusal reason and actual outputs.

For the independent change, the mentor supplies a new transition requirement or removes one
observation. The student predicts the refusal or timeout and proves it with the saved log. The
mentor reviews the transition table alongside the code to check that both describe the same
behavior.

## Trace the Integrated Behavior

In the fork, trace the behavior the states replace: the right-bumper shooting bindings, the
A-button feed binding from Step 1, and the trench and intake triggers that drop the hood. Record
which measured inputs reach each decision from Drive, Intake, Feeder, Shooter, and Hood. Then change
one transition guard in the student's state machine, predict the refusal, and compare a normal run
with the corresponding failure run.

## Keep the Shot Setup Together

Because Cobra chooses the shooter's table and the hood preset in separate bindings, a trench
crossing can leave the dropoff table running with the hood at DOWN. Name the table and its required
hood preset together in one place, keeping Cobra's pairing: near uses the hub table with DOWN,
neutral uses the dropoff table with UP, and far uses the dropoff table with MID. Aiming, operator
speed requests, hood selection, and readiness use that choice. Clearance can request DOWN; it does
not make a dropoff table valid at DOWN. A mismatch refuses feeding, and a changed mode starts a new
settling interval. Log the selected mode, hood goal and measurement, flywheel goal and measurement,
and the refusal reason together.

Test the shooting binding across zone changes and a trench-clearance condition, and test mismatch
refusal and recovery dwell separately. These checks preserve the shared dropoff table; they do not
establish its physical passing accuracy.

## For the Mentor

`curriculum-reference` contains an isolated transition policy, `frc.robot.curriculum.Acquisition`,
that receives observations as arguments. In `Badge3MentorSolution`, the integrated
`frc.robot.subsystems.acquisition.Acquisition` coordinates Drive, Intake, Feeder, Shooter, Hood, and
Possession; `ShotMode` pairs each table with its hood preset; and `ShotModeSimulationTest` and
`FeedPolicyTest` cover the zone, trench, mismatch and dwell cases. The log shows them as
`ShotSelection` and `Feeder/Refusal`. Compare them with the student's design after the student has
built their own.
