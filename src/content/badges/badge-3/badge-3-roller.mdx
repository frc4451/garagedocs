The student refines the roller from an output command into a mechanism that can distinguish
collection, invalid sensing, and a sustained jam. Start after Step 3. Complete the relevant fixture
sheet and voltage baseline before powered physical checks; the scripted sensing and jam experiments
run first in simulation. Read [Current Limiting](/frc/current-limiting),
[IO Layers](/frc/io-layers), and the linked CTRE CANrange documentation before changing the sensor
IO.

## Compare Output Modes

Begin with the saved voltage baseline. Run positive, reverse, and zero effort on Talon FX and Talon
FXS simulation. Then add Talon FX `TorqueCurrentFOC` through the typed current capability. Log
requested mode and effort, applied voltage, torque current, supply current, measured speed, and
configured limits. Supply current is not a replacement for the torque-current measurement in a jam
rule.

Use the same model, initial state, and duration for comparisons. Describe the input magnitudes as
separate choices in volts and amps, not equivalent values. Show the configured limit changing the
response. A current request also needs a bounded operating range; current limiting alone does not
detect a trapped game piece.

## Add CANrange IO

Cobra has no CANrange, so this IO starts from Phoenix 6's `CANrange` class. It reports
`getIsDetected()`, `getDistance()`, `getSignalStrength()`, `getMeasurementHealth()`, and
`getMeasurementTime()` as status signals; refresh them together and keep each signal's status. The
input record needs connection/status information, measurement validity, distance with units,
detection result, and sample time or age. Keep three outcomes distinct: present, absent, and
invalid. An invalid reading does not prove absence.

In simulation, first supply scripted input sequences through the same interface: absent to present,
present to absent, disconnected, and stale. On hardware, move the selected object into and out of
the configured range under mentor supervision. Record the selected threshold, hysteresis or
debounce, the observed distances, and the subsystem response. Choose those values from the fixture
and the game piece in front of it.

The student explains why a detection may be valid while a particular distance is unsuitable for the
intended decision. Check the pinned CANrange API and the device's reported health instead of
reducing validity to a single distance comparison.

## Detect a Sustained Jam

Cobra has no jam rule, but its rollers already log what one needs. The `SingleRollerIO` inputs
include `torqueCurrentAmps` and `velocity`, and `SingleRollerIOTalonFX` fills both from the motor.
Cobra's general `SingleRollerIOSim` fills `velocity` and supply current but leaves
`torqueCurrentAmps` at zero, so a torque-current rule could never latch in that simulation.

Write the rule as a small class that receives the collection request, sensor validity, measured
torque current, and measured speed, so a unit test can drive it without a motor. The rule requires
collecting, valid observations, substantial measured torque current, and low measured speed for a
continuous interval. Values such as 15 A, 1 rotation per second, and 0.2 seconds make a reasonable
first test; the student selects and justifies values for the actual mechanism.

To watch the rule in simulation, give a roller a scripted IO that implements the roller IO contract
and reports a chosen torque current and speed, with controls to inject and clear a stall and to
invalidate the sensor. Start collection, inject a stall, and confirm that the owner stops the roller
when the rule latches. Clearing the simulated stall must not clear the latch: stop the collection
command, reset the latch explicitly, then start a new command. Refuse a reset while collection is
still requested. Keep this scripted roller separate from Cobra's physical feeder.

Reset the timer when any required condition stops holding. Latch the jam once the interval expires.
Stop the roller, or use a justified limited hold with an explicit ending condition. Require an
explicit reset before collection resumes. Automatic reversal or repeated retry is not required.

Test a brief startup transient, normal collection, a sustained jam, invalid sensing, stopping the
command, and explicit reset. Record the reason for the stop. Simulate the jam by controlling load or
observations; a deliberate physical jam is not required.

## Independent Change

The mentor changes the simulated load or a sensor timing condition. The student predicts whether the
rule should latch, runs it, and explains the result using the saved signals. CANrange presence and
jam detection receive separate evidence because they answer different questions.

## Trace the Measurements in Cobra

In the fork, trace the intake roller from `Intake` to its selected IO adapter and find where
`SingleRollerIOTalonFX.updateInputs` fills `torqueCurrentAmps` and `velocity`. Then hold the
collection request and sensor validity fixed while the scripted IO changes measured speed and
current. Predict when the dwell starts, when the jam latches, and why the roller stays stopped after
the request ends until an explicit reset. Save the before/after traces and the independent change.

## For the Mentor

`Badge3MentorSolution` contains a worked jam exercise: `JamRule`, `JamExerciseIO`, `JamExercise`,
`JamRuleTest`, and `JAM-EXERCISE.md`, read in that order. Its simulation-only roller runs from a
gamepad on Driver Station port 4 in Teleop: hold A to collect, B to stop, X and Y to inject and
clear a stall, the bumpers to invalidate and restore the sensor, and Start to reset the latch. Use
it to demonstrate the latch and reset behavior after the student has written their own rule and
predictions.
