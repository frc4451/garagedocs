The student combines the simulators around a maple-sim drivetrain and investigates how drivetrain
contact changes a simulated path. Complete rows B3-11.1 to B3-11.3 before the Step 12 autonomous
runs; the B3-11.4 reproduction by another member can follow with the Step 15 handoff.

Start from the student's `Badge3Starter` fork with Step 6's fuel world and Step 10's camera IO in
place. Use one combined simulation: maple-sim for chassis motion and contact, the fuel world
(FuelSim) for fuel and scoring, and the camera world (PhotonVision) for observations of the same
fuel.

Read these first:

- [maple-sim](/frc/maple-sim)
- [FuelSim](/frc/fuelsim)
- [Physics in the IO Layer](/frc/physics-in-the-io-layer)
- [Unit Tests in Simulation](/frc/unit-tests-in-simulation)

## Pin and Inspect the Dependency

Add maple-sim `0.4.0-beta` and dyn4j `5.0.2` to the fork. Declare both in `build.gradle` instead of
adding a vendordep. When this badge pinned maple-sim, the public vendordep pointed to
`0.4.0-beta-obstacles-fix`, whose Maven artifact could not be resolved.

The Starter's `build.gradle` has no `repositories` block, so add one above `dependencies` with Maven
Central (for dyn4j) and maple-sim's Maven repository. Put the two `implementation` lines inside the
Starter's existing `dependencies` block, beside `implementation wpi.java.deps.wpilib()`:

```groovy
repositories {
    mavenCentral()
    maven { url = uri("https://shenzhen-robotics-alliance.github.io/maple-sim/vendordep/repos/releases") }
}

dependencies {
    implementation "org.ironmaple:maplesim-java:0.4.0-beta"
    implementation "org.dyn4j:dyn4j:5.0.2"
    // ...the Starter's existing dependency lines stay here
}
```

Record both versions in the fork's README, with the SHA-256 hash of the resolved
`maplesim-java-0.4.0-beta.jar` from Gradle's cache (under
`.gradle/caches/modules-2/files-2.1/org.ironmaple/` in the user's home folder). Treat a later
version as a deliberate dependency change that needs a rebuild and repeated experiments.

## Choose the Drivetrain Model

Start from Cobra's simulated drive. In the fork's SIM mode, `RobotContainer` builds `Drive` from an
empty `GyroIO` and four `ModuleIOSim` instances. Each one models its module's drive and turn motors
with `DCMotorSim`, so the simulated robot has no gyro, wheel slip, or field contact.

Choose which of maple-sim's AdvantageKit template projects matches Cobra's drive IO and explain why.
[The Drivetrain and What It Costs](/frc/maple-sim#the-drivetrain-and-what-it-costs) lists the
templates. Then explain how maple-sim's module and gyro simulation differ from `ModuleIOSim`.

Keep `ModuleIOSim` in the fork. Add a selector in `RobotContainer`'s SIM case, such as a constant,
that builds `Drive` from either the `ModuleIOSim` drivetrain or the maple-sim drivetrain. The same
commands can then run against both models and be compared in simulation.

## Assign One Update Owner

maple-sim's arena, `SimulatedArena`, advances the drivetrain physics once per robot period, with
its internal subticks. The module and gyro IO read the resulting sensor data. When the selector
chooses maple-sim, the `ModuleIOSim` physics updates must not run, so two models do not both move
the same robot. Preserve the normal estimator and path-follower interfaces.

Work through five ownership decisions and record each one:

1. **Subticks.** Run first at maple-sim's default subtick count and watch module steering in
   AdvantageScope, comparing requested and measured module angles. Record the observation, then
   choose a subtick count with `SimulatedArena.overrideSimulationTimings` and justify it from the
   log.
2. **Fuel.** maple-sim's 2026 arena places its own fuel through `placeGamePiecesOnField`. Decide how
   the arena keeps the field obstacles without placing fuel, so FuelSim stays the only fuel owner,
   and check that maple-sim holds no game pieces after a reset.
3. **Loop position.** Decide where the arena update runs in the robot loop. Find where
   `IterativeRobotBase` calls `simulationPeriodic` relative to `robotPeriodic`, where the fork runs
   the command scheduler. Write down whether the module IO reads physics produced in the same loop
   or the previous one, and what delay that adds between a command and its measured motion.
4. **Battery.** Find every place the fork writes the roboRIO input voltage.
   `SimulatedArena.simulationPeriodic` updates maple-sim's `SimulatedBattery` each subtick, and
   `SimulatedBattery` writes `RoboRioSim.setVInVoltage`. The fork's roller sims, such as
   `SingleRollerIOSimTalonFX`, also write it from their own current draw. Keep one owner, and
   register each mechanism's current draw with it.
5. **Reset.** Decide which call resets the combined simulation, covering the maple-sim drivetrain
   pose, the fuel world's fuel, and the camera world's targets, and check that no simulator keeps
   state from the previous run.

## Connect the True Pose

maple-sim's drivetrain simulation supplies the true pose that Steps 6 and 10 deferred. Replace three
poses with that true pose: the fixed test pose registered with FuelSim in Step 6, the camera world's
pose source from Step 10, and the pose that the AprilTag camera simulation renders from. Cobra's
`AprilTagVision` passes that simulation the global pose estimate. Fuel physics and camera rendering
then follow the simulated robot, while the estimator keeps its own estimated pose.

Record true field pose, estimated field pose, requested chassis speeds, measured module states,
battery behavior, and the experiment configuration. BLine receives the estimated pose. The true pose
is for simulated observations and comparison, not a shortcut into control.

## Check Contact before the Paths

Before the path experiments, write a short test that drives the maple-sim chassis into a field wall
with direct voltage. The test compares true motion with what the commanded voltage alone would
produce.
[A Mechanism in the Loop](/frc/unit-tests-in-simulation#a-mechanism-in-the-loop) shows how to run
the robot loop inside a test. This test is a prerequisite check; it does not replace the controlled
contact experiment below.

## Run Two Experiments

Run both experiments in the combined simulation, with the normal estimator controlling the robot and
the true pose used only for comparison. Save the log of every run.

First run a known BLine path in open space. Record its start and end poses, whether BLine finished
it, path error, and elapsed time. Repeat it from the same conditions to establish the variation
present in the model.

Then introduce a known obstacle or field boundary on a controlled path. Predict where contact will
occur and how it may change true motion, wheel readings, and the estimate. Run the path until BLine
finishes it or the autonomous period ends, and record which happened; do not put a time limit on the
path. Compare the true and estimated trajectories after contact.

Last, repeat the contact path with one parameter or initial condition changed, such as approach
speed or initial lateral position, keeping the remaining conditions fixed. Explain what changed,
what the logs support, and which contact or friction assumptions would need hardware measurements
before they describe a physical robot.

## Reproduce Both Simulators

Give another member the FuelSim and maple-sim instructions, pinned versions, expected observations,
and log locations. The member repeats the scoring shot and controlled miss from the Step 6 launch
experiment, the open-space path, and the contact experiment. Record where the instructions needed
correction. FuelSim reproduction already completed for the B3-15.1 handoff can be credited here. The
mentor checks the student's explanation of the physics, camera, battery, and reset owners, and of
the separation between true and estimated pose.

## Badge Check

S means simulation, W means written reasoning, and M means mentor-observed review. The student
records an evidence link and an explanation in the student's own words for each row in the fork's
README. The mentor asks the student to explain a change and its result, checks each row, then signs
and dates the step on the [sign-off sheet](/documents/badges/badge-3/badge-3-sign-off.pdf).

| Row | Work | Done When |
| --- | --- | --- |
| B3-11.1 | Plan maple-sim integration | W: Identify pinned version and matching template, explain IO changes and update ownership, and predict an experimental result before running it. |
| B3-11.2 | Motion and contact | S: Run a known BLine path in open space and a controlled field-contact experiment, recording whether BLine finished each path or the autonomous period ended. Vary one parameter or initial condition and explain the observed response. |
| B3-11.3 | True and estimated pose | S/W: Log true and estimated pose separately; control uses the normal estimated pose. Explain what the model adds and cannot establish about hardware. |
| B3-11.4 | Reproduce the explorations | S/M: Another member reproduces FuelSim and maple-sim experiments from instructions in the combined simulation; the student explains the physics, camera, battery, and reset owners. |

## For the Mentor

`curriculum-reference` adds maple-sim through its own `vendordeps/maple-sim.json`, pinned to
`0.4.0-beta` (the legacy route this step replaces), and contains the focused `MapleExperiment` and
`MapleVisionTest`, smaller independent physics examples. `Badge3MentorSolution` declares the same
versions in `build.gradle` and drives SIM through `GyroIOMapleSim` and `ModuleIOMapleSim`. It keeps
the template `ModuleIOSim` source for reference but has no selector, so a student's selector goes
beyond the reference. See `DriveSimulation` for the arena, subtick and fuel decisions,
`RobotContainer.updateSimulation` and `RobotContainer.resetSimulation` for the loop position and
reset, and `MIGRATION.md` for battery ownership. `FieldContactSimulationTest` and
`CombinedSimulationTest` cover contact and the combined simulation, and `EXPERIMENTS.md` lists the
path and parameter experiments.
