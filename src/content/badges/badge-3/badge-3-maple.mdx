This step investigates how drivetrain contact changes a simulated path. Complete rows
B3-11.1–B3-11.3 before the final Step 12 autonomous runs; the B3-11.4 reproduction by another member
can follow with the Step 15 handoff. Start from your Badge3Starter fork with Step 6's FuelSim world
and Step 10's camera IO in place. Read [maple-sim](/frc/maple-sim), [FuelSim](/frc/fuelsim),
[Physics in the IO Layer](/frc/physics-in-the-io-layer), and
[Unit Tests in Simulation](/frc/unit-tests-in-simulation). Use one combined configuration: maple-sim
for chassis motion and contact, FuelSim for fuel and scoring, and PhotonVision for observations of
the same fuel world.

## Pin and Inspect the Dependency

Add maple-sim `0.4.0-beta` and dyn4j `5.0.2` to the fork. When this badge pinned maple-sim on
September 27, 2026, the public vendordep pointed to `0.4.0-beta-obstacles-fix`, whose Maven artifact
could not be resolved, so declare both in `build.gradle` instead of adding a vendordep. The
Starter's `build.gradle` has no `repositories` block, so add one above `dependencies` with Maven
Central (for dyn4j) and maple-sim's Maven repository. Put the two `implementation` lines inside the
Starter's existing `dependencies` block, beside `implementation wpi.java.deps.wpilib()`:

```groovy
repositories {
    mavenCentral()
    maven { url = uri("https://shenzhen-robotics-alliance.github.io/maple-sim/vendordep/repos/releases") }
}

dependencies {
    implementation "org.ironmaple:maplesim-java:0.4.0-beta"
    implementation "org.dyn4j:dyn4j:5.0.2"
    // ...the Starter's existing dependency lines stay here
}
```

Record both versions in the student README, with the SHA-256 hash of the resolved
`maplesim-java-0.4.0-beta.jar` from Gradle's cache (under
`.gradle/caches/modules-2/files-2.1/org.ironmaple/` in your user folder). Treat a later version as a
deliberate dependency change that needs a rebuild and repeated experiments.

## Choose the Drivetrain Model

Start from Cobra's simulated drive. In the fork's SIM mode, `RobotContainer` builds `Drive` from an
empty `GyroIO` and four `ModuleIOSim` instances, each modeling its module's drive and turn motors
with `DCMotorSim`, so the simulated robot has no gyro, wheel slip, or field contact.

Choose which of maple-sim's AdvantageKit template projects matches Cobra's drive IO and explain why.
[The drivetrain, and what it costs](/frc/maple-sim#the-drivetrain-and-what-it-costs) lists the
templates. Then explain how maple-sim's module and gyro simulation differ from `ModuleIOSim`.

Keep `ModuleIOSim` in the fork. Add a selector in `RobotContainer`'s SIM case, such as a constant,
that builds `Drive` from either the `ModuleIOSim` drivetrain or the maple-sim drivetrain, so you can
run the same commands against both models and compare them in simulation.

## Assign One Update Owner

The arena advances the drivetrain physics once per robot period, with its internal subticks. The
module and gyro IO read the resulting sensor data. Remove the old drivetrain physics updates from
that configuration so two models do not both move the same robot. Preserve the normal estimator and
path-follower interfaces.

Work through four ownership decisions and record each one:

1. **Subticks.** Run first at maple-sim's default subtick count and watch module steering in
   AdvantageScope, comparing requested and measured module angles. Record what you observe, then
   choose a subtick count with `SimulatedArena.overrideSimulationTimings` and justify it from the
   log.
2. **Fuel.** maple-sim's 2026 arena places its own fuel through `placeGamePiecesOnField`. Decide how
   the arena keeps the field obstacles without placing fuel, so FuelSim stays the only fuel owner,
   and check that maple-sim holds no game pieces after a reset.
3. **Loop position.** Decide where the arena update runs in the robot loop. Find where
   `IterativeRobotBase` calls `simulationPeriodic` relative to `robotPeriodic`, where the fork runs
   the command scheduler. Write down whether the module IO reads physics produced in the same loop
   or the previous one, and what delay that adds between a command and its measured motion.
4. **Battery.** Find every place the fork writes the roboRIO input voltage.
   `SimulatedArena.simulationPeriodic` updates maple-sim's `SimulatedBattery` each subtick, and
   `SimulatedBattery` writes `RoboRioSim.setVInVoltage`. The Starter's roller sims, such as
   `SingleRollerIOSimTalonFX`, also write it from their own current draw. Keep one owner, and
   register each mechanism's current draw with it.

Record true field pose, estimated field pose, requested chassis speeds, measured module states,
battery behavior, and the experiment configuration. BLine receives the estimated pose. True pose is
for simulated observations and comparison, not a shortcut into control.

## Check Contact Before the Paths

Before the path experiments, write a short test that drives the maple-sim chassis into a field wall
with direct voltage and compares true motion with what the commanded voltage alone would produce.
[A Mechanism in the Loop](/frc/unit-tests-in-simulation#a-mechanism-in-the-loop) shows how to run
the robot loop inside a test. This establishes chassis contact behavior; it does not establish
normal-estimator path behavior. For B3-11.2–B3-11.3, run the combined-world route and the parameter
experiment using the normal estimator for control and truth only for comparison. Preserve both runs.

## Run Two Experiments

First run a known BLine route in open space. Record its start and end poses, completion or timeout,
path error, and elapsed time. Repeat it from the same conditions to establish the variation present
in the model.

Then introduce a known obstacle or field boundary on a controlled route. Predict where contact will
occur and how it may change true motion, wheel readings, and the estimate. Run with a time bound so
a robot blocked by an obstacle cannot command drive indefinitely. Compare the true and estimated
trajectories after contact.

Change one parameter or initial condition, such as approach speed or initial lateral position. Keep
the remaining conditions fixed. Explain what changed, what the logs support, and which contact or
friction assumptions would need hardware measurements before they describe a physical robot.

## Reproduce Both Simulators

Give another member the FuelSim and maple-sim instructions, pinned versions,
expected observations, and log locations. The member repeats a scoring shot, controlled miss,
open-space path, and contact experiment. FuelSim reproduction already completed for the required
handoff can be credited here. Record where instructions needed correction. The mentor checks the
student's explanation of model ownership and truth-versus-estimate separation.

## For the Mentor

`curriculum-reference` adds maple-sim through `vendordeps/maple-sim.json` and contains the focused
`MapleExperiment` and `MapleVisionTest`, a smaller independent physics example.
`Badge3MentorSolution` declares the same versions in `build.gradle` and drives SIM through
`GyroIOMapleSim` and `ModuleIOMapleSim`. It keeps the template `ModuleIOSim` source for reference
but has no selector, so a student's selector goes beyond the reference. `DriveSimulation` builds a
`SimulatedArena` from `RebuiltFieldObstaclesMap` with an empty `placeGamePiecesOnField`, and sets 20
ms periods with 40 subticks because the 24:1 steering reduction was unstable at the default step.
`RobotContainer.updateSimulation`, called from `Robot.robotPeriodic` before the scheduler, advances
the arena and then FuelSim; `registerBatteryLoad` adds each mechanism sim's current to
`SimulatedBattery`. `FieldContactSimulationTest` and `CombinedSimulationTest` cover contact and the
combined world. `EXPERIMENTS.md` lists the combined-world route and parameter experiment.
