The student prepares the library for current-based control while preserving the voltage baseline. Start after [Calculus for Controls](/badges/badge-3-calculus). Badge 2 supplies FX, FXS and Nova introductions, configuration records and the two CTRE roller simulations. Before advanced physical comparisons, verify the actual fixture and its voltage baseline using [Hardware Evidence Completion](/badges/badge-3-hardware#first-enable). Simulation can proceed while its physical appointment is pending.

## Bridge to the Supplied Adapters

The student begins with Badge 2's tested configuration record, builder, general mechanism models and selected physical roller. Compare the supplied FX and FXS adapters with the roller paths built in Badge 2 before the advanced comparisons. Trace a configuration field, a request and a measurement through each unfamiliar adapter; distinguish supplied code from the student's changes. Additional vendor implementations in the base are teaching assets, not evidence of prior mastery.

Keep controller-specific capability and gain records explicit. Constructor validation and builder tests still apply; inspect the vendor configuration result before using the device. The required FX/FXS comparisons cover roller, flywheel and pivot. Linear rail and additional elevator ports remain extensions.

## Keep the Requested Quantity Explicit

Voltage describes the electrical potential applied to the motor. Torque current is a different requested quantity, expressed in amperes. A current request cannot be implemented by passing the same number into a voltage method. Keep `Voltage`, `Current`, `AngularVelocity`, and `Angle` in the mechanism-facing API, then convert at the vendor boundary.

Read [IO Layers](/frc/io-layers), [Current Limiting](/frc/current-limiting), and [Manual Tuning: Introduction](/frc/manual-tuning-introduction). Draw the route from a subsystem goal to the vendor request and back through logged measurements. Identify the units at every conversion.

The guided change is a separate torque-current capability for Talon FX. The mentor's `TorqueFXExample` shows the 2026 request classes against the pinned base dependencies. The student adds a typed current method to their own design, rejects nonfinite values, and records the selected output mode. Talon FXS remains voltage-controlled. Unsupported current operation must fail visibly at configuration or request time; a no-op that appears successful does not meet the row.

Use separate gain sets for voltage and torque-current control. A voltage-mode proportional gain produces volts per unit of error; the corresponding current-mode gain produces amperes per unit of error. Copying the numeric gain between them does not preserve the controller.

## Preserve Simulation Ownership

General simulation advances its model through its existing periodic owner. Vendor simulation advances through the vendor IO's owned callback and feeds sensor state back to the controller. Adding another model update in the subsystem would advance time twice. Draw and explain the update order before changing it.

REAL constructs physical IO, SIM constructs the selected simulation, and REPLAY consumes recorded inputs with no physical controllers. Add one test that selects each mode and checks what was constructed. Keep model truth out of robot decisions: it may generate sensor observations and comparison plots, but normal control reads the same IO contract used on hardware.

## Independent Change

The mentor selects a different mechanism family. The student adds or deliberately refuses the new capability, demonstrates the result, and explains how the type or runtime check prevents an unsupported request. The student also traces a recorded input through replay and identifies an output recomputed by the robot code.

## Badge Check

S means simulation, H means hardware, W means written reasoning, and M means mentor-observed review. The student records an evidence link, mentor signature, and date for each row. The mentor asks the student to explain a change and its result before signing.
