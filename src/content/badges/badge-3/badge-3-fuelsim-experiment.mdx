The student connects a measured flywheel response to one simulated shot. Complete this required step
after [Step 5: Flywheel Characterization and Tuning](/badges/badge-3-flywheel), in the Badge3Starter
fork. Its fixed-pitch experiment can run alongside the pivot module; both are needed for final
autonomous integration. The launch model and controlled experiment provide the evidence for rows
B3-06.1 and B3-06.2 in the assessment table below.

Research these first:

- [FuelSim](/frc/fuelsim), for installing, registering and launching.
- [Shooter Example](/frc/shooter-example), for converting wheel speed to surface speed.
- [Pose Geometry](/frc/pose-geometry), for `RobotToShooter` arrow naming, and its
  [3D section](/frc/pose-geometry#the-3d-versions) for `Transform3d`.

## Add FuelSim to the Fork

Cobra has no fuel simulation. FuelSim is a single file: copy `FuelSim.java` from the pinned upstream
revision, commit `37eff89`, into the fork as its README directs, edit the package line to match its
new folder, and keep the MIT license notice with it. Record the commit in the student README.
Copying a newer version from `main` later is a dependency change that needs a rebuild and repeated
experiments.

FuelSim works in meters and meters per second. `launchFuel(launchVelocity, hoodAngle, turretYaw,
launchHeight)` takes a hood angle where 0 is a horizontal launch, and it throws an
`IllegalStateException` if no robot has been registered with `registerRobot`. It always releases the
fuel at the registered robot's center, raised by `launchHeight`. For a release offset from the robot
center, compute the release position and velocity yourself and call `spawnFuel(position, velocity)`.
`Hub.BLUE_HUB.getScore()` reports the blue hub's score. `stepSim()` advances the physics once; a
robot loop that calls `updateSim()` must call `start()` first.

## Work the Launch Numbers First

Take a worked example before writing code. A flywheel at a measured 22 rotations per second turns at
approximately 138.23 radians per second. With a 2 in wheel radius and a slip factor of 0.85, the
launch speed is approximately 138.23 × 2 in × 0.85 ≈ 235 inches per second (19.6 ft/s). Changing
only the slip factor to 0.50 gives approximately 138 inches per second (11.5 ft/s) from the same
measured motor speed. These are simulation experiment values, not hardware recommendations.

The 2 in radius and the 32 in release height used below are teaching values, not Cobra's. Find
Cobra's own values in `ShooterConstants`: the wheel radius in `shooterFlywheelConfig`, and the
release height in the builder that produces `robotToShooter`. Record both, and note what
`getTransform2d()` discards from that builder.

The worked shots launch from field position (2.00 m, 4.02 m), heading zero, at 60 degrees and a 32
in release height. Field positions stay in meters because WPILib's field frame is metric. Before
running them, calculate the drag-free peak height of each launch and compare it with the hub's entry
height, `Hub.ENTRY_HEIGHT` in the pinned file (1.83 m, about 72 in). Predict which launch can score
and which cannot, then run both and check the change in the hub's score. Another model or geometry
may produce a different result, so check the score change rather than assuming every launch scores.

## Own the Fuel World

Write a small adapter around FuelSim. Its fuel list and physics constants are `protected`, which
Java makes visible to any class in the same package, so an adapter placed in FuelSim's package can
read fuel positions without subclassing; extend the class only if the design needs it. Give the
adapter one launch method that checks possession and readiness, uses the measured flywheel speed,
and consumes the held piece only after launching. Calling it again with no held piece produces no
projectile.

Register the robot's dimensions, a pose supplier for physics, and field-relative speeds. The Starter
has no true-pose source, so in this step register a fixed test pose, as the worked test does. Step
11 adds maple-sim's true pose. Never pass the pose estimator as the physics truth: robot control
uses the estimator, and the physics world needs a pose the estimator cannot influence. Update the
world once per 20 ms simulation period; FuelSim owns its internal subticks. In a unit test, call
`stepSim()` directly.

FuelSim publishes its state to NetworkTables, which is live only. For saved evidence, have the
simulation owner mirror fuel positions, possession, launch count and score into the AdvantageKit
log, and record launch speed and pitch at each launch event. FuelSim's launch speed is in meters per
second: convert the scoring shot's 235 in/s and check that the logged value matches. For replay,
consume the saved robot inputs and inspect the original recorded world outputs. Running a fresh
physics world is a new experiment, and its outputs are new results rather than reconstructed
evidence.

## Apply Cobra's Hood and Table Conventions

Keep the small scoring experiment separate from the Cobra calibration record. Cobra's hood is zeroed
at a launch elevation of 28 degrees above horizontal, and Cobra's code was written with that offset
in mind without stating it. In the fork, find the commented `.plus(Degrees.of(28.0))` on the
CANcoder magnet offset in `HoodConstants`; it is the only trace of that offset in the hood code.
`Hood` sets its DOWN, MID and UP presets to 0, 17 and 22 degrees of displacement from that zero.
`HoodConstants.pivotConfig` (28 through 50 degrees, starting at 28) and `HubInterpolator` (a fixed
28 degrees) are written as launch elevation instead.

Make the offset explicit: name each quantity as displacement or elevation, and add the offset once
when converting. Calculate the launch elevation for MID and UP and log both values. Then explain why
the conversion test checks DOWN and UP as well as MID, and which mistake a MID-only check would
miss.

Preserve the supplied hub table entries. They were collected manually with stationary robot-center
to hub-center distances from fused odometry, at a fixed hood setting. An offset shooter position
still matters for aiming and release, but it must not change that table's stationary range
convention. The automatic outputs are the speed and pitch that `TargetInterpolator.update()`
calculates each loop for the interpolator `BobotState.getShooterInterpolator()` returns, which is
`HubInterpolator` while the robot is in the `NEAR_ALLIANCE` field zone; `ShootOnTheMoveCommand`
reads the same interpolator. Compare direct-table and automatic outputs at table entries and an
intermediate range, with several robot headings and zero velocity. Before running the comparison,
read `update()` and predict which distance it looks up at zero velocity.

Cobra's `ShooterConstants.robotToShooter` is a two-dimensional `Transform2d`. Build the
three-dimensional `RobotToShooter` release transform from it and a measured release height, and use
measured mechanism states. Record which geometry is established and which transfer, drag, or timing
parameters remain estimates. Declare physical fitting cases and reserved validation cases before
adjusting the model. Retain misses and repeatability results; do not edit a working table merely to
make a simulated shot score.

## Check an Impossible Launch First

At each launch, calculate the peak height without drag from the measured launch state: the release
height plus the upward speed squared divided by twice the gravitational acceleration. If that
optimistic peak is below the modeled hub rim, inspect release height, wheel-speed conversion,
contact radius, and wheel-to-fuel speed transfer before adjusting drag. Passing the height check
does not establish horizontal aim, a descending entry, or a score.

Measure the contact radius independently: wheel speed and exit speed alone identify only the product
of radius and speed transfer. Declare fitting and reserved validation cases before changing model
parameters, retain misses, and compare repeatability as well as score.

## Make the Student Adaptation

1. Reproduce the worked scoring shot and controlled miss in a FuelSim test in the fork. Record the
   model version, initial state, measured speed, radius, slip, angle, height, and score change.
2. Connect the launch method to the student's measured flywheel input and one explicit launch event.
   Keep a fixed angle and height for this first experiment. Confirm that a goal change does not
   instantly become the launch speed.
3. Predict the effect of one changed parameter. Repeat from the same initial conditions, save the
   trace, and compare the prediction with the result.
4. Demonstrate that not-ready and empty requests do not launch. Cancel while preparing and confirm
   that the feeder stops.
5. Write reproduction instructions for another member. Step 12 later replaces the fixed pitch with
   measured pivot angle and connects the same world to collection and PhotonVision.

The student explains model assumptions separately from controller performance. A successful
simulated shot does not calibrate slip, drag or contact behavior for a physical shooter.
