## Scenario

Answer five questions about scouting data: filter by drivetrain, select top scorers, average climb rates, check a threshold, and find a match.

Write each query with a stream and with a loop. Compare results and explain which version you find easier to read.

Every stream version should be **one expression**, from `list.stream()` to the terminal
operation. Every loop version must return the same type, including `Optional`, so callers can use either version.

A stream describes a sequence of operations on values. Operations such as `filter`
and `sorted` build the pipeline; a terminal operation such as `toList` or `findFirst`
starts processing and produces a result. Create a fresh stream for each query: a
stream cannot be reused after a terminal operation. A predicate is a yes-or-no test;
its `test(entry)` method is the test to call in the matching loop version.

The required calls use non-null lists and predicates, and `k` is non-negative. An
empty list is still a valid input: filtering and top-K return an empty list, grouping
returns an empty map, `anyTeamOver` returns `false`, and `firstMatching` returns
`Optional.empty()`. Never return `null` to represent no matching team.

Sort top-K by descending `pickScore`. When two teams have the same score, keep their
original input order. Both Java's ordered stream sort and `List.sort` are stable, so
you do not need to invent a second ranking rule. Limit the sorted result to at most
`k` entries; `k == 0` returns an empty list.

For list-returning pairs, agreement means equal values in the same order. For the map
pair, agreement means equal drivetrain keys mapped to equal rounded averages; map
iteration order is not part of the result. Agreement does not require identical list
mutability. `Stream.toList()` returns an unmodifiable list, while a loop may build a
mutable `ArrayList`. Callers in this assignment only read either result.

## Stretch Goals

First save passing copies of the required `TeamEntry.java` and `StreamQueries.java`.
Try each stretch goal in separate copies so added output and methods cannot interfere
with the required browser checks.

- Add `summary(List<TeamEntry>)` returning a record `Summary(int count, double
  totalScore, double maxClimbRate, String topTeamName)` from a single pipeline. Look at
  `Collectors.teeing`. Start with three passes, then decide whether the
  one-pass version is clearer.
- Take one query, write it a third time with `parallelStream()`, and time all three over
  100,000 entries with `System.nanoTime`. Be ready for the parallel version to lose.
- Rewrite `topKByPickScore` so it does not sort the whole list. A bounded priority queue
  can reduce the work to O(n log k) instead of O(n log n). Compare the implementations'
  measured behavior and readability for the input sizes you care about.
