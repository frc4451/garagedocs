## Scenario

Practice six recursive operations: factorial, array sum, string reversal, two versions of exponentiation, and binary search. Each method needs a stopping case and a recursive call that approaches it.

Trace a small input on paper before running it.

No loops in any of the bodies. `main`'s test driver is allowed them; the methods are not.

The required input contract matters when you choose base cases. `factorial` accepts
`0` through `20` and rejects negative values; results above `20!` do not fit in a
`long` and are outside this assignment. `sum` receives a non-null array and a `from`
index from `0` through `arr.length`. `reverse` receives a non-null string. Both power
methods accept a non-negative integer exponent. Binary search receives a non-null
array sorted in ascending order and an inclusive range; the supplied wrapper creates
that range, including `low == 0` and `high == -1` for an empty array.

The required reversal examples use simple Latin letters. The starter's
`charAt`/`substring` approach works with Java UTF-16 code units, so it is not a
general-purpose reversal for text containing a supplementary Unicode character,
whose surrogate pair would be split. Unicode-aware reversal is outside this rubric.

## Halving The Exponent

`powerSlow` makes one recursive call per unit of exponent. `powerFast` uses the
identity:

```text
base^exp = (base * base)^(exp / 2)   // when exp is even
         = base * base^(exp - 1)     // when exp is odd
```

Here `^` is mathematical exponent notation and `exp` is the exponent whose size is
called `n` in O(n). Do not copy this as Java: Java's `^` operator is bitwise XOR, not
exponentiation. Express the identity with multiplication and recursive calls.

Every even step halves the remaining exponent, so the depth goes from O(n) to O(log n).
Increment `slowCalls` and `fastCalls` at the top of the two methods; `main` prints both
counts for `2.0^10` so you can see the difference rather than take it on trust.
Each active call also occupies stack memory until it returns. Reducing depth therefore
reduces both the number of calls and the maximum number of power calls held on the
stack at once.

## Stretch Goals

First save a passing copy of the required `RecursionWarmups.java`. Work on each
stretch goal in a separate copy so extra methods, state, or output cannot interfere
with the required checks.

- Add `fib(int n)` the naive way and time `fib(35)`. Then add `fibMemo` backed by a
  `HashMap<Integer, Long>` and time it again. Record several runs and explain the
  repeated subproblems removed by memoization; individual timings remain noisy.
- Add a recursive maze solver over a `boolean[][]`: mark visited, recurse on the
  neighbours, and decide whether failed paths should remain marked. Unmarking permits
  a later branch to revisit a cell and is appropriate when the path itself affects
  which moves are legal; leaving it marked avoids repeated work when reachability
  depends only on the cell.
- Rewrite `reverse` so it does not call `substring` or repeatedly concatenate growing
  strings. Each operation can copy characters, so changing only the index is not
  enough to guarantee linear work. Pass an index and fill a character array or use a
  `StringBuilder`, then compare.
