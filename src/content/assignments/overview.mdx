Practice Assignments is Part 2 of [Java](/java). Here you use what you learned in [Fundamentals](/java/fundamentals) to build programs from written requirements. The requirements tell you what a program must do. A **rubric** is a checklist with points that helps you and your mentor review the work.

These programs run without a robot or robot-specific software. Start with the preparation on each assignment page; you don't need to finish all of Fundamentals first.

## Start Here

1. If you're new to Java, complete [Java Overview](/java/fundamentals/overview), [Java Setup](/java/fundamentals/setup), and [Printing](/java/fundamentals/printing).
2. Read [Introduction to Version Control](/tools/introduction-to-version-control) in Tools, then complete [A00: Practice Repository Setup](/java/assignments/a00-practice-repository-setup). A00 links the account, Git installation, and file-saving instructions you need.
3. Open [A01: Hello Team](/java/assignments/a01-hello-team). Read its preparation links and all its requirements before writing the program.
4. Write enough code to meet one requirement, run it, and compare the result with the assignment's example. Add the next requirement after the first works.
5. Run any provided checks, review the rubric, and save the completed work to GitHub using the submission steps below.

Use VS Code with local Java 25 or a supported browser exercise on Java 17. The browser runner needs internet and may take time to start. Tasks involving local files, several source files, or a debugger may require local tools; follow the assignment's instructions. If you can't install them, ask your mentor for an approved computer.

## Save and Submit

A **repository** holds your project files and their recorded history. **Git** records that history; **GitHub** hosts an online copy that your mentor can review. A00 creates one student-owned repository for the Practice track. Each later assignment names its own folder inside it, so a new assignment doesn't overwrite earlier work.

Saving in the editor, making a commit, and pushing are separate actions:

1. **Save the files** in the assignment folder on your computer. Follow the assignment's repository checkpoint for the folder name and required files.
2. **Update `README.md`.** This is the repository's introduction and submission checklist. Mark the completed work in its table and record the references you used.
3. **Commit the changes.** A commit records a checkpoint with a message describing the work. Follow [A00's commit steps](/java/assignments/a00-practice-repository-setup) if the process is unfamiliar.
4. **Push the commit to GitHub.** Open your repository on the GitHub website and check that the assignment files and updated checklist appear there.

Send your mentor or reviewer the repository's web address once. They can use the same address for later assignments and review how the work changed over time. A private repository works when the reviewer has access. Running an exercise in the browser does not submit your work or update GitHub.

The official [About Git guide](https://docs.github.com/en/get-started/using-git/about-git) provides more background on commits and sharing changes. You can return to it after completing A00.

## Read an Assignment

A00 is a setup checklist. The programming assignments that follow generally contain these parts:

- **Topic and Cites:** the skill being practiced and links to lessons to read first. "Cites" is the preparation list.
- **Difficulty and Time:** an estimate for planning. Leave time to revisit lessons or ask for help.
- **Scenario:** the problem the program should solve.
- **What to Build:** required names, information the program receives (**input**), results it produces (**output**), and unusual cases it must handle.
- **Hints:** starting points or documentation to use when you're stuck. They don't supply the completed program.
- **Repository Checkpoint:** the folder and saving steps for submitting this assignment.
- **Self-Grading Rubric:** the requirements to review and the points each earns.
- **Stretch Goals:** optional additions after the required version works.
- **Sources and Related Lessons:** references and further explanations.

Where provided, automated checks compare your program's behavior with selected cases. Passing those checks doesn't show that you've met every requirement. Read the rubric too, and be ready to explain your code to your mentor.

<span id="the-rubric"></span>

## Review Your Work

Most programming assignments divide 100 points as shown below. Use the rubric on the assignment itself: [A28: Big-O Reading](/java/assignments/a28-big-o-reading#self-grading-rubric), for example, gives different weights to explanations and measurements.

| Area | Points | What to Check |
| --- | --- | --- |
| Functionality | 60 | The code compiles, produces the required results, and runs without crashing for valid input. |
| Edge Cases | 15 | The program handles the unusual or limiting cases named in the assignment, such as an empty input or a value at the allowed limit. |
| Code Quality | 20 | Names describe their purpose, the organization is readable, and the code follows the assignment's design requirements. |
| Comments | 5 | Include the required author and date header. Explain decisions whose reasons wouldn't be clear from the code. |
| Total | 100 | Use the assignment's rubric to score the actual submission. |

As later lessons introduce methods and fields, apply those lessons when reviewing code quality: keep each method focused on one job, share repeated logic, use `final` for values that shouldn't change, and keep fields `private` where required. Remove unused code. The first assignments don't require you to learn these later concepts before you can begin.

If a check fails, record the input you used, the expected result, the actual result, and what you tried. Bring that evidence to your mentor. Work through the missed step together, then repeat it yourself before marking it complete.

## Use Hints

Make an attempt before using a hint. If you don't understand the requirement, ask for clarification first. If you read example code, close it and explain the approach in your own words before writing your version.

If you can't explain a line of your program, follow the linked lesson or ask your mentor to work through it with you. Record references in your repository's `README.md` so the reviewer can see what you used.

Complete the required version before trying a stretch goal. If an extension changes the required names or output, put it in a separate file or folder so the required submission remains available for review.

## When You're Stuck

Use these links when the named problem appears. They cover topics introduced at different points in the course.

- For text comparisons that give the wrong result, revisit [comparing strings](/java/fundamentals/conditionals#comparing-strings).
- If a line of input seems to be skipped after reading a number, review [number and line input](/java/fundamentals/console-input#mixing-token-reads-and-line-reads).
- If division loses the fractional part you expected, check [integer and decimal division](/java/fundamentals/calculations#integer-vs-floating-point-division).
- For a loop that goes past the end of an array, review [Arrays](/java/fundamentals/arrays), including how positions are numbered.
- For a `NullPointerException`, revisit [the null reference](/java/fundamentals/objects-and-references#the-null-reference) and check where the object should have been created.
- When replacing behavior inherited from another class, review [overriding](/java/fundamentals/inheritance#overriding) and the `@Override` check.
- If error-handling code hides what went wrong, revisit [Try-Catch](/java/fundamentals/try-catch).

For help reading an error message or preparing a question for your mentor, use [Reading Docs and Errors](/tools/reading-docs-and-errors#read-an-error) in Tools.
