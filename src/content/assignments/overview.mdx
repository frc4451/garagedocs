Practice Assignments is Part 2 of [Java](/java). Apply the Fundamentals lessons by building a program from written requirements. Each assignment names its preparation, expected behavior, and review rubric.

Keep these standalone Java programs in one GitHub repository. Each assignment has its own folder, so you can reuse an idea without overwriting an earlier submission. No WPILib installation or robot is required.

<RulesBox title="Start here">

1. Complete [A00: Practice Repository Setup](/java/assignments/a00-practice-repository-setup).
2. Read an assignment's preparation links and requirements.
3. Implement one requirement, run it, and compare the result with the example.
4. Use the automated checks where provided, then review the rubric with a mentor. Checks do not grade your explanation, comments, or every local task.
5. Push the completed folder and update your repository README.

Use VS Code with local Java 25 or the supported browser exercises on Java 17. The browser runner needs internet and may take time to start. File-system, debugger, and multi-file tasks may need local tools.

</RulesBox>

### Submit your work through GitHub

[A00: Practice Repository Setup](/java/assignments/a00-practice-repository-setup) creates one
student-owned repository for the full Practice track. Every later assignment names a
folder in that repository. When an assignment is complete, update the repository's
submission table, commit the assignment folder, and push it to GitHub.

Submit the repository URL to your mentor or reviewer once. They can use the same link to
check later assignments, review commit history, and compare your self-score with the code.
A private repository works if the reviewer has access.

### What an assignment looks like

Every assignment uses the same shape, so you always know where to look:

1. **Topic**: a few words naming the concept this targets
2. **Cites**: links into [Java Training](/java). Review the named topics if you cannot yet explain or use them
3. **Difficulty and time**: a rough estimate for someone who read the cited lessons and
   is not stuck looking up syntax
4. **Scenario**: the problem in plain language
5. **What to build**: the concrete requirements: method names, expected input and output,
   edge cases. This is the contract you are filling
6. **Hints**: collapsed, for when you are stuck. Method signatures, a one-line skeleton,
   or a pointer to the exact JavaDoc page
7. **Repository checkpoint**: the folder, checklist update, commit, and push that submit
   the work
8. **Self-grading rubric**: a point breakdown totalling 100
9. **Stretch goals**: optional extensions if you finish early
10. **References**: JavaDoc, background reading, related lessons

### Use hints and references

Try the required method before opening a hint. If you read example code, close it and explain the approach in your own words before implementing your version.

If you cannot explain a line, ask a mentor or follow the linked Fundamentals lesson. Record references you used in your README.

Complete the required version and preserve its passing output before attempting stretch goals. Put extensions that change method signatures or output in a separate file or folder so the required submission remains reviewable.

### Pitfalls that bite almost everyone

- **Comparing strings with `==`**: use `.equals()`. See [Comparing strings](/java/fundamentals/java-conditionals#comparing-strings)
- **Mixing `nextInt()` and `nextLine()`**: a stray newline stays in the buffer
- **Integer division**: `7 / 2` is `3`, not `3.5`. See [Integer vs floating-point division](/java/fundamentals/java-calculations#integer-vs-floating-point-division)
- **Off-by-one in array loops**: use `< array.length`, not `<=`. See [Arrays](/java/fundamentals/java-arrays)
- **`NullPointerException` from an object array**: new object arrays start full of `null`
- **Forgetting `@Override`**: the compiler catches typos and signature mismatches for you
- **`catch (Exception e) {}`** that hides bugs: catch specifics, or let it propagate
