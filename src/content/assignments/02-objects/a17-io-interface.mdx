## Scenario

Use an interface to separate a climber's requested actions and readings from the code providing them. Pass either a mock or a small simulation into the same Climber class.

Both implementations are console models. The mock prints requests; the simulation changes a number using a stated formula. Neither controls real hardware or models the full physics of a climber.

## What To Build

Complete [Interfaces](/java/fundamentals/interfaces) and [Dependency
Injection](/java/fundamentals/dependency-injection) first. Badge 1 assigns
both before A17. An interface states which calls are available; an implementation
decides what those calls do. Constructor injection means `Climber` receives a
`ClimberIO` object instead of constructing one for itself.

IO means **input/output**: readings come into the subsystem, and requests go out.
A mock is a small substitute that follows the same interface and records or prints
calls without contacting hardware.

Build the specified climber first, locally or in the browser, so you can use the same checks. As an extension, design an interface for an intake or pivot.

The required local submission is also the climber. If the embedded browser prompt
still says to choose any local mechanism, follow this page: complete and save the
climber first, then treat another mechanism as extension work.

## Build Locally

Create `ClimberIO.java`, `ClimberIOMock.java`, `ClimberIOSim.java`, `Climber.java`,
and `ClimberDemo.java` in the assignment folder. Put the matching top-level type
in each file. Declare the interface and four classes `public`, and make every
constructor and required method public. The browser combines all five types into
one file, where only `ClimberDemo` can be public.

## Trace The Swap

`ClimberIO` contains four public method signatures and no changing state. Both IO
classes write `implements ClimberIO`, so Java requires them to supply all four
public methods. Their private fields belong to their own objects.

`Climber` stores one `private final ClimberIO`. Its constructor receives that
object and saves it. The demo chooses either `new ClimberIOMock()` or
`new ClimberIOSim()` when it constructs a climber. After that choice, the same
`Climber` code calls the same four interface methods. Java dispatches each call to
the implementation in the object it received.

In the simulation, each call to `setVoltage` advances the model by one simulated
second. To *integrate* position means to accumulate that change over calls. The
position change for one call is `volts * 0.02`, so the first `setVoltage(6.0)` call
adds `6.0 * 0.02 = 0.12` meter. Clamp only the required upper limit at `0.30` meter.
This timestep and limit are assignment data, not robot constants or a full physics
model.

Follow the call order carefully. `Climber.climb` checks the current limit reading
before it asks the IO object to apply voltage. A call that first reaches `0.30`
therefore still uses the requested voltage; the next call sees the limit and
applies `0.0`. Under this required contract, a negative request at the top is also
replaced by zero. Treat bidirectional limit handling as a later design discussion,
not a change to this assignment.

## Stretch Goals

Finish and save the required climber first. Try stretch work in a copy so new
methods or output cannot interfere with the required trace.

- Add a third implementation, `ClimberIOReplay`, that returns readings from a hard-coded
  array of past values. Now you can re-run a match without a robot or a simulator.
- Add an `updateInputs` method that fills a small inputs object once per tick, and make
  every getter read from that instead. Compare your result with AdvantageKit's IO layer
  after reading [The IO Layer On The Robot](/frc/io-layers).

- As an optional model experiment, add a lower clamp at `0.0` and test negative
  voltage. Keep it out of the required version because the assignment contract only
  requires the upper `0.30` limit.
