### Scenario

Sort the same scouting entries by team number, average points, climb rate, and pick score. Give TeamEntry a default ordering with Comparable, then use Comparator for the other orderings.

### What to build

**`TeamEntry`** holding `teamNumber`, `teamName`, `averagePoints`, `climbRate` and
`matchesObserved`. Validate in the constructor: team number `[1, 99999]`, climb rate
`[0.0, 1.0]`, `matchesObserved` not negative.

- Implement `Comparable<TeamEntry>` with **natural order = team number ascending**.
  Use team number as the default ordering for this exercise
- Add `static double pickScore(TeamEntry t)` returning
  `averagePoints + climbRate * 25.0`

That weighting is arbitrary on purpose. The point is that *you* decide it, and that
deciding it is a strategy question rather than a programming one.

**`RosterSorter`** sorts the same roster four ways: by team number using natural
order and no comparator, by average points descending, by climb rate descending, and
by pick score descending with team number as the tiebreaker, then demonstrates that
sorting objects is **stable**.

  "<strong>Never subtract to compare.</strong> <code>a.teamNumber() - b.teamNumber()</code> looks neat and overflows on large values. <code>Integer.compare</code> and <code>Double.compare</code> exist precisely for this, and <code>Double.compare</code> also handles the awkward cases that <code>&lt;</code> gets wrong.",

### Stretch goals

- Add a `minMatches` filter so a team seen twice cannot top the pick list on a fluke
  average. Decide whether that belongs in the comparator or before the sort, and say why.
- Rewrite all four comparators with `Comparator.comparing`, `reversed()` and
  `thenComparing`. Compare the readability against the explicit versions.
