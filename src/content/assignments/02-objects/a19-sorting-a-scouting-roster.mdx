## Scenario

Sort the same scouting entries by team number, average points, climb rate, and pick score. Give TeamEntry a default ordering with Comparable, then use Comparator for the other orderings.

The supplied team names, numbers, and statistics are fixed exercise data. Do not
treat them as a current or verified scouting roster, and keep them unchanged because
the browser checks compare the resulting order and text.

## What To Build

**`TeamEntry`** holding `teamNumber`, `teamName`, `averagePoints`, `climbRate` and
`matchesObserved`. Validate in the constructor: team number `[1, 99999]`, climb rate
`[0.0, 1.0]`, `matchesObserved` not negative.

- Implement `Comparable<TeamEntry>` with **natural order = team number ascending**.
  Use team number as the default ordering for this exercise
- Add `public static double pickScore(TeamEntry t)` returning
  `averagePoints + climbRate * 25.0`

The supplied exercise weight is 25 points per unit of climb rate. Use that exact
weight for the required `pickScore`, because the checks and rubric depend on it. In
a real scouting system, choosing and documenting a different weight would be a
strategy decision; trying alternatives belongs in a stretch experiment after the
required version passes.

**`RosterSorter`** sorts the same roster four ways: once by team number using natural
order with no comparator, then with three comparator objects for average points
descending, climb rate descending, and pick score descending with team number as
the tiebreaker. It then uses another climb-rate comparator to demonstrate that
sorting objects is **stable**.

## Stretch Goals

First save a passing copy of the required version. Try each stretch goal in a
separate copy so changed ordering or extra output cannot interfere with the required
checks.

- Add a `minMatches` filter so a team seen twice cannot top the pick list on a fluke
  average. Decide whether that belongs in the comparator or before the sort, and say why.
- Rewrite the three alternate orderings with `Comparator.comparing`, `reversed()`
  and `thenComparing`. Reuse the climb-rate comparator for the stability check, then
  compare the readability against the explicit versions.
