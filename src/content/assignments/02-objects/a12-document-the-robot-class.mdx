### Scenario

Six weeks into build season somebody asks why `Robot` refuses a weight of 250. The
answer is in the code, but reading it means tracing a constructor. Javadoc puts the
answer where they will look and generates a page they can read without
opening your source at all.

### What to build

Open your `Robot.java` from [A11](/java/assignments/a11-simple-robot-class) and document it.

**The class itself**: a Javadoc block above `public class Robot` with a one-sentence
summary, a short paragraph (2–4 sentences) on the invariants it maintains, an
`@author` tag, and `@since` with the date or season.

**Every public constructor**: a one-sentence summary, `@param` for each parameter
describing what a valid value looks like, and `@throws IllegalArgumentException`
saying exactly when it fires.

**Every public method**: a summary, `@param` for each parameter, `@return` describing
the result (omit for `void`), and `@throws` for anything it can produce.

Use `{@code ...}` for names and literals, and `{@link ...}` to cross-reference.

### The shape of it

```java
/**
 * Constructs a fully-specified {@code Robot}.
 *
 * <p>Every parameter is validated. If any value is out of range,
 * the constructor throws and no {@code Robot} is created.
 *
 * @param name          the robot's display name; must be non-{@code null} and non-blank
 * @param teamNumber    the FRC team number; must be in {@code [1, 99999]}
 * @param maxSpeedMps   the robot's top speed in m/s; must be in {@code [0.0, 30.0]}
 * @param weightLbs     the robot's mass in pounds; must be in {@code [0, 200]}
 * @throws IllegalArgumentException if any parameter is outside its valid range
 */
public Robot(String name, int teamNumber, double maxSpeedMps, int weightLbs) { ... }
```

That shows the *form*. The content is yours: paraphrase the rules from A11 in your
own words rather than copying this block.

### Generate and read it

```bash
javadoc -d docs Robot.java RobotTester.java
```

Open `docs/index.html` in a browser and read your own class as a stranger would.
This step is not optional: most weak Javadoc looks fine in the source and falls apart
on the rendered page, where the summary line stands alone.

<RulesBox title="Hints" items={[
  "<strong>The first sentence is special.</strong> Javadoc lifts it into the summary table, on its own, with no context. \"Sets the speed.\" is useless there; \"Sets the top speed in metres per second, rejecting values outside 0 to 30.\" survives the trip.",
  "<strong>Document the <em>why</em>, not the <em>what</em>.</strong> <code>@param weightLbs the weight in pounds</code> tells the reader nothing they could not guess. <code>@param weightLbs the robot's mass in pounds; must be in [0, 200], since anything heavier cannot pass inspection</code> answers the question they need answered.",
  "<strong>Preconditions belong in <code>@param</code>, failures in <code>@throws</code>.</strong> The parameter tag says what a caller must supply; the throws tag says what happens when they do not. Splitting them that way stops the block turning into a paragraph.",
  "<strong>Run <code>javadoc</code> before you call it done.</strong> It warns about missing <code>@param</code> tags, typos in parameter names, and broken <code>{@link}</code> targets: a free proofreader."
]} />

### Stretch goals

- Add `{@link}` cross-references between `Robot` and the setters that enforce the same
  ranges, then check that the links resolve in the generated HTML.
- Write the class-level paragraph as if for somebody who will *subclass* `Robot`. What
  decide what callers can rely on and what remains free to change.
