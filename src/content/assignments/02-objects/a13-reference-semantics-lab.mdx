## Scenario

An object variable holds a reference. Two variables can refer to the same object, and a method receives a copy of a reference passed to it.

Predict five experiments before running them. Comparing your prediction with the output helps identify which part of reference behavior needs another look.

## Work Through It

For each of the five experiments:

1. **Predict** what every print will produce, *before running*. Write it in the
   `// PREDICTION:` comment already in the starter
2. **Run** it
3. **Reconcile.** If the result differs from your prediction, add `// SURPRISE: I expected X, got Y, because Z.` If it matches, explain why in one sentence.
   Start that sentence with `// Confirmed:` and state the reason.

You turn in the file with the predictions and explanations still in it. Correct
output alone does not earn the prediction-and-explanation requirements in the
Functionality and Comments rows of the rubric.

## Trace The Copies

Draw a box for each variable and a circle for each object. An assignment such as
`Robot b1 = a1;` copies the reference value from one box to another; it does not
copy the object. Both arrows then point to the same circle. A second `new Robot(...)`
draws a second circle, even when its constructor arguments match.

A method call makes another variable box for each parameter. For `speedUp(a4)`,
Java copies `a4`'s reference into `r`, so the two arrows temporarily point to the
same object. Calling a setter through `r` changes that shared object. In
`replace(a4)`, assigning a new reference to `r` changes only the parameter box;
the caller's `a4` box still holds its original reference.

Returning an object reference works the same way. A method such as `getRobot()`
returns a copy of its reference, not a copy of the object. If the returned object
is mutable, the caller can change that same object. A true defensive copy requires
constructing a separate object, which these experiments do not ask you to write.
