## Scenario

Store a button condition as a BooleanSupplier and read it on each tick. Compare the current value with the previous value to detect a new press.

This exercise runs Runnable actions directly. Its whileTrue runs an action on every held tick; WPILib's Trigger.whileTrue schedules a Command on the rising edge and cancels it on the falling edge. It does not repeatedly reschedule a command that finishes while held.

## Read The Starter

Badge 1's shorter route prepares you with Functions as Data, Lambdas, and
Functional Interfaces. You do not need Method References for the required work.
The starter uses anonymous classes in `main`, so first match each object to the
single method the scheduler can call later:

<ContentTable
  headers={["Stored type", "Call it later with", "Meaning here"]}
  rows={[
    ["<code>BooleanSupplier</code>", "<code>getAsBoolean()</code>", "Ask whether the button is pressed now."],
    ["<code>Runnable</code>", "<code>run()</code>", "Perform an action now."],
    ["<code>DoubleSupplier</code>", "<code>getAsDouble()</code>", "Read the current telemetry value now."]
  ]}
/>

`condition` stores the question, rather than the answer from one moment. Passing
`condition` to the scheduler gives it work to call on every tick. Calling
`condition.getAsBoolean()` during registration would produce only the `boolean`
answer from that moment, and the registration method does not accept a boolean.

One clear way to keep each condition, action, binding kind, and previous value
together is a small helper type. You may put a private nested class inside
`Scheduler`, for example:

```java norun
private static class Hook {
    private final BooleanSupplier condition;
    private final Runnable action;
    private final boolean repeatWhileTrue;
    private boolean previous;

    // Write a private Hook(...) constructor that stores the first three values.
}
```

This is a partial structure, not a completed scheduler. A `static` nested class is
declared between `Scheduler`'s braces, behaves like an ordinary helper class, and
does not need a separate `Scheduler` object. Store `Hook` objects in one
`List<Hook>`, add one in each registration method, and let one loop in `tick()`
decide whether to call `action.run()`. Initializing `previous` to `false` matches
the required first tick, which starts released. Each registered hook asks its own
supplier once during a tick and reuses that result for its decision and its
`previous` update. Two hooks may happen to wrap the same button condition, but
each hook still owns separate previous-state memory.

The anonymous classes in `main` read and update the `static` fields `trigger` and
`shooterRpm`. Static fields are class state, so this example does not demonstrate
capturing a local variable. If you later use a lambda with a local variable, that
local must be final or effectively final, as explained in
[Lambdas](/java/fundamentals/lambdas).

Telemetry needs the same pairing idea: each label must remain attached to its
`DoubleSupplier`. A private nested helper with `private final String label` and
`private final DoubleSupplier source` is enough. `poll()` asks each source for its
value when it prints, so it reports the value from the current tick.

## Build Locally

Create `Button.java`, `Scheduler.java`, `Telemetry.java`, and `CommandDemo.java`
in `assignments/a22-command-binding/`. Each file contains the matching `public`
top-level class. Make the constructors and methods used across files `public`.
Keep the helper types private inside their owning classes. Put the
`java.util.function` and collection imports above the classes that use them. The
browser starter keeps all four top-level types in one editor, so only
`CommandDemo`, the class containing `main`, is public there.

Run these commands from the assignment folder:

`main` presses the button across five ticks: released, held, held, released, and held, so
the rising edge happens **twice**. Getting `onTrue` to fire exactly twice, and
`whileTrue` three times, is the assignment.

Trace the five ticks on paper before debugging. Tick 1 runs no action. Ticks 2
and 5 are false-to-true changes, so both registered actions run. Because `main`
registers `onTrue` first and `whileTrue` second, their output must follow that
order on those ticks. Tick 3 is still
true, so only the repeating action runs. Tick 4 is false, so neither action runs,
but every hook must still save that false value for the next tick.

## What The Checks Cover

The automated checks compare the five-tick console trace: when each action runs
and the telemetry value after each tick. Compiling the supplied `main` also proves
that `onTrue` can chain into `whileTrue`, but it does not prove that the final
`whileTrue` call returns the same button. The checks do not inspect where previous
state lives, whether you duplicated loops, or whether you wrote the required
comment. Review those rubric items in your code even after all checks pass. This
scheduler uses simulated boolean and number values, so it needs no controller,
roboRIO, or physical robot.
