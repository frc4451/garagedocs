## Scenario

A scouting form should reject invalid values and let the user correct them. Read five fields, validate each one, then print a summary.

## What To Build

A single file `ScannerEcho.java`. Prompt for these inputs **in order**, re-prompting on bad
input until each value is acceptable:

<ContentTable
  headers={["Input", "Accepted"]}
  rows={[
    ["Team number", "An <code>int</code> from 1 to 99999 inclusive"],
    ["Team name", "Any non-empty string after trimming"],
    ["Driver count", "An <code>int</code> from 1 to 4 inclusive"],
    ["Average score", "A <code>double</code>, 0 or greater"],
    ["Climbed?", "<code>yes</code> or <code>no</code>, any case"]
  ]}
/>

Once all five are gathered, print the summary block:

```text
--- Team Summary ---
Team:           1234 (Example Robotics)
Drivers:        2
Avg score:      45.50
Climbed:        yes
```

## Requirements

- Exactly one `Scanner` for the whole program, closed before exit
- A re-prompt loop for **each** input. Wrong type or out of range prints a one-line error and
  asks again. Handle invalid supplied values without crashing; if input ends, stop instead of re-prompting forever
- Use `nextInt`, `nextDouble` and `nextLine` correctly, including the leftover-newline
  problem when you switch between numeric and line reads
- A separate `public static` helper per input, each taking the `Scanner`, prompting, validating and
  returning the value. `main` is a thin orchestrator:

```java norun
public static int     readTeamNumber(Scanner in);
public static String  readTeamName(Scanner in);
public static int     readDriverCount(Scanner in);
public static double  readAvgScore(Scanner in);
public static boolean readClimbed(Scanner in);
```

These lines show required declarations. They end in semicolons only to list the
signatures compactly; they are not five methods you can paste into the class. In your
program, each declaration needs a body between `{` and `}` that eventually returns the
listed type.

## Handle Input And EOF

Read [Try-Catch](/java/fundamentals/try-catch) before using the error-handling pattern below. `throw` stops the normal path and transfers control to a matching `catch` block.

`nextInt()` and `nextDouble()` read one whitespace-separated token. `nextLine()` reads the
rest of the current line. After a successful numeric token read, consume the rest of that
line once before the next helper tries to read a whole-line team name. When a numeric type check fails, consume the bad token with `next()` or discard its line with `nextLine()` before trying again. Checking the same unread token repeatedly would never make progress.

The browser supplies all saved sample lines and then reaches end of input (EOF). A terminal
can also reach EOF when input comes from a file. For a numeric field, check `hasNext()`
first: `false` means EOF. If a token exists, use `hasNextInt()` or `hasNextDouble()` to
decide whether it has the requested numeric type. For a whole-line read, use
`hasNextLine()` to distinguish an available line from EOF. If no token or line remains,
stop the run with one clear message. One workable design is to let a helper run
`throw new java.util.NoSuchElementException("Input ended.");` when its availability check
is false. Put the five helper calls and summary printing inside one `try` block in `main`,
then add one `catch (java.util.NoSuchElementException error)` block that prints
`error.getMessage()`. Because control jumps to the catch, the unfinished summary is
skipped. Keep ordinary invalid values inside the helper's re-prompt loop. This EOF path is
different from a bad value: there is nothing left to correct. Put `in.close()` after the
catch so both a complete run and an EOF run close the one scanner.

The first automated check supplies one valid set. The second supplies out-of-range numbers
and an invalid climbed response before valid replacements. These checks confirm the final
summary shape, but they do not test non-numeric text, an empty team name, EOF, helper

## Stretch Goals

Keep the checked required version unchanged. Try stretch behavior in a separate
`ScannerEchoStretch.java` file with a matching class name because it changes accepted input
or when the program exits.

- Give up after five bad attempts on any single field and exit with a clear message rather
  than looping forever.
- Accept a blank line for the average score, meaning "not recorded", and print `n/a` in the
  summary instead of a number.
