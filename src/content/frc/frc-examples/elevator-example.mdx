You built a launcher and a drivetrain on the IO pattern in [Kit Bot R07](/kit-bot/r07-launcher-io) and [R08](/kit-bot/r08-drive-io), writing every IO class yourself. On the competition robot FRC 4451 does not write those from scratch each time: `org.robotzgarage.frc2026`, the ROBOTZ Garage library toured in [Reading Our Robot Code](/frc/team-robot-code#the-two-packages), already has a `SingleRoller` with real, sim and vendor-sim IO implementations, and an `Elevator` that specialises it. This lesson builds an elevator on that library, in simulation, the way a new mechanism gets added to Cobra.

### The shape

```
Elevator (ROBOTZ Garage library)          extends   SingleRoller (ROBOTZ Garage library)
  ├─ ElevatorConfig                          ├─ SingleRollerIO io      ← TalonFX / SimTalonFX / Sim / empty
  ├─ height ↔ rotations conversion           ├─ inputs (AutoLogged)
  ├─ clamped goal                            ├─ LoggedTunableNumbers for kP…kA
  └─ ElevatorSim for logging/limits          └─ steadyStateCharacterization()
```

Everything you wrote by hand for the Kit Bot launcher (the interface, the inputs struct, the real and sim implementations, the tunable gains) is the `SingleRoller` half. `Elevator` adds what makes a roller an elevator: a drum radius that turns rotations into a height, travel limits, gravity, and a mechanism drawing.

### Step 1: the constants

Two configs, kept together so they cannot drift: the **real** TalonFX config and the **sim** config that carries the physics the model needs. The `ElevatorConfig` describes the mechanism itself and is shared by both.

```java
public class ElevatorConstants {
  public static final double reduction = 9.0;                 // motor rotations per drum rotation
  public static final Distance drumRadius = Inches.of(0.75);
  public static final Distance minHeight = Inches.of(0.0);
  public static final Distance maxHeight = Inches.of(56.0);
  public static final Mass carriageMass = Pounds.of(16.0);

  public static final Elevator.ElevatorConfig elevatorConfig =
      Elevator.ElevatorConfig.builder()
          .gearbox(DCMotor.getKrakenX60Foc(2))
          .minHeight(minHeight)
          .maxHeight(maxHeight)
          .drumRadius(drumRadius)
          .initialHeight(Inches.zero())
          .tolerance(Inches.of(0.5))
          .carriageMass(carriageMass)
          .simulateGravity(true)                              // never false for an elevator
          .moi(0.004)
          .reduction(reduction)
          .build();

  public static final TalonFXConfig elevatorTalonConfig =
      TalonFXConfig.builder()
          .canId(30)
          .canBus(Constants.rioBus)
          .reduction(reduction)
          .currentLimitAmps(60.0)
          .invert(false)
          .isBrakeMode(true)                                  // an elevator coasts down otherwise
          .foc(Constants.focEnabled)
          .slot0Config(new Slot0Configs()
              .withKS(0.15).withKG(0.35).withKV(0.12).withKA(0.0)   // feedforward; kG holds it up
              .withKP(4.0).withKI(0.0).withKD(0.1)
              .withGravityType(GravityTypeValue.Elevator_Static))
          .mmConfig(new MotionMagicConfigs()
              .withMotionMagicCruiseVelocity(RotationsPerSecond.of(40))
              .withMotionMagicAcceleration(RotationsPerSecondPerSecond.of(120)))
          .build();

  public static final TalonFXConfigSim elevatorTalonConfigSim =
      TalonFXConfigSim.builder()
          .config(elevatorTalonConfig)                        // the SAME real config…
          .dcMotor(DCMotor.getKrakenX60Foc(2))               // …plus what the physics model needs
          .moi(0.004)
          .build();
}
```

Three things to notice against the Kit Bot version. The gains are **on the motor controller** (`Slot0Configs`, Motion Magic), not in a WPILib `ProfiledPIDController`; [Motor Configuration](/frc/motor-controller-configuration#control-request-types) covers why. `withGravityType(Elevator_Static)` tells the TalonFX that kG is a constant lift, which is what an elevator needs (an arm would use `Arm_Cosine`). And the sim config wraps the real one rather than copying it, so a gain changed in `elevatorTalonConfig` is the gain the simulation runs.

### Step 2: the subsystem

FRC 4451's convention is a thin `SubsystemBase` that *owns* a library mechanism, exposes command factories, and nothing else, the same shape as Cobra's `Shooter` wrapping a `FlywheelFollower`:

```java
public class ElevatorSubsystem extends SubsystemBase {
  private static final String name = "Elevator";

  private static final LoggedTunableNumber stowHeight = new LoggedTunableNumber(name + "/StowInches", 0.0);
  private static final LoggedTunableNumber scoreHeight = new LoggedTunableNumber(name + "/ScoreInches", 48.0);

  private final Elevator elevator;
  private final ElevatorMechanism mechanism;

  public ElevatorSubsystem(SingleRollerIO io) {
    elevator = new Elevator(name, io, ElevatorConstants.elevatorConfig);
    mechanism = new ElevatorMechanism(ElevatorMechanism.ElevatorMechanismConfig.builder()
        .name(name).length(0.1).width(6).color(new Color8Bit(Color.kOrange)).build());
  }

  @Override
  public void periodic() {
    elevator.periodic();                                       // inputs, logging, tunables, sim
    mechanism.update(elevator.getHeight());                    // the drawing follows the measured height
  }

  public Command goTo(Distance height) {
    return run(() -> elevator.setGoalHeight(height)).until(elevator::atGoal);
  }
  public Command stow()  { return goTo(Inches.of(stowHeight.get())); }
  public Command score() { return goTo(Inches.of(scoreHeight.get())); }
  public Command hold()  { return run(() -> elevator.setGoalHeight(elevator.getHeight())); }

  public Trigger atGoal() { return new Trigger(elevator::atGoal); }
}
```

`elevator.setGoalHeight` takes a `Distance` and clamps it to the travel limits before converting to rotor rotations, so a command asking for 80 inches on a 56-inch elevator gets 56 rather than a carriage into the crossbar. `atGoal` uses the config's tolerance. Both come from the library, and both were things you had to write yourself in [Kit Bot R07 Part 2](/kit-bot/r07-launcher-io-part-2).

### Step 3: choose the IO

The one place the environment is decided ([Simulation First](/frc/simulation-first#the-three-modes)):

```java
SingleRollerIO elevatorIO = switch (Constants.currentMode) {
  case REAL -> new SingleRollerIOTalonFX(ElevatorConstants.elevatorTalonConfig);
  case SIM  -> new SingleRollerIOSimTalonFX(ElevatorConstants.elevatorTalonConfigSim);
  default   -> new SingleRollerIO() {};
};
elevator = new ElevatorSubsystem(elevatorIO);
```

In `SIM` the `SingleRollerIOSimTalonFX` runs the real TalonFX code path against a `DCMotorSim` (the [vendor-sim-state pattern](/frc/physics-sim-io#the-vendor-sim-state-pattern)), so Motion Magic, kG and the current limit all behave as they will on the robot.

### Step 4: bindings

```java
operator.a().onTrue(elevator.stow());
operator.y().onTrue(elevator.score());
elevator.setDefaultCommand(elevator.hold());
```

A default `hold()` means the elevator is always closed-loop on *something*; with kG in the controller that is what keeps it from sagging between commands.

### Step 5: watch it in simulation

`Elevator/PhysicalSim/*` is a second, independent `ElevatorSim` the library runs alongside the TalonFX simulation, fed with the applied voltage. It exists to log what the physics thinks (position, current draw, limit contact) without touching the controller loop. When its `PositionInches` and the measured `CurrentHeightInches` disagree, one of the two models has a wrong constant, and that is worth finding before the carriage is real.

<RulesBox title="Common mistakes">

- **<code>simulateGravity(false)</code>.** The sim elevator holds at zero volts, kG tunes to nothing, the real one drops.
- **Gains in the subsystem.** They belong in the TalonFX config. A <code>ProfiledPIDController</code> in <code>periodic</code> is the Kit Bot way and does not transfer to the controller.
- **Heights in rotations at the API.** The library's boundary is <code>Distance</code>. Convert at the edge (<code>drumCircumference</code>), never in a command.
- **Reduction off by the drum.** <code>reduction</code> is motor rotations per <em>drum</em> rotation; the drum radius does the rest. Do not fold the circumference into the reduction.
- **Trusting <code>atGoal</code> with a zero tolerance.** The default is zero inches; set <code>tolerance</code> or the command never ends.

</RulesBox>
