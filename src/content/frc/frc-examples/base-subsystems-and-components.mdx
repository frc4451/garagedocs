[Composing Mechanism Subsystems](/frc/composing-mechanism-subsystems) argues that a reusable mechanism should be a plain object owned by a subsystem, and gives the reason: if every motor wrapper extends `SubsystemBase`, a command that needs the whole shooter has to collect three separate requirements.

That argument is sound and it is not the only workable answer. FRC 254 built the other one, FRC 2910 run it on their 2026 robot, and both have the results to say it works. A student who reads competition code will meet it, and should recognise it rather than assume it is a mistake.

<RulesBox title="Before you start">

[Composing Mechanism Subsystems](/frc/composing-mechanism-subsystems) for the design this compares against, and [Subsystems](/frc/subsystems) for what `SubsystemBase` and command requirements do.

</RulesBox>

### The other design

Instead of a plain `Pivot` object that a subsystem owns, there is a **base subsystem** that already extends `SubsystemBase` and implements everything a position-controlled mechanism needs. A concrete mechanism extends it.

In FRC 2910's code that base is `ServoMotorSubsystem`, and the hood is four words of declaration:

```java
public class HoodSubsystem extends ServoMotorSubsystem {
```

The base class carries the parts every position mechanism shares: motion-magic setpoints, soft limits, conversion between motor rotations and mechanism units, encoder zeroing, and a `home()` routine that drives to a hard stop and resets the encoder there. Its configuration object builds the `TalonFXConfiguration` with the soft limits and brake mode already set:

```java
// 2910, ServoMotorSubsystemConfig
return BaseMotorConfig.createMotorConfiguration(sensorRotationsToMechanismUnitsRatio)
        .withSoftwareLimitSwitch(new SoftwareLimitSwitchConfigs()
                .withForwardSoftLimitEnable(true)
                .withForwardSoftLimitThreshold(forwardSoftLimitThreshold)
                .withReverseSoftLimitEnable(true)
                .withReverseSoftLimitThreshold(reverseSoftLimitThreshold))
        .withMotorOutput(new MotorOutputConfigs().withNeutralMode(NeutralModeValue.Brake));
```

`RollerMotorSubsystem` is the same idea for things that spin: no position goal, no soft limits, effort control.

What the subclass adds is only what is specific to that mechanism. `HoodSubsystem` adds its state machine and its homing constants, and nothing else:

```java
private static final double HOMING_DUTY_CYCLE = -0.1;
private static final double HOMING_MECHANISM_VELOCITY_SETPOINT = 0.5;
private static final double HOMING_SETTLE_TIME_REQUIRED = 0.1;
private static final double HOMING_DEGREE_TO_RESET_TO = -0.139;
```

The pattern originates with **FRC 254**, whose `ServoMotorSubsystem` is the ancestor of this one. 2910's repository carries a `FRC Team 254-License.md` at its root, which is how the lineage is recorded.

### What each design costs

The trade is the classic one, and the FRC-specific part is the requirements row. Command requirements are per `Subsystem`, so the choice of what is a subsystem decides what can run in parallel. That is why the composition page argues as it does: a turret, a hood and a flywheel that share one shot solution should be locked as one unit, and that is easiest when they are one subsystem.

The counter is that 2910 do not have that problem, because their `SuperStructure` coordinates the mechanism subsystems and the mechanisms are rarely commanded individually. When a superstructure is doing the coordinating, the requirement granularity matters much less, and the inheritance saves real boilerplate.

### Which to use

**GarageDocs and Cobra use composition.** Cobra's `Intake` owns a `Pivot` and a `Flywheel` as plain objects, the ROBOTZ Garage library is built that way, and every mechanism lesson in this group follows it. That is the house style and it is not changing.

Two honest reasons rather than one:

- **It matches the library that exists.** `SingleRoller`, `Pivot`, `Flywheel` and `Elevator` are already plain components with an IO boundary. Switching would mean rewriting them, and the gain would be boilerplate rather than capability.
- **It keeps the scheduler boundary where a beginner expects it.** One subsystem is one thing the robot does. A student who has recently learned command requirements can predict what conflicts, and that predictability is worth more in a training codebase than it is on a robot maintained by people who wrote the base class.

**Recognise the other one when you read it.** 254 and 2910's code is some of the best available to learn from, and `extends ServoMotorSubsystem` is not a beginner mistake. If you find yourself writing the same motion-magic-plus-soft-limits-plus-homing block for the fourth mechanism, you have found the problem the base class solves, and the fix inside our design is to push that block down into the component rather than up into a base class.

<RulesBox title="What to take from it either way">

- A homing routine belongs with the mechanism code, not copied into each subsystem.
- Soft limits and brake mode belong in the shared configuration builder, so no mechanism can forget them.
- Conversion between motor rotations and mechanism units belongs in one place, whichever place that is.
- If several mechanisms are always commanded together, something has to own that. A parent subsystem and a superstructure are both valid answers.

</RulesBox>
