The Kit Bot launcher in [R07](/kit-bot/r07-launcher-io-part-2) was one roller, voltage in, RPM out, with a calibration table you built by hand. Cobra's shooter is the same idea with everything the competition robot needs on top: two motors that must agree, velocity held by the motor controller instead of by you, a target that comes from *where the robot is*, and a way for the rest of the robot to know the wheel is ready. This lesson reads `frc.robot.subsystems.shooter` as it is in the repository; it is the example.

### The shape

```
Shooter (SubsystemBase)                       FlywheelFollower (ROBOTZ Garage library)
  ├─ FlywheelFollower shooter        owns →     extends FollowRollers
  ├─ LoggedTunableNumbers (setpoints)              ├─ FollowRollersIO io   ← TalonFX / SimTalonFX / empty
  ├─ command factories                             ├─ leader + follower inputs
  ├─ readiness Triggers                            ├─ tunable kP…kA
  └─ runShooterToHub() ← BobotState interpolator   └─ FlywheelSim for logging
```

`FollowRollers` is `SingleRoller`'s two-motor sibling: one IO that drives a leader and a follower, with both motors' inputs logged separately so a follower that has stopped following is visible. `FlywheelFollower` adds a `FlywheelSim` for physics logging, the way `Elevator` adds an `ElevatorSim` in the [Elevator Example](/frc/elevator-example#the-shape).

### Step 1: the constants

```java
public class ShooterConstants {
  public static final double shooterReduction = 24.0 / 24.0;
  public static final AngularVelocity maximumShooterVelocity = RotationsPerSecond.of(80);
  public static final AngularAcceleration maximumShooterAcceleration = RotationsPerSecondPerSecond.of(400);

  public static final FlywheelConfig shooterFlywheelConfig =
      FlywheelConfig.builder()
          .radius(Inches.of(1.5))
          .gearbox(DCMotor.getKrakenX60Foc(2))
          .moi(0.002)
          .reduction(shooterReduction)
          .build();

  public static final TalonFXConfig leaderShooterConfig =
      TalonFXConfig.builder()
          .canId(21).canBus(Constants.susBus)
          .reduction(shooterReduction)
          .invert(false).isBrakeMode(false)                 // a flywheel coasts down; brake mode fights it
          .foc(Constants.focEnabled)
          .slot0Config(new Slot0Configs()
              .withKS(16.0).withKV(0.125).withKA(0.0)       // feedforward, in AMPS: torque-current control
              .withKP(5.0).withKI(0.0).withKD(0.0))
          .mmConfig(new MotionMagicConfigs()
              .withMotionMagicCruiseVelocity(maximumShooterVelocity)
              .withMotionMagicAcceleration(maximumShooterAcceleration))
          .build();

  // …followerShooterConfig: same, canId 22, invertFollower(true)

  public static final TalonFXConfigFollowerSim flywheelFollowersConfigSim =
      TalonFXConfigFollowerSim.builder()
          .hardware(flywheelFollowersConfig)                  // the real pair…
          .dcMotor(DCMotor.getKrakenX60Foc(2))                // …plus the physics
          .moi(0.002)
          .build();
}
```

Two things are different from every Kit Bot mechanism. **The units of kS and kV are amps**, because the shooter is run with *torque-current* control (`setVelocityTorqueCurrent`): the controller commands motor current directly, which is proportional to torque, and FOC lets a Kraken do that precisely. Velocity control by current is stiffer and recovers faster after a shot than voltage control; [Control Request Types](/frc/motor-controller-configuration#control-request-types) has the comparison. And **brake mode is off**: a flywheel with brake mode spends current fighting its own inertia every time the setpoint drops.

### Step 2: the subsystem

```java
public class Shooter extends SubsystemBase {
  private static final String name = "/Shooter";

  private static final LoggedTunableNumber shooterVelocity =
      new LoggedTunableNumber(name + "/ShooterVelocity", 85.0);            // RPS, adjustable live

  private final FlywheelFollower shooter;

  public Shooter(FollowRollersIO shooterFlyWheelIO) {
    this.shooter = new FlywheelFollower(name + "/Shooter", shooterFlyWheelIO, ShooterConstants.shooterFlywheelConfig);
  }

  @Override
  public void periodic() {
    shooter.periodic();                                                     // inputs, logging, tunables, sim
  }

  public Command runShooterVelocityTorqueCurrent() {
    return run(() -> {
      double clamped = MathUtil.clamp(shooterVelocity.get(), 0.0, 200.0);
      shooter.setVelocityTorqueCurrent(RotationsPerSecond.of(clamped));
    });
  }

  public Command runShooterVelocityTorqueCurrent(AngularVelocity velocity) {
    return run(() -> shooter.setVelocityTorqueCurrent(velocity));
  }

  public Command stop() { return runOnce(shooter::stop); }
}
```

Note the pattern: `run(...)` commands that keep commanding the velocity every loop while they are scheduled, and `stop()` as a `runOnce`. A shooter is never "set and forget"; the command that wants it spinning owns it for as long as it runs. The `LoggedTunableNumber` setpoint means a mentor can change 85 to 90 from AdvantageScope's tunable editor mid-test without a deploy ([Tunable Constants](/frc/tunable-constants#declaring-a-tunable)).

### Step 3: the target comes from the pose

The Kit Bot's `runAtDistance` took a distance you typed. Cobra's shooter asks the robot where it is:

```java
/** Runs shooter to the velocity given by the hub interpolation table */
public Command runShooterToHub() {
  return run(() -> {
    InterpolatedCalculation calculation = BobotState.getHubInterpolator().getCalculation();
    AngularVelocity velocity = calculation.primaryVelocity();
    Distance distance = BobotState.getHubInterpolator().getDistanceFromTarget();

    Logger.recordOutput(name + "/ShootAtHub/VelocityRPS", velocity.in(RotationsPerSecond));
    Logger.recordOutput(name + "/ShootAtHub/DistanceFeet", distance.in(Feet));
    Logger.recordOutput(name + "/ShootAtHub/TargetPose", BobotState.getHubInterpolator().getTargetPose().get());

    shooter.setVelocityTorqueCurrent(velocity);
  });
}
```

`BobotState`, the [one global](/frc/bobot-state) that gets its own lesson under Cobra Architecture once pose estimation is covered, holds an interpolator per target. Each is an `InterpolatingDoubleTreeMap` from distance to flywheel velocity, exactly the structure you built in [Kit Bot R07 Part 2](/kit-bot/r07-launcher-io-part-2#from-one-fixed-voltage-to-a-calibration-table), with the distance computed every loop from the estimated pose to the target's field position. The shooter never knows about poses or targets; it asks for a velocity and logs why it chose it. The logging is what makes the table tunable at an event: `ShootAtHub/DistanceFeet` next to `ShootAtHub/VelocityRPS` next to whether the shot went in.

### Step 4: readiness, as a Trigger

Firing is a sequence (spin up, wait until fast enough, feed), and the "fast enough" is a `Trigger`, not a boolean method, so command groups can wait on it:

```java
public Trigger isShooterFlywheelNearRPS(AngularVelocity target, AngularVelocity tolerance) {
  return new Trigger(() -> this.shooter.getInputs().leaderVelocity.isNear(target, tolerance));
}

public Trigger isNearHubVelocity(AngularVelocity tolerance) {
  return new Trigger(() -> this.shooter.getInputs().leaderVelocity
      .isNear(BobotState.getHubInterpolator().getCalculation().primaryVelocity(), tolerance));
}
```

Which lets a scoring command read as the sequence it is:

```java
public Command scoreAtHub() {
  return shooter.runShooterToHub()
      .alongWith(
          Commands.waitUntil(shooter.isNearHubVelocity(RotationsPerSecond.of(1.0)))
              .andThen(feeder.feed()))
      .finallyDo(() -> feeder.stop());
}
```

The shooter keeps tracking the interpolated velocity for the whole command (the robot may be moving); the feeder waits for the Trigger, then runs; ending the command stops the feeder. [Command Groups](/frc/command-groups) is the grammar.

For the readiness Trigger, add a `Logger.recordOutput(name + "/Ready", …)` line in `periodic` (or log the feeder's state) and confirm on the discrete strip that feeding starts only after the velocity line has settled, not during the ramp. That single graph is the difference between a shooter that scores and one that lobs the first ball short every time.

<RulesBox title="Common mistakes">

- **Feeding on a timer instead of a Trigger.** Spin-up time depends on battery voltage and starting speed; only the measured velocity knows when it is ready.
- **kS/kV in volts on a torque-current mechanism.** Same names, different units. The numbers are an order of magnitude apart.
- **Brake mode on a flywheel.** Fights every decel, cooks the motor for nothing.
- **Reading only the leader.** The follower has its own inputs for a reason. Graph both.
- **A one-entry interpolation table.** It works at one distance and nowhere else, and simulation shows it the moment the robot moves.

</RulesBox>
