[Physics in the IO Layer](/frc/physics-in-the-io-layer) gives a mechanism a model: a motor, a gearbox, an inertia, a gravity term. Run it and the elevator reaches its setpoint on a graph without a robot existing. That answers questions about the mechanism.

It cannot answer whether the shot went in, because there is nothing to shoot. It cannot answer whether the intake picked up a fuel, because there is no fuel. The simulated robot drives through the trench, through the hub and through the other alliance's robots, because the only object in the world is the one you modelled.

A game simulation adds the rest: a field with walls and obstacles, game pieces with mass and bounce, and a scoring target that counts. This group covers two libraries that do that for 2026 and what each one costs to adopt.

### What a game simulation proves

The value is in the questions that need a game piece to exist:

- **An autonomous routine that collects and scores.** A path that drives over three fuel and a routine that intakes them are different claims. Without pieces on the field, [Autonomous Simulation](/frc/autonomous-simulation) can only check the path.
- **Whether the intake geometry reaches.** An intake whose bounding box sits above the fuel collects nothing, and that is visible in the simulation before it is visible on the practice field.
- **A shot solution across a range.** Sweep the distance, launch, and count what goes in. The interpolation table from [Units and Interpolation](/frc/math-toolbox-units-and-interpolation) gets a first pass this way instead of from the first practice session.
- **Driver practice before the robot exists.** A driver who has seen the cycle in simulation is not learning the cycle for the first time during a match.

### What it does not prove

A game simulation is a model of collisions, and collisions are where physics models are weakest. FuelSim's README says so directly: some of the parameters need tuning, "namely the coefficients of restitution of various collisions", and the result is close enough for simulation rather than a perfect analog. maple-sim runs a real rigid-body engine, which changes how the error behaves without removing it.

Specifically, do not conclude any of the following from a game simulation:

- **A tuned shooter.** The simulated fuel does not have the real ball's compression, surface, wear or spin. A hood angle that scores in simulation is a starting point for [Manual Tuning](/frc/manual-tuning-flywheel), not a result.
- **A reliable intake.** Real intakes fail on compliance, on pieces arriving at odd angles and on two pieces arriving at once. A rectangular bounding box models none of that.
- **Cycle times you can promise.** The simulated robot has no defence on it, no traffic, and a battery that never sags.

The rule from [Simulation First](/frc/simulation-first) still holds and gets sharper here: simulation proves that code does what you wrote, not that the mechanism works.

### Choosing between them

The question is what you already have.

**If the drivetrain simulation already works, start with FuelSim.** Cobra has `ModuleIOSim`, a pose estimator and a working simulator. FuelSim attaches to that without touching any of it: it asks for a pose supplier and a speeds supplier and leaves the drive code alone. The whole integration is a field, a constructor and a call in `simulationPeriodic()`.

**If you want the field to push back, use maple-sim.** A robot that can be pinned against the trench wall, shoved by an opponent, or stopped by a field element needs the drivetrain inside the physics engine. FuelSim's robot is a rectangle that fuel bounces off; it cannot be pushed, because its pose comes from your odometry rather than from a physics body.

The middle answer is the common one: run FuelSim first because it is cheap, find out whether game-piece simulation changes how the team works, and adopt maple-sim in the off-season if it does. Starting with the larger library and abandoning it halfway through January leaves the drive subsystem worse than it started.

### Where the simulated field shows up

Both libraries publish game-piece positions for AdvantageScope's 3D Field tab: FuelSim as a `Translation3d[]` on a NetworkTables topic, maple-sim through its arena's pose accessors. Added as game pieces on the 3D field, the fuel appears around the robot model you already configured in [Mechanisms in 3D](/frc/mechanisms-in-3d).

That shared destination is the practical reason to set up the 3D view before adopting either library. A game simulation with nothing drawing it is a score counter and a loop-time cost.
