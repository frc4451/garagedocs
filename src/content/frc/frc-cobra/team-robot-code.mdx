### Why this page exists

Every FRC lesson on this site teaches a pattern. This page shows where each pattern lives on the robot you will work on: [Cobra2026](https://github.com/frc4451/Cobra2026Private), FRC 4451's 2026 competition code. Read it once now to learn the shape, then come back to it from other lessons; each of them names the file to open.

The rule this codebase follows, and the one to follow when you add to it: **the robot's own code is thin, and the reusable parts live in a library.** Once you know where that line is, most of the repository is easier to read.

### The two packages

```text
src/main/java/
├── frc/robot/                           this robot, this season
│   ├── Main.java, Robot.java, RobotContainer.java, Constants.java
│   ├── subsystems/   drive, shooter, hood, feeder, intake, vision
│   ├── commands/     DriveCommands, ShootOnTheMoveCommand, …
│   ├── autonomous/   AutonomousManager, bline/BLineManager
│   ├── bobot_state/  BobotState, the robot's shared view of the world
│   ├── field/, util/
│   └── generated/    TunerConstants from Phoenix Tuner X (never hand-edited)
└── org/robotzgarage/frc2026/            the ROBOTZ Garage library, reused season to season
    ├── subsystems/   rollers, flywheel, elevator, pivot, vision
    ├── math/         interpolation, distance calculation
    └── util/         motor configs, controller helpers, VirtualSubsystem
```

`frc.robot` is what changes every year: which mechanisms this robot has, how they are wired, what the autos do. `org.robotzgarage.frc2026` is the ROBOTZ Garage library (ROBOTZ Garage is FRC 4451's team name): generic mechanisms with hardware behind an interface, built once and configured per robot. The split is [Packages and Project Layout](/java/java-packages#what-the-layout-looks-like) applied on purpose. A Cobra `Intake` is a handful of lines because the library's `SingleRoller` does the work.

### One mechanism, end to end

Follow the intake from hardware to button. Every mechanism on the robot is the same chain.

**1. The IO interface**, `org/robotzgarage/frc2026/subsystems/rollers/single/SingleRollerIO.java`. It declares what any single-motor roller can do (`runVolts`, `setVelocity`, `setGoal`, `stop`, and so on) and an `@AutoLog` inputs class listing everything worth reading back: position, velocity, applied voltage, currents, temperature, the current setpoint. This is the [IO layer](/frc/io-layer#the-interface) lesson, and it is [A17](/assignments/a17-io-interface) at competition scale. The inputs use the WPILib Units library (`Angle`, `AngularVelocity`, `Current`) rather than bare doubles, as [R03](/kit-bot/r03-constants#wpilibs-units-library) recommended.

**2. The implementations**, in the same folder. `SingleRollerIOTalonFX` and `SingleRollerIOTalonFXS` for Phoenix 6, `SingleRollerIONova` for a Thrifty Nova, `…WithCANCoder` variants where an absolute encoder is involved, and a `SingleRollerIOSim` family for the desk. One interface, six hardware answers. Each contains only what its device needs.

**3. The library subsystem**, `SingleRoller.java`. It owns an IO, an inputs object, and a name. Its `periodic` calls `io.updateInputs(inputs)` and then `Logger.processInputs(name, inputs)`; everything after that reads from `inputs`, never from hardware. It also carries the library's tunable feedforward and feedback configs. This is the class that keeps the robot subsystems short.

**4. The robot subsystem**, `frc/robot/subsystems/intake/Intake.java` and `IntakeConstants.java`. `Intake` composes one or more `SingleRoller`s and exposes **command factories**: `run(() -> …)` methods returning a `Command`, the shape from [Commands](/frc/commands#subsystem-command-factories). `IntakeConstants` holds the configs (CAN IDs, gear ratios, current limits, gains) as `public static final`, one per hardware variant plus a sim variant.

**5. The wiring**, `RobotContainer.java`. A `switch (Constants.currentMode)`: in `REAL` it builds `new SingleRollerIOTalonFX(IntakeConstants.intakeConfig)`; in `SIM` it builds `new SingleRollerIOSimTalonFX(IntakeConstants.intakeConfigSim)`. The `Intake` is the same either way. That is [R12](/kit-bot/r12-real-vs-sim#where-the-if-lives), and it is the reason the whole robot runs on a laptop.

**6. The button**, also in `RobotContainer`, binding a `GarageCommandXboxController` trigger to the factory method. This is [A22](/assignments/a22-command-binding) in production.

Every other mechanism follows the chain. The shooter uses `FlywheelFollower` over a `FollowRollersIO` (two motors, one leading); the hood is a `SingleRoller` on a TalonFXS; the swerve drive is the AdvantageKit template (`Module`, `ModuleIOTalonFX`, `GyroIOPigeon2`, `PhoenixOdometryThread`), which [Swerve Drive Example](/frc/swerve-drive-example#apply-synchronized-odometry-samples) walks through.

### BobotState: the one global

`frc/robot/bobot_state/BobotState.java` is the robot's shared picture of the world: the fused field pose, the vision observations queued for the pose estimator, the interpolation tables that turn distance to the hub into flywheel velocity, and the field targets ("closest drop-off", "the trench"). It is a `VirtualSubsystem`: it has a `periodic`, but no hardware, and no command requires it. Its state is static, so any subsystem or command can call `BobotState.getGlobalPose()` without being handed a reference.

That is a deliberate exception to the rule against globals. A robot has exactly one pose and one field, and threading them through every constructor would add ceremony without benefit. The discipline is that only `BobotState` writes them; everyone else reads. When you add state that more than one subsystem needs, this is where it goes. It is also where the [Shortest Paths](/java/java-algo-shortest-paths#where-this-sits-on-a-real-robot) idea of "which target is closest" is computed.

It has its own lesson, [BobotState: The One Global](/frc/bobot-state), covering the loop order, the VARCs, the interpolators and the game-logic Triggers. The base class it extends is [VirtualSubsystem](/frc/virtual-subsystem), the annotations on its fields are [Lombok](/frc/lombok), and the helpers it uses are in [The Math Toolbox](/frc/math-toolbox).

### Where to start reading

In this order. Each file is short enough to read in one sitting:

1. `Constants.java`: the `Mode` enum and the season's numbers.
2. `SingleRollerIO.java`: the interface and its inputs. Everything else is built on this shape.
3. `Intake.java` and `IntakeConstants.java`: the smallest complete mechanism.
4. `RobotContainer.java`: the `switch` on mode, then the button bindings.
5. `Shooter.java`: the same shape with interpolation and logging, which is what production adds.
6. `BLineManager.java`: about forty lines that make autos.

Then open a lesson and find its file. The codebase is organised so that you can.

<RulesBox title="Common mistakes when adding to it">

- **Putting hardware calls in a robot subsystem.** They belong in an IO implementation in the library. If the mechanism is new, the library gets a new IO; the robot gets a config.
- **Reading a motor directly instead of from <code>inputs</code>** after <code>processInputs</code>. Replay silently breaks.
- **A new <code>double</code> where a unit type exists.** The next reader cannot tell metres from inches, and neither can the code.
- **A magic number in a subsystem.** It goes in the <code>*Constants</code> class, next to its siblings.
- **A second global.** If it is not the robot's pose or its view of the field, it is probably a subsystem's own state.

</RulesBox>
