A robot pose describes where the robot is on the field and which way it faces. WPILib represents this state with `Pose2d`: an x-coordinate, a y-coordinate, and a heading.

Pose estimation keeps that value current while the robot moves. Autonomous paths, distance-based shots, and field-relative mechanism commands depend on the estimate using the same field coordinates as their targets.

<RulesBox title="Before you start">

This group uses WPILib geometry types throughout. Read [Pose Geometry](/frc/geometry-classes) first if `Pose2d`, `Transform2d`, and coordinate frames are unfamiliar.

</RulesBox>

### The field coordinate system

WPILib uses north-west-up (NWU) coordinates for the robot and field:

- +X points forward.
- +Y points left.
- +Z points up.
- Positive rotation is counterclockwise when viewed from above.

WPILib field layouts normally keep the origin on the blue-alliance end, with Field +X pointing away from the blue wall. Code can represent both alliances in this fixed frame and transform alliance-specific paths or targets separately.

```java
Pose2d fieldToRobot =
    new Pose2d(2.0, 3.0, Rotation2d.fromDegrees(90.0));
```

This pose places the robot at (2 m, 3 m), facing Field +Y.

**Odometry** integrates wheel and gyro measurements from a known starting pose. It updates quickly, but it cannot detect wheel slip from the encoders alone.

A **pose estimator** maintains odometry and accepts timestamped field-relative observations. WPILib uses each observation's timestamp to account for delivery delay. Standard deviations tell the estimator how much influence to give that observation.

### One failure example

Suppose the wheels report 1.0 m of travel while a collision makes them slip. The physical robot might move only 0.8 m. Odometry cannot observe that difference, so its pose becomes wrong by about 0.2 m.

A camera can later observe AprilTags and produce a field-relative pose. Robot code must reject unusable observations and assign uncertainty based on the measurement conditions before passing accepted observations to the estimator.

Keep the stages distinct:

- A sensor reports an observation.
- Filtering decides whether the observation is usable.
- The estimator combines accepted observations with odometry.
- The resulting pose remains an estimate that must be logged and checked.
