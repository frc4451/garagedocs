Wheel odometry starts from a known pose and integrates drivetrain motion. Encoders measure wheel or module position, and a gyroscope supplies the robot's heading. WPILib combines the changes into a new `Pose2d` each update.

Odometry updates without a camera or field marker. It cannot observe wheel slip or correct an incorrect conversion factor on its own, so its error accumulates until another source corrects the estimate.

<RulesBox title="Prerequisite">

This page assumes the coordinate frames and types from [Pose Geometry](/frc/geometry-classes).

</RulesBox>

### Measurements, not motor commands

Odometry uses measured positions:

- Differential drive uses cumulative left and right wheel distances plus gyro angle.
- Swerve drive uses one cumulative `SwerveModulePosition` per module plus gyro angle.
- Each distance must be in meters.
- Module arrays must use the order used to construct `SwerveDriveKinematics`.

Do not feed requested motor output, target velocity, or a module's instantaneous speed into an odometry position argument.

### Differential-drive odometry

Construct `DifferentialDriveOdometry` with the current sensor readings and known starting pose:

```java
DifferentialDriveOdometry odometry =
    new DifferentialDriveOdometry(
        gyro.getRotation2d(),
        getLeftDistanceMeters(),
        getRightDistanceMeters(),
        startingPose);
```

Call `update` after reading current sensors:

```java
@Override
public void periodic() {
    Pose2d fieldToRobot = odometry.update(
        gyro.getRotation2d(),
        getLeftDistanceMeters(),
        getRightDistanceMeters());
}
```

The wheel distances are cumulative readings. WPILib compares them with the previous update internally.

### Swerve-drive odometry

A swerve module position contains cumulative drive distance and the module's steering angle.

```java
SwerveModulePosition[] positions = {
    frontLeft.getPosition(),
    frontRight.getPosition(),
    backLeft.getPosition(),
    backRight.getPosition()
};

SwerveDriveOdometry odometry =
    new SwerveDriveOdometry(
        kinematics,
        gyro.getRotation2d(),
        positions,
        startingPose);
```

Read a fresh array before each update:

```java
@Override
public void periodic() {
    Pose2d fieldToRobot = odometry.update(
        gyro.getRotation2d(),
        getModulePositions());
}
```

This example uses front-left, front-right, back-left, back-right because `kinematics` was constructed in that order. A different consistent order also works.

### Higher-rate samples

Some drivetrains collect synchronized gyro and module samples faster than the normal robot loop. Apply each sample with its timestamp and keep the arrays aligned.

FRC 4451's Cobra drivetrain follows this pattern with pose estimators:

```java
for (int i = 0; i < sampleTimestamps.length; i++) {
    SwerveModulePosition[] positions =
        getModulePositionsForSample(i);

    poseEstimator.updateWithTime(
        sampleTimestamps[i],
        rawGyroRotation,
        positions);
}
```

Every value at index `i` must describe the same sampling time. Mixing a new gyro angle with old module positions introduces error that can resemble bad calibration.

### Gyro behavior

The gyro argument supplies the measured heading. WPILib maintains an internal offset between that reading and the pose heading, so resetting the pose does not require physically zeroing the gyro.

A device can report a continuous angle, a wrapped angle, or an orientation adjusted by its API. Convert the device convention at the IO boundary and expose a `Rotation2d` with the sign expected by the drivetrain code.

If the gyro is unavailable, swerve kinematics can estimate a heading change from module deltas:

```java
Twist2d robotMotion = kinematics.toTwist2d(moduleDeltas);
rawGyroRotation =
    rawGyroRotation.plus(new Rotation2d(robotMotion.dtheta));
```

This fallback depends on the same wheel measurements that can slip. Log the disconnect and treat the resulting heading as degraded.

### Resetting the pose

Reset with current sensor readings and the field pose that should correspond to them:

```java
public void resetPose(Pose2d fieldToRobot) {
    odometry.resetPosition(
        gyro.getRotation2d(),
        getModulePositions(),
        fieldToRobot);
}
```

Common reset sources include an autonomous starting pose and a deliberate operator action at a known location. A normal vision correction should go through a pose estimator instead of repeatedly resetting odometry.

### Diagnosing drift

- **Distance conversion:** A straight test produces a repeatable scale error.
- **Module steering offsets:** A swerve robot reports sideways or curved motion during a straight test.
- **Wheel slip or impact:** The estimate changes more than the physical robot moved.
- **Unsynchronized samples:** The estimate wobbles or curves during fast rotation.
- **Gyro sign or mounting:** Estimated heading changes in the wrong direction or about the wrong axis.
- **Mechanical play:** Reversing direction produces a repeatable dead band.

Record measured and estimated motion in a log. There is no useful general drift percentage; the result depends on the robot and test conditions.

### Odometry and pose estimation

WPILib pose estimators wrap the corresponding odometry behavior. If the robot will use vision or QuestNav, make the pose estimator the drivetrain's authoritative pose and call its update method every loop.
