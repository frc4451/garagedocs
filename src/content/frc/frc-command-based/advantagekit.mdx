<RulesBox title="An architecture, not just a tool">

AdvantageKit is listed among external tools, but adopting it is an architectural decision rather than an add-on. Your robot class changes, your subsystems get structured around the [IO layer](/frc/io-layer#the-problem-it-solves), and logging stops being something you remember to do.

That is the trade: more structure up front, in exchange for being able to reproduce any match on a laptop afterwards. This lesson covers the framework; [Hardware Abstraction with IO Layers](/frc/io-layer#the-subsystem-side) covers the subsystem structure it expects, the [Simulation](/frc/simulation-first) group covers running that structure on a laptop, and [Log Replay](/frc/log-replay) covers replay.

</RulesBox>

### Record inputs for replay

AdvantageKit is a logging, telemetry, and replay framework developed by Team 6328 (Mechanical Advantage). It records the inputs exposed through the project's logging structure. After a match, replay can feed those values through robot code to reproduce and investigate its behavior.

The IO layer records sensor inputs before subsystem logic uses them. During [log replay](https://docs.advantagekit.org/data-flow/built-in-logging), robot code receives those recorded values in the same order. Inputs omitted from the log cannot be reconstructed later.

AdvantageKit is open source and supports vendor hardware through the project's IO implementations.

### How replay uses the IO layer

AdvantageKit requires you to structure your code using the [IO Layer pattern](https://docs.advantagekit.org/data-flow/recording-inputs/io-interfaces/). Instead of reading sensors directly, your subsystems interact with an IO interface that can be swapped between real hardware, simulation, or a log file player.

During a match, the IO layer reads real hardware and AdvantageKit automatically logs all input values. After the match, you can run your code in replay mode, where the IO layer reads from the log file instead of hardware. Your robot code runs unchanged, receiving the exact same inputs it received during the match.

### LoggedRobot

The robot class extends `LoggedRobot` instead of `TimedRobot`:

```java
public class Robot extends LoggedRobot {
    private Command autonomousCommand;
    private RobotContainer robotContainer;
```

It is a drop-in replacement: same `robotPeriodic`, same `autonomousInit`, same 20 ms loop. The difference is that loop timing is handed to the logger, which is what makes replay possible: in replay mode the loop runs as fast as the log can be read rather than in real time.

Setup happens in the constructor, before anything else exists:

```java
public Robot() {
    // Record metadata, stamped into every log
    Logger.recordMetadata("ProjectName", BuildConstants.MAVEN_NAME);
    Logger.recordMetadata("BuildDate", BuildConstants.BUILD_DATE);
    Logger.recordMetadata("GitSHA", BuildConstants.GIT_SHA);
    Logger.recordMetadata("GitBranch", BuildConstants.GIT_BRANCH);
    Logger.recordMetadata(
        "GitDirty",
        switch (BuildConstants.DIRTY) {
            case 0 -> "All changes committed";
            case 1 -> "Uncommitted changes";
            default -> "Unknown";
        });

    switch (Constants.currentMode) {
        case REAL:
            // Log to a USB stick ("/U/logs") and publish live
            Logger.addDataReceiver(new WPILOGWriter());
            Logger.addDataReceiver(new NT4Publisher());
            break;
        case SIM:
            Logger.addDataReceiver(new NT4Publisher());
            break;
        case REPLAY:
            setUseTiming(false); // Run as fast as possible
            String logPath = LogFileUtil.findReplayLog();
            Logger.setReplaySource(new WPILOGReader(logPath));
            Logger.addDataReceiver(new WPILOGWriter(LogFileUtil.addPathSuffix(logPath, "_sim")));
            break;
    }

    Logger.start();

    robotContainer = new RobotContainer();
}
```

`BuildConstants` is generated by the build, not written by hand. It stamps the git commit, branch, and whether the working tree was dirty into every log file.

<RulesBox title="Why the metadata matters">

When a log shows behaviour nobody can explain, the first question is always "what code was actually on the robot?"

`GitSHA` answers it exactly, and `GitDirty` answers whether the code on the robot corresponded to a commit at all. Check both before spending an hour analysing a log.

Also: **plug in the USB stick.** On a real robot `WPILOGWriter` writes to `/U/logs`. No stick, no log, and the post-match analysis you were counting on does not exist.

</RulesBox>

### AdvantageKit Subsystem Structure

```java
public class Flywheel extends SubsystemBase {
    // 1. Define the inputs that will be logged
    // API: @AutoLog annotation - https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/AutoLog.html
    @AutoLog
    public static class FlywheelInputs {
        public double velocityRadPerSec = 0.0;
        public double appliedVolts = 0.0;
        public double currentAmps = 0.0;
    }

    // 2. Define the IO Interface
    public interface FlywheelIO {
        default void updateInputs(FlywheelInputs inputs) {}
        default void setVoltage(double volts) {}
    }

    private final FlywheelIO io;
    private final FlywheelInputsAutoLogged inputs = new FlywheelInputsAutoLogged();

    // Constructor injects the implementation (Real, Sim, or Replay)
    public Flywheel(FlywheelIO io) {
        this.io = io;
    }

    @Override
    public void periodic() {
        // 3. Update inputs from the IO layer
        io.updateInputs(inputs);
        
        // 4. Log the inputs automatically
        // API: Logger.processInputs() - https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/Logger.html#processInputs(java.lang.String,java.lang.Object)
        Logger.processInputs("Flywheel", inputs);

        // Your logic uses 'inputs.velocityRadPerSec' instead of 'motor.getVelocity()'
    }

    public void runVolts(double volts) {
        io.setVoltage(volts);
    }
}
```

### Logging

AdvantageKit automatically logs all fields in classes annotated with [@AutoLog](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/AutoLog.html). It uses a high-performance binary format (WPILOG/RLOG) that records data every loop cycle with minimal overhead. ([Logging Documentation](https://docs.advantagekit.org/getting-started/what-is-advantagekit/example-output-logging/))

You can also log custom outputs using [Logger.recordOutput()](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/Logger.html#recordOutput(java.lang.String,java.lang.Object)):

`Logger.recordOutput("MyState/Target", targetValue);`

`Logger.recordOutput("Odometry/Pose", pose);`

### Inputs vs Outputs

There are three logging mechanisms and they are easy to confuse:

<ContentTable
  headers={["Mechanism", "Recorded as", "Used for"]}
  rows={[
    ["<code>@AutoLog</code> on an inputs class", "<strong>Input</strong>", "Anything read from hardware; makes replay possible"],
    ["<code>@AutoLogOutput</code> on a method", "<strong>Output</strong>", "Values your code computed or commanded"],
    ["<code>Logger.recordOutput(key, value)</code>", "<strong>Output</strong>", "One-off values from inside a command"]
  ]}
/>

The distinction is the whole trick. **Inputs are replayed back into the code; outputs are what the code produced.** If a sensor reading is recorded as an output, replay will not feed it back in, and the replay is meaningless.

```java
// input: read from hardware, replayed
io.updateInputs(inputs);
Logger.processInputs("Drive/Module0", inputs);

// output: computed by us, not replayed
Logger.recordOutput("Odometry/Trajectory", activePath.toArray(new Pose2d[0]));
```

### Log Replay

Log replay is AdvantageKit's core feature. After a match, download the log file and run your robot code in replay mode. The IO layer reads from the log file instead of hardware, feeding the recorded sensor values into your code in the same order they occurred during the match.

This lets you debug match issues without the robot. You can step through code, inspect variables, modify logic, and verify that fixes work against real match data. The replay is deterministic: if your code is deterministic, the replay will match the robot's behavior exactly.

<RulesBox title="Getting started">

- Use the [IO Layer pattern](https://docs.advantagekit.org/data-flow/recording-inputs/io-interfaces/) for all subsystems that interact with hardware.
- Log all inputs using [@AutoLog](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/AutoLog.html) annotations.
- Log important outputs and states using [Logger.recordOutput()](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/Logger.html#recordOutput(java.lang.String,java.lang.Object)).
- Keep input classes simple: use primitives and basic data structures.
- Use [AdvantageScope](https://docs.advantagescope.org) to visualize and analyze log files.
- Keep your code deterministic: avoid random numbers, timestamps, or other non-deterministic sources in logic.

</RulesBox>

### @AutoLogOutput

Not every subsystem needs a full IO layer. For a simple mechanism, `@AutoLogOutput` logs the return value of a method with no other setup:

```java
@AutoLogOutput(key = "Conveyor/velocity")
public double getConveyorVelocity() {
    return conveyor.getVelocity().getValueAsDouble();
}
```

Because the annotation logs a **return value**, write setters that return the value they set. That is what puts commanded values in the log alongside measured ones, with no extra logging code anywhere:

```java
@AutoLogOutput(key = "Intake/targetPos")
public double setIntakePosition(double pos) {
    pivot.setControl(motionMagic.withPosition(pos));
    return pos;
}
```

Now `Intake/targetPos` and `Intake/Position`, commanded and actual, can be dragged onto the same graph. A `void` setter would leave half of that picture missing.

Remember these are **outputs**: visible in AdvantageScope, but not fed back in during replay. Anything read from hardware that your logic depends on belongs in an `@AutoLog` inputs class instead.

### Should you use it?

AdvantageKit is not free, and the honest answer depends on the robot. Here is the trade as it actually plays out.

<ContentTable
  headers={["What you get", "What it costs"]}
  rows={[
    ["<strong>Replay.</strong> A match log becomes a test case: change the code, replay the same inputs, see what the new code would have done. This is the one capability nothing else offers, and it is why the pattern exists.", "<strong>Every input must go through an IO interface.</strong> One extra class and one <code>@AutoLog</code> struct per mechanism, and the discipline of never reading hardware after <code>processInputs</code>. Miss it once and replay silently lies."],
    ["<strong>One log with everything in it.</strong> Inputs, outputs, commands, and the values you <code>recordOutput</code>, timestamped together, readable in AdvantageScope.", "<strong>An annotation processor in the build.</strong> Generated <code>*AutoLogged</code> classes, a vendordep pinned to the WPILib year, and build errors that name a file you did not write."],
    ["<strong>Tunables and telemetry for free.</strong> <code>LoggedTunableNumber</code> gives live gain tuning; <code>@AutoLogOutput</code> gives a graph for the cost of an annotation.", "<strong>A steeper first week.</strong> The template robot has more files than a plain command-based one, and a rookie meets IO, inputs, modes and logging before writing a single <code>run(…)</code>."],
    ["<strong>Simulation for the price of one more IO class.</strong> The same seam that enables replay makes <code>*IOSim</code> a natural place to put physics.", "<strong>Small mechanisms get heavier than they need.</strong> A one-motor roller does not need six files. The library's <code>SingleRoller</code> exists precisely to pay that cost once."]
  ]}
/>

**When it is the wrong choice.** A first robot such as the [Kit Bot](/kit-bot), with two subsystems, no simulation, and a team learning what a subsystem is. Kit Bot deliberately does not use AdvantageKit for that reason: the IO pattern is taught there with plain interfaces, and telemetry goes straight to NetworkTables. Nothing about the Kit Bot needs replay, and every file AdvantageKit adds is a file between a new programmer and their first working mechanism.

**When it is the right choice.** A competition robot whose autos and shots you will debug from logs at an event, with a mechanism library that already carries the IO cost so each new subsystem does not. That is Cobra, and it is why the lessons in this section are written the way they are: [IO Layers](/frc/io-layer#what-autolog-generates), [Tunable Constants](/frc/tunable-constants#declaring-a-tunable) and [Subsystems](/frc/subsystems#setters-that-return-what-they-set) all use AdvantageKit's annotations, because the code you will read and write does. [Reading Our Robot Code](/frc/team-robot-code#the-conventions-to-absorb) shows where each of those lands in the repository.

The pattern and the framework are separable, and it is worth knowing which is which. The IO pattern (hardware behind an interface, a sim implementation, a struct of inputs read once per loop) is good design with or without a logger, and it is what [A17](/assignments/a17-io-interface) and [R07](/kit-bot/r07-launcher-io#the-io-interface) teach. AdvantageKit is what turns that pattern into replay.
