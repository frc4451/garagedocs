### Command-Based Structure

A command-based project separates three concerns:

**Subsystems:** Physical hardware (drivetrain, intake, shooter) and the methods that control it.

**Commands:** Actions and logic: what to do and when.

**RobotContainer:** Setup and wiring: subsystem construction, button bindings, the auto chooser.

[WPILib Guide](https://docs.wpilib.org/en/stable/docs/software/commandbased/structuring-command-based-project.html)

### Directory Layout

Give each subsystem its own **package**, not just its own file. Simple projects sometimes put every
subsystem directly in `subsystems/`, and that works until a subsystem grows past one class. At that
point hardware abstractions, simulation implementations, and helpers all pile into one directory
with no indication of what belongs to what.

```
src/main/java/frc/robot/
├── Main.java                  // Entry point
├── Robot.java                 // Lifecycle (init, periodic)
├── RobotContainer.java        // Subsystem construction and bindings
├── Constants.java             // Robot-wide settings: mode, CAN buses, controls
├── generated/
│   └── TunerConstants.java    // Generated by Phoenix Tuner X
├── subsystems/
│   ├── drive/
│   │   ├── Drive.java
│   │   ├── Module.java
│   │   ├── ModuleIO.java
│   │   ├── ModuleIOTalonFX.java
│   │   ├── ModuleIOSim.java
│   │   └── GyroIOPigeon2.java
│   ├── intake/
│   │   ├── Intake.java
│   │   └── IntakeConstants.java   // Pivot and roller configs
│   ├── shooter/
│   │   ├── Shooter.java
│   │   └── ShooterConstants.java
│   └── vision/
│       ├── Vision.java
│       ├── VisionIO.java
│       └── VisionIOPhoton.java
├── commands/                  // Multi-subsystem commands only
│   ├── DriveCommands.java
│   └── SmartShootCommand.java
└── util/                      // Helpers
    ├── PhoenixUtil.java
    └── LoggedTunableNumber.java
```

<RulesBox title="Note what is not in commands/">

There is no `RunIntakeCommand` and no `SetShooterSpeedCommand`. Single-subsystem actions are
**factory methods on the subsystem itself**; see
[Commands](/frc/commands#subsystem-command-factories).

The `commands/` package holds only commands that coordinate several subsystems and cannot be written
as a factory. Keeping it small is the point: everything the intake can do lives in `Intake.java`, so
you find it by opening one file instead of searching a directory.

</RulesBox>

### Constants

Write every CAN ID, setpoint, and gain once, in a constants file, so no value is typed twice.
Constants live at two levels:

- **`Constants.java`** holds settings the whole robot shares: the runtime mode, the CAN buses,
  controller deadbands, and tuning flags.
- **One constants file per subsystem**, in that subsystem's package: `IntakeConstants.java` beside
  `Intake.java`, `ShooterConstants.java` beside `Shooter.java`.

A subsystem's constants file describes everything the subsystem owns. The Intake subsystem owns two
components, a pivot and a roller, so `IntakeConstants` holds the configuration for both: a
`PivotConfig` for the pivot and a `RollerConfig` for the roller, plus the named positions and
requests the Intake uses. A change to the intake then stays inside the `intake` package, and
`Constants.java` stays short. This partial example shows the layout:

```java
package frc.robot.subsystems.intake;

public final class IntakeConstants {
  private IntakeConstants() {}

  /** Named pivot positions, measured from horizontal. */
  public enum Position {
    STOWED(Degrees.of(90)),
    INTAKE(Degrees.of(-5));

    public final Angle angle;

    private Position(Angle angle) {
      this.angle = angle;
    }
  }

  public static final RollerConfig intakeRoller = new RollerConfig(3, Inches.of(1.5));

  public static final PivotConfig intakePivot =
      PivotConfig.builder()
          .reduction(60)
          .axis(Axis.HORIZONTAL)
          .minAngle(Degrees.of(-10))
          .maxAngle(Degrees.of(100))
          .startingAngle(Degrees.of(90))
          .tolerance(Degrees.of(2))
          .build();
}
```

The values are illustrative, not Cobra's. Field geometry belongs to no subsystem, so it gets its
own class; Cobra keeps it in `FieldConstants`.

Import the subsystem's constants class and name each constant through it:

```java
import frc.robot.subsystems.intake.IntakeConstants;

public class Intake extends SubsystemBase {
  private final Pivot pivot;
  private final Roller roller;

  public Intake(PivotIO pivotIO, RollerIO rollerIO) {
    this.pivot = new Pivot("Intake/Pivot", IntakeConstants.intakePivot, pivotIO);
    this.roller = new Roller("Intake/Roller", IntakeConstants.intakeRoller, rollerIO);
  }
```

`IntakeConstants.intakePivot` shows where the value comes from at the line that uses it, so a
reader never has to search the imports to find its source. Import classes by name, without wildcard
imports such as `IntakeConstants.*` and without static imports of project constants or utility
methods. [Java Code Style](/java/fundamentals/code-style#use-imports-and-comments-carefully) lists
the import rules.

Two habits worth naming explicitly, because plenty of FRC code does the opposite:

**No `m_` prefix on fields.** WPILib's own examples use `m_motor`; this curriculum uses `motor`.
Editors already colour fields differently from locals, so the prefix adds characters to every
reference without adding information.

**No `k` prefix on constants.** `intakePivotDown`, not `kIntakePivotDown`. A robot constant is
always written through its class, as in `IntakeConstants.intakePivotDown`, so the class name
already marks it as a constant. The [Practice](/java/assignments) assignments use
SCREAMING_SNAKE_CASE for constants instead, the standard Java convention that course assesses.

Whichever conventions you adopt, hold to them across the whole project. Two styles in one repository
is worse than either style alone.

### Subsystem Files

Each subsystem holds hardware objects and the methods that drive them.

```java
package frc.robot.subsystems.conveyor;

import frc.robot.subsystems.conveyor.ConveyorConstants;

public class Conveyor extends SubsystemBase {
  private final TalonFX conveyor = new TalonFX(ConveyorConstants.conveyorMotorPort);
  private final TalonFXConfiguration config = new TalonFXConfiguration();

  public Conveyor() {
    config.MotorOutput.NeutralMode = NeutralModeValue.Coast;
    config.CurrentLimits.StatorCurrentLimitEnable = true;
    config.CurrentLimits.SupplyCurrentLimitEnable = true;
    config.CurrentLimits.StatorCurrentLimit = 60;
    config.CurrentLimits.SupplyCurrentLimit = 40;

    PhoenixUtil.tryUntilOk(5, () -> conveyor.getConfigurator().apply(config));
  }

  @AutoLogOutput(key = "Conveyor/velocity")
  public double getConveyorVelocity() {
    return conveyor.getVelocity().getValueAsDouble();
  }

  @AutoLogOutput(key = "Conveyor/dutyCycle")
  public double setConveyorDutyCycle(double dc) {
    conveyor.set(dc);
    return dc;
  }

  public Command setConveyorCommand(double speed) {
    return run(() -> setConveyorDutyCycle(speed));
  }
}
```

<RulesBox title="Subsystem Guidelines" subtitle="Organization rules:">

- **One subsystem per package.** The package holds the subsystem, its constants file, and any IO
  interfaces it needs.
- **All IDs, setpoints, and component configs from the subsystem's constants file,** named
  through its class, as in `ConveyorConstants.conveyorMotorPort`.
- **Configure in the constructor,** and retry the apply; see
  [Subsystems](/frc/subsystems#configuration-can-fail-silently).
- **Simple methods.** The subsystem knows *how*; commands decide *when*.
- **Command factories belong here.** A single-subsystem action is a method on the subsystem, not a
  class elsewhere.
- **Keep `periodic()` nearly empty.** Logging and safety checks only; behaviour lives in commands.

</RulesBox>

### Log Key Naming

Anything logged gets a key that reads like a path:

```java
@AutoLogOutput(key = "Intake/Position")
public double getIntakePosition() {
  return pivot.getPosition().getValueAsDouble();
}
```

Log viewers such as AdvantageScope build their tree from the slashes, so `Intake/Position` and
`Intake/velocity` group together automatically. Start every key with the subsystem name and stay
consistent. A key nobody can find during a match may as well not have been recorded.

### RobotContainer

`RobotContainer` centralizes setup and wiring. It holds initialization only, never runtime
behaviour.

```java
public class RobotContainer {
    // Subsystems
    private final Drive drive;
    private final Intake intake;
    private final Shooter shooter;

    // Controllers
    private final CommandPS5Controller controller = new CommandPS5Controller(0);
    private final CommandPS5Controller operator = new CommandPS5Controller(1);

    private final LoggedDashboardChooser<Command> autoChooser;

    public RobotContainer() {
        drive = new Drive(/* IO implementations; see Physics in the IO Layer */);
        intake = new Intake(/* pivot and roller IO */);
        shooter = new Shooter();

        registerNamedCommands();
        autoChooser = new LoggedDashboardChooser<>("Auto Choices", AutoBuilder.buildAutoChooser());
        configureButtonBindings();
    }

    private void configureButtonBindings() {
        // Default commands
        intake.setDefaultCommand(intake.intakeDefaultCommand());
        shooter.setDefaultCommand(shooter.setDutyCycleSetpointCommand(0));

        // Bindings use the subsystems' own factories
        controller.povDown().whileTrue(intake.intakeDeployCommand());
        controller.R2().and(controller.R1().negate())
            .whileTrue(intake.deployAndIntakeCommand());
    }

    public Command getAutonomousCommand() {
        return autoChooser.get();
    }
}
```

<RulesBox title="RobotContainer Guidelines" subtitle="Organization rules:">

- **Group by function:** separate methods for bindings, named commands, and auto setup.
- **No loop logic.** Configuration only; behaviour belongs in commands.
- **Use a default command for continuous behavior,** such as reading drive sticks. Commands that
  drive an output also stop it when they end.
- **Bind factories directly.** `intake.deployAndIntakeCommand()` reads better than
  `new DeployAndIntakeCommand(intake)`.
- **Provide `getAutonomousCommand()`.**

</RulesBox>

### Utility Classes

Helpers belong in `util/`. A few earn their place on almost every robot:

```java
package frc.robot.util;

public final class PhoenixUtil {
    private PhoenixUtil() {}

    /** Attempts to run the command until no error is produced. */
    public static void tryUntilOk(int maxAttempts, Supplier<StatusCode> command) {
        for (int i = 0; i < maxAttempts; i++) {
            var error = command.get();
            if (error.isOK()) break;
        }
    }
}
```

Others worth having: deadband and clamp helpers, a tunable-constant wrapper (see
[Tunable Constants and Characterization](/frc/tunable-constants-and-characterization#declaring-a-tunable)),
and a logged pathfinder wrapper if you use PathPlanner with AdvantageKit.

<RulesBox title="General Organization Rules" subtitle="Best practices:">

- **One class per file,** file name matching the class.
- **Clear separation:** subsystems own hardware; commands own decisions.
- **Dependency injection.** Pass subsystems into multi-subsystem commands via the constructor; no
  static subsystem instances.
- **One constants file per subsystem,** beside it and imported by class name; robot-wide settings
  stay in `Constants.java`.
- **Consistent naming** across the whole repository.
- **Descriptive names.** `intakePivotDown` beats `pos2`.

</RulesBox>
