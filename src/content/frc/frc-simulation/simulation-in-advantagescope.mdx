### Why not just the Sim GUI

The Sim GUI can enable the robot and drive it, and its NetworkTables pane shows every value the code publishes as a scrolling list of numbers. That is enough to see that something changed and not enough to see how it changed: whether the elevator overshot, by how much, whether it settled, whether one swerve module is fighting the others, or where the robot thinks it is.

**AdvantageScope** shows those things by drawing. Connected live to the simulator it graphs, maps and animates the same values as they happen. It is also the tool you will point at the real robot and at match logs later, so the layout you build today is the layout you will debug a match with. The Tools section covers the application itself ([AdvantageScope: Tour](/tools/advantagescope-tour)); this page is the simulation workflow on FRC 4451's code.

### Connecting

With the simulator running ([Running the Simulator](/frc/running-the-simulator)):

1. Open AdvantageScope.
2. **File → Connect to Simulator** (`Ctrl+Shift+K`). This is not "Connect to Robot", which goes to `10.TE.AM.2`; the simulator is at `127.0.0.1`.
3. The status in the title bar changes from *Disconnected* to *Live*, and the key tree on the left fills in.

If the tree stays empty: the simulator is not running, a firewall blocked it on first launch, or the robot code is not publishing. FRC 4451's `Robot.java` publishes over NT4 in `SIM` mode (`Logger.addDataReceiver(new NT4Publisher())`), so with the simulator up there is always something to see.

### The key tree

The tree on the left mirrors the log structure. With AdvantageKit, every subsystem's **inputs** appear under its name (`Intake/Position`, `Intake/AppliedVoltage`, `Drive/Module0/DrivePositionRad`), and every **output** you logged appears under `RealOutputs/…`: `RealOutputs/Odometry/Global`, `RealOutputs/SwerveStates/Setpoints`, `RealOutputs/Intake/State`. Values with a struct type (poses, module states, mechanisms) have an icon showing what the tabs can do with them.

Type in the search box above the tree to filter; drag a key onto a tab to plot it. Dragging keys onto tabs is most of the interface.

### The Line Graph: commanded versus measured

The first graph to build for any mechanism, every time:

<StepsBox title="Does it go where it is told?">

1. Open a **Line Graph** tab.
2. Drag the **goal**, `Intake/PositionGoal`, onto the left axis.
3. Drag the **measured** value, `Intake/Position`, onto the same axis.
4. Drag `Intake/AppliedVoltage` onto the right axis, so effort is visible next to result.
5. In the Sim GUI, enable Teleoperated and command the mechanism (a button binding, or `setGoal` from a test command).

</StepsBox>

Now read it. The goal is a step; the measured line should rise to meet it. Each shape points at something to check. **Overshoot**, the measured line crossing the goal and coming back, usually means too much kP or not enough kD. **Steady-state error**, the two lines settling apart, usually means not enough kG or kS, or a wrong feedforward. **Oscillation**, the measured line wobbling around the goal, usually means too much gain. A **slow** approach that never quite arrives usually means too little gain, or a velocity limit in the profile. A voltage line held at 12 V during the move means the mechanism is at its physical limit and no gain will make it faster. (The gain names kP, kD, kS and kG are defined in [Control Theory](/frc/pid-control), two groups on. For now, treat them as the adjustable constants, and notice that the shape of the graph suggests which one to look at.)

With the vendor-sim-state pattern from [Physics in the IO Layer](/frc/physics-in-the-io-layer#the-vendor-sim-state-pattern), what you read here is the real controller's closed loop, so the fix you make is the fix that goes on the robot. Add `Intake/PositionSetpoint` alongside the goal to see the motion profile. The setpoint is the profile's current target, and the measured value should track the setpoint rather than the goal.

**Discrete values** (a state enum, a boolean, a command name) drop onto the discrete fields strip under the graph and draw as coloured bands aligned with time. `RealOutputs/Intake/State` there, above the position graph, shows exactly which state the mechanism was in when the position did something odd.

### The 2D and 3D Field

Drag `RealOutputs/Odometry/Global` (a `Pose2d`) onto a **2D Field** tab and the robot appears on this season's field, moving as you drive it in the Sim GUI. Add `RealOutputs/Odometry/Trajectory` (a `Pose2d[]`) and the active autonomous path draws under it. [Simulating Autonomous](/frc/autonomous-simulation) relies on this view.

The **3D Field** tab does the same in three dimensions, with a robot model. Pick one in the tab's settings (a generic KitBot is fine; FRC 4451's own model lives in AdvantageScope's assets folder). A `Pose3d[]` logged as components (the elevator carriage's pose, the arm's pose relative to the robot) makes the model articulate, so the simulated elevator visibly rises. Camera poses logged as `Pose3d` show where the vision system thinks its cameras are, which is how a wrong `robotToCamera` transform gets caught before the robot exists.

### The Swerve tab

Drag `RealOutputs/SwerveStates/Measured` and `RealOutputs/SwerveStates/Setpoints` (both `SwerveModuleState[]`) onto a **Swerve** tab, and the robot's rotation (`Drive/Gyro/YawPosition` or the pose) into its rotation slot. Four arrows per set, one per module, length for speed and direction for angle. The setpoint arrows and the measured arrows should sit on top of each other; a module whose measured arrow lags or points the wrong way suggests a wrong steer offset, a wrong inversion, or a bad gain. In simulation, that means checking the constants in `TunerConstants` or `ModuleIOSim`.

### The Mechanism tab

Every `LoggedMechanism2d` the code records appears under `RealOutputs` at whatever key it was given. Drag one onto a **Mechanism** tab and it is drawn to scale and animated. Commanded and measured mechanisms can be overlaid: draw the assembly a second time from the goal instead of the measured position, in a different colour and a different line weight, and the gap between the two drawings shows the error without reading a number.

Cobra has the per-component ligament classes (`ElevatorMechanism`, `PivotMechanism`) and the configs for a canvas, but does not construct one yet, so this tab is empty on Cobra today. [Mechanism Visualization](/frc/what-a-mechanism-drawing-shows) builds the missing layer.

Keep this view open while writing a new mechanism's sim. A wrong sign, a wrong reduction, or gravity turned off shows as soon as the drawing moves the wrong way.

### Joysticks and Console

The **Joysticks** tab draws a controller with its live axes and buttons, from `DriverStation/Joystick0/…`, which AdvantageKit publishes as inputs (plain WPILib does not send sticks over live NetworkTables; see [AdvantageScope: Controllers and the Console](/tools/advantagescope-controllers-and-the-console#inspect-controller-inputs)). When a binding does not fire, this is how you tell whether the button was pressed as far as the code is concerned.

The **Console** tab is the robot's `System.out` and the DS messages, timestamped and searchable, synchronized with every other tab. A `println` in a command lands here beside the graph of what the mechanism did at that moment.

### Save the layout

A layout is a set of tabs with their keys and settings, and it takes a few minutes to build. **File → Export Layout** saves it as a `.json`; **Import Layout** brings it back on any machine. Keep the standard layouts in the robot repository, one per mechanism, one for drive, one for autos, so "open the intake layout" is a shared instruction. When someone improves one and commits it, everyone gets it.

### Recording a simulation

In `SIM` mode FRC 4451's code publishes to NT4 and does not write a log file, so the data exists only while AdvantageScope is watching. When a run is worth keeping (a before/after tuning comparison, a bug you want a teammate to see), add a writer in the `SIM` branch of `Robot.java`:

```java
case SIM:
  Logger.addDataReceiver(new NT4Publisher());
  Logger.addDataReceiver(new WPILOGWriter());   // writes logs/*.wpilog in the project folder
  break;
```

The `.wpilog` opens in AdvantageScope like a match log (File → Open), and it is what [Log Replay](/frc/log-replay) can feed back into the code.

<RulesBox title="Common mistakes">

- **Connect to Robot instead of Connect to Simulator.** The tree stays empty because it is waiting for <code>10.TE.AM.2</code>.
- **Plotting measured alone.** Without the goal on the same axis, a graph cannot tell you whether the number is right.
- **Both on the same axis when their units differ.** Position in rotations and voltage in volts share a scale badly; put voltage on the right axis.
- **Trusting the model over the drawing.** If the Mechanism tab shows the arm swinging the wrong way, check the code even though the numbers look plausible.
- **Rebuilding a layout every session.** Export it once; import it next time.

</RulesBox>
