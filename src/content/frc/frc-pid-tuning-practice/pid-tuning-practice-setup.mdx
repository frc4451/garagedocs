The three sessions in this group tune an elevator, an arm and a shooter by hand. They run the [Manual Tuning](/frc/manual-pid-tuning) recipes against simulated mechanisms, so the procedure and the habits carry over to the robot and only the numbers change. This page gets the environment running; do it once.

<RulesBox title="Before you start">

Read [Manual Tuning: Every Gain Is Canonical](/frc/manual-pid-tuning) first. Each session below names the recipe it runs and assumes you know the skeleton: zero everything, feedforward first, then `kP`, then `kD`, then verify at other setpoints.

You need WPILib installed ([Environment Setup](/frc/environment-setup)), which includes Elastic and AdvantageScope, plus Git and either GitHub Desktop or a command-line clone ([Install Git](/tools/install-git)).

</RulesBox>

### The practice project

The sessions use [mantik-pid-practice](https://github.com/itkan-robotics/mantik-pid-practice), a WPILib project with four simulated mechanisms: an elevator, the same elevator under an exponential profile, an arm, and a shooter flywheel. Each is a NEO on a SparkMax driven through the [YAMS](https://github.com/Yet-Another-Software-Suite/YAMS) mechanism library, which publishes the gains as live-tunable numbers and draws the mechanism for AdvantageScope. Gains are in volts: `kP` is volts per metre (elevator) or per degree (arm), `kV` is volts per unit of velocity, and so on. The recipes were written for torque-current amps; the steps are the same and the numbers are much smaller. The project is a 2025 WPILib project, so build it with the 2025 tools or update the vendordeps first.

You can run the same sessions against FRC 4451's own code instead. Every `SingleRoller` in Cobra publishes its gains as tunables and has a simulated TalonFX behind it ([Tunable Constants](/frc/tunable-constants#reacting-to-a-change), [Simulating a TalonFX](/frc/talonfx-simulation)). The practice project is simpler to start with because there is nothing else in it.

<StepsBox title="Setup steps">

1. Clone the repository. On the GitHub page, use the green *Code* button and *Open with GitHub Desktop*, or clone from a terminal. Put it somewhere on the local drive, not in OneDrive or another synced folder; WPILib builds are unreliable there.
2. Open it in the WPILib copy of VS Code: `Ctrl+Shift+P`, *WPILib: Open Folder*, choose the cloned folder.
3. Start the simulation: the WPILib button, or `Ctrl+Shift+P` and *WPILib: Simulate Robot Code*. Wait for *Build successful*, then choose *Sim GUI*. The Sim GUI is a stand-in for the Driver Station and does not need the FRC Game Tools installed ([Running the Simulator](/frc/running-the-simulator)).
4. In the Sim GUI, drag a keyboard joystick from the *System Joysticks* list into slot 0 if none is loaded. Its buttons are mapped to the Z, X, C and V keys.
5. Choose a mechanism. The project publishes a chooser to SmartDashboard; pick *Elevator* for the first session.
6. Open Elastic and add a *Live Tuning Command* widget: new tab, *Add Widget*, then SmartDashboard, Mechanisms, Commands, the mechanism's subsystem. This is the switch that lets you edit gains while the code runs.
7. Open AdvantageScope and connect to the simulator (*File*, *Connect to Simulator*, or `Ctrl+Shift+K`). Open a *Mechanism* tab and drag the mechanism's entry from SmartDashboard onto it. This is the drawing of the mechanism.
8. Open a *Line Graph* tab. Under the mechanism's entry, drag `measurement/position` and `closedloop/setpoint/position` onto the left axis, so commanded and measured share a scale ([commanded versus measured](/frc/advantagescope-sim#the-line-graph-commanded-versus-measured)), and `motor/outputVoltage` onto the right axis. The velocity pair (`measurement/velocity`, `closedloop/setpoint/velocity`) goes on a second graph, or on this one when a session asks for it.
9. Zoom the graph to a window of one to two seconds. Scroll to zoom; drag along the time axis to scrub; the pause button freezes it while you read a value.
10. In the AdvantageScope *Tuning* tab, enable publishing (the button next to the search box) so the gain fields become editable. The gains are under `closedloop/feedback` (`kP`, `kI`, `kD`) and `closedloop/feedforward` (`kS`, `kV`, `kA`, `kG`); the profile limits are under `closedloop/motionprofile`. The same fields exist in Phoenix Tuner's *Config* tab and in the REV Hardware Client when you move to hardware.
11. Set the Sim GUI to *Teleoperated* and press the *Live Tuning* button in Elastic. It turns blue while tuning is active. Pressing a joystick button turns it off again; turn it back on before editing a gain.

</StepsBox>

<RulesBox title="Two things to check before every session">

- The graph shows **setpoint and measurement on one axis**. If you cannot see both, you cannot see error, and every recipe is about error.
- **All gains are zero.** A value left from the last session hides the effect of the one you are finding. The recipes say to zero everything first; do it in the tuning table, not from memory.

</RulesBox>

### On the real robot

The same sessions transfer to hardware with the vendor tool in place of the tuning table. In Phoenix Tuner the gains are on the *Config* tab and the graph is *Rotor Position* and *Velocity*; the robot must be enabled in the Driver Station, and Tuner's control must be allowed to take over from the code. The REV Hardware Client is arranged the same way. The mechanism drawing is unnecessary on hardware, since the mechanism is in front of you; the line graph is not, since overshoot at the speeds a tuned mechanism reaches is hard to see and easy to measure.
