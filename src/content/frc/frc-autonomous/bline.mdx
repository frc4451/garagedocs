### What BLine is

BLine is an open-source path-following suite for holonomic drivetrains: a web editor for drawing
paths, and a Java library, **BLine-Lib**, that follows them. Its pitch is *build fast autos, tune
what the robot actually does*, and its distinguishing choice is that a path is a **sequence of
points**, not a trajectory in time.

The latter is critical to understand, because it can be the reason to pick BLine over the
alternatives.

### "Get to Point"

PathPlanner and Choreo generate a ***trajectory***: at every instant `t`
1. Here is where the robot should be, how fast, and pointing which way. 
2. The follower's job is to make the robot match that schedule. 

It is time-optimal. If the robot is bumped, the wheels slip, or a mechanism takes longer than
expected, the schedule has moved on without it and the follower is now chasing a ghost.

This can also mean that when the if the robot started one second late for any reason, the auto is
one second behind, and needs to accelerate unsafely to catch up. This can result in accidents where
robots slam into game pieces. In the 2025 season when Choreo would load every autonomous trajectory
at the start of Autonomous.

BLine reads the robot's current pose every cycle and asks a geometric question: *how far along the
drawn line am I, and which point is next?* There is no clock to fall behind. If the robot gets
shoved two feet sideways it simply drives back onto the line from where it is; if it is blocked for
a second, it resumes from where it stopped. The docs put it plainly: paths "should wait for physical
progress rather than a clock."

The trade is real in both directions. BLine will not slow down for a corner just because it is
sharp; a drawn polyline is not proof the chassis can follow it at the requested acceleration; and a
physically blocked robot "may keep trying forever unless the command composition adds a timeout or
fallback." What you get in exchange is an auto that survives contact, which in a game with defence
is worth a great deal.

BLine trusts whatever pose you give it. With odometry alone it works for short, clean routines; for
longer autos, direction changes, and anything that might involve a collision, the docs strongly
recommend vision correction, which is what
[PhotonVision](/frc/photonvision#pass-observations-to-the-estimator) feeds into your pose estimator.
Bad pose in, bad path out.

### Wiring it to the drivetrain

In the AdvantageKit v26.0.2 swerve template, change the existing measured `Drive.getChassisSpeeds()`
method from `private` to `public`. Keep its body and `@AutoLogOutput` annotation. The template uses
it from inside `Drive`; the separate manager below needs a public accessor. It reports
robot-relative motion calculated from measured module states, not the speed last requested by a
command.

Everything goes through one `FollowPath.Builder`, built once and reused for every path. It needs the
drive subsystem and three things the subsystem must be able to do (report its pose, report its
speeds, and accept a speed command), plus three PID controllers.

```java
package frc.robot.autonomous.bline;

import edu.wpi.first.math.controller.PIDController;
import edu.wpi.first.wpilibj2.command.Command;
import frc.robot.lib.BLine.FollowPath;
import frc.robot.lib.BLine.Path;
import frc.robot.subsystems.drive.Drive;

public class BLineManager {
  private final FollowPath.Builder pathBuilder;

  public BLineManager(Drive drive) {
    pathBuilder =
        new FollowPath.Builder(
                drive, // the subsystem every built command requires
                drive::getPose, // Supplier<Pose2d>: field-relative pose
                drive::getChassisSpeeds, // Supplier<ChassisSpeeds>: robot-relative
                drive::runVelocity, // Consumer<ChassisSpeeds>: robot-relative
                new PIDController(
                    2.5, 0.0, 0.0), // translation: error is distance left along the line
                new PIDController(3.0, 0.0, 0.0), // rotation: error is heading, wraps at ±180°
                new PIDController(
                    2.0, 0.0, 0.0)) // cross-track: error is sideways distance off the line
            .withDefaultShouldFlip() // author on blue; flip for red from the Driver Station
            .withPoseReset(drive::setPose); // Reset odometry at path start
  }

  public Command followPath(String name) {
    return pathBuilder.build(new Path(name));
  }
}
```

This is FRC 4451's actual wiring from their 2026 robot, lightly trimmed. Three things in it to
notice:

- **The three PIDs are three different errors.** Translation is *how much line is left*, rotation is
  *heading*, cross-track is *how far off the line sideways*. The docs' tuning advice follows from
  that: tune translation first, rotation second, cross-track last, "so each plot has one main
  unknown."
- **`withDefaultShouldFlip()`** means you draw every path as if you are the blue alliance and BLine
  mirrors it when the Driver Station says red. One set of paths, not two.
- **`withPoseReset`** tells the drivetrain where the path starts. Builder options persist, so every
  command built while the option is set resets the pose when it starts. Cobra's example builds one
  path, where that is what it wants. An auto with several paths resets only at the first one; later
  paths should trust the pose the robot has earned. Set the option, build the first path, then clear
  it before building the rest, as BLine's documentation shows:

```java
Command first = pathBuilder.withPoseReset(drive::setPose).build(new Path("firstPath"));
pathBuilder.withPoseReset(ignored -> {}); // later paths keep the pose the robot has earned
Command second = pathBuilder.build(new Path("secondPath"));
Command third = pathBuilder.build(new Path("thirdPath"));
Command auto = Commands.sequence(first, second, third);
```

The first command keeps the reset it captured when it was built.

### Where paths come from

**Drawn.** [BLine Web](https://bline-docs.pages.dev/gui/) is a browser editor: click waypoints onto
the field, set headings and constraints, preview, export JSON. The file goes in the deploy folder
and is loaded by name:

```
src/main/deploy/autos/
├── config.json           global defaults, written by the editor
└── paths/
    └── score-left.json
```

```java
Path scoreLeft = new Path("score-left"); // no .json
```

**Written.** A path is also just Java, which is what makes runtime-built routes possible, such as a
path from wherever the robot is now to the loading zone:

```java
import edu.wpi.first.math.geometry.Rotation2d;
import edu.wpi.first.math.geometry.Translation2d;
import frc.robot.lib.BLine.Path;

Path.setDefaultGlobalConstraints(new Path.DefaultGlobalConstraints(
    4.5,     // max translation velocity (m/s)
    12.0,    // max translation acceleration (m/s²)
    720.0,   // max rotation velocity (deg/s)
    1500.0,  // max rotation acceleration (deg/s²)
    0.03,    // end translation tolerance (m)
    2.0,     // end rotation tolerance (deg)
    0.45     // intermediate handoff radius (m)
));

Path toLoading = new Path(
    new Path.Waypoint(new Translation2d(4.0, 2.0), Rotation2d.fromDegrees(0)),
    new Path.TranslationTarget(new Translation2d(6.0, 2.8)),
    new Path.RotationTarget(Rotation2d.fromDegrees(90), 0.5, true),
    new Path.EventTrigger(0.7, "deployIntake"),
    new Path.Waypoint(new Translation2d(7.5, 3.4), Rotation2d.fromDegrees(90))
);
```

A **Waypoint** is a position with a heading; a **TranslationTarget** is a position the robot passes
through without caring about heading; a **RotationTarget** asks for a heading by a certain fraction
of progress. The **handoff radius** is the circle around each intermediate target inside which BLine
considers it reached and moves on. It decides whether the robot cuts corners or squares them.

<ReferenceImage
  src="/media/frc/bline-path-element-layers.svg"
  alt="Diagram showing translation anchors forming straight path segments while rotation targets and event triggers attach to progress along a segment"
  caption="Translation anchors shape the route. Rotation targets and events add behavior without bending that route. Diagram courtesy of"
  sourceUrl="https://bline-docs.pages.dev/concepts/path-elements/"

For most pass-through targets, BLine can advance after the robot crosses a projected progress
threshold even when it passes outside the target's radius. A radius-only handoff instead keeps the
old target active until the robot enters its circle. Use radius-only behavior when the robot must
physically visit that point.

### Events

An `EventTrigger` at `t = 0.7` fires when the robot is 70 % of the way along the path, by progress
rather than by time, which is the same design again. It is bound by name:

```java
FollowPath.registerEventTrigger("deployIntake", intake.deployCommand());
```

A `Runnable` runs inline and must be fast; a `Command` is scheduled and keeps running under normal
WPILib rules, even after the path ends. A command that requires the drivetrain conflicts with
`FollowPath`. A mechanism event can also conflict with an outer command group that already owns that
mechanism. `BLineCommands` proxies child commands to change when those requirements are held; it
does not remove real drivetrain conflicts.


For the first Badge 2 routine, let events change a flag and keep the mechanism command inside the
routine. This partial method belongs in the autonomous manager. It uses the existing `pathBuilder`
and `drive`; `feedParent` is the student's Step 9 subsystem. Its `feedCommand()` continuously checks
possession and flywheel readiness and stops on end. Its `stop()` puts every owned component into the
documented safe state.

Import `AtomicBoolean`, `Commands`, and `Command`. Call this factory once when populating the
chooser; event registrations are static, so building another routine with the same keys would
replace them. Give other routines distinct keys.

```java
public Command scoringAuto() {
  AtomicBoolean feedRequested = new AtomicBoolean(false);
  FollowPath.registerEventTrigger("score/feedOn", () -> feedRequested.set(true));
  FollowPath.registerEventTrigger("score/feedOff", () -> feedRequested.set(false));

  Command first = pathBuilder.withPoseReset(drive::setPose).build(new Path("score-first"));
  pathBuilder.withPoseReset(ignored -> {});
  Command second = pathBuilder.build(new Path("score-second"));
  Command third = pathBuilder.build(new Path("score-third"));
  Command paths = Commands.sequence(first, second, third);

  Command feedRegion =
      Commands.waitUntil(feedRequested::get)
          .andThen(feedParent.feedCommand().until(() -> !feedRequested.get()))
          .repeatedly();

  return Commands.sequence(
          Commands.runOnce(() -> feedRequested.set(false)), Commands.deadline(paths, feedRegion))
      .withTimeout(14.0)
      .finallyDo(
          interrupted -> {
            feedRequested.set(false);
            drive.stop();
            feedParent.stop();
          });
}
```

Place the two matching event keys on the drawn paths. Here events do not schedule commands, so the
ordinary WPILib composition can own the feed parent for the routine. The path sequence is the
deadline: when it ends, the feed command is interrupted too. The example's 14-second bound is a
simulation exercise limit; record a timeout separately from arrival. Repeating the region allows
another on/off pair later in the route. Add the second required mechanism action using the same
explicit ownership and end behavior.

Run completion, timeout while enabled, cancellation while enabled, disable, and a second run.
Inspect the command state and mechanism goals as well as voltage. A single stop call cannot contain
an independently scheduled command that writes another output next loop. The offset exercise still
needs a separately constructed version without the nominal first-path pose reset.

### Which tool, when

Both are on the same robot for a reason. Use **PathPlanner** when the motion itself is the hard
part: a long, fast, curved route where the optimiser's speed profile is the point. Use **BLine**
when robustness is the hard part: short segments between scoring positions, anything that might take
contact, routes that start from wherever the robot happens to be. FRC 4451 runs both; the manager
above is their BLine side.

<RulesBox title="Common mistakes">

- **Tuning all three PIDs at once.** Translation, then rotation, then cross-track: one unknown per
  plot.
- **No timeout on a path that might be blocked.** `withTimeout(...)` on the built command, or a
  fallback in the sequence.
- **A sharp corner drawn at full speed.** Add a velocity constraint on that segment; nothing will
  slow it for you.
- **`withPoseReset` left set after the first path.** The option persists on the builder, so every
  later path resets the pose and throws away the corrected pose mid-auto. Clear it after building
  the first path.
- **An event command that requires the drive subsystem.**
- **Trusting the drawn line more than the pose estimate.** If the pose is off by half a metre, so is
  the path.

</RulesBox>
