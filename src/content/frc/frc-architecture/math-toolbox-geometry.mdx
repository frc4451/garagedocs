Of the three things that go wrong in robot code more than everything else (units, **frames** and ranges), frames are the ones geometry is for: robot-relative where field-relative was expected, a red match played on the blue alliance's field, a target's heading forgotten when the error was computed. Every class on this page exists to make one of those mistakes hard to write. The other two failure modes have [their own page](/frc/math-toolbox-units-and-interpolation).

The Java-level maths (`Math.hypot`, `atan2`, floating-point) is in [Math](/java/fundamentals/math); the field's coordinate frame is drawn in [AdvantageScope: Poses on the Field](/tools/advantagescope-poses-on-the-field#pose-and-coordinates); the geometry types and the three pose operations are in [Pose Geometry](/frc/pose-geometry). This page starts where those end.

`org.robotzgarage.frc2026.math.distance_calc.PoseUtils` is what FRC 4451 added when WPILib's geometry did not have the exact question. Each is a few lines, and each is there because a command needed it:

The parallel/perpendicular pair is the idea to take away. A target pose has a heading; "error" relative to it is not one number but two, along the face and toward the face, and a controller on each is how a robot lines up with a wall without oscillating diagonally. Read `getParallelError`: it is `minus` (the transform between the poses), `getAngle` (its direction), and a sine.

### Cobra's own: the alliance flip

The field is drawn once, in blue-alliance coordinates, in `FieldConstants`: hub, trenches, bumps, drop-offs, all as `Translation3d`/`Pose2d` constants. On a red match every one of those is on the other side. `AllianceFlipUtil` is the single place that knows how:

```java
public static double applyX(double x)  { return shouldFlip() ? FieldConstants.fieldLength - x : x; }
public static double applyY(double y)  { return shouldFlip() ? FieldConstants.fieldWidth  - y : y; }
public static Rotation2d apply(Rotation2d r) { return shouldFlip() ? r.rotateBy(Rotation2d.kPi) : r; }
public static Pose2d apply(Pose2d p)   { return shouldFlip() ? new Pose2d(apply(p.getTranslation()), apply(p.getRotation())) : p; }
public static boolean shouldFlip()     { return DriverStation.getAlliance().isPresent() && DriverStation.getAlliance().get() == Alliance.Red; }
```

Flipping both X and Y and rotating headings by 180° is a **rotational** flip. The field has rotational symmetry about its centre, so the red alliance's hub is the blue hub rotated half a turn, not mirrored across the centre line. (A game with a mirrored field would flip X only and negate the heading; this is the constant to check each January.) Every VARC applies it to its target on every `update()`, so nothing else in the code has to consider alliance, and `BobotState.getCurrentFieldZone()` sorts the two flipped hub X values before comparing, because after the flip "near" and "far" swap sides.

The path libraries do the same job for autos: PathPlanner's and BLine's *flip* options mirror a path drawn on blue for red, using the same field dimensions; see [BLine](/frc/bline#wiring-it-to-the-drivetrain), and the both-alliances rule in [Simulating Autonomous](/frc/autonomous-simulation#the-three-tools-in-simulation).

### Why the principles are here at all

Every helper above is a wall around the same mistake. A `Pose2d` cannot be added to a `Translation2d`; `relativeTo` cannot forget the target's heading; `AllianceFlipUtil` is the one place that knows which way the field turns. Take the walls away and the mistakes come back one at a time, each costing a field session. Keep them, and the geometry in a command reads as *what* it computes instead of *how*.
