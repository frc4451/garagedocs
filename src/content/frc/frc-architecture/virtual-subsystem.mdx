`SubsystemBase` does two unrelated things: it gives a class a `periodic()` that runs every loop, and it makes that class a **resource the scheduler arbitrates**: commands `require` it, and two commands that require the same subsystem cannot run together. For a motor that is exactly right. For "the robot's estimate of where it is" or "a camera that publishes what it sees" it is wrong: nothing should be able to own the pose, and a command that accidentally required the vision system would block every other command that did. Cobra's answer is a base class that provides the first thing without the second.

### The class

All of it, from `org.robotzgarage.frc2026.util.VirtualSubsystem`:

```java
/** Subsystems that are intended to run periodically, independently of the CommandScheduler. */
public abstract class VirtualSubsystem {
  private static final List<VirtualSubsystem> virtualSubsystems = new ArrayList<>();

  /** Every subsystem that extends VirtualSubsystem gets added to the list of Subsystems
      that are called every robot period. */
  public VirtualSubsystem() {
    virtualSubsystems.add(this);
  }

  public static void listVirtualSubsystems() {
    for (VirtualSubsystem subsystem : virtualSubsystems) {
      System.out.println(String.format(
          "[robotzgarage] Connected Virtual Subsystem '%s'", subsystem.getClass().getSimpleName()));
    }
  }

  /** Call periodic() on every virtual subsystem. */
  public static void runPeriodically() {
    for (VirtualSubsystem subsystem : virtualSubsystems) subsystem.periodic();
  }

  /** Call simulationPeriodic() on every virtual subsystem. */
  public static void runSimulationPeriodically() {
    for (VirtualSubsystem subsystem : virtualSubsystems) subsystem.simulationPeriodic();
  }

  public abstract void periodic();
  public abstract void simulationPeriodic();
}
```

Three ideas, each a line or two:

- **Self-registration.** The constructor adds `this` to a static list. Extend the class, construct one instance, and it is in the loop, with no registration call to forget. (`SubsystemBase` does the same thing: its constructor registers with the `CommandScheduler`.)
- **A static entry point.** `runPeriodically()` walks the list. Whoever calls it decides *when* in the loop the virtual subsystems run.
- **A simulation hook.** `simulationPeriodic()` mirrors `Robot.simulationPeriodic()`; a virtual subsystem that owns a simulated world, such as the vision sim from [Simulating Vision](/frc/sim-vision#the-three-pieces), updates it here.

### When it runs, and why that is the point

The call site is `Robot.robotPeriodic()`, and the order is the reason the architecture works:

```java
@Override
public void robotPeriodic() {
  Threads.setCurrentThreadPriority(true, 99);
  VirtualSubsystem.runPeriodically();       // ① BobotState, vision, dashboard, before any subsystem
  CommandScheduler.getInstance().run();      // ② subsystem periodic()s, then commands
  Threads.setCurrentThreadPriority(false, 10);
}
```

So within one 20 ms loop:

<StepsBox title="One loop">

1. **Virtual subsystems, in construction order.** `RobotContainer` constructs `BobotState` first, then the vision subsystems, then the dashboard manager. `BobotState` recomputes the VARCs, interpolators and zone from last loop's pose. `AprilTagVision` reads its cameras and offers pose observations into `BobotState`'s queues. `TeleopShiftManager` logs the shift clock.
2. **The scheduler runs subsystem `periodic()`s.** `Drive` runs odometry, **drains** the observation queues (the observations from step 1) into its pose estimators, and writes the new pose back into `BobotState`. The mechanisms update their inputs.
3. **The scheduler runs commands.** A scoring command reads `BobotState.getHubInterpolator().getCalculation()`, computed in step 1 from the previous loop's step-2 pose, and commands the shooter.

</StepsBox>

Two consequences. Vision observations reach the pose estimator in the same loop they were made, because vision runs before drive. Had vision been a `SubsystemBase`, its `periodic` would run inside step 2 in whatever order the scheduler chose, and an observation might sit in the queue a loop longer. And everything `BobotState` derives is one loop behind the pose, which its own comments acknowledge as acceptable ([BobotState](/frc/bobot-state#the-flow-through-one-loop)). Twenty milliseconds of staleness in aim is acceptable; twenty milliseconds of staleness in a vision measurement's timestamp would be wrong, which is why observations carry their own capture time.

None of them has a motor. That is the tell: a class with a motor is a `SubsystemBase`, because a motor is a thing two commands must not fight over. A class with a camera, a clock, or a table of derived numbers has nothing to fight over, and giving it scheduler semantics only creates a way to deadlock it.

### Writing one

```java
public class BatteryMonitor extends VirtualSubsystem {
  private static final LoggedTunableNumber warnVolts = new LoggedTunableNumber("Battery/WarnVolts", 11.5);
  private final Alert lowBattery = new Alert("Battery below warning voltage", AlertType.kWarning);
  private final LinearFilter filter = LinearFilter.movingAverage(25);   // ~0.5 s of samples

  @Override
  public void periodic() {
    double volts = filter.calculate(RobotController.getBatteryVoltage());
    Logger.recordOutput("Battery/FilteredVolts", volts);
    lowBattery.set(volts < warnVolts.get());
  }

  @Override
  public void simulationPeriodic() {}
}
```

Construct it once (`new BatteryMonitor();` in `RobotContainer`) and it runs. It logs, it raises an `Alert` the dashboard shows, and no command can require it, which is right: no command should be able to own the battery voltage.

Test it in simulation by dragging `Battery/FilteredVolts` onto a graph and spinning up the shooter: the `BatterySim` from [Simulating a TalonFX](/frc/talonfx-simulation#the-reference-implementation) sags the simulated supply, the filtered line dips, and the alert appears if it crosses the tunable.

<RulesBox title="Common mistakes">

- **Constructing one twice.** Each construction registers; two instances run twice per loop. Construct in one place.
- **Requiring it.** It cannot be required, because it is not a <code>Subsystem</code>, but a <code>Trigger</code> built from it can gate a command, which is what you wanted.
- **Depending on construction order.** The list runs in the order the constructors ran. If a virtual subsystem must run after another, make the dependency explicit (read last loop's value, as <code>BobotState</code> does) rather than relying on which line came first in <code>RobotContainer</code>.
- **Throwing from <code>periodic()</code>.** One exception in <code>runPeriodically()</code> stops every virtual subsystem after it in the list, and then the scheduler. Guard anything that can fail.
- **Doing hardware I/O in one.** A camera read is fine (it is already asynchronous); a blocking CAN call is not. Keep the loop under 20 ms; the <code>Threads.setCurrentThreadPriority</code> lines around the call are there because timing matters here.
- **Forgetting <code>simulationPeriodic</code> is abstract.** You must implement it, even as <code>{}</code>. The compiler will remind you.

</RulesBox>
